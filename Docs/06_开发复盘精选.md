# 开发复盘精选

> 从一百多条验收反馈与排障记录中挑出的 15 个案例：**现象 → 根因 → 修复 → 验证 → 经验**。
> 选题标准是"能讲出工程判断"，而不是"改了几行代码"。

---

## 1. 地面探测的两副面孔：卡在台缘，和被"吸"上栅栏

**现象**：沿装卸平台坡道向上走，角色停在台缘前不动；而走到横向栅栏下面时，又被瞬间抬到栅栏顶面。

**根因**：同一个地面探测写了两处缺陷。台缘处坡道顶面与平台边缘之间有一条板厚端面缝，
向下射线只打到端面（`normal.y≈0.29`），被当成不可站立面过滤后角色回落到 y=0；
而栅栏那条是把"角色上方 4 米内所有命中的最高点"当成了地面。

**修复**：地面探测只接受"当前地面高度 + 0.35 米以内、法线朝上"的命中；
坡道高端向台体内多伸入 0.5 米让顶面连续；低台阶跨越加入 0.35 米抬升复测。

**验证**：新增 3 条物理回归用例（低台阶可跨越 / 高墙不可翻越 / 可行走坡道不阻塞）；
播放模式下从坡道低端走到平台，高度平滑从 0 升到 1.2。

**经验**：探针类代码最危险的不是"没打到"，而是"打到了但打到了别的东西"——
过滤条件（法线、高度窗口）必须和用途一起设计。

## 2. 平台上的 AI：高度补少了，又补多了

**现象**：站在 1.2 米平台上的敌人，弹道贴地打不到人；修完之后敌人又只会警惕、不进入交战，
视角锥还画在头顶或地面。

**根因**：AI 的逻辑坐标只有平面（XZ，必须能在无头服务端运行），射线起点缺少脚下地面高度——
第一版修复只给"射手"补了高度，但误判了 `target.CenterWorld` 的语义，
又给"目标"补了一次，瞄准点高出目标 1.25 米，视线射线从玩家头顶飞过。
调试视角锥的高度则来自"从 y=50 向下打物理射线"，第一个命中的是单位自己的胶囊顶。

**修复**：射手侧按 NavMesh 采样补地面高度，目标中心原样使用；
调试高度与 AI 判定共用同一个导航网格采样。

**验证**：运行时打点取证（敌人眼位、玩家中心、修复前后目标点对比）；
高低差场景实机确认视线判定与交战恢复。

**经验**：坐标语义要在类型上写清楚——"平面坐标"和"世界坐标"混用一次，
就会在平地上完全正常、一有高差就全错。

## 3. 敌人把玩家挡住：单位需要自己的物理层

**现象**：敌人贴近玩家时模型卡在一起，玩家推不动、走不了。

**根因**：移动碰撞用全层遮罩扫掠，只排除自己；敌人的命中胶囊被当成了墙。
此前"地面探测排除敌人"是靠 `GetComponentInParent<EnemyAgentView>()` 打的临时补丁，
数量一多（联机 2~4 人 + AI 同场）问题被急剧放大。

**修复**：新增单位物理层（layer `Units`）与 `PhysicsLayers` 单一来源；
移动扫掠排除单位层，地面探测改用统一遮罩，删掉临时补丁。
层未登记时遮罩退回全层并告警一次——宁可回到旧问题，也不能让"移动穿墙"出现。

**验证**：3 条对照用例（单位层不阻挡 / 默认层仍阻挡 / 层已登记）；
同场景内同一颗胶囊换层前后对照：留在单位层可走满 1 米，改回默认层立刻卡在 0.38 米。

**经验**：用"组件类型判断"给物理世界打补丁，最终一定会被专用层替换；早换成本低。

## 4. 坡道侧面被钉死：去穿透修了三次才对

**现象**：玩家走到坡道中央往侧面走，会卡在坡道侧面，任何方向都动不了。

**根因**：平台与坡道是薄板箱体，侧面是 90° 硬棱。跨过边缘的下一帧地面吸附把脚底降到下层地面，
但胶囊水平投影仍压在侧棱里、下沿低于棱口上沿——起点已与几何重叠，
PhysX 对每个方向都返回 0 距离命中，"允许位移"恒为 0。

**修复（三次迭代）**：

1. 第一版：用 `OverlapCapsuleNonAlloc` 找重叠几何、沿"球心到碰撞体最近点"的水平分量推出。
   结果引入新缺陷——非凸网格碰撞体（地形）的 `ClosestPoint` 会把输入点原样返回，
   退化分支落到"包围盒中心 → 球心"，地形包围盒中心正是地图正中，
   于是推出方向变成"沿地图半径向外辐射"，出现瞬移（全区扫描 71 处异常、最大 1 米）。
2. 第二版：改方向来源，沿**本帧移动方向**试探挪一小步重新做重叠查询，
   "原来压着、挪一步后不再压着"的几何才放松，且**彻底不再修改位置**——
   瞬移从构造上不可能发生。
3. 用 176 个探针的全图网格扫描做回归：超出请求距离 0 处、横向偏移 0 处。

**验证**：新增回归用例（贴着几何移动不会产生额外位移、重叠时朝棱边挤不会钻进高台）；
实机：坡底走上平台、坡道侧面走下、平台北缘走下全部恢复正常。

**经验**：修复"卡住"时最容易顺手写出"推人"；推人必须证明方向来源在所有几何上都成立。

## 5. 敌人贴脸不进交战：重复创建的载体与漏绑的命中标识

**现象**：联机中敌人贴到玩家身上却不进入交战，原地旋转；子弹打人也不掉血。

**根因**：进图流程先建了一次玩家载体 A，紧接着战局重置又建了载体 B，**A 没有销毁**；
而重置循环漏了 `BindPlayerHitTarget`——活着的载体没有命中标识，
AI 视线判定恒为 false，敌人只能靠噪音点移动。

**修复**：命中标识绑定移进唯一的装配入口（只有一处，漏不了）；
载体创建幂等；移出世界时显式销毁。

**验证**：日志指纹（"碰撞载体就位"对同一玩家打印两次）+ 实机确认恢复交战。

**经验**：同一份状态被两个入口创建时，第二个入口一定会漏掉第一个入口的收尾动作——
把动作收敛到唯一入口，比补洞更便宜。

## 6. 自己模型"移动发糊"：按事件次数插值 vs 按时间插值

**现象**：联机中移动时自己的角色糊、一顿一顿，停下来立刻清晰；队友却正常。

**根因**：视觉跟随写在移动事件回调里、固定 `Lerp(0.5)`——按**事件次数**而不是按时间。
单机事件与帧同拍看不出问题；联机改成固定 60 Hz 步进后事件数与帧数不再对应，
模型永远追不上模拟位置。队友走的是时间驱动的插值缓冲，所以只有自己糊。

**修复**：改成每渲染帧的指数跟随 `1 - exp(-22·dt)`；移动事件只记录模拟位置与朝向。

**验证**：实机对照（自己 / 队友）确认拖影消失。

**经验**：任何"跟随/插值/衰减"都必须以时间为基准写成帧率无关形式——
这是单机转联机时最容易暴露的一类隐藏假设。

## 7. 容器"有的能搬有的搬不动"：三个根因与对象身份

**现象**：联机搜刮时物品有时能搬进背包、有时不能；搬进背包的物品再也拖不动。
服务器日志却显示每条命令都成功。

**根因（三层）**：

1. 场景切换时旧场景 `OnDestroy` 把新场景刚注册的网络处理器全量退订；
2. 容器内容消息不带格子坐标，客户端一律自动摆放，两端布局分叉；
3. 两端容量不一致时同步逻辑**换掉了容器对象**，同一编号指向不同网格，
   界面的"双击识别"与"拖拽定位"都建立在对象引用上，于是时好时坏。

**修复**：注册归属标记（退订前确认持有者）；坐标随内容消息往返；
同步永不替换容器对象（容量以本地装备为准、内容以服务器为准，不一致只留警告）。
随后又发现同步会重建物品实例，补上按"定义 + 数量 + 朝向"复用对象的池，
并让界面改用"容器 + 格子 + 定义"做身份判断。

**验证**：新增 6 条单测；本地真实链路（编辑器客户端 + 无头服务器）双向往返，
注册表与背包始终是同一个对象。

**经验**：同步逻辑里"重建对象"看起来干净，但只要界面拿对象引用当身份，
就会产生无日志的静默失效——同步要复用身份，界面也不该把对象当身份。

## 8. 点"继续游戏"进门就倒地：四个条件凑齐才出现的自伤

**现象**：持有枪械时从主菜单点"继续游戏"，进安全屋立刻开火并倒地，角色还能移动。

**根因（四环）**：

1. 单机没有绑定"伤害规则的射手编号"，默认 0，而战斗单位编号从 1 开始——
   取不到射手，"玩家免伤"和"不能打自己"两条规则同时失效；
2. 枪口在武器视图尚未装备时回退到角色中轴（自己的胶囊体内部）；
3. 点"继续游戏"的鼠标左键在进场景后仍按着，第一帧真的开枪；
4. 内容热更后 AK 伤害 77，两发 154 > 100 血，直接判死。

**修复**：新增规则编号绑定并在两处装配点调用；枪口兜底改到体前 0.6 米并同步武器表现；
靶场加"玩家受伤即报错"的守卫，防止同类症状再以"躺着还能走"的形式出现。

**验证**：新增 3 条自伤回归用例；同时修掉"单机击杀数一直不涨"的姊妹症状。

**经验**："三个条件凑齐才出现"的缺陷靠盯屏幕很难复现——把不可能事件写成断言守卫，
让下一次它以报错而不是以怪象出现。

## 9. 弹道三症状：从补丁式修复收敛到"统一瞄准平面"

**现象**：准星贴身时子弹像打到自己；开局第一枪偏得离谱、过一会变好；偶尔弹道与准星不共线。

**根因**：三个独立问题——命中探针不过滤射手；开局首帧的瞄准解算与枪口取样顺序错位；
弹道线保留真实高度（枪口 1.05 米）而准星在地面，45° 视角下投影必然错开。

**修复（三轮迭代）**：

1. 探针新增"把射手当透明"的投射 + 修正 Tick 顺序（回写位置 → 采集输入 → 更新武器 → 取枪口）；
2. 弹道改三点折线（枪口 → 枪口地面 → 终点地面）——起点贴枪口，但终点与准星仍错开；
3. 拍板"统一瞄准平面"：瞄准、准星反投影、弹道渲染全部使用同一个平面高度（脚底 + 枪口高度），
   弹道恢复两点真实线段。代价是瞄准点沿相机视线前移约 1.05 米（朝向近处差 3~4°），
   准星屏幕位置不变——用一致性换掉了所有投影补丁。

**验证**：新增 9 条用例（探针跳过自己、弹道落点、射手编号传递、贴脸朝向保护）；
编辑器实测三轮确认。

**经验**：当同一个显示问题需要第三个补丁时，停止打补丁，去找"两个元素不在同一个坐标系"这个根。

## 10. 服务器 CPU 打满与进图"闪回出生点"：两条同源缺陷

**现象**：云服务器空闲也 99% CPU；联机进图几秒后玩家闪回出生点，闪回前弹道与准星对不上。

**根因**：

1. 专用服务器没有任何帧率上限，`-batchmode -nographics` 下主循环以机器极限空转，
   每帧还要跑完整 Tick——成本随帧率线性放大；
2. 移动链路每张场景各建一个实例、输入序号各自从 0 开始，而服务器按"序号递增"过滤重复包。
   换图时旧链路的尾包把新战局的"已处理序号"顶到几百，新链路前几百条输入被静默丢弃——
   服务器把玩家留在出生点，客户端本地预测继续前进；序号追平时误差超过 0.6 米硬吸附阈值，
   一次 `SnapTo` 把玩家拉回服务器位置。这段窗口里弹道起点取本地枪口、终点取服务器命中点，
   两端错开十余米，所以弹道不穿准星。

**修复**：服务器模式启动即设 `Application.targetFrameRate = 60`（覆盖仿真 / 快照 / 心跳节拍）；
输入序号改为进程级单调递增、跨场景共用。

**验证**：本机无头对照实验——修复前 25 秒消耗 129.98 秒 CPU（≈5.2 核），修复后 1.95 秒；
云端空闲主线程 93.8% → 6.7%，整机 96.7% 空闲；客户端日志中的三次大回滚与序号推算逐一对上。

**经验**：无头进程不会"自动温和"——它按机器上限跑；序号类的状态一旦按场景重建，
在跨场景的协议里就是定时炸弹。

## 11. 云端面板口令正确仍 403：HTTP 头区结束判定

**现象**：状态页输入正确管理口令仍 403；EditMode 全绿，单元测试传"完整请求字节"恰好绕过问题。

**根因**：真实收包循环把"刚读完请求行"当成头区结束（为 telnet 单行请求保留的容忍逻辑），
而正常 HTTP 请求的头字段可能晚一个 TCP 段到达——`X-Admin-Token` 根本没被解析。

**修复**：头区结束只认 `CRLFCRLF`（抽成纯函数 + 6 条单测）；
单行容忍逻辑搬进读循环，判据改为"短暂等待后仍无后续字节"；
本地起真实服务器复验 403/200 全对后才重新出包。

**验证**：公网带正确口令 → 200；不带 / 错误口令 → 403；`?token=` 兼容写法 → 200。

**经验**：协议解析的单元测试如果只喂"理想字节流"，就测不出真实网络的**分片到达**——
要么用真实回环验证，要么把"分段到达"写进用例。

## 12. 中文缺字：动态字体图集写坏的半成品状态

**现象**：某次批次后新增中文文案大量缺字/乱码，旧文案正常。

**根因**：提交的字体资产是动态字体，只预烘了旧文案的 253 个字形；
新增文案超过图集容量后 TMP 动态扩页失败，留下
`characterLookupTable['角'].glyphIndex = 24004` 但 `glyphLookupTable` 没有 24004
的半写入状态。

**修复**：工具改为扫描项目内全部界面文案，按 2048×2048 / 64pt / 6px padding
预烘焙全部汉字并切成 **Static**（运行时不再写图集）；新增"字体资产覆盖全部界面文案"的测试，
缺字时直接列出字符。

**验证**：静态资产 600 字符 / 600 字形 / 1 张图集，覆盖率 100%；
主菜单、角色选择、背包、商人、暂停、结算等界面截图确认无缺字。

**经验**：把"内容驱动的资源"（字体子集）纳入构建工具 + 自动化检查，
否则它会在每次加文案时随机爆炸。

## 13. 滚轮"滚十几圈只动一点点"：一个量纲错误

**现象**：商店列表滚动极慢，滚十几圈只移动几像素。

**根因**：按"Windows 一格滚轮 = 120"写了 0.4 像素/单位，以为一格滚 48 像素；
而新版 Input System 在 Windows 上把滚轮归一成"一格 = 1.0"，
于是实际一格只有 0.4 像素。

**修复**：不再假设量纲——先把原始值归一成"格数"（绝对值大于 10 的按 120 制换算），
再按"一格 = 一行（48 像素）"换算；键盘方向键也走同一条格数通道。

**验证**：反射调用滚动函数，两种量纲的一格都精确移动 48 像素；实机手感一次滚动看到整行变化。

**经验**：跨层传递的数值必须带单位语义；"输入设备的一格是多少"应该被归一化在边界上，
而不是散落在每个消费方。

## 14. 资源热更"下载成功但不生效"：寻址重写误伤 catalog 缓存

**现象**：日志显示资源下载成功，但游戏里数值还是旧的；只有一行 `catalog 加载失败`。

**根因**：本工程的寻址重写函数只判断"能不能从地址里取出文件名"，
把 Addressables 自己的 catalog 缓存路径（`com.unity.addressables/<哈希>.bin`）
也翻译成了更新源 URL，导致缓存写入失败、内容层静默退回本体。
修复：重写只翻译属于内容层命名空间（`content/`）的地址。

**验证**：真实更新源下重新下载并确认内容版本生效；此后每次发布包都包含一条
"游戏内热更实际下载并生效"的冒烟检查。

**经验**：全局重写/拦截类函数的默认行为应该是"不认识的别碰"，
放行未知地址比翻译所有地址安全。

## 15. 改公司名把玩家进度"改没了"：存档路径也是数据契约

**现象**：调整公司名 / 产品名之后，测试机上玩家的进度"消失"了。

**根因**：`Application.persistentDataPath` 的路径由公司名 + 产品名拼出，
改名等于换了存档目录。

**改进**：把改名视为"数据迁移事件"——修改 `companyName / productName` 的提交必须同时
迁移旧存档（或明确声明放弃），并在提交信息里写清楚；迁移在真实文件系统上验证。

**经验**：任何会影响持久化位置的元数据都属于数据契约；改它之前先问"存档去哪了"。
