## 1. 一分钟版：这是什么项目

**RaidDemo**：一款 Windows 平台的 **3D 斜俯视（45°）搜打撤（Extraction Shooter）**游戏，
对标《逃离鸭科夫》——紧张感来自**贪心与撤离时机的抉择**，而不是塔科夫式的对枪与穿甲博弈。

- **单人**：主菜单 → 安全屋（整备 / 买卖 / 接任务 / 试枪 / 选图）→ 工业区战局
  （搜刮、与 AI 交火、撤离或被击倒）→ 结算 → 回屋，装备真的会丢，仓库真的会存住。
- **联机**：2~4 人 PVE 合作，统一客户端 + 独立专用服务器；同一间共享安全屋、
  全员回屋后房主才能从出口选图出击。
- **工程侧**：一次只读代码审查留下 72 条编号问题，之后逐条复核、分批修复；
  自研启动器 + 更新源做分发与热更。

> 依据：`README.md`、`Docs/审查报告/RaidDemo_审查问题状态复核.md`

## 2. 技术选型与理由

| 选择 | 版本 | 为什么 |
| --- | --- | --- |
| Unity | 6000.6.0f1 | 既定环境；也正好撞上"新版本的坑"（见第 6 节的 il2cpp 结论） |
| URP | 17.6.0 | 卡通低多边形风格，URP 的着色器与后处理够用且轻 |
| Input System | 1.20.0 | 需要手柄/键盘统一投影与"输入意图"抽象，旧输入系统表达不了 |
| Netcode for GameObjects | 2.13.2 | 需要"服务端权威 + 客户端预测"这条现成但可控的链路；不用第三方同步方案是为了能讲清每次同步的代价 |
| Addressables | 2.10.3 | 资源热更与远程目录；数据表 / 场景 / 角色 / 音效分包 |
| HybridCLR | **未引入** | 探针验证在当前 Unity 版本不可用，按 ADR-008 降级（见第 6 节） |
| 自研启动器 + 更新源 | — | 本体更新必须发生在进程之外；自研让它能与"游戏内热更"共用同一份更新清单 |

> **一句话**：选型不追新，每一种都要能回答"不用它会怎样"。

> 依据：`README.md` 技术栈表、`Docs/Decisions/`（ADR-002/003/004/007/008）

## 3. 架构分层与程序集边界

工程按"**规则向内、依赖向下**"分程序集（约 20 个 asmdef）：

```text
Bootstrap（装配 + 联机 + 启动层）        ← 唯一知道"场景里有什么"的地方
  ├── UI / Presentation / Diagnostics    ← 只读状态、发请求、画东西
  ├── Modules：AI / Combat / Inventory / Raid / Meta / Simulation / Input
  └── Shared / Data / Kernel.Pure        ← 纯逻辑，不需要引擎
```

三条硬规则（都有测试兜着）：

1. **低层禁止反向依赖高层**（例如 `Data` 不许 `using RaidDemo.UI`）；
2. **单文件不超过 400 行**、源码与配置不含任何本机绝对路径——由 `PathRulesTests` 强制执行；
3. **纯逻辑与表现分离**：移动仿真、战局计时、背包规则、AI 状态机都是普通 C# 类，
   因此可以在 EditMode 下断言行为，不需要真的进 Play。

> **为什么值得讲**：这不是"分层好看"，而是让 716 条测试能在几秒内跑完的前提；
> 也是联机时"同一套规则跑在服务端与客户端"的前提。

> 依据：`Docs/00_项目工程规范与系统设计.md`、`Assets/Game/**/*.asmdef`、`Assets/Game/Tests/EditMode/PathRulesTests.cs`

## 4. 三个可深挖的设计

### 4.1 联机权威：服务器说了算，客户端只做预测与表现

- 上行只有**意图**（移动方向、朝向、扳机、换弹、搜刮、装备、购买、出击），
  服务端用固定步长推进权威世界，再把快照与事件下发给客户端；
- 客户端本地也跑同一份移动仿真做**预测**，收到快照后做**和解**：
  误差超过容差才回滚重放（日志里能直接看到"误差 x 米，重放 n 条输入"）；
- **服务端也会校验上行输入**：非法槽位、NaN / Infinity、超范围一律丢弃，
  不合法的一律不改权威状态（这条是被自己的审查报告点出来后补的）。

> 深挖方向：为什么不是帧同步？——合作 PVE 对确定性要求低，但对"看不见的作弊"与
> "掉线恢复"要求高，状态同步 + 服务端裁定更省事。

### 4.2 容器与物品：一份规则、三种调用方

背包 / 装备 / 仓库 / 战利品箱都走同一套 `InventoryGrid` + 命令层：
客户端界面、单机内嵌服务器、专用服务器**共用同一份放置规则**，
区别只在"命令由谁执行、结果怎么回"。

- 客户端操作是**乐观更新**：本地先画，服务器随后回发权威内容覆盖；
- 服务器拒绝时会把权威容器推回去，避免"界面显示装了、服务器说没装"的长期漂移；
- 战利品容器是"内容按服务器、容量按本地、物品对象尽量复用"（双击/拖拽/拆分都验证过）。

### 4.3 三层版本与分发

```text
本体版本（bundleVersion）→ 启动器按清单增删文件、原子替换、失败回滚
资源版本（catalog 哈希）→ 游戏内 Addressables 热更，只下变化的文件
代码版本（当前留空）    → 由启动器替换本体承担
       ↓
统一对外暴露一个 buildId：0.10.1+c9bdad504
```

- 更新清单带逐文件 SHA-256，启动器支持断点续传；更新源是独立小程序（Web 面板可上传/发布/回滚/校验）；
- **版本握手**：进房前比对两端本体版本，不一致直接拒绝并提示该更新到哪一版；
  老客户端（没有这个字段）按"未知"放行——这条兼容规则是刻意设计的，
  否则"服务器一升级，老客户端全体进不去"。

> 依据：`Docs/Modules/11_热更新与分发.md` 第 2 / 13 节、`Tools/Launcher/`、`Tools/UpdateSource/`

## 5. 工程规范与验证：怎么保证"它真的能跑"

| 手段 | 现状 |
| --- | --- |
| EditMode 测试 | **716 / 716**（移动仿真、背包与容器、战斗与伤害、AI 状态机、战局闭死、局外经济、联机协议、热更清单、版本握手……） |
| 批处理验收脚本 | 启动器 `13/13`、更新源 `17/17`、版本握手 `6/6`、战局超时链路 `5/5`（都可在本机重跑） |

| 自查闭环 | 只读代码审查（72 条）→ 逐条状态复核（仍存在 62 / 已修 2 / 部分修复 3 / 口径变化 4 / 无法判定 1）→ 按性价比分批修（第一档 9 条 + 联机权威链 8 条） |

> 所以"复核"这一步不是形式，它直接决定要不要动手、动哪里。

## 6. 已知边界与技术债（主动交代）

| 边界 | 事实与代价 |
| --- | --- |
| **进程内代码热更不可用** | HybridCLR 社区版与 Unity 6000.6 的 il2cpp 不兼容（探针 27 处编译错误，证据留档）。降级方案：代码更新走启动器的本体更新——代价是必须重启游戏 |
| **联机没有反作弊** | 服务器校验输入合法性，但不做反外挂；这是合作 PVE，不是竞技 |
| **性能未做量测** | 没有 Profiler / GC 数据；已知可优化项（伤害数字与弧形体力条未走对象池等）记在复核文档里 |
| **架构层面的技术债** | `Bootstrap` 偏重（`ServerRuntime` 28 个 partial）、方法长度与裸日志还没有自动门禁——第四档推迟，理由与清单见复核文档 7.2 节 |
| **内容规模** | 1 张地图、2~4 人、5 个固定任务、无配件与改装系统 |
| **素材授权** | 以 CC0 / 官方免费包为主，逐项登记在 `Docs/Assets/M7_素材使用与归档清单.md` |

> 讲技术债的方式：**说清"知道它、为什么现在不修、什么时候修"**，比假装没有更可信。

## 7. 高频问题与回答要点

1. **"你的联机为什么用状态同步而不是帧同步？"**
   合作 PVE、人数少、对确定性要求低；帧同步要处理浮点确定性与输入延迟，收益不明显。
2. **"客户端预测错了怎么办？"**
   快照回来做和解：位置误差超容差才回滚重放，日志里能看到误差与重放条数。
3. **"玩家作弊怎么办？"**
   服务端不接受任何"结果"只接受"意图"；输入做合法性校验。但明确说：没有反外挂。
4. **"物品状态为什么不放 ScriptableObject 上？"**
   资产是共享的，运行时状态必须绑在实例上——这正是自审发现的问题之一（同型号两把枪共享弹匣），
   修复方向已记录在复核表 `RD-AUD-011`。
5. **"为什么不用现成的联机方案 / 插件？"**
   需要"服务端权威 + 客户端预测 + 自己掌握每条同步的代价"，NGO 提供传输与序列化，规则自己写。
6. **"热更新的方案怎么定的？"**
   资源走 Addressables（已验证）；代码本来打算 HybridCLR，探针证明当前版本不可用后**降级**为
   启动器更新本体，并把失败证据留档（ADR-008）。
7. **"怎么保证更新不出事？"**
   清单哈希 + 断点续传 + 原子替换 + 失败回滚；更新源有校验接口；游戏内热更失败时保留上一份内容。
8. **"测试怎么写的？"**
   纯逻辑优先：把规则做成普通 C# 类，EditMode 直接断言；依赖引擎生命周期的才放 PlayMode。
9. **"代码规范怎么落地？"**
   单文件 400 行、禁止绝对路径由测试强制；其余规范（方法长度、参数、日志）列入第四档待补门禁。
10. **"这个项目最难的地方？"**
    联机权威链的收口：客户端本地结算、服务端没有超时、结算数字各自算一套——
    这组问题互相依赖，必须一次改完才能验（见第 8 节路径的最后一步）。
