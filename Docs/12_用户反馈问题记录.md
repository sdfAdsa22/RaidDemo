# 用户反馈问题记录

> 本文档专门记录**项目负责人在验收测试中反馈的问题**，以及每一次的定位过程与修复方式。
>
> 为什么不并入其它文档：
>
> - `排障记录/` 文件夹记的是**我在执行中遇到的问题**（编辑器行为、工具链、工程约束、测试自身），
>   它明确不收录业务缺陷；
> - `Modules/` 下的设计文档记的是**系统应该怎么设计**，不记"设计落地后哪里做错了"；
> - `Decisions/` 下的 ADR 记的是**主动做出的取舍**，而这里记的是**被动发现的错误**。
>
> 三者性质不同，混在一起会让每份文档都变得不好查。
>
> **为什么值得单独建一份**：常规单元测试只能验证"我想到的情况"，
> 而验收反馈暴露的是"我没想到的情况"。这类问题重复出现的模式很有价值——
> 本文档最后一节就是从这个角度做的复盘。
>

> （新增第二十五节：U-70~U-79 —— P4 联机验收反馈与修复；并记录负责人定稿的

## 记录格式

每条问题按以下小节记录，缺一不可：

| 小节 | 要求 |
| --- | --- |
| 反馈原话 | 尽量保留负责人当时的原话，不要转译——措辞本身就是定位线索 |
| 现象 | 可观察到的具体表现，包含"哪些情况正常、哪些不正常" |
| 定位过程 | 怎么从现象找到根因的，中间排除过哪些可能 |
| 根因 | 一句话说清是什么错了 |
| 修复 | 改了什么，为什么这么改 |
| 验证 | 用什么方式证明修好了。**区分"单元测试"与"真实调用路径"** |
| 提交 | 对应的 git 提交短哈希 |

## 一、M1 阶段：移动与相机

### U-01：视角不对，应该是俯视角

**反馈原话**

> 视角不对，应该是俯视角，如上图的视角

**现象**：进入播放模式后看到的是接近平视的斜角，能看清远处的箱子侧面，俯视感不足。

**定位过程**：直接读相机配置。俯角参数写的是 45 度——这是一个"看起来像俯视"的直觉值，
但对 3D 俯视角游戏来说太平了，视线几乎贴着地面。

**根因**：相机俯角取 45 度，是按"斜视角"的印象拍的，没有参照目标游戏的实测角度。

**修复**：俯角改为 62 度。这个区间（45~62）是斜俯视 3D 的常见取值，
既能看清地面布局，又保留立体感。

**验证**：进入播放模式截图人工确认。

**提交**：`b3a4b7f`

### U-02：玩家下半身埋在地里

**反馈原话**

> 我在 unity 里运行后玩家的下半身在地里

**现象**：角色只露出上半身，下半截被地面切掉。

**定位过程**：检查角色节点的位置与几何体的尺寸。根节点放在地面高度上，
而角色用的是 Unity 内置的胶囊图元——**胶囊图元的原点在几何中心，不在脚底**，
于是节点落在地面上时，半个胶囊自然埋到了地面以下。

**根因**：图元的原点约定与"站在地面上"这个意图不匹配。

**修复**：根节点改为脚底对齐，按胶囊高度的一半把视觉子节点上移，
使根节点位置在语义上等于"脚踩在地面上的那个点"。这样后续所有涉及位置的计算
（生成点、相机跟随、碰撞检测）都可以直接用根节点坐标，不需要到处加减一个偏移量。

**验证**：播放模式截图确认脚部与地面贴合。

**提交**：`b3a4b7f`

### U-03：移动鼠标时整个画面跟着动

**反馈原话**

> 视角和鼠标没对上，且移动鼠标时摄像头窗口也会移动，应该是摄像头和玩家固定，只有移动时才变化

**现象**：鼠标一动，整个画面跟着晃；玩家会以为自己在移动相机。

**定位过程**：读相机跟随逻辑，发现它按角色朝向做了"前瞻"——
角色朝哪边看，相机就往那边偏一点，本意是让瞄准方向前方多露出一些。

**根因**：前瞻与"摄像机固定跟随"的预期冲突。在斜俯视游戏里，
画面朝向变化会直接破坏玩家对"按住某个方向就是往那个方向走"的空间感。

**修复**：移除朝向前瞻，相机只跟随位置。**这是一条设计结论，不只是 bug 修复**：
斜俯视项目里相机不应随瞄准转动。

**验证**：播放模式人工确认。

**提交**：`b3a4b7f`

### U-04：鼠标靠近角色时角色自己转

**反馈原话**

> 当鼠标放在玩家模型上时，玩家会开始旋转

**现象**：鼠标越靠近角色，角色转得越厉害，甚至开始抖动。

**定位过程**：看瞄准解算。瞄准方向 = 瞄准点 − 角色位置，再归一化。
当鼠标贴近角色时，这个向量长度趋近于 0，方向在数值上极度不稳定——
鼠标挪动一个像素，方向可能就翻转 180 度。当时的死区只有 0.01 米，几乎起不到过滤作用。

**根因**：死区过小，数值噪声被当成了真实的瞄准意图。

**修复**：死区放大到 0.5 米，并把瞄准解算从 MonoBehaviour 里抽成独立的
`AimResolver` 静态类——**这是这次修复里更重要的一半**：
抽出来之后，"死区内返回零向量""死区外返回单位向量"这些行为可以写成单元测试，
而不是只能靠人拖着鼠标去感受。

**验证**：新增 `AimResolverTests`，覆盖死区边界、零向量、单位长度、抖动稳定性等 15 个用例。

**提交**：`b3a4b7f`

### U-07：准星与角色朝向对不上

**反馈原话**

> 准星和模型的橙色长条不在一条线上

**现象**：鼠标指向某处，准星画在那个位置，但角色模型朝着另一个方向，两者差 90 度。

**定位过程**：这是本阶段最费时的一个问题，因为**同一个映射我写错过两次**：

1. 第一次多写了一个负号，朝向差了 180 度；
2. 第二次直接照搬平面角度，朝向差了 90 度。

真正的原因是两个坐标系的方向约定不同：

| 层 | 平面 | 0 度指向 | 90 度指向 |
| --- | --- | --- | --- |
| 模拟层 | 二维 XY 平面 | +X | +Y |
| Unity 场景（相机朝 +Z 俯视） | XZ 平面 | 屏幕右（+X） | 屏幕上（+Z） |

而角色模型的"鼻子"在本地 +Z 方向，因此正确的换算是：

```text
Unity 旋转角 = 90 − 模拟角度
```

**根因**：模拟层与表现层的角度基准差 90 度，且换算方向（顺时针 / 逆时针）相反。

**修复**：修正换算，并把整段推导过程写进 `PlayerMotor.cs` 的注释——
这类"两个坐标系之间的固定换算"光看一行代码是看不懂的，
必须把两个坐标系的定义一起写下来，否则下一个人只会再错第三次。

同时移除了角色朝向的角速度插值：它依赖 `deltaTime`，编辑器失焦时每帧只转不到 1 度，
模型会卡在错误朝向上，看起来像是映射又错了。**这是排查过程中的一个假线索**，
记录下来避免以后重复踩。

**验证**：播放模式截图，确认准星与角色朝向一致。

**提交**：`bf4dec2`

## 二、M2 阶段：物品与背包

### U-08：无法拖拽物品到背包里

**反馈原话**

> 无法拖拽 物品到背包里，没法双击物品快速移动到背包里

**现象**：从战利品箱往背包拖物品，**完全没有任何反应**——不是放不进去、
也不是弹回原位，而是像鼠标根本没被界面接收到。

**关键线索**：同一容器内部拖动（把箱子里的物品挪到箱子另一格）是正常的。
这个"部分可用"的特征很有误导性——它让人第一反应是去怀疑放置规则或者输入系统，
而这两处其实都没问题。

**定位过程**：既然规则层有测试覆盖、同容器拖动又正常，那问题只可能在界面到命令这一段。
直接读拖拽的收尾代码，一眼看到：

```csharp
var view = FindGridAt(pointer, out var cell);       // view = 松手时所在的容器（目标容器）
if (view != null && view.Grid.TryGetOrigin(m_DragItem, out var origin))
```

`TryGetOrigin` 是在**目标容器**里找这件物品的坐标。跨容器搬运时物品根本不在目标容器里，
它必然返回 `false`，于是整个分支被跳过，**命令一次都没有发出去**。

而在同容器内拖动时，物品确实就在 `view` 里，查询成功，所以看起来一切正常。

**根因**：查询物品坐标时用错了容器——应该查源容器，写成了目标容器。

**修复**：改为从 `m_DragSource.Grid` 查询坐标，并在代码里写明为什么必须是源容器。

**验证**：这次没有只依赖单元测试。单元测试覆盖的是规则层，而 bug 在界面层，
所以用反射直接调用界面的真实方法：

- 调用 `BeginPointerDown`，指针位置取战利品箱 (0,0) 格的中心；
- 调用 `EndDrag`，指针位置取背包 (0,0) 格的中心；
- 结果：箱子 9 件 → 8 件，背包 0 件 → 1 件。

指针坐标不是硬编码的，而是用 `RectTransformUtility` 从格子的世界坐标反算出来的屏幕坐标，
因此走的是与真实鼠标完全相同的那条换算路径。

**提交**：`97b4a95`

### U-09：无法双击快速搬运

**反馈原话**

> 没法双击物品快速移动到背包里

**现象**：双击物品没有任何反应。

**定位过程**：查命令路由的注册表与处理器的实现——`InventoryQuickTransferIntent`、
`InventoryQuickTransferCommandHandler` 都在，而且有单元测试覆盖，测试是通过的。
再查界面，发现 `BeginPointerDown` 里只处理了"开始拖拽"，
**界面从来没有发出过这条命令**。

**根因**：功能没有接上。命令层与规则层都实现完了，界面层漏了。

**修复**：在左键按下时判定双击（窗口 0.35 秒，接近操作系统默认值）。
目标容器固定取"另一个"：在战利品箱里双击就是捡进背包，在背包里双击就是放回箱子。
这样双击的语义只取决于物品在哪，玩家不需要先想清楚要搬到哪儿去。

同时加了**三连击保护**：触发一次快速搬运后清掉记录，避免"双击 + 再点一下"
被当成第二次双击又搬一遍。

**验证**：与 U-08 相同的方式，走界面的真实方法：

- 双击背包里的物品 → 背包 1 → 0 件、箱子 8 → 9 件；
- 双击箱子里的物品 → 背包 0 → 1 件、箱子 9 → 8 件。

**提交**：`97b4a95`

### U-10：头盔与防弹背心可以互换位置

**反馈原话**

> 只剩一个小问题，头盔除了放在头部，也能放在护甲位置，护甲同理也能放在头部

**现象**：钢盔能穿在躯干上，防弹背心能戴在头上。

**定位过程**：读槽位规则：

```csharp
case EquipmentSlot.Head:
case EquipmentSlot.Body:
    return category == ItemCategory.Armor;   // 两者判据完全相同
```

两个槽位接受的是**同一个分类**，判据一模一样，所以必然可以互换。
往上游追，问题不在槽位规则，而在分类的粒度：`ItemCategory` 里只有一个 `Armor`，
头盔与防弹背心在数据上就是同一种东西，规则层没有任何信息可以用来区分。

**根因**：分类粒度不足。分类是装备槽规则的唯一依据，而它没有精确到规则需要的程度。

**修复**：把 `ItemCategory.Armor` 拆成 `Helmet` 与 `BodyArmor`。

选择拆分类而不是新增一个"允许槽位"字段，理由是：分类本来就已经是槽位规则的唯一依据，
把它做精确之后，槽位规则不需要任何额外字段就能表达正确语义；
多一个字段就是多一处可能与分类不一致的地方。

**连带影响（重要）**：枚举值发生位移，而这些值是**序列化在 `.asset` 文件里的整数**。
钢盔的 3 恰好仍是 `Helmet`，但防弹背心的 3 变成了头盔、背包的 4 变成了 `BodyArmor`——
所有分类都错位了。因此必须**重新生成全部物品资产**。

这件事没有造成任何麻烦，正是因为物品资产是**由代码生成器产出**的
（`ItemContentBuilder` 里一张数据表），重跑一次即可。
如果当初是手工在 Inspector 里填的，就得逐个打开 13 个资产改分类。

**验证**：三层验证。

1. 新增 3 项单元测试：钢盔进护甲槽失败、背心进头盔槽失败、钢盔进头盔槽成功；
2. 抽查重新生成的资产，确认分类整数值正确（钢盔=3、背心=4、背包=5、金表=6）；
3. 运行时走真实命令链路：

```text
钢盔 → 护甲槽：成功=False 代码=inventory_slot_mismatch 物品还在箱子里=True
钢盔 → 头盔槽：成功=True  槽位=钢盔
```

第 3 条同时验证了失败操作的原子性——被拒绝时物品留在原处，没有丢。

**提交**：`420cbed`

### U-11：准星盖在背包面板上

**来源**：不是口头反馈，是负责人在反馈界面效果时发来的截图，我复核时发现的。

**现象**：瞄准准星画在打开的背包面板之上。

**定位过程**：查两个画布的层级设置，发现准星画布与背包画布的 `sortingOrder` **都是 100**。
层级相同时，Unity 让**后创建**的画布渲染在上层；准星画布是启动过程中后建的，
于是它赢了。

**根因**：两个画布层级相同，渲染顺序由创建顺序偶然决定。

**修复**：两层处理。

1. 背包面板画布提到 200，保证面板永远在准星之上；
2. 打开背包时**直接隐藏准星**——那时玩家在整理装备，准星本来就没有意义。

只做第 1 条也能让图看起来对，但那是"碰巧对了"；第 2 条才是把语义写正确。

**验证**：无法截图验证（见复盘第 4 条），改为数值验证画布层级与网格视图结构。

**提交**：`4cad8b1`

### U-16：枪械与角色朝向不一致

**反馈原话**

> 枪械和玩家方向没对上

**现象**：截图里角色身上的橙色朝向标记指向左下，而枪指向右上，两者大致相反。

**定位过程**：先分别验证两套朝向的换算：

| 瞄准方向 | 枪口朝向 | 角色朝向 |
| --- | --- | --- |
| (1, 0) | (1.00, 0.00) | (1.00, 0.00) |
| (0, 1) | (0.00, 1.00) | (0.00, 1.00) |
| (-1, 1) | 归一化 | (-0.71, 0.71) |

**两套映射完全一致**，所以问题不在换算，而在"何时更新"。

再看输入采集：

```csharp
if (!wantsToFire)
{
    m_WeaponController.SetTriggerHeld(false);
    return;          // 不按住左键就直接返回，瞄准方向根本没被同步
}
```

**根因**：瞄准方向只在开火帧才写入武器。玩家不开火时转动鼠标，角色朝向跟着变，
枪却停在最后一次开火的方向上。

**修复**：把瞄准方向的同步提到开火判断之前，每帧都更新。
开火意图里仍然携带方向（服务端要校验），两者不冲突。

**教训**：**状态同步与动作触发是两件事，不能写在同一个条件分支里。**
瞄准是持续状态，开火是离散动作——把前者塞进后者的 `if` 里，就变成"只有开火时才瞄准"。

**提交**：`2fcbaeb` 之后的修复提交

### U-17：右下角信息只显示一部分

**反馈原话**

> 右下角的 ui 显示只有一部分

**定位过程**：先测量实际几何，排除锚点问题：

```text
屏幕=2560x1225  画布=1920x918  缩放=1.33
面板底左=(2160, 53)  顶右=(2507, 213)     距屏幕右边缘 53px
```

**锚点位置是正确的**，面板完整地在屏幕内。那么只剩一种可能：**文字被自己的矩形裁掉了**。

**根因**：`UnityEngine.UI.Text` 的默认溢出模式是 **Wrap（自动换行）**。
文字只要略宽于矩形，后半段就被折到第二行；而标签矩形的高度只有 28 到 40 像素，
第二行随即被垂直裁掉——看上去就是只显示了一部分。

**修复**：把 `horizontalOverflow` 与 `verticalOverflow` 都设为 `Overflow`，
并把面板边距从 40 提到 56。**宁可让文字略微超出矩形，也不要它被无声地裁掉**：
超出只是不美观，裁掉是信息缺失。

**教训**：界面元素看起来被切掉时，**先测几何排除布局问题，再去查渲染层**。
这次如果直接去调锚点，会改一堆本来没问题的地方。

### U-18：不按左键就按 R 无法换弹（自查发现）

**来源**：修 U-16 时读同一段输入采集代码发现的，负责人还没试到这一步。

**现象**：换弹命令被写在开火分支内部：

```csharp
if (!wantsToFire) { ...; return; }   // 不按左键就返回
...
if (wantsToReload) { 派发换弹命令 }   // 于是这里永远不会执行
```

**根因**：两个彼此独立的输入被写成了嵌套关系。换弹与开火没有依赖，
但代码结构上让换弹变成了"开火时才可能发生"。

**修复**：拆成两个并列的分支，并把这个理由写进注释。

**教训**：与 U-16 同源——**多个独立输入不要共享提前返回的分支**。
一个判断提前 `return` 之前，要确认后面没有任何与它无关的逻辑被跳过。

### U-19：换弹后背包里的子弹没消失

**反馈原话**

> 换蛋后背包里的子弹没有消失

**定位过程**：先实测换弹全过程：

```text
换弹命令=True 备弹 30->18 弹匣=30 背包变更事件=1次
```

**弹药确实被扣掉了**——30 发正好装满一个 30 发的弹匣，数字完全正确。
所以问题不在逻辑，而在**界面没有收到通知**。

**根因**：`AmmoReserve.Consume` 直接修改网格数据，**没有发布 `InventoryChangedEvent`**。
背包界面只在收到事件时刷新，于是一直显示换弹前的数量。

这是对 M2 定下的架构约束的破坏：状态变更必须让订阅方知道。
M2 的所有变更都走命令处理器，事件在处理器里统一发；
而换弹扣弹药是**战斗层的计时行为**，绕过了那条通路，于是漏发了事件。

**修复**：换弹完成、扣掉弹药之后，按主背包的容器标识广播一次背包变更事件。
控制器因此需要知道主背包的容器标识，由启动层在装配时传入。

**教训**：**任何"绕过原有通路直接改状态"的新代码路径，都要主动补上事件广播。**
命令处理器有统一发事件的地方，而计时行为、AI 行为、环境效果没有——
这类旁路是新功能最容易漏事件的位置。

### U-20：弹道与准星不在一条线上

**反馈原话**

> 子弹弹道和十字准星不在一条线

**定位过程**：先看两者的几何定义。

| 元素 | 位置 |
| --- | --- |
| 准星 | 相机射线与**地面**的交点（高度 0） |
| 枪口 | 角色脚底 + 1.05 米 |
| 原弹道 | 从枪口**水平**打出去 |

相机俯角 62°，水平线在屏幕上的投影必然比同距离的地面点高出一截——
**两者在屏幕空间不可能重合**，这是几何决定的，不是偏移量没调好。

**修复**：弹道改为"从枪口指向地面瞄准点"，并让散布绕竖直轴旋转这个瞄准点。
于是弹着点必然与准星重合，除非中途命中目标。实测：

```text
弹道终点=(9.00, 0.00, -7.97)   准星世界点=(9.00, 0.00, -8.00)    偏差 3 厘米
```

顺带这个模型更符合直觉：**你瞄哪儿，子弹就飞向哪儿**。
打在靶子上的那几发终点是 `(8.6, 0.6, 0)`——正是子弹从枪口飞向瞄准点途中
撞上靶面的位置，说明"中途命中"这条路径也正确。

**教训**：表现与规则不一致时，先检查两者的**几何定义是否相同**，
而不是去调参数。这次如果去硬调弹道高度，只会让它在某些距离上碰巧对上、换个距离又错。

### U-21：Play Maximized 下右下角信息被裁掉

**反馈原话**

> 编辑器里的选的是 play maximized，如图，只能看到 ak 74 和 0/
> 将武器 UI 移到左下角

**现象**：Game 视图选择 **Play Maximized** 时，右下角的战斗信息被窗口边缘裁掉，
只能看到前半截文字。

**定位过程**：我这边在默认布局下反复测量都是正常的——文字右边缘距屏幕右缘 75 像素，
内容完整。差异只在 Game 视图的显示模式：Play Maximized 下窗口边缘更贴近画面边缘，
右侧内容随之被裁。

**处理**：按负责人要求把战斗信息移到**左下角**。

**教训**：界面元素贴屏幕边缘时，要考虑 Game 视图的显示模式差异。

### U-22：贴边 UI 被裁 —— 真正的根因（推翻了 U-21 的结论）

**背景**：U-21 把"信息被裁"归因于 Play Maximized 的显示模式，并据此把 HUD 移到左下角。
移动之后问题依旧，只是从裁右边变成裁左边。**这说明 U-21 的结论是错的。**

**决定性的观察**：往画布左上角加了一行诊断文字（与 HUD 无关的位置），
**连它自己也被裁了**——截图里只能看到 `size 1920x918 scale 1.33`，
而完整文本是 `canvas size 1920x918  scale 1.33`，开头的 `canvas ` 七个字符不见了。

一个与 HUD 毫无关系的元素同样被裁，说明**被裁的不是某个 UI 元素，而是整个画面被推出了可视区域**。

**完整证据链**

诊断给出的画布数据是完全正常的：

```text
canvas size 1920x918   scale 1.33
canvas 世界 0 .. 2560        ← 画布正好覆盖屏幕（屏宽 2560）
ammoLabel 左 75  右 421      ← 标签完整落在屏幕内
```

再算被裁掉的宽度：字号 26、缩放 1.33，每字符约 19 物理像素，
`canvas ` 七个字符约 **133 像素**。

再看 Game 视图的配置：

| 项 | 值 |
| --- | --- |
| 面板实际宽度 | 2560 物理像素 |
| Free Aspect 渲染分辨率 | 等于面板宽度 = 2560 |
| **Scale 滑块** | **1.1x** |
| 放大后显示宽度 | 2560 × 1.1 = **2816** |
| 超出可视区域 | **256 像素**（居中时两侧各裁 128） |

**133 与 128 吻合，根因确认。**

**根因**：Game 视图的 **Scale 滑块**设成了 1.1x。

- Free Aspect 下渲染分辨率**永远等于面板尺寸**，再放大 10% 必然超出面板 → 边缘被裁；
- Full HD 把渲染锁死在 1920×1080，1.1 倍后仍小于面板（2112 < 2560）→ 放得下。

**这也解释了之前所有看起来矛盾的现象**：

| 版本 | 被裁的一侧 |
| --- | --- |
| 右对齐 | 右边 |
| 左对齐 | 左边 |
| 诊断文字（左上角） | 左边 |
| Full HD | 不裁 |

画布比视口大且居中时**两侧都超出**，内容靠哪边就裁哪边。
**换边距、换角、换对齐方式都不可能解决**——问题不在 UI 里，而在显示层。

**处理**：把 Scale 调到 1x。**代码无需修改**，诊断文字已删除。

**教训（这一条最贵）**：

> **"UI 贴边内容被裁"的检查顺序应当是：先确认画布与像素的对应关系，再怀疑锚点。**

我这次反着来了，先改边距、再把 HUD 从右下移到左下、又改了对齐方式——
**白改两轮，而且每一轮都让现象换了个方向，反而更迷惑**。

正确的第一步其实只要一行代码：把画布的 `sizeDelta` 与世界四角打出来，
与屏幕尺寸一比就知道画布有没有正确覆盖屏幕。这次加上诊断之后，
一次测量就定位到了根因。

另一个教训是：**U-21 当时就下结论"这是显示模式的问题"并据此改了代码**，
而实际上只观察到一个现象、没有验证假设。如果当时就测画布数据，能省掉一整轮。

### U-23：子弹到准星处就截止，射程不起作用

**反馈原话**

> 目前子弹是到十字准星处截止，我想的是不应该到十字准星处截止，
> 应该是每种武器的射程不同，子弹最多到射程处

**定位过程**：这是 U-20 的修复引入的副作用。

U-20 为了修"弹道与准星不在一条线"，把射线方向改成了**从枪口指向地面瞄准点**——
方向朝下，于是射线正好在瞄准点落到地面。**射程参数形同虚设。**

根因是我把"方向参考点"当成了"终点"。

**修复**：三件事必须一起改，只改一件会破坏另外两件——

| 环节 | 改法 |
| --- | --- |
| **方向** | 取水平方向（瞄准点只用来定方位） |
| **长度** | 射线长度 = 武器射程 |
| **绘制** | 弹道画在地面上，因此仍穿过准星 |

**验证**：把准星放在 3 米处，子弹越过准星打到 **8.61 米**处的靶子正面。

**教训**：**修一个问题时引入的副作用，往往比原问题更隐蔽。**
U-20 的修复让弹道对齐了，却让射程失效——而射程失效不会"看起来不对"，
它只是让玩家觉得"这枪好像没有射程概念"。

一个可操作的做法：**修完一个涉及多个参数的问题后，把被牵连的参数逐个验一遍。**
这次如果 U-20 修完就验一次"射程还生效吗"，能省掉这一轮往返。

### U-24：体力弧的形状与颜色

**反馈原话**

> 改为白色体力条，目前是弧线向下，改为向上

**根因**：两处都是我按"进度条"的直觉定的，但没有考虑它在**这个位置**上读起来像什么。

| 项 | 第一版 | 问题 | 现在 |
| --- | --- | --- | --- |
| 形状 | 缺口在正上方，圆弧向下垂 | 看起来像挂在角色**身下**的一只碗 | 缺口在正下方，圆弧**向上拱起**，填充从左下经顶部到右下 |
| 颜色 | 青色，低于三成转橙 | 灰盒场景底色深浅不一，彩色不够跳 | **白色**（力竭仍保留红色警示） |

**教训（这条不是调参数能解决的）**：

> **形状的语义比颜色更容易被误读。**同样的数值和颜色，
> 碗形和拱形传达的意思完全不同——前者像"挂在身下的东西"，
> 后者才是"悬在头顶的体力条"。

我第一版只验证了"数值对不对"（45% 的填充长度精确吻合），
却没验证"它在那个位置看起来像什么"。**表现层的东西，
光靠数值正确不足以说明它对了。**

### N-01：Game 视图切到 Full HD 后画面变大

**反馈**：切到 Full HD 后画面被放大，Free Aspect 不会。

**结论：不是缺陷，是 Game 视图的显示行为。**

Free Aspect 按 Game 视图面板的实际宽高比与尺寸渲染；Full HD 强制 16:9 并固定为 1920×1080 像素，
再由编辑器缩放到面板上显示。只要面板不是 16:9，构图就会变化。

**对游戏本身没有任何影响**：界面用的是 `CanvasScaler.ScaleWithScreenSize`，
参考分辨率 1920×1080，任何分辨率下都会按比例自适应。

**给的结论**：开发期保持 Free Aspect；等到 M8 录演示视频时再切 Full HD，
那时的诉求是"输出尺寸稳定"，值得为它切换。

## 四、M5.5 增量（2026-09-12）

### U-25：医疗包之类的物品无法使用

**反馈原文**：「目前医疗包之类的物品无法使用？是之后有安排吗？」

**定位**：不是缺陷而是**范围缺口**。医疗品在 M2 就作为可搜刮物品存在，
但「使用消耗品」从来没有被排进任何里程碑：`ItemBehavior` 扩展点是 M2 就留好的，
却一直没有具体实现。玩家搜到医疗包的唯一用途是卖钱与占格子。

**根因**：M2 只做了「物品能进出背包」，没有做「物品能产生效果」。
两者在文档里被混为一谈，于是这个缺口在三个里程碑里都没被发现。

**做法**：把「使用物品」作为 M5.5 的增量补上——`MedicalBehavior`（回血量 + 读条时长）、
`ItemUseInteraction`（纯逻辑读条）、`H` 快捷键与右键菜单两个入口。

**教训**：**「有这件物品」不等于「这件物品有用」。**
以后再引入一类新物品时，要同时问一句「它的效果由谁负责实现，排在哪个里程碑」，
否则会造出一批只能卖钱的空壳。

### U-26：右键菜单横向太宽，压住背包格子

**反馈原文**：「右键菜单横着太宽了，缩小成一半」（附截图）

**定位**：菜单宽度写死 200 像素，而菜单项只有两三个汉字，右侧全是空白。
在 1080p 下它压住了背包右半边的格子。

**根因**：定宽度时按「看起来像个菜单」估的，没有按**最长菜单项的实际宽度**去算。

**做法**：宽度改为 100 像素（刚好容纳文字 + 内边距），位置收敛逻辑保持不变。

**教训**：界面元素的尺寸应当由**内容**决定，而不是由「像不像那么回事」决定。
凡是写死的尺寸，都要能回答「这个数字是按什么算出来的」。

## 五、M5.6 修复批次（2026-09-12）

这一批四条问题有一个共同的形状：**系统都做完了，但「生效」的那一步没接上**。

### U-27：护甲、头盔没有防护作用

**反馈原文**：「护甲、头盔没有防护作用」「这些是之后有计划修改还是 bug？」

**根因**（两处，缺一不可）：
1. **头盔从未被读取**：开战时只读了身体护甲槽，头盔从头到尾没有任何代码引用；
2. **护甲只在开局读一次**：`Create(maxHealth, armor)` 之后不再更新，战局中捡到并穿上也不生效。

而玩家开局是空手，两个因素叠加的结果是——**实战中护甲恒为 `null`**，防护价值等于零。

**做法**：`CombatantState` 拆成头部/身体两套护甲状态，命中上部位（暴击）由头盔挡、其余由背心挡；
新增 `SetArmor` 并在换装后同步；磨损记在真正挡下那一击的那套护甲上。

**教训**：**「装备槽里有东西」不等于「它在生效」。**
凡是「玩家装上之后应当产生某种效果」的系统，都要有一个明确的生效点（读取/同步），
否则功能会以「看起来做完了」的形态存在很久。

### U-28：负重数值有问题

**反馈原文**：「带把枪、头盔、护甲就把负重拉满了，你有什么建议？是取消武器、护甲、背包的重量吗？」

**定性**：不是 bug，是**数值在错误的前提下定下来的**。M2 定 20 kg 时还没有真实对局，
而当时的物品重量是按「全捡一遍就能看出效果」调的；等 M5 有了对局，它变成了「正常玩都跑不动」。

**做法**：上限 20 → **50 kg**，装备减重（背心 5.0 / 头盔 1.2 / 步枪 3.2 / 突击背包 2.5），
一套基础装约 11.9 kg。**没有取消装备重量**——重量是贪婪循环的物理载体，取消等于删掉核心系统。

**教训**：数值结论必须标注它依赖的前提。M2 的推理（"上限要落在稍微贪一点就越线的位置"）
本身没错，错的是它把灰盒阶段的物品重量当成了长期数值。

### U-29：背包装备后没有作用

**反馈原文**：「背包装备后没有作用」

**根因**：随身网格是开战时按固定 5×5 创建的常量，装备背包**从来不改变它**。
小包与突击包都只是躺在装备槽里的装饰品——而物品定义里其实早就写好了 4×4 / 6×6 的内部格数。

**做法**：背包决定容量（无包 5×5 口袋、小包 6×6、突击包 7×7）；
换包时先把物品搬进新网格，**任何一件放不下就放弃调整**并保留原网格（项目没有地面掉落系统）。

**教训**：与 U-27 同一形状——**数据写了、规则没接**。
新增一个「可装备的物品」时，必须同时问：它装备之后改变的是哪个数值，谁负责读它。

### U-30：测试箱里没有背包

**根因**：固定产出按配置顺序放置，步枪（3 格）→ 背心（6 格）→ 头盔（4 格）
先把 6×4 的空间切碎，最后 9 格的背包无处可放，被**静默丢弃**。

**做法**：放置前按物品占地从大到小排序（沿用 M2 的老规则），并把测试箱放大到 6×5。

**教训**：这条教训**两年前就吃过一次**（M2 灰盒填充），代码注释里还写着，
但加新功能时没有沿用。**已知规则应当写进公共路径（这里是 LootRoller 本身），
而不是留在某个方法的注释里。** 另外「放不下就静默丢弃」本身也是问题，应当返回被丢弃的清单。

### U-31：换背包后搜索容器的格子消失

**根因**：容量变化会整块重建界面，重建销毁了战利品视图，但状态里仍记着原容器 ID；
而 `OpenLootContainer` 只在 ID 变化时才重建视图——于是面板既看不到，重搜同一个箱子也不会回来。

**做法**：重建前取出打开的容器 ID 并把状态清零，重建后按原样恢复。

**教训**：与 M5.5 的右键菜单是**同一类错误的第二次**（视图被销毁，字段还指着它）。
这类问题的共同特征是：**界面里有「谁开着」这类状态，而视图可以被销毁重建**。
应当形成一条硬规矩——**凡是持有视图引用的字段，在视图被销毁的那条路径上必须一起清空**。

## 六、M6 局外、移动与界面批次（2026-09-12）

这一批七条问题有一个非常集中的形状：**装配漏了一层**。

### U-32：安全屋有提示但看不到设施模型

**反馈原文**：「有提示但没有商人、仓库、出口模型」

**根因**：生成器把设施宿主对象摆在原位之后**又**挪了一次，而子物体是按世界坐标创建的——
父物体一动，箱子被二次位移，直接被推出房间。交互标记位置是对的，所以提示照常出现。

**做法**：在创建子物体**之前**先把宿主摆到位。

**教训**：生成器里「世界坐标 + 父物体」混用时，**父物体的位置必须在建子物体前定死**。
这类错误的症状是「东西不见了但功能还在」，比崩溃更难查。

### U-33：安全屋玩家形象与战局不一致

**根因**：安全屋的角色只建了身体圆柱，没建头部与朝向指示。

**做法**：补齐两者，配色与战局完全相同。

**教训**：同一个「我」出现在两个场景里时，表现必须一致——否则玩家会怀疑是不是两个人。

### U-34：战利品面板压住背包

**根因**：战利品面板的横坐标**写死 600**，而那是按 5×5 口袋算的；
换上 6×6 背包后背包列宽了 56 像素，于是叠在一起。

**做法**：横坐标改为按背包实际宽度推算。

**教训**：布局里的数字若依赖另一个会变化的值，就必须**算出来**而不是估一个。

### U-35：装备武器后无枪模型、不能射击、无伤害数字

**根因**：安全屋当初只做了移动、背包与交互，**没有战斗装配**——
没有武器控制器、没有开火命令、靶子也不在战斗层里。

**做法**：把战局那一套搬进来（同一套控制器与命令），靶子登记成战斗单位。

**教训**：新建一个「场景」时，最容易漏的不是逻辑而是**装配**。
判断标准很简单：在战局里跑得通的东西，在这个场景里有没有对应的创建代码。

### U-36：按 E 开测试箱却打开了仓库

**根因**：`SetVisible(true)` 里的「自动绑定仓库」条件写的是「当前不是仓库就切过去」，
于是它把刚被显式打开的测试箱顶掉了。

**做法**：条件改为「当前没有打开任何容器」。

**教训**：**默认值不能覆盖显式指定**。凡是「没指定就兜底」的逻辑，
判断条件必须是「确实没指定」，而不是「当前值不等于默认值」。

### U-37：装备后只显示武器名、弹药 `--/--`、按 R 无效

**根因**：战局里每帧都做两件事——`SyncEquippedWeapon` 把武器告诉控制器、`Tick` 推进射速与换弹；
安全屋两件都没做。而武器名之所以正常，是因为它由安全屋直接读装备槽显示，**与控制器无关**，
正好掩盖了真正的原因。

**做法**：补上同步与 Tick（并按武器射程设置准星最大距离）。

**教训**：当「一部分信息正常、另一部分不正常」时，先查**它们是不是来自同一个数据源**。
这次的正常那半是假象。

### U-38：开枪没有弹道

**根因**：弹道与枪声是两个只订阅开火事件的表现层组件，安全屋的装配漏了它们。

**做法**：与战局一致地创建并绑定事件总线。

**教训**：与 U-35、U-37 同源——**装配清单要对照战局抄一遍**，
而不是凭记忆挑几个看起来必要的。

### U-39：走到地图台阶/坡道与台缘衔接处会卡住

**反馈原话**：「玩家模型走到地图台阶上时会卡住」

**现象**：沿装卸平台的坡道向上走，在坡道高端与平台北缘的衔接处停住；
角色没有报错、没有掉出地图，但无法继续进入台面。

**定位过程**：用移动模拟直接推进，并在每一步后同步 PlayerMotor，
记录位置与高度。日志显示角色停在台缘前约 2 厘米处：
向下射线在该位置只命中了 `Dock_Ramp_West` 的板厚端面（`normal.y≈0.29`），
没有命中坡道顶面；地面吸附把它当成立面过滤掉后回落到 y=0，

坡道顶面止于台缘前方，角色走到缝上时只能探测到端面，
地面高度判断与碰撞扫掠同时失效。

- 场景生成器把坡道高端向台体内多伸入 **0.5 米**，让坡道顶面连续覆盖到台面下方；
- `PlayerMotor` 地面探测加入 **最大可上台阶高度 0.35 米**与可站立面过滤；
- `PhysicsMovementCollisionService` 忽略倾角 ≤45° 的可行走斜面，
  并在脚底受阻时把胶囊抬高 0.35 米复测，允许真正的低台阶跨越。

**验证**：新增 `PhysicsMovementCollisionTests` 3 项（低台阶可跨越 / 高墙不可翻越 /
可行走坡道不阻塞）；播放模式模拟从坡道低端走到平台，高度从 0 平滑升到 1.2，
越过台缘后不再卡住。

**提交**：随本次「移动修复」提交。

### U-43：主菜单点击一次后鼠标隐藏，继续/新游戏无法操作

**反馈原话**：「我在 unity 里运行游戏，在主菜单界面鼠标点击一次后就隐藏了；
点击继续游戏无反应，游戏卡住需要退出重进；
点击新游戏要再次点击，但鼠标已经隐藏了，按 esc 就退出来」

**现象**：主菜单第一次点击后光标消失；「继续游戏」点不中；
「新游戏」卡在二次确认；此时按 Esc 会直接退出游戏。

**定位过程**：
- `SafeHouseBootstrap.Update` 的 `uiOpen` 只包含背包、商人、安全屋地图，
  **没有包含主菜单**；只要这三个界面没开，就每帧执行 `SetCursorLock(true)`。
- `RaidFlowController.ShowMainMenu()` 虽然调用了一次 `UnlockCursor()`，
  但下一帧立刻被上述逻辑重新锁上。第一次点击让 Game 视图获得焦点，锁定随之生效。
- 主菜单按钮靠鼠标位置做悬停检测；光标锁定后指针停在中心，按钮不再被命中。
- 「新游戏」二次确认本身按设计工作，但确认期间光标已隐藏，
  第二次点击无法命中；Esc 又命中主菜单的“退出游戏”。
- `SceneBootstrap.Update` 存在同族问题：结算 `ShowResult()` 解锁后，
  下一帧仍会因为 `m_RaidActive == true` 重新锁定，所以结算按钮同样点不了。

**根因**：光标锁定条件只看“有没有打开背包类界面”，没有看**流程状态**。
主菜单与结算属于“需要鼠标”的状态，却被当成战局操作状态。

**修复**：
- 新增 `CursorLockPolicy`：只有没有界面且当前流程不需要鼠标时才锁光标；
- 安全屋与战局场景在 `MainMenu / Result` 状态主动释放光标；
- 新游戏二次确认期间，Esc 先取消确认而不是退出游戏；
- 菜单隐藏/显示时重置二次确认状态。

**验证**：
- 播放模式：主菜单状态 `lock=None, visible=True`；结算状态 `lock=None, visible=True`；
  二次确认在隐藏菜单后正确重置。
- 新增 `CursorLockPolicyTests` 3 项：安全屋锁、打开界面不锁、主菜单/结算不锁。

**提交**：随本次「光标修复」提交。

### U-44：从 GreyboxRaid 启动时继续游戏后场景静止

**反馈原话**：「我在 unity 开启游戏后，点击继续游戏和新游戏都会无反应导致游戏卡死」

**现象**：编辑器里打开 `GreyboxRaid.unity` 后按 Play，主菜单出现；

- 调用 `EnterSafeHouse()` 后：`state=SafeHouse`，但 `scene` 仍是 `GreyboxRaid`，
  `m_RaidActive` 仍为 false。
- `SceneBootstrap.Update` 因为 `m_RaidActive=false` 每帧直接进入

真正执行 `SceneManager.LoadScene(SafeHouseSceneName)`。这样无论从哪个场景进入主菜单，
「继续游戏」都会落到安全屋。

**验证**：从 `GreyboxRaid` 启动，调用继续后实测
`state=SafeHouse, scene=SafeHouse`，不再停在静止的战局场景。

## 七、M7 批次 1（2026-09-12）

> 本批次的首个交付：玩家角色从灰盒（圆柱 + 球 + 朝向块）换成 **Kenney 角色**，

### U-45：走路与跑步只有刚起步时有动画

**反馈原话**：「走路和跑步都是只有刚开始时有动画，之后是平移没动画」

**现象**：主角开始移动时播放一次动作，随后姿势冻结，位置仍被移动逻辑推进——表现为滑步。

**根因**：Kenney 的动画剪辑默认**没有开启 Loop Time**。循环类剪辑播放一次后停在最后一帧，
而表现层的位移来自 `PlayerMotor`，两者脱节。

**修复**：在模型导入设置里给循环类剪辑（`idle` / `walk` / `sprint` / `holding-right`）打开 Loop Time；
射击（`holding-right-shoot`）与倒地（`die`）保持单次。

**验证**：`idle loop=True`、`walk loop=True`、`sprint loop=True`、`holding-right-shoot loop=False`、`die loop=False`。

**提交**：`e5fbe85`

### U-46：站在平台上的敌人弹道贴地，打不到玩家

**反馈原话**：「平台上的敌人攻击时弹道在地面上，打不到玩家」

**现象**：敌人站在 1.2 米的装卸平台上开火，曳光贴着地面飞，射线打在平台侧面或地面上。

**根因**：AI 的逻辑坐标只有平面（XZ，必须能在无头服务端运行），
`AiWeaponController.FireOnce` 用 `new Vector3(position.X, MuzzleHeightMeters, position.Y)` 作为起点，
**缺少射手脚下的地面高度**；平台高度属于场景信息，逻辑层拿不到。

**修复**：给 `PhysicsHitProbe` 增加 `liftOriginToGround` 开关。
AI 侧传 `true`：射线起点先按 NavMesh 采样抬到射手脚下的地面高度，再叠加枪口高度；
玩家侧保持 `false`：玩家传入的已经是带高度的世界坐标，再抬一次会重复计算。

**验证**：354 项 EditMode 测试全绿；高低差效果待负责人实机确认。

**提交**：`e5fbe85`

### U-48：F1 视角锥从头顶/地面发出，与单位实际站位不符

### U-49：敌人开火看不见弹道，像在平台下面

**反馈原话**：「会攻击但是弹道看不见，可能在平台下」

敌人枪口世界高度 = 2.30（平台 1.25 + 枪口 1.05）✅
目标中心         = 2.10                        ✅

### U-50：敌人贴近时把玩家挡住，模型卡在一起（已知问题，暂不修）

玩家与 AI 的宿主对象统一标记 `Units` 层（TagManager 新登记，layer 6）；

## 八、M7 批次 2（2026-09-12）

> 本批反馈来自负责人对「下沉盆地 + 场景道具替换」的第一次实机验收。
> 四条里有三条是新地形与旧布局叠加后暴露出来的，一条是新增表现效果（透视孔）自身的判定缺陷。

### U-51：小兵穿模；靠近物品时瞬移到物品上方

**反馈原话**：「小兵会穿模」「小兵有时候会在靠近物品时瞬移到物品上方」

**根因（两个）**：

1. **落地采样选错层**。批次 2 为了覆盖 6 米下沉，把 `EnemyAgentView` 的落地采样半径从 4 米放大到 12 米；
   而 `NavMesh.SamplePosition` 返回的是"离采样点最近"的导航面，不是"脚下那一层"。
   装卸平台顶面（-4.8）与谷底（-6）只差 1.2 米，敌人在平台 12 米内任意位置都会被吸到平台上。
2. **AI 没有移动碰撞**。`AiMovement.Step` 在"没有路径"时（寻路失败 / 路径走完 / 目标很近）直接朝目标直线走，
   直线推进不做任何障碍判断，于是穿过墙体与集装箱。

**修复**：新增 `NavMeshGroundSampler`，改成"从下往上一层层试"（层高 -6 → +6、间隔 1.5 米、每层半径 1 米），
先命中的那层就是脚下这层；`EnemyAgentView` 与 AI 逻辑用的 `NavMeshGroundHeightProvider` 共用它。
同时给 `AiMovement` 注入 `IMovementCollisionWorld`（与玩家移动同一条接口、实现为 PhysX 胶囊扫掠），
半径取 0.55（大于胶囊 0.4，给持枪手臂留出余量）。

**验证**：实机读取五个敌人的落地高度，全部等于所在层的导航面高度（谷底 -5.92 / 平台 -4.75），
没有单位浮空或站在箱子上；让敌人正面冲向集装箱，位移被完全挡住（修复前会穿过去）。

**提交**：`645a682`

### U-54：没被遮挡的墙也透明，出现莫名其妙的圆洞

**反馈原话**：「这个是常态的吗？为什么没遮挡也透明？」

**根因**：透视孔的判定只有两条——像素落在圆内、且比角色胸口更靠近相机。
第二条只比较"离相机的远近"，不判断"这条视线是否真的打在角色身上"；
于是墙顶边缘、平台顶面、矮墙这类**只是擦过视线**的面也会被抠掉。

**修复**：保留圆孔外观，在写半径前加一道 CPU 闸门——从相机朝角色头 / 胸 / 膝三点打射线，

**验证**：空地 `IsOccluded=false` 半径 0；完全躲在集装箱后 `true` 半径 135 px（正常开孔）；
只被矮箱擦到脚下 `false` 半径 0（不再出现圆洞）。

### U-55：敌人走出一段距离后保持姿势平移

**反馈原话**：「敌人移动动画前一段正常，移动一段距离后就像图片一样保持该姿势平移」
（附截图：远处一名敌人在空地上保持固定姿势）。玩家侧正常，三个敌人变体里只有士兵这样。

（`Walk → Walk_Shoot → Run_Gun → Run`）取了 `Run_Gun`；
而循环名单里只有 `Idle / Walk / Run / Duck`，**兜底选中的 `Run_Gun` 没开 Loop Time**。
0.73 秒的剪辑播完就定格在最后一帧，位置仍被 AI 逻辑推着走——
巡逻速度 2 米/秒，也就是走出约 1.5 米后开始滑行。黄防化服与红头盔不受影响：
它们的 `Walk` 剪辑是循环的。

**修复**：

1. 循环名单补上会被当作走路/跑步播放的 `Walk_Shoot / Run_Gun / Run_Shoot`；
2. 新增 `CharacterAnimationLoopTool`，把"是否循环"从"名字表"搬到**使用点**：
   构建器把剪辑绑到 Idle / Walk / Run 这类"会长期停留"的状态时再确认一次，
   没开就地打开、重新导入并换上新对象（玩家构建器共用同一工具）；
3. 新增资产测试 `CharacterAnimationLoopTests`：循环状态必须绑循环剪辑，一次性状态不得循环。

**验证**：364 项 EditMode 测试全绿（新增 2 条）；三个敌人的控制器逐状态复查——
士兵 Walk = `Run_Gun` loop=true，其余两个 Walk = `Walk` loop=true，
`Idle_Shoot / Death / HitReact` 仍保持不循环；三个敌人预制体的 Animator 引用未断裂。

**排障记录**：[M7-P-17](排障记录/M7_问题记录与排障手册.md)（M7-P-05 的复发形式）

#### A-03：阵亡后仍能开枪 —— 布尔优先级写错

`PlayerCharacterView` 里写的是 `m_Animator == null || m_IsDead && !IsLocalPlayer(...)`。
C# 中 `&&` 的优先级高于 `||`，于是**本地玩家已阵亡**时整体条件为假、不会提前返回，
倒地动画被自己的枪声打断，看起来就是"尸体站起来开枪"。

修复分两处：

1. 视图的条件抽成静态方法 `PlayerCharacterView.ShouldPlayShootAnimation(...)` 并加断言测试
   ——这类缺陷不报错不崩溃，只有进游戏盯着看才发现，必须用可断言的表达式钉住；
2. 武器侧加闸门：`PlayerWeaponController.SetAlive(bool)`，阵亡后 `Tick` 与换弹请求全部拒绝
   （失败码 `combat_incapacitated`，与"没有武器"区分开，避免把排查方向带偏），
   阵亡瞬间还会**松开扳机**，否则复活/重开后第一帧会凭空打出一发。

#### A-04：冲刺阈值三份对不上 —— 收敛到"逻辑层的结论"

原实现里逻辑层用速度阈值 4.5 判定奔跑，动画控制器用 5.0，脚步用 3.5。
而且逻辑层的阈值本身**会随负重变化**（超载时按速度修正系数下调），
在表现层复制一个固定数字注定有一天对不上。

做法是把判定权完全交给模拟层：`PlayerMovementChanged.IsSprinting` 是唯一结论，
动画控制器新增 Bool 参数 `Sprinting`（不再比较速度），脚步节拍器改为
`Advance(speed, deltaTime, isSprinting)`。**全工程只剩一个奔跑判定点。**

#### A-01：敌人 Run 状态是死代码 —— 阈值落在 AI 速度区间之外

AI 的速度档位是巡逻 2 / 警戒 2.5 / 调查 3 / 交战 3.2 / 撤退 4.2，
而走路与跑步的切换阈值写的是 **4.5**——没有任何状态能达到它，"跑"这个动作一次都不会播。
改为 **3.6**：交战时仍然走路，只有重伤撤退（4.2）才真的跑起来。

#### A-05：开火播完固定回 Idle —— 追击中每枪闪一下站立

玩家与敌人的开火状态原本都只有一条"播完回 Idle"的出口。
现在改成按当时的移动状态回到走 / 跑 / 站立三选一（条件互斥，按顺序判定），
追击中连射不再出现"闪一下站立"的割裂感。

## 十一、复盘：这批问题说明了什么

### 1. 相机与手感的常量不能凭直觉给（U-01、U-03、U-04、U-05）

M1 的 6 个缺陷里有 4 个是同一类：**参数取了"看起来差不多"的估计值**——
俯角 45 度、相机距离 24 米、瞄准死区 0.01 米、相机前瞻。
它们的共同点是：代码逻辑完全正确，只是数字不对，而数字不对在单元测试里看不出来。

**改进方向**：这类常量要么按角色尺寸反算（例如相机距离 = 角色高度 × 若干倍），
要么明确标注为"待实测调参的初始值"。全部凭手感拍数，只会把调参成本推给验收环节。

### 2. 界面层是当前唯一没有自动化验证的一层（U-08、U-09）

这两个问题都出在"界面到命令"这一段：一个参数传错、一个功能压根没接。
规则层有 59 项测试，命令层有 12 项，而**界面层一项都没有**——
问题正好集中在这个空白处。

**已经采取的措施**：修复 U-08、U-09 时改用"反射调用界面真实方法 + 用格子世界坐标反算指针位置"
的方式验证，走的是与真实鼠标相同的路径。这个方法可以沉淀成界面层的自动化测试手段。

### 3. 当一条规则要靠分类区分行为时，分类必须精确到规则需要的程度（U-10）

`Armor` 这一个分类同时喂给两个槽位，本身就是设计漏洞，不是实现失误。
**判断标准**：如果两件物品在任何一条规则下应当有不同表现，它们在数据上就不能是同一个分类。

### 4. 截图复核是有价值的一环（U-11）

我无法操作真实鼠标，所以界面类问题只能靠负责人实测暴露。
U-11 说明：**即使我拿不到鼠标，负责人随手发来的一张截图也可能暴露层级、布局、配色问题**。
以后遇到"界面效果反馈"，除了看功能，也要主动扫一遍层级与遮挡。

### 5. 这些问题的分布（截至 M2）

| 类别 | 数量 | 占比 |
| --- | --- | --- |
| 参数取值不当 | 4 | 36% |
| 界面接线错误 | 2 | 18% |
| 坐标 / 层级换算 | 2 | 18% |
| 分类粒度不足 | 1 | 9% |
| 使用环境差异（非缺陷） | 2 | 18% |

**结论：约三分之一的问题来自"数值估计"，约三分之一来自"界面层缺乏验证"。**
这两件事都有明确的改进手段，不需要等到 M3 才发现。

## 十二、M7 批次 4（2026-09-13）界面布局反馈

> 这一批正在做界面美化；以下三条都是换皮后在实机截图中发现的布局问题。

### U-56：搜索物品时背包界面没有居中

**反馈原话**：「搜索物品时背包界面没有居中」
（附截图：搜刮武器架时，三栏内容整体偏左，右侧留白明显大于左侧）。

**根因**：`ComputeContentOrigin` 计算内容组宽度时，右栏**永远按最宽的 10 列仓库预留**。
实际搜刮的武器架只有 4 列，内容组却按 10 列宽度居中，实际只画到第 4 列——
右侧自然空出一大块。注意面板本身是 `CreateCenteredPanel` 居中的，偏的是面板里的三栏内容。

**修复**：

1. 新增 `m_RightContainerColumns`，记录当前右栏容器实际列数；
2. `ComputeContentOrigin` 按实际列数算 `rightWidth` 与栏间距；没有右栏时不预留右侧空间；
3. 容器宽度变化时走 `RebuildLayout` 重建整套布局（`OpenContainerView` 判断列数不同即重建），
   重建时保留右栏 ID 与标题，避免「战利品：武器架」在重建后变成别的标题；
4. 战局里关闭搜刮面板后，`Toggle` 再打开时若右栏已空，会按 0 列重建，内容恢复居中。

**验证**：SafeHouse 中注册一个 4×3 的「武器架」容器并打开背包，1280×720 实机截图中
面板左右内容留白约 152 / 156 像素；仓库（10 列）与无右栏两种状态也分别检查。
393 项 EditMode 测试全绿。

### U-57：左下角战斗 HUD 底板太长，有一半是空的

**反馈原话**：「左下角框太长了，有一半是空的」（附截图：底板右侧大片留白）。

**根因**：`CombatHud.PanelWidth` 固定 340，而最长的一行
「甲 3级 60 ｜ 盔 2级 40」加上左右内边距只需要约 200 像素。

## 十七、M7 批次 5 性能修正（2026-09-13）

批次 5 处理批次 3 审计中推迟的两条问题：A-02 动画播放速率缩放、A-06 敌人模型重复剪辑清理。

### A-02：移动速度与剪辑设计速度不一致导致的滑步

**现象**：角色的移动动画始终按剪辑原始速度播放（倍率恒为 1）。玩家步行 3.5、奔跑 6.5 m/s，
敌人有巡逻 2 → 撤退 4.2 五档速度，而一段剪辑的设计速度只有一个；速度偏离越多，脚底打滑越明显。
超载时玩家速度最低只有 0.4 倍，动画看起来像在冰面上迈碎步。

**方案（负责人拍板：每状态播放速率）**：

1. 新增 `LocomotionAnimationRate`（纯换算）与 `LocomotionAnimationBinding`（挂在模型预制体上的设计速度）。
   设计速度 = 2 × 步幅 ÷ 剪辑长度，步幅直接取 `FootstepCadence` 的公开常量
   （走路 0.95 米、奔跑 1.55 米），脚步与动画共用同一份数据；
   倍率限制在 0.5～2.0，站定（低于 0.2 m/s）与缺数据时返回 1（不缩放）。
2. 动画控制器新增 Float 参数 `LocomotionRate`（默认值 1），只绑定在 Walk / Sprint
   （敌人 Walk / Run）上；待机、开火、受击、倒地保持剪辑原始速度——没有采用全局 `Animator.speed`，
   避免一次性动作跟着加速。
3. `PlayerCharacterView` / `EnemyAgentView` 每帧把速度换算成倍率写进参数。
   玩家用模拟层的 `IsSprinting` 选档；敌人用构建器写入的 `RunSwitchSpeed` 选档，
   该值与控制器 Walk→Run 的过渡条件同源，表现层不再复制常量。
4. 开发者数据面板（F2）新增「速度 x.x m/s　动画倍率 x.xx×」一行：
   滑步时能当场判断是倍率没跟速度走，还是设计速度估错了。

**实测设计速度**（构建器读取剪辑长度自动计算，单位 m/s）：

| 角色 | 走路剪辑 / 设计速度 | 跑步剪辑 / 设计速度 | 典型倍率 |
| --- | --- | --- | --- |
| 玩家（Kenney Mini Characters） | walk 0.667s → 2.850 | sprint 0.500s → 6.200 | 步行 3.5 → 1.23×；奔跑 6.5 → 1.05× |
| 士兵（无 Walk，兜底 Run_Gun） | Run_Gun 0.733s → 2.591 | Run_Gun 0.733s → 4.227 | 交战 3.2 → 1.24×；撤退 4.2 → 0.99× |
| 防化服 / 绿头盔敌人 | Walk_Shoot 1.000s → 1.900 | Run_Gun 0.733s → 4.227 | 巡逻 2 → 1.05×；交战 3.2 → 1.68×；撤退 4.2 → 0.99× |

**验证**：新增 5 条换算规则测试 + 4 条资产接线测试（参数默认值、只绑移动状态、
设计速度与控制器实际绑定的剪辑一致、模型不再导入重复剪辑），407 项 EditMode 测试全绿。
滑步的最终观感由负责人在实机确认。

### A-06：`Character_Enemy.fbx` 每个动作存两份

**现象**：模型里 17 个动作各存两套命名（`Idle` 与 `CharacterArmature|Idle`），共 34 段剪辑；

### U-63：敌人待机时反复举枪、抖枪

**反馈原话**：「敌人会莫名其妙的举枪抖枪，正常吗？」

### U-66（批次 2 验收返工）：口径徽标浮在行框外、货架溢出面板

### U-67（批次 2 验收返工）：滚轮滚了十几圈只动一点点

**反馈原话**：「滚轮滑动很慢，我滚轮滑了十几圈就动一点点，分析原因。」

**原因（量纲错误）**：我按"Windows 一格滚轮 = 120（WHEEL_DELTA）"写了
`0.4 像素 / 原始单位`，以为一格滚 48 像素。但新版 Input System 在 Windows 上会按
`scrollWheelDeltaPerTick` 把滚轮**归一成"一格 = 1.0"**（UGUI 的 `InputSystemUIInputModule`
内部正是用这个常量做换算的）。于是实际一格只有 `1.0 × 0.4 = 0.4` 像素——
滚十几格才移动几像素，正好是反馈里的体感。

**修复**：不再假设量纲——**先把原始值归一成"格数"，再按"一格 = 一行（48 像素）"换算**：
绝对值大于 10 的按 120 制除以 120，其余视为已经是格数；键盘 ↑↓ 也走同一条格数通道
（0.25 格/帧 ≈ 12 像素）。

**验证**：反射调用 `UpdateShopScroll`，一格（归一制 `-1`）与一格（120 制 `-120`）
都使内容移动 48 像素，回滚两格回到顶部；
实机手感：一次滚动即可看到整行变化。

## 二十四、U-69：走下平台 / 坡道侧面被钉死（2026-09-13）

> 反馈原话：「当玩家走到斜坡中央，往两侧走，会卡在斜坡侧面。」

### 复现（真实帧循环，用 `PlayerInputCollector` 的脚本化输入驱动）

| 时刻 | 位置 | 脚底高度 |
| --- | --- | --- |
| 起点（西坡道中央） | (-4.00, -17.25) | -5.390（站在坡面上） |
| 按侧向 0.3 秒 | (-2.32, -17.25) | -5.390（坡道东边缘在 x=-2.25） |
| 再过 0.3 秒 | (-2.18, -17.25) | **-6.000**（越过边缘落到草地） |
| 之后 0.6 秒 | (-2.18, -17.25) | -6.000（**纹丝不动**） |

卡死后分别按北、西两个方向，位置完全不变；对该位置朝四个方向做与游戏同参数的胶囊扫掠，
**每个方向都返回 `d=0.000` 的命中**（`Dock_Ramp_West`）。

### 根因

1. 平台与坡道是**薄板 / 箱体**，侧面是 90° 竖直硬棱（坡道板厚 0.3 米，碰撞体 x∈[-5.75,-2.25]）；
2. 角色每帧水平移动约 0.05 米，**跨过边缘的下一帧，地面吸附就把脚底降到下层地面**（落差 0.3~1.2 米）；
3. 但胶囊半径 0.4 米——此时胶囊水平投影仍压在侧棱里（实测重叠 0.33 米），且胶囊下沿低于棱口上沿；
4. 移动判定是 `允许位移 = max(0, 命中距离 - 安全间隙)`。起点一旦与几何重叠，
   PhysX 在**每个方向**都返回 0 距离命中 → 允许位移恒为 0；"抬高 0.35 米跨台阶"的救援同样失败
   → 角色被永久钉死。

### 修复：移动碰撞新增「去穿透」

- `PhysicsMovementCollisionService` 在解析位移**之前**先做去穿透：用 `OverlapCapsuleNonAlloc` 找出重叠的阻挡几何，
  沿"胶囊上下球心 → 碰撞体最近点"的**水平分量**把角色逐步推出（每步 0.05 米，上限 1 米），
  再照常扫掠——朝墙走的结果仍是"被挡住"，不会像"忽略 0 距离命中"那样允许穿墙；
- 方向只取水平分量：地板 / 斜面的推出方向是竖直的，由比例阈值过滤，脚底高度仍归地面吸附管；
- 实现拆到 `PhysicsMovementCollisionService.Depenetration.cs`（partial，主文件保持 400 行以内）。

**修复过程中踩到的三个坑（都写进了代码注释与回归测试）：**

1. **必须在同一帧内完全脱离重叠**：只推 0.2 米、剩下 0.1 米重叠时，扫掠依旧被 0 距离命中挡住；
2. **推完要留余隙**：正好推到"贴合面"时，扫掠从相切位置出发仍会返回 0 距离命中（实测 resolved 停在 0.3 米不再前进），
   因此推出目标定为"半径 + 0.03 米"（比扫掠安全间隙 0.02 米略大）；
3. **球心压在棱面上时最近点计算会退化**（`ClosestPoint` 原样返回球心自身）：需要兜底方向
   （碰撞体包围盒中心 → 球心）——这正是**平台边缘**那条用例第一次没修好的原因。

### 验证

- 新增 3 条回归测试：`贴着高台侧面时能走出去而不是被钉死`、`球心正好压在棱面上时也能脱困`、
  `去穿透只把人推离棱边不会让人钻进高台`；**EditMode 431 项全绿**；
- 实机复验（同一条脚本化输入）：
  - 坡道中央往侧面走：(-4,-17.25) → (-1.80) → (-0.15) → (1.54)，**越过后继续走** ✅
  - 平台北缘走下：(2,-21) → (2,-19.96) → (2,-17.93) → (2,-14.85)，**不再停在 -19.00** ✅
  - 草地上朝坡道侧面挤：停在 x=-1.88（胶囊后沿与棱面留 0.03 米余隙），**被挡住但没有卡死、也没有穿进去** ✅

### 二次修复：第一版"推人"引入了瞬移（同日，U-69 回归）

**负责人反馈的新现象**：修完之后出现三处异常——玩家**走不上平台**、
从某处**水平向左走会瞬移进坡底**、从某处**竖直向下走会瞬移到另一处**；
AI 也会"直接从平台移到玩家位置"。

**定位（全区探针扫描）**：在装卸区 / 厂房一带按 3 米网格布 176 个探针，每个点朝四个方向
做与游戏同参数的移动解析，比对"请求位移"与"返回位移"：
**71 个异常点全部落在 `Terrain_Basin`（地形网格碰撞体）上，最大额外位移 1.00 米**
（例如 (-2,-29) 朝北走凭空多出 1 米、(-14,-29) 朝东走多出 (-0.78,-0.90)）。

**根因（两个叠加）**：

1. 第一版去穿透**真的修改角色位置**（每帧最多推 1 米）；
2. 触发面比预想宽得多：胶囊半径 0.4 米，即使站在地表上方，**胶囊边缘也会吃进起伏的地形**；
   而"离开方向"是用 `ClosestPoint` 求的——**非凸网格碰撞体（地形、山体这类大网格）的
   `ClosestPoint` 会把输入点原样返回**（实测），退化分支只能退到"包围盒中心 → 球心"，
   而地形的包围盒中心正好是**地图正中**，方向于是变成"沿地图半径向外辐射"。

**修法（不再依赖几何求方向、也不再改位置）**：把胶囊沿**本帧移动方向**试探性地挪一小步
（半径 + 0.05 米），重新做一次重叠查询：**原来压着、挪一步后不再压着**的几何才放松——
只忽略它的 0 距离命中，角色按自己的速度走出来；朝里走、贴着蹭照旧被挡住；
代码里**彻底不再修改位置**，任何"瞬移"从构造上都不可能发生。

**验证**：

- 全区扫描复测：**超出请求距离 0 处、横向偏移 0 处**（修复前 71 处、最大 1.00 米）；
- 回归测试新增 `贴着几何移动不会产生额外位移`（用网格碰撞体复刻地形），
  原先那条"推离棱边"的用例改成 `重叠时朝棱边挤不会钻进高台`；**EditMode 432 项全绿**；
- 实机：坡底一路走上平台（y 从 -6 升到 -4.8）✅；坡道中央往侧面走下后继续移动 ✅；
  平台北缘走下不再停在 -19.00 ✅；同场 AI 位置稳定、无位移 ✅。

## 二十五、M9 · P4 联机验收反馈（2026-09-14）

本节记录负责人对 **P4 大厅与房间（联机）** 的验收反馈：10 条缺陷 + 1 条需求。
这一轮的共同特征很鲜明——**同一条代码在单机下正常、在联机下失效**，
原因基本都是"单机由本地世界回答的问题，联机必须换成由服务器回答"。

### U-70 口令栏"打不进数字"

**现象**：联机界面口令框里输入数字，屏幕上什么都不显示（看起来像输入框坏了）。

**根因**：口令框是遮罩输入框，显示时用 `●`（U+25CF）替代每个字符；
而工程的字体资产是**静态预烘焙**的，字符采集器的白名单里**没有几何图形区（U+25A0–U+25FF）**，
`●` 被静默丢弃 → 构建里该字形缺失 → 整行显示为空白。

**修法**：① 采集器补上几何图形区（顺带覆盖 ■□◆◇▲▼）；② 重建中文字体资产；
③ 按负责人要求，口令与房间密码**改为明文显示**（遮罩在这个场景里只会让"到底输进去没有"变成靠猜）。

### U-71 图1：房间界面无法返回上一界面

**现象**：进入"创建 / 加入房间"界面后出不去——没有返回按钮，Esc 也没反应。

**根因**：该界面（未进房形态）**没有任何返回入口**；Esc 的处理写的是
"若已在房间 → 离开房间"，未进房分支是空的。

**修法**：新增「返回」按钮（按面板余量取 140 宽，右对齐不越界），
未进房时 Esc 走同一条"返回服务器列表"路径（断开连接并回到联机界面）。

### U-72 图2：鼠标点输入框后消失 + Esc 一次触发两个动作

**现象**：点房间名/口令输入框后鼠标不见了；按 Esc 光标回来了、但同时退回了上一界面。

**根因**：安全屋每帧按"界面是否打开"决定光标锁定，而它只认识背包 / 商人 / 图鉴，
**不认识新增的联机界面与房间界面** → 点输入框那一帧光标被重新锁上；
Esc 又被两处同时处理（房间界面 → 返回；安全屋 → 光标 / 暂停）。

**修法**：流程层暴露 `IsBlockingScreenVisible`（主菜单 / 结算 / 联机 / 房间），
安全屋把它并入 `uiOpen`：既不抢光标，也不抢 Esc。

### U-73 图1：点「返回主菜单」没反应

**根因**：点击执行"断开会话 → 显示主菜单"，而**断开连接会同步触发状态回调**，
回调看到"玩家处在联机流程中"就把服务器列表**又推了回来**。

**修法**：加显式的"玩家主动退出"标记，断开回调见到它就跳过重新显示联机界面。

### U-74 靠近箱子完全没有"按 E 搜索"提示

**根因**：`SceneBootstrap.IsPlayerAlive()` 在**联机客户端恒为 false**——
联机不建本地战斗世界（战斗全在服务器），而该函数的守卫是
`if (m_CombatWorld == null || m_PlayerCombatantId == 0) return false;`。
搜刮提示、医疗包使用、撤离读条全部以它为门，于是整片功能静默消失。

**修法**：联机分支改为读服务器下发的状态（`!m_LocalDowned`）。

### U-75 搜索后物品搬不进背包（已修：P4.5-a）

**根因**：P3-2 只接管了**拖拽移动**与**装备 / 卸下**；M2 的**双击快速转移**
走的是另一条意图 `InventoryQuickTransferIntent`，**仍在本地执行**——
本地网格先改、服务器的权威内容随后覆盖回去 → "怎么搬都不动"。旋转 / 整理同样漏网。

**修法（第一轮，2026-09-14）**：上行消息加 `Kind` 与 `Count` 字段，
客户端把**移动 / 快速转移 / 旋转 / 整理 / 拆分**五类意图全部接管为"只上行"，
服务器注册同一批 handler 并按 Kind 分派；回归 **592/592** 全绿。

**补充：第一轮之后"还是搬不动"——真正的现象根因在刷新环节（同日定位并修复）**

用 `-logLevel verbose` 重跑，拿到三段证据：

```
服务器：玩家 1 背包命令（种类 0）：112->1 结果=True（success）   ← 命令到了、也执行成功了
客户端：[联机] 容器内容已同步：17 个（服务器权威）                ← 数据确实收到了
界面  ：m_EventBus.Subscribe<InventoryChangedEvent>(_ => RefreshAll())  ← 只在本地事件到达时才重画
```

单机时命令在本地执行、handler 在本地事件总线发变更事件 → 界面重画；
联机时命令由**服务器**执行，事件发在服务器进程里，客户端收不到；
而客户端"应用服务器内容"的代码**只改网格、没补发事件** → 界面永不重画 →
**数据搬了、画面没搬**，玩家感受就是"搬不动"。

**修法**：把"应用服务器内容"抽成 `LootContainerSync.Apply(...)`，铺完网格后**补发一条本地
`InventoryChangedEvent`**（新增变更类型 `sync`，与 `place`/`equip` 区分，避免别人动箱子时响界面音）。
新增 4 条测试（物品入网格 / **应用完必须发事件** / 清空也要发 / 未知容器安静跳过）；回归 **596/596**。

**教训**：P3-1 当时用**读日志**的方式验收（"内容已同步 4→3 件"），日志只反映数据、不反映画面——
**有界面的功能，验收必须包含"看一眼画面"。** 详见 `Modules/10_联机.md` §25.5 / §25.6 与排障手册 P-40 / P-41。

**第三轮（收口，2026-09-14）**：把界面重画这条链路修好之后，"搬不动"仍在真实链路里复现。
于是换成**直接读客户端内存里的真实状态**（编辑器当客户端，反射读 `m_ContainerRegistry` 与 `m_Loadout`），
一次就看出关键矛盾：**同一个 1 号容器，注册表与装备指向两个不同的网格对象**。

于是又收口了两处根因（详见 §二十六与 `Modules/10_联机.md` §25.7）：

1. **场景切换的退订把新场景刚注册的网络处理器删干净**（旧场景 `OnDestroy` 发生在新场景注册之后）；
2. **容器内容消息不带格子坐标**，两端布局必然分叉——"有的能过去、有的不能"就是它；
3. **两端容量不一致时换掉了网格对象**，一个背包变成三份数据——"搬进去看不见、看得见搬不动"就是它。

### U-76 图3：地图上出现紫色椭圆体

**根因**：两层叠加——① 战局装配根在 `InitializeCombat()` 里无条件生成**灰盒试枪靶子**
（原点前方 9 米排四个胶囊），正常玩法里没有意义；
② 靶子用 `CreatePrimitive` 生成，拿到的是引擎内置默认材质，而工程是 URP →
**构建版里渲染成洋红**（missing shader）。

**修法**：删除战局里的靶子生成（试枪由安全屋靶场承担）；
新增 `PresentationFallback`，所有运行时兜底图元统一使用工程自己的 URP 材质。

### U-77 敌人贴脸不进交战、原地旋转

**根因**：① P4 开局先 `SpawnPlayerIntoWorld` 建载体 A，紧接着 `RestartRaid` 又建载体 B，
**A 没有销毁**（日志里"碰撞载体就位"对同一玩家打印两次即指纹）；
② `RestartRaid` 的循环漏了 `BindPlayerHitTarget` → 活着的载体没有命中标识 →
AI 视线判定恒为 false，敌人只能靠噪音点移动（表现为贴上来），并停在警惕；
同一条链路还会让**子弹打人不掉血**。

**修法**：绑定移进 `AddPlayerToCombat`（只有一处，漏不了）；`CreatePlayerBody` 幂等；
`RemovePlayerFromWorld` 显式销毁载体。

### U-78 图2：联机里队友模型浮空

**根因**：`RemotePlayerView` 里那份地面探测是**另写的一套**——取"射线上最高命中"，
缺了 `GroundProbe` 的三条规则（只认朝上的面 / 单次抬升上限 0.35 米 / 排除自身碰撞体），
站在集装箱、栅栏、坡体旁边时被抬到更高的面上。

**修法**：删除重复实现，远端视图统一调用 `GroundProbe.SampleGroundHeight`。

### U-79 自己模型移动时发糊、停下就清晰

**根因**：`PlayerMotor` 的视觉跟随写在移动事件回调里、固定 `Lerp(0.5)`——
**按事件次数而不是按时间**。单机事件与帧同拍看不出问题；
联机改成固定 60 Hz 步进后，事件数与帧数不再一一对应，
模型**永远追不上模拟位置** → 移动中落后 + 一顿一顿（肉眼即拖影/发糊），停下收敛即清晰。
队友走的是时间驱动的插值缓冲，所以"只有自己糊"。

**修法**：改成每渲染帧的指数跟随 `1 - exp(-22·dt)`；移动事件只记录模拟位置与朝向。

## 二十六、M9 · P4.5-a 收口：格子坐标、容器对象与容量归属（2026-09-14）

### U-80 "有的能过去有的不能，搬进背包的物品再也搬不动"

**反馈原话**："还是有问题，有的能过去有的不能，且移到背包的物品无法移动"。

**现象**：联机战局里搜刮箱子——物品**有时能搬进背包、有时不能**；已经搬进背包的物品
**怎么拖都不动**。而服务器日志显示每条命令都执行成功、客户端也回了一条"容器内容已同步"。

**定位过程**：换成**直接读客户端内存里的真实状态**（编辑器当客户端，反射读 `m_ContainerRegistry`
与 `m_Loadout`），一次就看见矛盾：

```text
注册表 #1（命令按它执行）      ：5×5，0 件
loadout.Backpack（界面按它画） ：6×6，3 件
```

同一个容器编号，两处指向**不同的网格对象**。

**根因（三处，各自都能单独造成"搬不动"）**：

| # | 根因 | 症状指纹 |
| --- | --- | --- |
| ① | 场景切换时旧场景 `OnDestroy` 把新场景刚注册的网络处理器**全量退订** | 进图那一次同步是好的，之后服务器发什么都没反应 |
| ② | 容器内容消息**不带格子坐标**，客户端一律自动摆放 | 两端布局分叉 → "有的能过去、有的不能" |
| ③ | 两端容量不一致时 `Apply` **换掉了网格对象** | 一个背包三份数据 → "搬进去看不见、看得见搬不动" |

**修复**：

1. 新增静态归属标记：注册时认领、退订前先确认自己是不是持有者（`s_ActiveChannelOwner`）；
2. `ContainerItemMessage` 增加 `CellX / CellY`：服务器打包取真实坐标，客户端**原位复原**
   （放不下才回退自动摆放，并且必须留警告）；
3. `LootContainerSync.Apply` **永不替换容器对象**：容量不一致只记一条警告，内容照旧铺进本地网格。
   容量归属规则写死为「**容量以本地装备为准、内容以服务器为准**」。

**验证**：

- 新增 2 条单元测试（容量不一致必须沿用同一对象 / 内容消息坐标往返），EditMode **600/600** 全绿；
- **真实链路往返实验**（编辑器当客户端 + 无头服务器，命令源坐标取自客户端自己的网格）：

| 步骤 | 客户端看到的结果 | 服务器自检 |
| --- | --- | --- |
| ① 箱子 100 → 背包 (3,3) | 背包出现该物品，坐标 **(3,3)** | 背包 1 件[ammo.9x19.standard@**3,3**] |
| ② 背包 (3,3) → 箱子 100 (0,0) | 背包清空，箱子收到物品 @**(0,0)** | 背包 0 件[] |
| 全程 | 注册表 #1 与 `loadout.Backpack` **始终是同一个对象** | 两条命令均 `结果=True` |

两次独立运行结论一致（第二次换了另一件物品）。

**已知边界（转入 P5）**：服务器目前按**自己配发的一套装备**建随身容器，因此玩家从局外带进图的
背包内容不会进入服务器那份（反过来会被服务器的空背包覆盖）。把"带进局的装备"同步到服务器
属于 **P5 的装备同步**，与共享仓库是同一块地基。在那之前，两端容量不一致会被记为一条警告，
不再影响搬动；详见 `Modules/10_联机.md` §25.7 / §25.9。

### 顺带修复：阵亡那一刻战局推进抛异常

排查上面这条时，服务器日志里还夹着一次阵亡就报一次的异常：

```text
InvalidOperationException: Collection was modified; enumeration operation may not execute.
```

**根因**：`TickRaid` 在 `foreach (var pair in m_PlayerBodies)` 循环体里调用 `TickPlayerRaid`，
而阵亡结算会走 `RemovePlayerFromWorld` → `m_PlayerBodies.Remove(...)`——
**边遍历边改集合**。它不只是抛一次异常：本帧剩下的战局推进会被整段跳过。

**修法**：先把要推进的玩家编号拷进 `m_RaidActorBuffer`，再按编号逐个推进
（集合的遍历与修改彻底分开）。这是 P4.5 里与容器那条同源的"**共享集合的所有权**"缺陷。

## 二十七、U-81：双击搬东西"时好时坏"、背包里的东西拖不动（2026-09-14）

**负责人反馈**（在上一节修完之后复测）："**有的能过去有的不能**，且搬到背包里的物品**无法再移动**。"

**定位（实测证据，不是推测）**：用"编辑器当客户端 + 无头服务器"读内存里的真实状态——
同一格、同一件东西，在两次内容完全相同的同步之间的**实例号不同**：

```text
[A 进图]                  箱子 100：medical.bandage.small 实例号 -1661239390
[B 重新同步同一份内容后]   箱子 100：medical.bandage.small 实例号 -1706226684
```

也就是说，每次同步客户端都会把容器内容**重建一遍**（`ClearGrid` + 逐件 `new`）。
而界面的"身份"判断建立在对象引用上：

- **双击识别**用 `ReferenceEquals(本次点击的物品, 上次点击的物品)`；
- **拖拽松手**用 `TryGetOrigin(m_DragItem)` 按对象找坐标。

于是只要一次同步落在两次点击之间（双击被判成两次单击）、或落在一次拖拽中间
（松手时一条命令都发不出去），这次操作就**静默失效**——同步由"任何人的容器操作 /
新客户端接入"驱动，玩家点得越快越容易撞上，所以体感正是"时好时坏"。

**修复**：

1. **同步时复用物品对象**：新增 `LootContainerItemReusePool`，按「定义 + 数量 + 摆放方向」
   复用本地旧实例，只有真正变化的物品才新建。**内容仍完全以服务器为准**
   （数量、坐标、朝向全部按服务器写入），复用只保证"同一件东西还是同一个对象"；
   键里不含坐标——搬动一格仍是同一件东西，玩家可以拖完一格接着拖。
2. **界面不再把对象当身份**：双击识别改为比较「容器 + 格子 + 物品定义」；
   拖拽松手时若对象已被换掉，按"同一个格子上的同一种物品"兜底取坐标。

**验证**：新增 4 条单元测试（同一内容两次同步对象不变 / 换格子对象不变 /
数量变化必须换新实例 / 池中实例只能取一次），EditMode **604/604** 全绿；
客户端与服务器两侧的对象与坐标一致性在真实链路上复测。

**为什么之前没被发现**：这条缺陷**不产生任何日志**——它只是"这一次比较不相等"。
自动化验收当时是直接下发背包命令（绕过了界面的双击与拖拽判定），所以命令全部成功、
看不出问题；必须从"界面自己的入口"走一遍才会暴露。教训记在排障手册 P-44。

## 二十八、U-82：房主移动一卡一卡 + 枪不跟准星（2026-09-14，已定位未修）

**负责人反馈**（双人实机验收）："房主的枪一直指向一个方向"；"房主移动时会一卡一卡、
时不时瞬移很短距离，而联机加进来的玩家移动时正常。先找到原因。"

**定位方式**：实机复现 + 取数（编辑器当客户端 + 无头服务器，脚本化输入；
服务器侧临时加了"上行输入被覆盖丢弃"的计数）。

**① 移动一卡一卡**

| 条件 | 服务器每秒被覆盖丢弃的输入 | 客户端回滚 |
| --- | --- | --- |
| 客户端约 60 FPS | **0 条/秒** | 0 次 |
| 同一客户端压到 20 FPS | **12~13 条/秒** | 每次快照一次，误差恒 **0.108 米** |
| 负责人那一局（房主 18 FPS） | 同机制 | 66 次（61 次正好 0.108 米） |
| 负责人那一局（加进来的玩家） | 无 | 1 次 |

0.108 米正好是**一步（1/60 秒）的位移**（冲刺 6.5 m/s ÷ 60；负重后 6.0 ÷ 60 = 0.100，
走路 3.5 ÷ 60 = 0.058），而对账容差是 **0.08** 米——比冲刺一步小、比走路一步大。

**根因**：客户端帧率低于 60 时一帧补齐多步、连发多条输入，而服务器的待处理输入只有一个槽位、
**新输入直接覆盖旧的**（实测每秒丢 12~13 条）→ 被丢的输入在客户端已经算过，
"已处理序号 ↔ 实际步数"错开一步 → 客户端位置稳定领先一步；容差又比"冲刺一步"小，
于是**每次快照都判超差**，而修正是 `SnapTo(...)` 硬瞬移 → 每 50 毫秒一次的短距离瞬移。
这也解释了"为什么只有房主"：低帧率那一端才会在一帧里补多步。

**② 枪一直指向一个方向**：枪的朝向来自 `m_WeaponController.AimDegrees`，
而每帧写它的 `CollectCombatInput()` 只在**单机分支**被调用；联机分支
`CollectMultiplayerCombatIntent()` 只上报扳机与换弹 → 角度从头到尾没更新过。
**每个联机客户端看自己都是这样**，不是房主专属（远端玩家目前不画枪，所以不容易发现）。

**修复与复测**：

1. 服务器输入由"单槽覆盖"改为**队列**（每个固定步消费一条，满了拒收新输入）；
2. 客户端**不再补回卡顿时间**（一帧最多 4 步），避免一次加载卡顿变成几十条连发输入；
3. 对账容差改为 `max(0.12, 1.5 × 速度 × 1/60)`，超差时**模拟立刻采用权威值、
   表现层平滑吸收**，只有 ≥0.6 米（传送 / 重开 / 卡墙）才硬瞬移；
4. 瞄准同步抽成 `SyncAimToWeapon()`，单机与联机分支都每帧调用。

**复测数据**（同一套"编辑器当客户端 + 无头服务器"脚本）：

- 60 FPS 冲刺：服务器**丢输入 0 条**、队列积压 4~5 条、客户端回滚 **1 次**（出生传送）；
- 20 FPS 冲刺（实测 fps=20.0）：**丢输入 0 条**、队列积压 4~5 条、回滚**无新增**；
- 修复前同样条件：每秒被覆盖 12~13 条、每次快照都回滚（误差恒 0.108 米）；
- 枪：瞄准方向由 `(0,1)` 改为 `(-1,0)`，武器朝向 90° → 180°（修复前恒为 90°）。

单元测试 609/609 全绿（新增"一帧内补多步不丢步"与 4 条容差规则用例）。
诊断（服务器丢输入 / 积压计数 + 客户端 `RollbackCount`）保留在代码里，默认静默。

## 三十一、U-88：持有枪械时点"继续游戏"，一进安全屋就倒地（2026-09-16，已修）

**负责人报告**（附游戏内截图）："当玩家持有枪械的情况下，在主菜单点击继续游戏，
一进游戏就会开火且玩家倒地，此时玩家还能移动。"

**现象拆解**（先看清"看到了什么"）：

- 角色不是"姿势怪"，而是在播 **`die` 片段**（Kenney 的 `die` 挂在动画控制器的 Die 状态上，
  唯一入口是 `PlayerCharacterView.OnDamageApplied` 的 `SetTrigger("Die")`）；
- HUD 显示 **28 / 30**，也就是**打了两发**；
- "倒地还能走"是因为移动由模拟层驱动，视图里的 `m_IsDead` 只拦动画更新、不拦移动。

合起来只有一种解释：**进安全屋的第一时间，玩家朝自己开了两枪，把自己打死了。**

**根本原因链（四环，缺一不可）**：

1. **单机没绑定"伤害规则用的射手编号"**（根因）：`PlayerWeaponController` 构造时
   `m_ShooterId = playerId`，默认 **0**；两处装配（`SafeHouseBootstrap.Combat`、
   `SceneBootstrap.Combat`）都没传它，而 `BindCombatant` 全仓只有**服务器**调用。
   偏偏 `CombatWorld` 的战斗单位编号**从 1 开始**，于是"拿 0 去查单位表"永远查不到射手。
2. **两条保护规则因此一起失效**：`ResolveDamage` 里"取到射手才判玩家免伤"，
   取不到就是**不拦**——"玩家之间免伤"（U-85 定的规则）与"不能打自己"同时失效。
3. **触发窗口极短但必中**：枪口在"武器视图尚未装备"时回退到
   `角色位置 + 1.2 米`（角色中轴上、**自己的胶囊体内部**），而 `IsEquipped` 是同一次调用的
   后半段才赋值 → **进场景第一帧**（以及刚换枪那一帧）枪口就在体内；
   `PhysicsHitProbe` 不做"排除射手"过滤，射线第一个命中的就是自己。
   点"继续游戏"用的鼠标左键在进场景后仍按着，于是这一帧真的开枪。
4. **数值放大**：AK 在内容热更后是 **77 伤害**（`Stats_weapon.rifle.ak74.asset`），
   两发 154 > 100 血 → 直接判死。

> 为什么以前没暴露：以前 AK 是 25 伤害（25×2=50，打不死），而且必须"有枪 + 点菜单的鼠标键还按着"
> 同时成立。这是"三个条件凑齐才出现"的缺陷，靠盯屏幕很难复现。

**顺带修掉的第二个症状**：同一根因让单机里所有伤害事件的 `AttackerId` 都是 0，
而玩家单位编号是 1 → `OnKillCounted` 的击杀归属永远对不上 → **单机击杀数一直不涨**。

**修复（四处，全部带注释说明"为什么"）**：

1. `PlayerWeaponController` 增加"规则编号"字段与 `BindCombatantForRules()`：
   **事件编号**继续用玩家编号（表现层按它过滤"是不是我的枪声"），
   **伤害规则**改用它（免伤判定、自伤拦截、伤害事件的攻击者）；
2. 安全屋与单机战局两个装配点在创建玩家战斗单位后调用它；
3. 枪口兜底改为"体前 0.6 米"（与举枪前移量一致），并让安全屋在装配结束时
   立刻同步一次武器表现——第一帧不再有"枪口在体内"的窗口；
4. 安全屋加一条守卫：**靶场里玩家受到伤害就报错并补血**（这是不可能事件，出现即说明别处有缺陷），
   避免同类症状再次以"角色躺在地上还能走"的形式悄悄出现。

**测试**：新增 `WeaponSelfDamageTests`（打中自己不产生伤害 / 绑定后玩家之间仍免伤 /
伤害事件带战斗单位编号）。EditMode **695 / 695**。

**遗留**：需要负责人按同样步骤实机复现一次确认（有枪 + 点继续游戏），
确认后再决定是否打补丁版本 `1.0.1` 并重新发布更新源。

## 三十八、U-95：弹道三处缺陷——命中自己 / 开局偏移 / 弹道与准星不共线（2026-09-17，已修）

**负责人反馈**：

1. "准星靠近玩家时点击左键射出的子弹好像会打到自己的模型，在玩家周围打到什么东西"；
2. "刚开始游戏射击时弹道和准星一点都对不上（偏得离谱），过一会就好了很多"；
3. "偶尔也会弹道和准星不在一条线"。

**排查结论（三条症状对应三个根因）**：

| # | 症状 | 根因 | 证据 |
| --- | --- | --- | --- |
| 1 | 打到自己 | `PhysicsHitProbe` 不过滤射手；方向是"地面枪口 → 瞄准点"，瞄准点落在角色附近/侧后方时射线从体外**穿过自己的身体**；自伤只在伤害层拦下，开火事件仍带着"命中自己"的终点 → 弹道画到自己身上，子弹也被自己挡住 | 探针裸 `Physics.Raycast`；Unity 实测：体外朝身体射 `outside=True`（1.60 米命中）、体内起步不命中；自伤过滤在 `ResolveDamage` 而非探针 |
| 2 | 开局偏得离谱 | 每帧顺序问题叠加：瞄准解算在"回写玩家最新位置"**之前**（开局第一帧用默认 (0,0)）、枪口在武器视图更新**之前**取（用上一帧位置）、开局准星在屏幕中心被死区吸住 | `SceneBootstrap.Tick` 与 `SceneBootstrap.CombatPresentation.UpdateCombat` 的调用顺序 |
| 3 | 弹道与准星不共线 | 弹道线**保留真实高度**（枪口 1.05 米），而准星在地面——45° 斜俯视下投影必然错开（打空/近处最明显）；`ResolveShotDirection` 的注释还停在"弹道画在地面上"的旧设计 | `TracerRenderer.ProjectToGround` 旧实现与 `Docs/Modules/03_Combat.md` 13.7 节漂移 |

**修法**：

- 探针新增 `TryRaycastIgnoringTarget`：把射手编号当作透明，命中它时继续往后投（与相机遮挡探测同一套
  `RaycastNonAlloc` + 最近有效命中的做法）；玩家与 AI 两条开火链路都传自己的战斗单位编号；
  旧的 `TryRaycast` 保持原语义（AI 视线等不受影响）。
- 顺序修正：`SceneBootstrap` / `SafeHouseBootstrap` 的"回写最新位置"提前到输入采集之前；
  `UpdateCombat` / `UpdateWeaponPresentation` 的"取枪口"挪到武器视图更新之后；
  瞄准同步（`SyncAimToWeapon`）统一提到 `UpdateCombat` 开头，让枪模型朝向、枪口与弹道方向
  基于同一帧数据（此前枪的朝向比准星慢一帧）。
- 弹道落点：`TracerRenderer.ProjectToGround` 改为"向下探测各自的地面/平台面"（探测遮罩排除单位层），
  起点与终点都贴到各自下方地面——既穿过准星，又保留平台上的可见性。

**验证**：EditMode **725 / 725**（新增 9 条：探针跳过自己 5 条、弹道落点 3 条、射手编号传递 1 条）；
编辑器实机冒烟通过。**待负责人实机复验**：准星贴脸/侧后方开枪不再打到自己、开局第一枪方向正常、
弹道穿过准星。

**联机差异说明**（排查时确认的事实，供后续参考）：命中判定在服务器（起点=玩家中线、方向=上报朝向），
客户端弹道是"本地枪口 → 服务器命中点"——"单机好、联机差"是结构上可能出现的，
本次修的三条对两种模式都成立；服务器起点与客户端枪口的前移差异（0.6 米）留作后续可选加固。

**补充修复（2026-09-17 第二轮，负责人编辑器实测后反馈）**：

| 现象 | 根因 | 修法 |
