## 1. 三层更新模型

一个 Unity 程序里，"能被更新的东西"分三类，更新能力与执行位置完全不同——
把它们混在一起讲是热更话题最常见的困惑来源，所以本项目的三章结构从一开始就分开：

| 层 | 技术 | 更新内容 | 执行位置 | 玩家感知 |
| --- | --- | --- | --- | --- |
| 本体 | 自研启动器（ADR-007） | `RaidDemo.exe`、`UnityPlayer.dll`、AOT 程序集、启动层、非热更资源（场景等） | **游戏进程外**（Windows 下运行中的文件被占用，只能由没在运行的程序替换） | 打开启动器 → 检查更新 → 下载 → 启动游戏 |
| 资源 | Addressables 2.x（ADR-002） | 贴图、模型、音频、预制体、**数据表 ScriptableObject** | 游戏内运行期 | 进游戏前的"检查更新"界面（进度条） |
| 代码 | HybridCLR（ADR-003） | 业务逻辑程序集（`RaidDemo.*`） | 游戏内运行期；**仅 Windows，无平台政策障碍** | 无感知，逻辑直接变新 |

**为什么必须是这个分层**（面试与文档都要能讲清）：

1. IL2CPP 发行构建里，AOT 编译死的那部分**没有任何自我替换通道**——这是平台事实，不是设计选择，
   因此"最外层更新"只能落在游戏进程之外，即启动器。
2. 资源和代码可以在运行期被加载，是因为 Unity 的资源系统与 HybridCLR 的元数据补充机制
   本来就把"数据"和"代码"当作可延迟加载的输入，而不是编译产物的一部分。
3. 三层共用**同一份清单协议**（第 3 章）：版本比对、哈希校验、下载、失败回退是同一套逻辑，
   只是文件类型与执行位置不同。这是本方案体量可控的关键。

## 2. 版本标识与语义

三层各有自己的版本，但对外只暴露一个组合标识 `buildId`——联机握手与问题排查都用它。

| 标识 | 形式 | 生成方式 | 用途 |
| --- | --- | --- | --- |
| `bodyVersion` | 语义化 `MAJOR.MINOR.PATCH`（例 `0.10.0`） | 发布脚本写入，与 `ProjectSettings` 的 `bundleVersion` 一致 | 启动器比对本体的版本标签、联机握手 |
| `contentHash` | catalog 的 SHA-256 前 12 位（例 `3f9a12c4d0b1`） | Addressables 构建后对 `catalog_*.json` 计算 | 资源一致性判定（内容寻址，天然幂等） |
| `codeVersion` | 构建序号（例 `0.10.0.7`） | 发布脚本按当日构建递增 | 人工可读的代码层版本号 |
| `codeHash` | 热更程序集集合的合并哈希前 12 位 | 对全部热更 DLL 的 SHA-256 排序后再哈希 | 代码一致性判定、防"文件对不上版本号" |
| **`buildId`** | `bodyVersion+contentHash8+codeHash8`（例 `0.10.0+3f9a12c4+d41b77ee`） | 前三者拼装 | **联机握手、日志、问题反馈的统一标识** |

**版本号写入位置**（发布脚本负责，避免手工维护）：

- 本体：`ProjectSettings/ProjectSettings.asset` 的 `bundleVersion` → 构建产物里的 `version.json`；
- 资源 / 代码：只存在于清单与运行时缓存中，不写回工程文件。

**联机握手（对接 M9）**：客户端加入房间时上报 `buildId`；服务器（专用服务器构建）在构建时把
自身 `buildId` 写为常量，不一致则拒绝并提示"客户端版本与服务器不一致，请更新到 x.y.z"。
服务器只做**版本锚点**，自身不做热更（更新 = 重新部署，见第 10 章）。

## 3. 更新清单协议（manifest.json v1）

清单是三层更新的**唯一契约**。它足够简单，任何一个静态文件服务器都能托管；
也足够完整，客户端只凭它就能判断"我缺哪些文件、要下载多少、下载完对不对"。

### 3.1 更新源目录布局

```text
<更新源根目录>/                      ← 本地 HTTP 或云主机的静态目录，内容完全一致
├─ manifest.json                     ← 当前发布清单（完整、含三层）；"发布"= 最后覆盖它
└─ versions/
   ├─ 0.10.0/
   │  ├─ manifest.json               ← 该版本的清单副本（回滚 = 把它复制回根目录）
   │  ├─ body/…                      ← 本体文件（保持构建产物的相对目录结构）
   │  ├─ content/…                   ← Addressables 的 catalog 与 bundle
   │  └─ code/…                      ← 热更程序集与 AOT 补充元数据
   └─ 0.10.1/…
```

**发布原子性**：新版本先整目录上传，**最后**才覆盖根 `manifest.json`。
在覆盖之前，任何客户端拉到的都是旧清单，不会出现"清单指向半份文件"的中间状态。

### 3.2 字段定义

```jsonc
{
  "schemaVersion": 1,                  // 协议版本；客户端遇到不认识的值要拒绝更新并提示升级启动器
  "generatedAt": "2026-09-15T12:30:00+08:00",
  "body": {                            // 本体层：启动器消费
    "version": "0.10.0",
    "files": [
      { "path": "RaidDemo.exe",  "size": 644608, "sha256": "…64位十六进制…" },
      { "path": "RaidDemo_Data/…", "size": 1234567, "sha256": "…" }
    ]
  },
  "content": {                         // 资源层：游戏内 Addressables 消费者
    "version": "0.10.0.3",
    "catalog": { "path": "catalog_0.10.0.3.json", "size": 15234, "sha256": "…" },
    "files": [ { "path": "…bundle", "size": 0, "sha256": "…" } ]
  },
  "code": {                            // 代码层：游戏内 HybridCLR 消费者
    "version": "0.10.0.7",
    "assemblies": [ { "path": "RaidDemo.Gameplay.dll", "size": 0, "sha256": "…" } ],
    "metadata":   [ { "path": "RaidDemo.AotMetadata.dll", "size": 0, "sha256": "…" } ]
  }
}
```

规则：

1. `path` 一律是**相对路径 + 正斜杠**，客户端与服务端都用 `Path.Combine` 拼接，
   禁止出现绝对路径与盘符（`PathRulesTests` 的同一条纪律，工具侧同样遵守）。
2. `size` 用于下载前预估与快速失败；`sha256` 是**唯一**的完整性判据，下载后必须逐文件校验。
3. 清单里**不写服务器地址**：地址由启动器的"更新源档案"提供（本机 / 云主机 / 自定义），
   换源不需要重新出包——这是 ADR-007 "更新源可切换"的实现方式。
4. 版本目录保留最近 **2** 个版本；面板删除更早的版本目录，根清单不受影响。
5. **空层用"版本号为空字符串"表示**：Unity 的 `JsonUtility` 会把值为 `null` 的层写成
   "字段齐全但内容为空"的对象（实测 `"content": { "version": "", "catalog": {…}, "files": [] }`），
   而不是 `null`。因此**消费方一律用 `version` 是否为空判断该层是否存在**，
   不要依赖 `null` 判断——这条写进协议，避免启动器与游戏两端理解不一致。

### 3.3 客户端比对与更新流程

```text
拉取 <源>/manifest.json
   │
   ├─ 读取本地清单快照（<安装根>/.raiddemo/manifest.json）
   ├─ 逐文件比对：新增 / 哈希变化 / 已从清单移除
   │     └─ 无差异 → 直接启动游戏
   ├─ 有差异 → 下载到 <.staging/版本号/>（保留 .part 支持断点续传）
   ├─ 逐文件校验 sha256：任何一条不过 → 放弃本次更新，保留旧版本
   ├─ 备份被覆盖文件到 <.backup/时间戳/> → 原子替换 → 删除移除项
   ├─ 写回本地清单快照 → 清理 staging
   └─ 任一步失败 → 从备份恢复 → 用旧版本启动（游戏必须始终可启动）
```

**断点续传**：以 `Range: bytes=<已有长度>-` 续传；服务器返回 `200`（不支持 Range）时
退化为整文件重下并记录一条日志。`.part` 文件在校验通过前不参与比对，不会被误认为已完成。

**失败回退的验收含义**：拔网线 / 关更新源 / 中途杀进程，三种情况下都必须能启动**旧版本**。
这条会在批次 2 的验收里逐条实测。

## 4. 更新源（本地 + 云）

### 4.1 形态

`Tools/UpdateSource/`：**独立 .NET 程序**（不依赖 Unity 运行时），承担两件事：

1. 静态托管更新源目录（`manifest.json` + `versions/`），支持 Range 请求；
2. 提供**Web 可视化面板**：查看 / 上传 / 发布 / 回滚版本。

面板功能清单：

| 区域 | 内容 |
| --- | --- |
| 版本总览 | 当前发布的三层版本、`buildId`、发布时间、文件数与总大小 |
| 版本历史 | `versions/` 下的全部版本；一键**回滚**（把旧清单复制回根目录） |
| 上传发布 | 浏览器上传版本包（zip）→ 服务端解包到 `versions/<版本号>/` → 自动校验哈希与清单一致性 → 提示"可发布" |
| 校验工具 | 对任意版本重算 SHA-256 并比对清单（防止手工改文件） |
| 访问日志 | 最近 N 条下载请求（IP 去敏、文件、状态码、耗时） |

写操作（上传 / 发布 / 回滚 / 删除）需要口令；**只读与下载不需要**，便于他人复现链路。

### 4.2 部署

- **本地**（开发与演示）：`Tools/UpdateSource` 直接运行，监听 `127.0.0.1:8090`，更新源目录指向本机构建输出；
- **云主机**：与专用服务器**同机不同进程**（游戏服务器占用 UDP 7777 与 TCP 8080 状态页，
  更新源用 TCP 8090），部署脚本沿用 `deploy/` 目录的写法（`deploy/updatesource.sh`），
  启动方式为后台进程 + 日志文件，随机器重启自启。

> 端口与地址的真实值不入库：开发机上的接入信息记录在 `Docs/Local/云主机接入.local.md`；
> 仓库里的文档一律使用 `<云主机IP>` 占位（与 `deploy/README.md` 同一纪律）。

### 4.3 落地产物与云部署（批次 3 完成）

| 产物 | 位置 | 说明 |
| --- | --- | --- |
| 服务端工程 | `Tools/UpdateSource/` | .NET 8 + `HttpListener`（无 ASP.NET 依赖），Windows / Linux 同一份代码 |
| 使用说明 | `Tools/UpdateSource/README.md` | 构建、发布、接口清单、目录布局、命令行小坑 |
| 验收脚本 | `Tools/UpdateSource/verify/p3_updatesource_check.ps1` | 沙盒起真实服务端，17 条判据 |
| 云上管理脚本 | `deploy/updatesource.sh` | `start` / `stop` / `restart` / `status` / `logs`（与 `server.sh` 同一风格） |

**云主机部署形态**（与专用服务器同机不同进程，互不干扰）：

```text
/root/raid-demo/                  ← 专用服务器（UDP 7777 + TCP 8080 状态页）
/root/raid-demo-updatesource/     ← 更新源（TCP 8090）
    RaidDemo.UpdateSource         ← linux-x64 自包含单文件（不依赖机器上的 .NET 运行时）
    updatesource.sh
    update-source/                ← manifest.json + versions/<版本>/…
```

**部署时实测到的三个坑**（都写进了 README 与本文档，避免下次重复踩）：

1. **路径含空格会截断参数**：`Start-Process -ArgumentList` 的数组是空格拼接的，
   `D:\unity game\…` 会被切成两段，服务端于是把更新源建到了 `D:\unity`。
   验收脚本现在带防呆断言（比对启动日志里的根目录），这类"工具跑错地方"的问题必须在脚本层挡住。
2. **服务端必须解码 URL 路径**：构建产物里有 `RaidDemo_Data/Resources/unity default resources`
   这类含空格的文件名，客户端转义成 `%20`，服务端不解码就会 404——
   现象是"更新到一半失败"，而失败文件看着完全正常。
3. **`HttpListener` 对没有 `Content-Length` 的 POST 直接返回 411**（在业务代码之前），
   用 curl 调写接口要带一个空体（`-d ''`）；浏览器与 PowerShell 会自动带上，不受影响。

## 5. 启动器（Tools/Launcher）

### 5.1 形态与界面

`Tools/Launcher/`：**独立 .NET WinForms 程序**（ADR-007 指定形态：不依赖 Unity 运行时、
不进游戏程序集、先于游戏存在）。界面元素：

- 更新源下拉框：`本机` / `云主机` / `自定义`（前两项由 `launcher.config.json` 提供地址，可持久化）；
- 版本信息区：本地 `buildId`、远端 `buildId`、差异文件数与总体积；
- 主按钮：`检查更新` → `更新并启动`（无差异时直接显示 `启动游戏`）；
- 进度区：阶段文字（准备 / 下载 / 校验 / 替换）+ 单文件与总进度双进度条 + 速度；
- 详情折叠：当前下载文件、失败原因、重试按钮；日志写入 `<安装根>/.raiddemo/launcher.log`（滚动保留）。

### 5.2 与游戏的关系

启动器启动游戏时传入运行参数，让"更新源地址"与"默认游戏服务器地址"来自同一份配置：

```text
RaidDemo.exe -updatesource <更新源地址> -connect <默认服务器地址> -buildid <本地 buildId>
```

- `-updatesource`：游戏内资源 / 代码热更使用（省去在游戏里再配一次地址）；
- `-connect`：主菜单"联机"的默认地址预填（本地档案 = `127.0.0.1`，云档案 = 公网地址）；
- 游戏侧对这三个参数都按"可选"处理：直接双击 `RaidDemo.exe` 也要能正常单机游玩。

### 5.3 边界

**启动器自身不做热更**（已拍板）：它自己的更新 = 重新下载启动器压缩包。
理由是收益低（启动器代码量小、改动频率低）而成本高（需要引导程序或双进程替换），
这一点会写进 README 的边界说明，避免被当成遗漏。

### 5.4 落地产物与验收（批次 2 完成）

| 产物 | 位置 | 说明 |
| --- | --- | --- |
| 启动器工程 | `Tools/Launcher/` | .NET 8 WinForms；**通过链接文件与 Unity 共用同一份协议实现**（清单模型 / 差异比对 / 哈希工具），协议不会两端各写一份 |
| 使用说明 | `Tools/Launcher/README.md` | 构建、发布（自包含单文件）、配置字段、两种用法、边界 |
| 验收脚本 | `Tools/Launcher/verify/p2_launcher_check.ps1` | 13 条判据：首次安装 / 增量更新 / 源切换 / 失败回退 |

两个实现细节值得记下来（都是实测踩到的）：

1. **`System.Text.Json` 默认不处理 public 字段**——清单模型为兼容 Unity 的 `JsonUtility` 用的是字段，
   少了 `IncludeFields = true` 会"解析成功但得到空清单"，属于最难看出的静默错误；
2. **重定向输出时 `Console.OutputEncoding` 不生效**——实测写出的仍是系统 GBK，
   必须显式替换 `Console.Out`（`StreamWriter` + UTF-8）才能让验收脚本按文案断言，
   否则脚本会"因为乱码"而误报失败。

## 6. 游戏内热更

### 6.1 Addressables 资源热更

**热更范围（已拍板：以"数据表 + 选定美术"为主，不做整包迁移；下表的修正是批次 0 的验证结果，
原因见 6.2 的社区版限制）**：

| 进热更 | 说明 |
| --- | --- |
| 数据表 ScriptableObject：物品定义（18 个）、`ItemCatalog`、`AudioCatalog`、`PresentationCatalog` | 共 21 个 `.asset`；**它们挂的类在热更程序集里，因此必须走 AB 打包，否则 `scripting missing`** |
| 两张场景：`GreyboxRaid`（战局）、`SafeHouse`（安全屋） | 场景上的 `SceneBootstrap` / `SafeHouseBootstrap` 等脚本属于热更程序集（同理） |
| 15 个角色预制体（12 个可选角色 + 3 个敌人） | 挂着 `LocomotionAnimationBinding`（热更程序集） |
| UI 主题、图标、图集 | 按分组发布，可单独更新 |
| 武器 / 道具美术、音效、特效 | 按分组发布，可单独更新；场景引用到的环境资源会作为依赖自动进包 |
| 启动层与 AOT 程序集 | **不进热更**（本体层，只能由启动器更新） |
| 引擎包与第三方插件（Netcode / URP / TMP / Addressables 等） | **不进热更**（AOT） |

**分组策略：按"更新频率"分组，而不是按资源类型**（ADR-002 的教训条目）：
`group-data`（高频，数值随时可调）、`group-ui`、`group-art`、`group-audio`。
分组过细会让 catalog 膨胀，过粗会让"改一个数值"变成"重下全部美术"，四组是当前内容的平衡点。

**运行时流程**（Bootstrap 之后、主菜单之前）：

```text
启动 → Addressables 初始化 → 拉远端 catalog
        ├─ 失败/离线 → 用本地缓存 catalog 进入（界面提示"使用本地版本"）
        ├─ 无差异 → 直接进入
        └─ 有差异 → 下载 → 校验 → 更新本地 catalog → 进入
                    （失败：回退本地 catalog，绝不阻断进入游戏）
```

### 6.2 HybridCLR 代码热更

> 本节是**批次 0 验证后的定稿版本**：先按"启动层继续引用业务程序集、靠 DHE 兜底"规划，
> 验证后发现该前提不成立（社区版没有 DHE，AOT 不能引用热更程序集），因此改为
> **启动层削薄 + 业务程序集整体搬迁**。决策过程记录在 ADR-008，依据见 6.3。

**硬约束**：官方文档原文——"**请不要在 AOT 程序集中引用热更新程序集，这会导致打包出错**"。
能让 AOT 与热更程序集双向互调的"差分混合执行（DHE）"**只包含在付费旗舰版**里，本项目使用社区版，
因此程序集边界必须严格单向：**热更程序集可以引用 AOT 程序集，反过来绝对不行**。

**程序集边界（本阶段做的是"搬迁 + 削薄"，不是打标记）**：

| 层 | 程序集 | 热更性 | 说明 |
| --- | --- | --- | --- |
| 启动层 | 新建 `RaidDemo.Host`（极薄加载器） | **AOT，不可热更** | 只做四件事：解析启动参数、加载热更 DLL、反射调用入口、加载失败时显示兜底错误界面。发布后不再修改 |
| 业务层 | `RaidDemo.Bootstrap`（含 `SceneBootstrap` / `SafeHouseBootstrap` / `RaidFlowController` 等组合根）、`Kernel.*`、`Shared`、`Data*`、`Simulation`、`Input`、`Presentation`、`Inventory`、`Combat`、`AI`、`Raid`、`Meta`、`UI`、`Diagnostics` | **热更程序集** | 全部业务代码，构建为 DLL 走代码层清单 |
| 编辑器层 | `RaidDemo.Bootstrap.Editor` | 不参与运行时 | 保持现状 |
| 第三方 | Netcode / URP / TMP / Addressables 等 | AOT，随本体 | 不得被业务程序集以外的方式牵动 |

**为什么可以整体搬迁（批次 0 实查，不是推测）**：全项目 55 个 MonoBehaviour / ScriptableObject 类型中，
真正"挂在随包资产上"的只有 **13 个 MonoBehaviour 类型**（分布在 `Bootstrap` / `Presentation` / `UI` / `Input`
四个程序集）；其余 42 个类型全部由运行期 `AddComponent` / `new` 创建——HybridCLR 对运行期创建的热更脚本
是"任何时候都完美支持"。因此只要把挂着这 13 个类型的资产交给 Addressables 打包，
业务程序集就能整体进入热更层，不需要逐个改造成薄壳。

**脚本挂在资源上的三条纪律**（官方文档明确，违反必炸）：

1. 挂热更脚本的资产**必须走 AssetBundle / Addressables 打包**，不能随主包（`Resources` 等）；
   对照本项目，这意味着 **2 张场景 + 15 个角色预制体 + 21 个数据表 `.asset`** 必须进 Addressables（见 6.1）——
   这也解释了为什么"数据表进热更"和"场景进 Addressables"不是可选优化，而是代码热更的前置条件；
2. 热更程序集要登记进 `HybridCLRSettings` 的 `HotUpdateAssemblyDefinitions`（打包时自动写入 assembly 列表文件）；
3. **上线后热更程序集名不可更改**（assembly 列表在包内不可变），改名 = 只能发新本体。

**构建与加载**：构建期产出 `RaidDemo.*.dll`（业务）+ AOT 补充元数据 DLL（`metadata`）；
运行期由 `RaidDemo.Host` 用 `Assembly.Load` 加载清单里的 DLL，再反射调用入口。
缺失的补充元数据会在运行时报"泛型方法找不到"类异常，因此**补充元数据的清单要与实际泛型使用同步更新**，
并在批次 5 验收里覆盖。

**结论与推进方式**：

1. **资源热更没有兼容性风险**——Addressables 2.10.3 可直接用于 6000.6，按 ADR-002 固定该版本，批次 4 直接安装。
2. **代码热更是 M10 唯一的高风险项**——HybridCLR 8.14.1 的官方映射里没有 6000.6，正属于官方所说的"尚未合并最新 il2cpp"情形。
   它不是"不能用"，而是**"必须先用探针验证"**；把这件事在批次 0 讲清楚，而不是留到批次 5 才发现，是本节的主要目的。
3. **批次 5 的第一步固定为"可装性探针"**（在项目克隆上做，不污染主线），记录四个信号：
   ① `HybridCLR/Installer` 是否匹配到 `il2cpp_plus` 分支并成功落地本地 il2cpp；
   ② `HybridCLRData/LocalIl2CppData-*` 是否生成；
   ③ Windows IL2CPP 构建是否通过；
   ④ 热更 DLL 能否加载、AOT 泛型补充元数据是否正常。
   探针结论无论成败都写回本节。
4. **探针失败时的三条路（按优先级）**：
   - **A（官方推荐路径）**：临时安装 Unity 6000.5.x，在克隆上完成 HybridCLR 安装后再切回 6000.6 验证——官方文档明确给出该做法；
   - **B（保底交付）**：发行后端退回 Mono，代码热更改用 `Assembly.Load` 演示——工程上成立，但失去"IL2CPP + 解释器"这一层讲解价值；
   - **C（最低线）**：只交付启动器 + 资源热更（ADR-007 已写明优先级：资源热更与启动器优先于代码热更）。
5. **与本体 / 资源热更解耦**：无论代码热更最终走哪条路，批次 1~4 与启动器交付都不受影响。
   IL2CPP 发行构建本身只依赖 Windows IL2CPP 模块，**与 HybridCLR 无关**——两件事不要在排期上绑死。
6. **架构修正（因"社区版没有 DHE"触发，已落成 ADR-008）**：
   ① 新建极薄 AOT 加载器 `RaidDemo.Host` + 反射入口，业务程序集整体进热更层；
   ② 带热更脚本的 38 个资产（2 场景 + 15 角色预制体 + 21 数据表）必须进 Addressables，
      否则 `scripting missing`；连带收益是地图与角色资源也具备热更能力；
   ③ 批次 4 的 Addressables 分组因此要在"数据表 + 选定美术"之外，额外纳入**场景组与角色组**——
      这不是范围膨胀，而是代码热更的前置条件（详见 6.1 与 6.2）。

## 7. 构建与发布流水线

一条流水线，六步，全部脚本化（批次 1 落地，菜单与命令行两种入口等价）：

```text
1. 出包          Unity 菜单「RaidDemo/M10/构建客户端（Windows IL2CPP）」
                 → Builds/Client/<bodyVersion>/
2. 资源构建      菜单「RaidDemo/M10/构建资源（Addressables）」
                 → 产出 catalog + bundle（进 content 层）
3. 代码构建      菜单「RaidDemo/M10/构建热更程序集」
                 → 产出业务 DLL + AOT 元数据（进 code 层）

                 → 逐文件 SHA-256 → manifest.json（含三层）
5. 上传          启动器面板或脚本上传到更新源 `versions/<版本号>/`
6. 发布          校验通过后在面板点「发布」（覆盖根 manifest.json）
```

发布脚本的产物全部落在 `Builds/Update/<版本号>/`（`Builds/` 已被 `.gitignore` 忽略，
构建产物不入库；入库的是脚本本身）。

## 10. 边界与刻意不做

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 二进制差分（bsdiff 等） | 不做 | Unity 产物按文件哈希比对已有足够增量，收益与复杂度不成正比（ADR-007） |
| HTTPS / 域名 / CDN | 不做 | 演示环境用明文 HTTP + SHA-256 校验；正式发行才需要证书体系 |
| 启动器自更新 | 不做 | 收益低、成本高（需要引导程序），写入边界说明 |
| 服务器端代码热更 | 不做 | 专用服务器作为**版本锚点**，更新 = 重新部署（`deploy/` 流程复用） |
| 全量美术资产迁移进 Addressables | 不做（但带热更脚本的资源是**强制**的） | 必须进 Addressables 的只有 38 个"挂着热更脚本"的资产（2 场景 + 15 角色预制体 + 21 数据表）；其余美术按分组逐步纳入，不做一次性搬迁 |
| 多平台热更 | 不做 | 项目仅面向 Windows（决策 D-15） |

## 13. 批次 6：版本握手与全链路演练（已完成，2026-09-15）

### 13.1 版本握手（已完成）

**目标**：客户端进房时上报 `buildId`；服务器比对不一致时拒绝，并提示"请更新客户端"。

**`buildId` 的组成**：`<本体版本>+<内容摘要>+<代码摘要>`，实现里只有两处会用到它——
日志与握手判定。三段来源：

| 段 | 来源 | 说明 |
| --- | --- | --- |
| `bodyVersion` | `Application.version` | 构建时由 `PlayerSettings.bundleVersion` 写入；**握手只比这一段** |
| `contentHash8` | `HotUpdateRuntime.ContentVersion` 的最后一段（`0.10.1.c9bdad504` → `c9bdad504`） | 未启用热更时为空 |
| `codeHash8` | 当前恒空（代码更新走启动器，见第 12 节） | 保留字段，将来启用进程内代码热更时填入 |

**为什么内容段不参与判定**：资源差异由 Addressables 自己的寻址吸收，而服务器是版本锚点、
它本身没有内容层。拿内容段当拒绝条件，会让"资源热更过的客户端"连不上服务器——
那恰好是本批次要支持的主流形态。

### 13.3 本轮演练发现并修掉的两个缺陷

**① HTTP 更新源下 catalog 加载失败（内容热更静默退回本体）**

症状是"资源下载成功、游戏里却还是旧数值"，日志里是一行被忽略的
`catalog 加载失败，使用本体自带内容`。根因：寻址重写函数只按"能不能取到文件名"判断，
于是 Addressables 自己的 catalog 缓存路径
`<persistentDataPath>/com.unity.addressables/<哈希>.bin` 也被改写成更新源 URL；
Addressables 随后把 URL 当目录去创建，Windows 抛 `文件名、目录名或卷标语法不正确`。

修法：重写函数改为三步判定——本地缓存里有同名文件就用本地；否则只有 `content/` 命名空间
（与 RemoteLoadPath 一致）的地址才翻译成 URL；其余一律原样返回。
规则抽成 `HotUpdateRuntime.IsContentLayerAddress`，配 2 条 EditMode 测试钉住。

**② 玩家构建会往 Addressables 产物目录写 catalog，且不清空**

菜单 ①（玩家构建）也会写一份 `catalog_<版本>.bin/.hash` 到 `Builds/Addressables/<平台>/`，
而它不清空目录。于是"① → ⑥"（跳过 ⑤）时目录里会同时躺着两个版本的 catalog：
清单把它们都收进去（客户端白下两个文件），而资源版本号取到哪一个还不保证。

修法：菜单 ⑥ 在生成清单前清掉"文件名里不带当前版本号"的 catalog。
正确的完整顺序仍是 ① → ④ → ⑤ → ⑥（⑤ 会清空整个输出目录）。
