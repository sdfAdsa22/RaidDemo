## 1. 目标与范围

| 项目 | 结论 |
| --- | --- |
| 玩法 | **2~4 人 PVE 合作**，共同对抗 AI；单机 1 人 |
| 拓扑 | **统一客户端 + 独立专用服务器**；不做 Host-Client |
| 客户端形态 | **同一个客户端程序**：主菜单含「联机」入口，单机与联机不做版本区分 |
| 单机模式 | **本机内嵌服务器**（进程内跑同一套权威逻辑），与联机共用一条代码路径 |
| 平台 | 客户端仅 Windows（D-15）；服务器本机 / 局域网 / 云主机 |
| **不做** | PVP、匹配系统、反作弊、完整账号体系、跨平台联机、服务器集群、多房间并发 |

## 2. 形态：一套代码，两种运行方式

```text
[客户端 RaidDemo.exe]                 [服务器 RaidDemoServer.exe（无头）]
  主菜单                               监听端口（默认 7777，可配置）
   ├─ 单机：进程内启动内嵌服务器          ├─ 房间生命周期管理（单房间）
   └─ 联机：连接远端/本机服务器            ├─ 权威模拟（移动 / 战斗 / AI / 战局）
        ├─ 创建房间（成为房主）            ├─ 服务端存档（按账号隔离）
        └─ 加入房间（输地址 + 密码）        └─ 版本握手（对接 M10 热更）
```

- 逻辑与客户端内嵌服务器**是同一套代码**，服务器程序有两种外壳：
  - **本机 / 局域网**（Windows）：**带可视化 Dashboard 的服务器窗口**——显示监听地址、房间状态、玩家列表、日志，
    并提供开局 / 停止房间等操作；
  - **云主机**（Linux）：`-batchmode -nographics` 无头运行，通过 **Web 状态页**查看房间、玩家与日志
    （服务器内置 HTTP 状态页；备选：宝塔静态页 + `status.json`，Q-08 已确认）；
- 启动参数通过命令行传入，**不含绝对路径**（第 3 章约束）；
- 服务器启动后显示两行地址：`本机 127.0.0.1:7777` 与 `局域网 <内网IP>:7777`（云主机显示公网地址），方便房主转达。

## 3. 权威边界

| 内容 | 归属 |
| --- | --- |
| 位置 / 朝向、开火与命中、伤害与死亡、AI 行为、掉落、容器与搜刮进度、撤离计时、战局结算 | **服务器权威** |
| 输入采集、预测、插值、动画 / 特效 / 音效 / UI | 客户端 |
| 仓库、金币、任务等局外进度（联机模式） | **服务端存档**，按账号隔离（见第 6 节） |
| 仓库、金币、任务等局外进度（单机模式） | 本地存档，**与联机存档互不兼容** |

## 4. 房间模型：一台服务器 = 一个房间

```text
服务器启动（空闲）
   │  第一个客户端点「创建房间」
   ▼
房间成立 —— 创建者成为房主（房间管理员）
   │  其他人「加入房间」（地址 + 密码）
   ▼
等待大厅（2~4 人，房主可见全员列表）
   │  房主点「开始战局」
   ▼
战局（服务器权威）→ 撤离 / 阵亡 → 结算 → 回到大厅
   │  房主「解散房间」
   ▼
服务器回到空闲，等待下一批人创建
```

- **房主只是管理员**：负责开局、设置（房间名 / 密码 / 地图 / 难度）与踢人；
  他没有任何规则裁判权——权威始终在服务器，房主掉线不影响战局。这是与 Host-Client 的本质区别。
- **多房间并发明确推迟**：多房间要求服务器进程内并发多个会话实例（每个会话独立的战斗世界、AI、事件总线、存档区），
  对作品集 Demo 收益有限、成本接近翻倍。

## 5. 连接与加入

| 场景 | 做法 |
| --- | --- |
| 本机（服务器与客户端同机） | 一键「本机联机」，自动填 `127.0.0.1:7777` |
| 局域网 | **UDP 广播自动发现**：客户端扫描后列出局域网房间，免手输 IP；同时保留手输兜底 |
| 云主机 / 外网 | 手输公网地址（阿里云轻量 `47.104.210.207:7777`，公网直连）；客户端与启动器保留"本机 / 云主机 / 自定义"服务器档案，可一键切换 |
| 密码 | 可选 4 位数字，房主设置；密码错误有明确提示 |

**不做「房间号」**：房间号需要目录服务器把号码翻译成地址，等于额外维护一套后端；
密码已经能承担"防止乱入"的职责。若将来出现目录服务需求，再评估。

## 6. 身份与存档（联机模式）

### 6.1 轻量账号

- 首次进入联机模式：输入**昵称 + 4~6 位口令** → 服务器建号（口令存哈希），返回 token 存本地；
- 之后自动登录；换机器时用昵称 + 口令重新登录；
- **不做**邮箱验证、找回密码、改密流程——那是产品功能，不是岗位考察点。

### 6.2 服务端存档

- 存储位置：服务器侧 `server_saves/<账号>.json`，按账号隔离；
- 内容：仓库、金币、任务进度、联机节奏数据；
- **与单机存档完全隔离、互不兼容**——这是设计目标而非妥协：避免"联机刷装备带回单机"的平衡问题；
- 经济循环归服务器：商人与仓库操作在客户端产生指令、服务器落库，客户端只做界面与即时反馈。

## 7. 同步机制（沿用 ADR-001 的状态同步）

| 内容 | 机制 |
| --- | --- |
| 位置 / 朝向 / 血量 / 弹药 / 战局倒计时 | 快照（20 Hz）+ 客户端插值 |
| 开火 / 命中 / 拾取 / 换弹 / 死亡 / 撤离 | 事件 RPC（一次性） |
| 本地玩家移动 | 客户端**预测** + 服务器**和解**（不做完整战斗回滚） |
| 远端玩家与 AI | 客户端插值 + 外推 |
| 战斗判定 | **表现先行、服务器裁定**：客户端立即播弹道 / 火光 / 音效，命中与伤害以服务器结果为准 |
| AI | 全部在服务器运行，客户端只播动画与特效 |
| 版本握手 | 客户端上报"本体版本 + Addressables catalog 哈希 + 热更程序集版本"，不一致则提示更新（对接 M10） |

> **范围确认（2026-09-13 负责人拍板）**：
> - **P-07「倒地与救援」纳入 M9**（即上表 P3.5）——该机制在单机 1 人下没有玩法意义，联机后才成立；

## 10. 关键改造清单（对现有代码的影响）

| 现有实现 | 改造 |
| --- | --- |
| `SceneBootstrap`（单例组装根） | 拆出"会话装配"，支持"进程内一个会话"与"服务器进程内一个会话"两种宿主 |
| `EventBus` / `ServiceLocator` | 保持接口不变，改为会话级生命周期（服务器进程同样持有） |
| `PhysicsHitProbe`（现住表现层） | 服务端实现同一接口（无头环境同样有 PhysX），表现层保留原实现 |
| `Meta` / `SaveFileStore`（本地存档） | 抽出存储接口；联机模式换为服务器实现（按账号），单机保持本地文件 |
| `CommandRouter`（M0 预留） | 联机时命令来自网络输入，单机时来自本地输入——输入源可替换 |
| UI | 新增主菜单联机入口、登录界面、房间 / 大厅界面 |
| 构建流程 | 新增 Dedicated Server 构建目标与一键启动脚本 |

## 11. 风险与降级策略

1. **预测 / 和解是最大复杂度来源** → 先做"无预测也能玩"（接受延迟抖动），再加本地玩家预测；时间不足时只保留移动预测。
2. **`SceneBootstrap` 单例是最大改造点** → P0 先做装配审计，把"服务器必须能跑哪些代码"圈出来。
3. **无头服务器上的 NavMesh 与物理** → P2 实测；导航烘焙数据需随服务器包一起发布。
4. **云主机形态**：已确定为阿里云轻量 **Linux**（Q-07 已解决）→ 需要安装 Unity 的 Linux Dedicated Server 构建模块；
   首次部署先验证镜像运行库（glibc 版本），过旧则换 Ubuntu 22.04 镜像。
5. **断线重连** → 目标：短线（60 秒内）可回局，超时按阵亡结算；可降级为"断线即回大厅"。

## 13. 面试可讲点

- 为什么必须服务端权威、为什么不做 Host-Client；
- 状态同步 vs 帧同步的取舍；快照频率与带宽预算；
- 客户端预测与和解的边界（为什么战斗不做完整回滚）；
- AI 在服务器运行的代价与收益；
- 版本握手如何保证联机双方资源 / 代码一致（与 M10 热更衔接）。

## 15. 部署环境与接入（2026-09-13 体检结论）

> 完整接入信息（公网 IP、SSH 命令、面板地址）记在**不入库**的 `Docs/Local/云主机接入.local.md`，
> 本文件只保留不含敏感信息的结论。理由：本仓库是**公开仓库**，公网 IP 入库等于对外公布入口。

### 15.1 云主机（阿里云轻量 · 华北1 青岛）

| 项目 | 实测值 | 结论 |
| --- | --- | --- |
| 系统 | Alibaba Cloud Linux 3.2104 U11（RHEL 8 系），内核 5.10.134 | 合格 |
| glibc | 2.32 | 满足 Unity Linux 构建 ≥ 2.17 的运行要求 |
| 硬件 | 2 核 / 1871 MB 内存 / 磁盘 40 GB（可用 31 GB） | 单房间 2~4 人够用 |
| 工具链 | tar、unzip、curl、wget、python3 已装；`git` 未装（需要时再装） | — |
| 面板 | 宝塔面板独占 8888/tcp；未装 nginx / mysql | Web 状态页用服务器内置 HTTP 实现，不依赖面板 |
| 系统防火墙 | firewalld 已放行 `7777/udp`（本次补）与 `8080/tcp` | 合格 |
| 云防火墙 | 7777 只有 TCP 规则，**UDP 待补** | 见 15.3 与 Q-09 |

### 15.2 端口规划

| 端口 | 协议 | 用途 | 对外暴露 |
| --- | --- | --- | --- |
| 7777 | UDP | 游戏同步（Netcode for GameObjects / Unity Transport） | 是（玩家直连） |
| 8080 | TCP | 服务器 Web 状态页 | 是（只读状态） |
| 8888 | TCP | 宝塔面板 | **仅运维**，建议限制来源 IP |
| 22 | TCP | SSH（**仅公钥登录**，`PasswordAuthentication no`） | 仅运维 |

### 15.3 连通性实测（从开发机出网，2026-09-13）

| 目标 | 方法 | 结果 |
| --- | --- | --- |
| SSH | 公钥登录（私钥在开发机，不入库） | **通**；服务器保持关闭密码登录 |
| TCP 8080 | 开发机连接 + 服务器侧记录来源 | **通**（服务器记录到开发机来源 IP，链路完整） |
| UDP 7777 | 两轮共 6 个自定义 UDP 包 | **不通**：服务器未收到任何包；同机 DNS over UDP 正常，排除开发机出网问题 → 判定为云防火墙缺 UDP 规则 |

> 影响范围：仅 **P6 云主机验收**受阻；P0~P5 在本机用「服务器进程 + 2 客户端」推进，不等这条规则。
