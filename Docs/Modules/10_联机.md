## 1. 目标与范围

| 项目 | 结论 |
| --- | --- |
| 玩法 | **2~4 人 PVE 合作**，共同对抗 AI；单机 1 人 |
| 拓扑 | **统一客户端 + 独立专用服务器**；不做 Host-Client |
| 客户端形态 | **同一个客户端程序**：主菜单含「联机」入口，单机与联机不做版本区分 |
| 单机模式 | **本机内嵌服务器**（进程内跑同一套权威逻辑），与联机共用一条代码路径 |
| 平台 | 客户端仅 Windows（D-15）；服务器本机 / 局域网 / 云主机 |
| **不做** | PVP、匹配系统、反作弊、完整账号体系、跨平台联机、服务器集群、多房间并发 |

## 2. 形态：一套代码，两种运行方式

```text
[客户端 RaidDemo.exe]                 [服务器 RaidDemoServer.exe（无头）]
  主菜单                               监听端口（默认 7777，可配置）
   ├─ 单机：进程内启动内嵌服务器          ├─ 房间生命周期管理（单房间）
   └─ 联机：连接远端/本机服务器            ├─ 权威模拟（移动 / 战斗 / AI / 战局）
        ├─ 创建房间（成为房主）            ├─ 服务端存档（按账号隔离）
        └─ 加入房间（输地址 + 密码）        └─ 版本握手（对接 M10 热更）
```

- 逻辑与客户端内嵌服务器**是同一套代码**，服务器程序有两种外壳：
  - **本机 / 局域网**（Windows）：**带可视化 Dashboard 的服务器窗口**——显示监听地址、房间状态、玩家列表、日志，
    并提供开局 / 停止房间等操作；
  - **云主机**（Linux）：`-batchmode -nographics` 无头运行，通过 **Web 状态页**查看房间、玩家与日志
    （服务器内置 HTTP 状态页；备选：宝塔静态页 + `status.json`，Q-08 已确认）；
- 启动参数通过命令行传入，**不含绝对路径**（第 3 章约束）；
- 服务器启动后显示两行地址：`本机 127.0.0.1:7777` 与 `局域网 <内网IP>:7777`（云主机显示公网地址），方便房主转达。

## 3. 权威边界

| 内容 | 归属 |
| --- | --- |
| 位置 / 朝向、开火与命中、伤害与死亡、AI 行为、掉落、容器与搜刮进度、撤离计时、战局结算 | **服务器权威** |
| 输入采集、预测、插值、动画 / 特效 / 音效 / UI | 客户端 |
| 仓库、金币、任务等局外进度（联机模式） | **服务端存档**，按账号隔离（见第 6 节） |
| 仓库、金币、任务等局外进度（单机模式） | 本地存档，**与联机存档互不兼容** |

## 4. 房间模型：一台服务器 = 一个房间

> **2026-09-14 更新（P4.5）**：下图是 P4 的形态——"房间界面 → 房主开局 → 直接进地图"。
> 负责人随后定稿：**联机首站改为共享安全屋**（可走动、互相同步），
> 房主在**全员回到安全屋**之后才能在出口选图、全员一起进图。完整改动见 §25。

```text
服务器启动（空闲）
   │  第一个客户端点「创建房间」
   ▼
房间成立 —— 创建者成为房主（房间管理员）
   │  其他人「加入房间」（地址 + 密码）
   ▼
等待大厅（2~4 人，房主可见全员列表）
   │  房主点「开始战局」
   ▼
战局（服务器权威）→ 撤离 / 阵亡 → 结算 → 回到大厅
   │  房主「解散房间」
   ▼
服务器回到空闲，等待下一批人创建
```

- **房主只是管理员**：负责开局、设置（房间名 / 密码 / 地图 / 难度）与踢人；
  他没有任何规则裁判权——权威始终在服务器，房主掉线不影响战局。这是与 Host-Client 的本质区别。
- **多房间并发明确推迟**：多房间要求服务器进程内并发多个会话实例（每个会话独立的战斗世界、AI、事件总线、存档区），
  对作品集 Demo 收益有限、成本接近翻倍。

## 5. 连接与加入

| 场景 | 做法 |
| --- | --- |
| 本机（服务器与客户端同机） | 一键「本机联机」，自动填 `127.0.0.1:7777` |
| 局域网 | **UDP 广播自动发现**：客户端扫描后列出局域网房间，免手输 IP；同时保留手输兜底 |
| 云主机 / 外网 | 手输公网地址（阿里云轻量 `47.104.210.207:7777`，公网直连）；客户端与启动器保留"本机 / 云主机 / 自定义"服务器档案，可一键切换 |
| 密码 | 可选 4 位数字，房主设置；密码错误有明确提示 |

**不做「房间号」**：房间号需要目录服务器把号码翻译成地址，等于额外维护一套后端；
密码已经能承担"防止乱入"的职责。若将来出现目录服务需求，再评估。

## 6. 身份与存档（联机模式）

### 6.1 轻量账号

- 首次进入联机模式：输入**昵称 + 4~6 位口令** → 服务器建号（口令存哈希），返回 token 存本地；
- 之后自动登录；换机器时用昵称 + 口令重新登录；
- **不做**邮箱验证、找回密码、改密流程——那是产品功能，不是岗位考察点。

### 6.2 服务端存档

- 存储位置：服务器侧 `server_saves/<账号>.json`，按账号隔离；
- 内容：仓库、金币、任务进度、联机节奏数据；
- **与单机存档完全隔离、互不兼容**——这是设计目标而非妥协：避免"联机刷装备带回单机"的平衡问题；
- 经济循环归服务器：商人与仓库操作在客户端产生指令、服务器落库，客户端只做界面与即时反馈。

## 7. 同步机制（沿用 ADR-001 的状态同步）

| 内容 | 机制 |
| --- | --- |
| 位置 / 朝向 / 血量 / 弹药 / 战局倒计时 | 快照（20 Hz）+ 客户端插值 |
| 开火 / 命中 / 拾取 / 换弹 / 死亡 / 撤离 | 事件 RPC（一次性） |
| 本地玩家移动 | 客户端**预测** + 服务器**和解**（不做完整战斗回滚） |
| 远端玩家与 AI | 客户端插值 + 外推 |
| 战斗判定 | **表现先行、服务器裁定**：客户端立即播弹道 / 火光 / 音效，命中与伤害以服务器结果为准 |
| AI | 全部在服务器运行，客户端只播动画与特效 |
| 版本握手 | 客户端上报"本体版本 + Addressables catalog 哈希 + 热更程序集版本"，不一致则提示更新（对接 M10） |

## 10. 关键改造清单（对现有代码的影响）

| 现有实现 | 改造 |
| --- | --- |
| `SceneBootstrap`（单例组装根） | 拆出"会话装配"，支持"进程内一个会话"与"服务器进程内一个会话"两种宿主 |
| `EventBus` / `ServiceLocator` | 保持接口不变，改为会话级生命周期（服务器进程同样持有） |
| `PhysicsHitProbe`（现住表现层） | 服务端实现同一接口（无头环境同样有 PhysX），表现层保留原实现 |
| `Meta` / `SaveFileStore`（本地存档） | 抽出存储接口；联机模式换为服务器实现（按账号），单机保持本地文件 |
| `CommandRouter`（M0 预留） | 联机时命令来自网络输入，单机时来自本地输入——输入源可替换 |
| UI | 新增主菜单联机入口、登录界面、房间 / 大厅界面 |
| 构建流程 | 新增 Dedicated Server 构建目标与一键启动脚本 |

## 11. 风险与降级策略

1. **预测 / 和解是最大复杂度来源** → 先做"无预测也能玩"（接受延迟抖动），再加本地玩家预测；时间不足时只保留移动预测。
2. **`SceneBootstrap` 单例是最大改造点** → P0 先做装配审计，把"服务器必须能跑哪些代码"圈出来。
3. **无头服务器上的 NavMesh 与物理** → P2 实测；导航烘焙数据需随服务器包一起发布。
4. **云主机形态**：已确定为阿里云轻量 **Linux**（Q-07 已解决）→ **Linux Dedicated Server 构建模块已安装（2026-09-14）**；
   首次部署先验证镜像运行库（glibc 版本），过旧则换 Ubuntu 22.04 镜像。
5. **断线重连** → 目标：短线（60 秒内）可回局，超时按阵亡结算；可降级为"断线即回大厅"。

## 15. 部署环境与接入（2026-09-13 体检结论）

> 完整接入信息（公网 IP、SSH 命令、面板地址）记在**不入库**的 `Docs/Local/云主机接入.local.md`，
> 本文件只保留不含敏感信息的结论。理由：本仓库是**公开仓库**，公网 IP 入库等于对外公布入口。

| 端口 | 协议 | 用途 | 对外暴露 |

### 15.3 连通性实测（从开发机出网；UDP 一栏为 2026-09-14 复验结果）

| 目标 | 方法 | 结果 |
| --- | --- | --- |
| SSH | 公钥登录（私钥在开发机，不入库） | **通**；服务器保持关闭密码登录 |

### 20.2 导航地基（2026-09-14）

新增 `Bootstrap/Session/Network/ServerRuntime.Navigation.cs`：地图场景生效后烘焙
`NavMeshSurface`，随后用**服务器自己将要使用的寻路实现**（`NavMeshPathfindingService`）
算三条真实路径并打日志（平地 / 装卸平台高差 / 厂房内部）。

验收证据（Windows 开发版 + `-server -map GreyboxRaid -batchmode -nographics`）：

```
[服务器] 加载地图场景：GreyboxRaid
[服务器] 导航数据已烘焙：三角面顶点 1952 个，耗时 21 ms。
[服务器] 导航自检「堆场平地」：路径可用，3 个途径点。
[服务器] 导航自检「装卸平台高差」：路径可用，2 个途径点。
[服务器] 导航自检「厂房内部」：路径可用，4 个途径点。
```

**结论：无头服务器可以烘焙并使用导航网格。** 关键前提是场景生成器把
`NavMeshSurface.useGeometry` 设为**收集物理碰撞体**（`PhysicsColliders`）而不是渲染网格——
后者要求模型开启 Read/Write，而工程里 93 个模型全部是 `isReadable: 0`。

过程中暴露并修掉了两个真实缺陷（详见 M9 排障手册 P-15 / P-16）：

1. **从 `AfterSceneLoad` 里 `LoadScene` 是延迟生效的**——刚加载完就去找场景里的组件必然找不到。
   改为"登记待办 + 每帧检查活动场景"。
2. **寻路服务写死了"地面在 y=0"**——而 M7 起地图是下沉盆地（谷底 -6 / 平台 -4.8 / 塬面 0），
   于是寻路**全部失败**并静默降级成直线推进。改用与敌人视图、AI 地面高度同一套分层采样
   （`NavMeshGroundSampler`）后恢复正常。
   这条同时解释了此前"AI 在盆地里走路发直"的观感——不是状态机的问题，是寻路从来没成功过。

- **阵亡的敌人继续出现在快照里**（`IsAlive=false`）：客户端据此保留尸体并停住它，
  否则敌人被打死后会从画面上直接消失，而玩家期待的是留下一具尸体。

验收证据（本机三进程，开发版构建；客户端 A 日志）：

## 21. P3 执行计划：交互与战局闭环（2026-09-14 定稿）

### 21.1 现状盘点（开工前必须知道的事）

服务器侧目前**没有任何容器与搜刮系统**：容器内容、掉落、背包操作、撤离读秒全部在客户端
（`SceneBootstrap.Inventory.cs` / `ContainerRegistry` / `LootSearch`），只有 P2-1 为战斗手搓的一份
固定装备（AK + 120 发）。也就是说，联机里"两人各搜各的箱子、各捡各的东西"——
谁先拿到、箱子里剩什么，两边完全不一致。

### 21.2 沿用已定的改造套路

与 P2 的战斗完全同构，不再另开架构：

> **界面与表现继续订阅本地事件，但事件的来源从"本地逻辑"换成"服务器广播"。**

P2 里 `WeaponFiredEvent` 这么改就通了（客户端一行表现层代码都没动），
背包同理：`InventoryChangedEvent` / 容器内容变更 / 搜刮进度都从服务器下发。

### 21.3 批次拆分

| 批次 | 内容 | 验收判据 |
| --- | --- | --- |
| **P3-1 容器与背包权威化** | 服务器用与客户端同一份内容定义生成容器初始内容并持有容器注册表；容器内容与搜刮进度下行；客户端容器界面改为只读展示 + 上行意图 | 两名客户端看到的容器内容**逐格一致**；两人搜同一个箱子时只有先到者成功，后者收到明确反馈 |
| **P3-2 背包操作上行** | 拾取 / 丢弃 / 移动 / 装备 / 换弹取弹全部变成上行命令（`InventoryCommand`）；服务器执行后广播结果 | 联机里捡起的物品在背包里可见、可装备；弹药消耗仍走服务器的换弹路径 |
| **P3-3 撤离与结算** | 撤离点读秒、带出价值、阵亡损失由服务器裁定，**各自结算**；结算界面与"战局可重开" | 服务器日志能看到两人各自撤离/阵亡的结算；战局结束后可重开 |
| **P3-4 收尾与回归** | 断线处理、单机一致性回归、文档与验收脚本 | 单机全流程不回归；EditMode 全绿 |

### 21.4 已知风险

1. **客户端容器界面是"本地为王"写法**（改完就地广播事件）——P3-1 要把写入口收到服务器，
   界面本身尽量不动；若发现某处是"界面直接改数据"，先把它改成命令再谈同步；
2. **掉落随机数**：容器内容由服务器生成即可，但要注意**不要用客户端的 `UnityEngine.Random`**
   （两个进程的序列不同），服务器用 `DeterministicRandom`（与武器散布同源）；
3. **背包与战斗的耦合**：换弹消耗弹药走的是 `PlayerWeaponController` 的 `PlayerLoadout`，
   把背包搬上服务器时这条路径必须一起搬，否则会出现"服务器换弹扣的是它自己那份背包"。

### 21.5 开工侦察结论（2026-09-14，P3-1 前的两点确认）

读完客户端背包装配之后，P3-1 有两条结论直接影响做法：

1. **命令层可以整层复用，不需要新写一套。** 客户端已经走「意图 → `CommandRouter` →
   `InventoryCommandHandler`」的结构，`InventoryContext(registry, loadout, eventBus)` 把
   "容器在哪"与"改完通知谁"都抽象掉了。服务器只要用**同一份 handler + 自己的 registry**
   注册一遍，就能直接执行客户端的背包意图——P3-2 的上行命令因此是"接管道"而不是"造管道"。
2. **容器编号目前是"注册顺序号"，必须先变成两端一致的稳定编号。** 客户端现在是
   `Register(背包)=1 / Register(弹药挂)=2 / Register(仓库)=3`…按装配顺序自增，
   两个进程一旦装配顺序不同，同一个编号就指向不同的箱子——而所有背包命令都带编号。
   做法：**由场景生成器把稳定编号写进容器对象**（房间里的箱子），玩家侧容器
   （背包 / 弹药挂 / 仓库）用固定的保留段，两端都从同一份定义读。

这两点确认之后，P3-1 的落地顺序是：稳定编号 → 服务器建 registry 与初始内容 →
容器内容下行 → 客户端容器界面改为只读展示。

**它只改出生位置，读秒、判定、结算走的是与真实游玩完全相同的代码路径**。

## 22. P3.5 倒地与救援（已完成，2026-09-14）

### 22.1 规则

| 规则 | 数值 / 行为 |
| --- | --- |
| 生命两态 | 存活 → **失能（倒地待救）** → 死亡；失能不是死亡 |
| 流血倒计时 | 60 秒；归零即死亡并按 `Killed` 结算 |
| 施救 | 队友在 **2.5 米**内**按住 F 持续 3 秒**；松手或走远即进度清零（不能"救一半留着"） |
| 被救起后 | 恢复 **40 点**生命，重新可以移动与开火 |
| 倒地期间 | 不能移动、不能开枪，只能等（服务器直接丢弃他的移动与战斗输入） |
| **单机（1 人）** | **不进入失能**：没人能来救，倒地只会白等 60 秒，因此直接按死亡结算（设计文档的明确要求） |

```text
回大厅：全员结算后服务器回到「等待中」，房主可再开一局（「解散房间」则回空闲）
```

单机路径完全不变：主菜单「开始游戏」→ 安全屋 → 出击。

### 23.3 服务器状态机（一台服务器 = 一个房间）

| 阶段 | 允许的操作 | 转移 |
| --- | --- | --- |
| 空闲 `Empty` | 登录、创建房间 | 创建 → 等待中 |
| 等待中 `Waiting` | 登录、加入、离开、房主开局 | 开局 → 战局中；最后一人离开 → 空闲 |
| 战局中 `InRaid` | 离开（等同于退赛）、全员结算 | 全员结算 → 等待中 |

规则细节（全部由 `LobbyRoom` 这个纯逻辑对象持有，见 23.5）：

- 房主离开时**转移给剩余第一名成员**——不转移会让房间卡在"没人能开局"的死局；
- 单人也能开局：两人合作是主要玩法，但开发期"一个人进图试枪"是最常用路径；
- 房间密码可选，选了就必须是 4 位数字（与设计文档 §5 一致）；
- **不做房间号**（需要目录服务器，设计文档已明确推迟）；局域网发现补上了"免输 IP"，公网仍是手输地址。

### 23.4 关键决策（本批新拍板）

| 事项 | 决策 | 理由 |
| --- | --- | --- |
| 人数上限的执行位置 | **在「加入房间」时拒绝，而不是连接审批回调** | 连接审批只能在握手阶段回一个"拒绝"，说不出"房间满了"还是"密码错"；放在加入时拒绝，玩家能看到具体原因，且未登录的连接不占用房间名额 |
| 身份口令存储 | 服务器侧 PBKDF2（SHA-256，随机盐）＋ token | 口令绝不能明文落库；token 让"之后自动登录"不必每次输口令 |
| 联机存档与单机存档 | **继续隔离**（P5 落库时生效，本批只建账号） | 防止"联机刷装备带回单机" |
| 状态页的写操作 | **只允许来自本机回环地址的请求** | 状态页要暴露"停止房间 / 停止服务器"这类动作，云端端口又是公网可达；用回环限制把默认攻击面降为零，运维走 SSH 隧道 |
| 开局触发 | 房主请求；自动化脚本可用服务器参数 `-autostart 秒` 代替点击 | 自动开局只替换"谁触发"，走的仍是同一条服务器开局路径 |
| 结算后的去向 | 全员结算 → 服务器回「等待中」，客户端回大厅界面 | 与设计文档 §4 的房间生命周期一致 |

### 25.1 定稿的联机流程

```text
启动 → 主菜单「联机」→ 连接 + 登录
   │
   ▼
房间界面：创建 / 加入房间（这一层还是"门外"，玩家还没有身体）
```

### 25.2 三个改动点（工程含义）

### 25.5 P4.5-a 的根因记录（搜刮后物品搬不进背包）

P3-2 只接管了 **拖拽移动**（`InventoryMoveIntent`）与**装备 / 卸下**，
而 M2 的**双击快速转移**走的是另一条意图 `InventoryQuickTransferIntent`——它仍然在**本地**执行：
客户端本地网格先改、随后服务器的权威容器内容下发把它覆盖回去，玩家看到的就是"物品怎么都搬不动"。
同一条漏网的还有**旋转（R）**与**整理**。

修法沿用 P3-1 的"命令层整层复用"：给上行消息加一个 `Kind` 字段
（移动 / 快速转移 / 旋转 / 整理），服务器按 Kind 分派到**同一份客户端 handler** 上执行——
不新增协议族，也不会出现"两套放置规则"。

**已修复（2026-09-14）**：`InventoryCommandKinds`（移动 / 快速转移 / 旋转 / 整理 / 拆分）
+ 消息新增 `Kind` 与 `Count` 字段；客户端把这五类意图全部接管为"只上行"，
服务器注册**同一批** handler 并按 Kind 分派。新增三条测试钉住"字段往返"与"服务器能执行快速转移"；
EditMode **592/592** 全绿。

### 25.6 U-75 的真正现象根因：客户端没有补发本地变更事件（2026-09-14 定位并修复）

§25.5 修的是"双击/旋转/整理此前根本没上行"这个**真实但并非现象主因**的缺陷——修完之后
玩家反馈"还是搬不动"。用 `-logLevel verbose` 重跑一次，三段证据拼出了真正的根因：

```
服务器：玩家 1 背包命令（种类 0）：112->1 结果=True（success）     ← 命令到了、执行成功
客户端：[联机] 容器内容已同步：17 个（服务器权威）                  ← 数据也收到了
界面  ：m_EventBus.Subscribe<InventoryChangedEvent>(_ => RefreshAll())  ← 只在本地事件到达时重画
```

单机时命令在本地执行，handler 会在本地事件总线上发 `InventoryChangedEvent` → 界面重画；
联机时命令由**服务器**执行，那条事件发在**服务器**的进程里，客户端收不到；
而客户端应用服务器内容的代码**只改网格、没有补发事件** →
`RefreshAll()` 永不触发 → **数据搬了、画面没搬**。

**修法**：把"应用服务器内容"抽成独立部件 `LootContainerSync.Apply(...)`，
在铺完网格后**补发一条本地 `InventoryChangedEvent`**（新增变更类型 `sync`，
与 `place`/`equip` 区分开，避免别人动箱子时在自己客户端响界面音）。
界面、负重条、护甲刷新、界面音效全部沿用既有订阅，不需要给界面加联机分支。

**新增 4 条测试**（`LootContainerSyncTests`）钉住：物品入网格、**应用完必须发事件**、
服务器说箱子空了要清空且仍然发事件、本地没有的容器安静跳过且不惊动界面。回归 **596/596** 全绿。

**这条验收教训**：P3-1 当时是**读日志**验收的（"容器内容已同步 4→3 件"），
而日志只反映数据、不反映画面。**凡是有界面的功能，验收必须包含"看一眼画面"这一步。**

### 25.7 P4.5-a 收口：另外三处根因（2026-09-14 定位并修复）

§25.5 / §25.6 之外，同一轮排查还挖出三处**独立**缺陷。它们各自都能单独造成"搜刮搬不动"，
所以必须一起收口——只修其中任何一处，现象都会以略不同的样子留下来。

**① 场景切换会把新场景刚注册的网络处理器删掉**

场景切换的真实顺序是 `新场景 Awake（注册）→ 旧场景 OnDestroy（退订）`，
而 `DetachFromServer()` 是**按名字全量退订**的：旧场景的销毁回调把新场景刚注册的
快照 / 移动 / 战斗 / 敌人 / 容器 / 结算 / 生命处理器删了个干净。
症状极具迷惑性：**进图那一次同步是好的**（发生在删除之前），之后服务器发什么都没反应。

修法：新增静态归属标记 `s_ActiveChannelOwner`——注册时认领，退订前先确认自己是不是持有者；
不是持有者就什么都不做。这样"谁注册谁负责退订"在跨场景共享的连接上依然成立。

**② 容器内容消息不带格子坐标**

消息原本只有"有什么、几个、是否横放"，客户端一律用 `AutoPlace` 重新摆放。
只要任一端显式摆过位置，两端布局就分叉；此后客户端拖拽带着**自己那份坐标**上行，
服务器按它的坐标找物品——找到的是别人、或者什么都没有。这就是"**有的能过去、有的不能**"。

修法：`ContainerItemMessage` 增加 `CellX / CellY`；服务器打包时取 `grid.TryGetOrigin`，
客户端按坐标**原位复原**，只有放不下时才回退 `AutoPlace`，并且**必须留一条警告**
（静默退化正是两端悄悄分叉的来源）。

**③ 两端容量不一致时换掉了容器对象（本轮修复）**

服务器按**它自己那份装备**建随身容器（默认配发 5×5 口袋），客户端带的是局外装备
（背了背包就是 6×6 / 7×7）——两边容量本来就会不一致。而 `LootContainerSync.Apply`
遇到尺寸不一致时是**新建网格对象塞进注册表**：一个背包由此变成两份数据，
服务器内容铺进新网格，而 `PlayerLoadout` 与已打开的界面视图仍然指向旧网格。
表现正是"**搬进去的东西看不见、看得见的东西搬不动**"。

修法：`Apply` **永不替换容器对象**——容量不一致只记一条警告（同一组合只报一次，避免刷屏），
内容照旧按坐标铺进本地那个网格。容量归属规则因此明确为：

> **随身容器的容量以本地装备为准**（决定屏幕上有几个格子），
> **内容以服务器为准**（决定格子里有什么）。

**新增 2 条测试**：`Apply_CapacityMismatch_KeepsLocalGridObject`（对象必须仍是同一个 +
内容必须真的铺进去）、`ContentsBatch_RoundTripsCellCoordinates`（消息每加一个字段都要往返验证，
否则字段永远是被序列化一方的默认值，坐标恒为 (0,0)）。EditMode **600/600** 全绿。

### 25.8 验收证据：真实链路的搬运往返（2026-09-14）

单机测试只能证明规则对；"两端是否真的对同一件事达成一致"必须在**真实链路**上验。
实验环境：无头服务器（`-server -logLevel verbose`）+ **编辑器当客户端**，玩家是房主，
命令的源坐标一律从**客户端自己的网格**里取（与界面拖拽同一条路径）；
为了让"容量不一致"这个条件成立，先把客户端背包换成 6×6（模拟"在安全屋背了背包再进图"）。

| 步骤 | 客户端看到的结果 | 服务器 verbose 自检 |
| --- | --- | --- |
| 进图 | 背包 6×6，注册表 #1 与 loadout.Backpack **同一对象** | — |
| ① 箱子 100 → 背包 (3,3) | 背包出现该物品，坐标 **(3,3)** | 背包 1 件[ammo.9x19.standard@**3,3**] |
| ② 背包 (3,3) → 箱子 100 (0,0) | 背包清空，箱子收到物品 @**(0,0)** | 背包 0 件[] |

两次独立运行结论一致（第二次换了另一件物品）：

- **格子坐标两端一致**——客户端拿自己那份坐标发命令，服务器能在同一格找到物品；
- **搬进去的物品能再搬出来**——"搬进背包就搬不动"不再出现；
- **容器对象全程不变**——"同一对象=True"出现在每一步，装备与界面没有指向旧网格。

**容量说明（设计内行为）**：同步事件之后，客户端会按**本地装备**把容量"自愈"回 5×5
（背包栏里没背背包 → 口袋容量），这一步由 `RefreshBackpackCapacity` 同时更新
注册表 / 装备 / 界面三处，因此不会产生分叉。**容量以本地装备为准**这条规则由此在代码里落地。

### 25.9 P4.5-a 的已知边界（交接给 P5）

联机战局里，玩家**从局外带进图的随身装备**目前不会进入服务器那份：服务器按默认配发逻辑
自己造一套（5×5 口袋背包 + 一把 AK + 一叠备弹），客户端带的是自己的局外装备。
由此产生两条影响：

1. **背包容量可能不同**（客户端 6×6 / 7×7，服务器 5×5）。按 §25.7 的容量归属规则，
   以本地装备为准，因此不影响搬动；但玩家把物品放到服务器没有的格子时，服务器会拒绝，
   客户端随后的权威回包会把画面纠正回来。
2. **背包里的带入物会被服务器的内容覆盖**（服务器那份是空的）。这是玩家可感知的缺口，
   属于 **P5 的装备同步**范畴——服务器必须先知道"这名玩家带进来了什么"，
   共享仓库与按账号落库才有地基。P4.5-a 不做，只记为已知边界，避免提前做两次。
3. **一人硬掉线会连带踢掉其余玩家**（2026-09-14 全流程验收发现，完整取证见排障手册 P-48）：
   把队友进程直接杀掉后，服务器判定其超时并清理；**在同一时刻，其余玩家的上行单向中断**，
   服务器再过 10 秒按协议超时把他们也踢掉——表现为"队友掉了，我也被踢，房间解散"。
   应用层已逐条排除（`timeScale`／帧循环／发包分支／预测积压／界面阻塞），
   最后一环在 NGO/UTP 传输层内部。**处置：带进 P5 的"掉线宽限 + 重连"一并解决**——
   这条链的触发点正是"服务器立即清理掉线玩家"，宽限期落地后触发点自然消失；
   若 P5 之后问题仍在，再上传输层手段（UTP 内部日志／抓包）定性。
   验收判据见第 9 节 P5 行。

### 25.10 物品实例在同步中的归属：内容以服务器为准，对象尽量沿用本地那一件

§25.7 解决了"容器网格对象**被换掉**"，但没有解决"容器里的**物品对象被重建**"。
后者同样是静默缺陷，且症状更"玄学"：

> 双击搬东西**时灵时不灵**、背包里的东西**拖到位置松手没反应**，日志里一行错误都没有。

**实测证据**（编辑器当客户端 + 无头服务器，两次同步之间内容完全没变）：
同一格上的同一件物品，实例号从 `-1661239390` 变成 `-1706226684`，
也就是 `LootContainerSync.Apply` 每次都把容器重铺了一遍。

**为什么这会让界面失灵**：界面的"身份"判断建立在对象引用上——

```text
双击识别 ：ReferenceEquals(本次点击的物品, 上次点击的物品)   → 对象一换就不相等
拖拽松手 ：m_DragSource.Grid.TryGetOrigin(m_DragItem, ...)  → 对象一换就找不到坐标
```

一次同步只要落在两次点击之间、或落在一次拖拽的过程里，这个操作就**静默失效**。
同步由"任何人操作容器 / 新客户端接入"驱动，因此玩家点得越快越容易撞上。

**规则（P4.5-a 收口后）**：

> **内容以服务器为准**——有什么、几个、在哪个格子、是否横放，全部按服务器下发；
> **对象尽量沿用本地那一件**——同一容器里"同一定义 + 同一数量 + 同一摆放方向"的旧实例
> 优先复用，只有真正变化的物品才新建。

两条一起看才是完整规则：**容量以本地装备为准（§25.7）、内容以服务器为准、
对象以"能复用就复用"为准**。界面因此可以放心把物品对象当作"这一件东西"来用。

**落地**：

- `LootContainerItemReusePool`：铺放前的复用池（键 = 定义 + 数量 + 摆放方向，**不含坐标**——
  搬动一格仍是同一件东西）；`LootContainerSync.Apply` 每个容器建一个池，先 `Collect` 再清空再 `Take`；
- 界面侧仍然不把对象当身份：双击识别用「容器 + 格子 + 物品定义」
  （`InventoryScreenController.Identity.cs`），拖拽松手时对象被换掉则按"同一格同一种物品"兜底取坐标；
- 测试 4 条：同一份内容两次同步**对象不变**、换格子**对象不变**、数量变化**必须换新实例**、
  池中实例**只能取一次**。EditMode **604/604** 全绿。

**为什么不是"干脆每次全量重建"**：全量重建的代价落在**所有**把引用当身份的地方
（双击、拖拽上下文、界面缓存、订阅键），而且它不报错、只表现为"偶尔没反应"。
联机同步的默认写法应当是"**内容按权威侧覆盖、对象尽量沿用**"。

### 25.11 实机定位：移动"一卡一卡"与"枪不跟准星"（2026-09-14，尚未修复）

P4.5-a 交付后第一次双人实机验收里出现两条新问题，都在真实链路上取到了数字：

**① 移动一卡一卡（房主），加进来的玩家正常**

| 条件 | 服务器每秒"被覆盖丢弃"的输入 | 客户端回滚 |
| --- | --- | --- |
| 客户端约 60 FPS | **0 条/秒** | 0 次 |
| 同一客户端压到 20 FPS | **12~13 条/秒** | 每次快照一次，误差恒 **0.108 米** |
| 负责人那一局（房主 18 FPS） | 同机制 | 66 次（其中 61 次正好 0.108 米） |
| 负责人那一局（加进来的玩家） | 无 | 1 次 |

0.108 米 = **一步（1/60 秒）的位移**（冲刺 6.5 ÷ 60）；走路一步只有 0.058 米。
而对账容差是 `0.08` 米——**比冲刺一步小、比走路一步大**，于是"走路正常、冲刺就抖"。

两条根因叠加：

1. `MovementServerWorld.TrySubmitInput` 的待处理输入是**单槽**，新输入**直接覆盖**旧的：
   客户端帧率低于 60 时一帧补多步、连发多条，服务器每个固定步只消费一条 →
   被丢的输入在客户端已经算过 → "已处理序号 ↔ 实际步数"错开一步 → 客户端稳定领先一步。
2. 容差比一步还小 + 修正动作是 `SnapTo(...)`（硬瞬移）→ 偏差永远修不完，
   每次快照都硬吸一次，就是玩家看到的"一卡一卡 + 极短距离瞬移"。

**修复（已落地）**：

1. 服务器输入改**队列**（`MovementServerWorld.Inputs.cs`，上限 32 条、满了拒收新输入），
   每个固定步消费一条，让"已处理序号 ↔ 执行步数"一一对应；
2. 客户端**不补回卡顿时间**（一帧最多 4 步，多出的时间丢掉），避免把一次加载卡顿
   变成几十条连发输入把服务器队列灌满（修复前实测队列在第 36 条输入就被灌满）；
3. 对账容差 = `max(0.12, 1.5 × 速度 × 1/60)`（冲刺 0.163 米、走路 0.12 米），
   超差时**模拟立刻采用权威值、表现层平滑吸收**，只有 ≥0.6 米（传送 / 重开 / 卡墙）才硬瞬移。

**复测**（同一套脚本）：60 FPS 冲刺与 20 FPS 冲刺**丢输入均为 0 条**、队列积压稳定在 4~5 条、
客户端全程只有 1 次回滚（出生传送）；修复前同样条件每秒被覆盖 12~13 条、每次快照都回滚。

**② 枪一直指向一个方向**

枪的朝向由 `m_WeaponController.AimDegrees` 驱动，而每帧写它的只有单机分支的
`CollectCombatInput()`；联机分支 `CollectMultiplayerCombatIntent()` 只上报扳机与换弹。
因此**每个联机客户端看自己的枪都是固定的**（远端玩家目前不画枪，所以不容易互相发现）。

**修复**：抽出 `SyncAimToWeapon()`，单机与联机分支都每帧调用（联机只影响表现）。
**复测**：瞄准方向由 `(0,1)` 改成 `(-1,0)`，武器朝向随之 90° → 180°。

**本次留下的诊断**（Verbose；没有覆盖时不打）：

- 服务器 `[服务器][诊断] 玩家 N：本秒被覆盖丢弃的未消费输入 X 条（累计 Y 条）`
  （`ServerRuntime.Movement.Diagnostics.cs`、`MovementServerWorld.TryGetInputDiagnostics`）；
- 客户端 `SceneBootstrap.RollbackCount`（本局回滚次数，可直接读，不必数日志）。

排障过程与教训见 `排障记录/M9_问题记录与排障手册.md` 的 **P-45 / P-46**。

### 25.12 本轮联机基础问题修复：三条下行补全与两条保活规则

2026-09-14 的全流程实机排查（排障手册 **P-48**）里，逐条证伪了"客户端没武器、弹匣不更新、
结算后掉线"等症状，最终收敛为**三条缺失的下行数据**与**两条保活规则**。
它们是机制级行为，后续改动必须遵守：

**① 装备槽镜像：装备状态第一次有了下行通道**

装备槽（`EquipmentLoadout`）不是网格容器，此前**没有任何下行通道**：服务器配发的武器
只存在于服务器那份载荷里，客户端进图后 HUD 显示"无武器"、按开火没有任何反应——
而服务器日志一切正常。

- 约定：装备槽按 **1×N 伪容器**表达（列固定 0，**行号 = `EquipmentSlot` 枚举值**），
  使用保留编号 `ContainerIds.EquipmentMirror = 4`；
- 编解码集中在 **`EquipmentMirrorCodec`**（`Build` / `Apply` 纯函数，EditMode 测试钉住约定）；
- 下行搭在**既有的容器内容批次**上（`BuildContainerContentsBatch(playerId)` 末尾追加一条），
  因此自动获得"背包命令执行后重发"的时机；"客户端主动请求容器内容"这条路径也必须带玩家上下文
  （它是最可靠的下发时机，早于处理器注册的推送会丢）；
- **客户端应用时先清空再重建**：镜像是权威状态而不是增量，服务器取下的装备必须真的消失；
- **不注册进容器注册表**：它不参与任何命令，装备变更仍然走装备命令（服务器权威）。

**② 弹药数下行：HUD 弹匣第一次会动**

客户端不推进武器（扣弹、换弹全在服务器算），但开火事件原先**不带弹匣数**，
HUD 的弹药数永远停在收到装备的那一刻。

- 服务器：`OnCombatFired` 填 `MagazineAmmo`（`ServerCombatCoordinator.TryGetMagazineAmmo`）；
  **取不到时用 `-1` 哨兵**（AI 射手没有玩家弹匣，写 0 会被显示成"打空了"）；
- 客户端：`KindFired` / `KindReload` 事件里**仅当来源是自己**时把弹匣数应用到本地
  `WeaponRuntime.SetMagazineAmmo`（越界值夹取，网络乱序不抛异常）。

**③ 两条保活规则：暂停、结算、无人局都不许停网络**

排查里反复出现同一个坑：**"界面暂停世界"被顺手做成了"网络也停"**，10 秒后被 NGO
协议超时踢下线（`ProtocolTimeout`）。两条规则从此固定：

1. **上行节拍用未缩放时间**（`TickMultiplayerClient(Time.deltaTime, Time.unscaledDeltaTime)`），
   **时间冻结期间（`Time.timeScale <= 0`）只发零输入**——发包的唯一目的是保活，
   界面上残留的按键状态绝不能变成服务器上的移动或开火（`StepAndSendInput` / `SendInputToServer`）；
2. **快照到达节拍就发**，哪怕这一批里**没有玩家**（战局结束、全员已离开世界）：
   `MovementServerWorld.TryCaptureSnapshots` 用 bool 返回"是否到达节拍"而不是"玩家数"，
   调用方据此继续下发空批次；敌人快照在没有玩家时不发。

**本次留下的诊断**（可直接从外部观测，不必翻日志）：

- 客户端 `SceneBootstrap.SentInputCount`（真正上行的包数，含每 600 包一条的进度日志）

### 26.2 世界模型：服务器"现在托管哪张图"

新增 `ServerWorldKind`（None / SafeHouse / Raid）作为**唯一判据**，它决定"哪些系统该活着"：

- **安全屋世界**：只有移动碰撞（玩家能走动、能被墙挡住）。**不烘导航**、不建战利品容器、
  不收集撤离点、不建 AI——这些系统在安全屋里跑起来只会制造"这里怎么会有战局数据"的困惑；
- **战局世界**：导航网格、战利品容器、撤离点、AI 全部重建一次（它们的惰性初始化原先假设
  "一张图一整局"，服务器开始切图之后这个假设不再成立）；
- **切换是两阶段的**：`SceneManager.LoadScene` 要到本帧稍后才生效，因此先作废旧世界
  （把人撤出权威世界、注销场景容器、停 AI、丢导航），等目标场景成为活动场景之后
  再执行"世界就绪"回调（开局 / 回屋）。`SceneRuntime.World.TickWorld()` 是唯一的检查点。

**为什么切图时必须显式注销场景容器**：容器编号是"地图里第 i 个生成点"，
换图之后同一个编号指向别的东西（或什么都不指向）。不注销的典型症状是
"第二局搜到的还是上一局的箱子"。

### 26.3 移动链路下沉：安全屋与战局共用一份实现

安全屋没有战斗、没有搜刮、没有 AI，但它有**移动**——而移动恰恰是联机里规则最密的一块。

因此把 `SceneBootstrap` 里的移动部分整体下沉为 `MultiplayerMovementLink`（两个文件，
上行 / 快照各一个），战局与安全屋各持有一份实例：

- **上行与预测**：固定步 60 Hz、一帧最多补 4 步、冻结（`timeScale <= 0`）时只发保活零输入；
- **快照**：本机按速度取容差对账（P-45 的规则）、远端玩家进插值缓冲（延迟 0.1 秒）；
- **通道归属是静态的**：网络连接由大厅会话跨场景持有，而"移动快照"这个处理器名只有一个。
  场景切换的顺序是「新场景 Awake（注册）→ 旧场景 OnDestroy（退订）」，
  旧场景若无条件退订就会把新场景刚注册的处理器删掉——症状是"进图后队友与敌人全都不动"。
  因此退订前必须确认"我是不是当前持有者"（这条规则从战局侧推广到了两个场景）。

**顺手修掉的一处旧缺陷**：打开背包 / 结算时，本地意图被清了、但**待上行意图**没有清，
于是服务器会继续按上一帧的方向移动玩家（客户端原地不动、每次快照把它往前拉一下）。
现在两个场景统一走 `ClearLocalMovementIntent` / `ClearMovementIntent`（本地 + 上行 + 奔跑一起清，朝向保留）。

### 26.4 出口门禁的三层判定

| 层 | 位置 | 作用 |
| --- | --- | --- |
| 客户端提示层 | `SafeHouseUI.MapPanel` | 面板上直接写清楚"等房主 / 等队友回屋"，按键被拦时给一句人话 |
| 客户端请求层 | `SafeHouseBootstrap.Multiplayer.TryDeployFromSafeHouse` | 非房主、或房间不在等待阶段时不发请求 |
| 服务器权威层 | `TryStartRaidFromSafeHouse` → `AreAllMembersInSafeHouse` | 真正的判定：房主 + 房间等待中 + **每个成员都在服务器的安全屋世界里** |

服务器拒绝时回一条明确的失败结果（`LobbyError.StartRejected` + 中文原因），
客户端把它显示出来——玩家不会遇到"点了没反应"。

### 26.5 明确不做（边界，与 §25.3 一致）

- 仓库 / 商人 / 背包内容在 **P5 共享仓库**之前仍是各自的本机进度；
- 靶子与衣柜走本地表现层，不参与服务器判定；
- 玩家携带进图的装备仍由服务器按默认配发（P5 的装备同步范畴，见 §25.9）；
- 远端玩家外观仍复用本机选择的角色（每名玩家各自的外观属于大厅同步范畴）。

### 27.1 交付对照（§25.4 / §25.9 的边界逐条关闭）

### 27.2 几个关键设计点

**① 容器编号的三段式**：客户端只有 1/2/3（背包 / 弹药挂 / 仓库），
服务器上一人一份（1000+），而仓库是**全房间一个**（`ServerSharedStash = 5`）。
因此"命令里的 3 号容器"必须先翻译再执行（`TranslateContainerId`），
快照批次也要把共享仓库翻译回 3 号再发给每个客户端。

**② 共享仓库在文档级、账号进度在数组里**：撤离结算要同时改"仓库"和"钱包"，
放在同一个 JSON 文档里意味着**一次写入**——不会出现"装备没了、仓库也没有"的中间态。

**③ 新账号发一套基础装备**：`ServerStarterKit`（AK + 120 发）在建号时直接进**随身装备**，
新玩家进图就能打；撤离时又按规则入共享仓库，循环闭合。
它同时是"没有可用武器"时的兜底配发规格，两处共用一个来源。

**④ 联机下商店暂时关闭**：商店的一次交易要同时改"共享仓库"和"我的金币"，
两者现在都在服务器上（客户端那份只是镜像）。在它服务端权威化（记为 **P5.5**）之前，
联机里打开商店只会显示一份和服务器不一致的账，因此暂时关闭并提示；单机商店不受影响。

**⑤ 掉线宽限不是万能药**：宽限本身按设计工作（日志可见"保留其位置与背包 N 秒"，
重连接管有单测），但**"一人掉线，队友不受影响"在同机强杀进程的场景下达不到**：
实测表明强杀一个客户端后约 1 秒，其余客户端到服务器的**上行**会一起消失
（服务器侧全员 `ProtocolTimeout`，而服务器既没有发送错误、也没有传输层故障事件）。
完整取证、被证伪的旧假设与下一步路线见排障手册 **P-51**（P-48 的续集）。
