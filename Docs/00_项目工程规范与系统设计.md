## 1. 项目定位

### 1.1 一句话描述

一款 **3D 斜俯视（45°）搜打撤（Extraction Shooter）** 单机 Demo：玩家携带装备进入地图，搜刮物资、与 AI 交火，在限时内抵达撤离点，将战利品带回仓库用于变卖、改装与接取任务。

### 1.2 目标用途

| 项目 | 说明 |
| --- | --- |
| 主要用途 | **2027 届秋招「Unity 开发岗」求职作品集** |
| 次要用途 | 面试讲解材料（架构、取舍、踩坑记录） |
| 评价重心 | **系统完整性、代码质量、工程规范、可扩展性** |
| 非评价重心 | 美术表现、内容体量、玩法创新度 |

### 1.3 对标基线（重要：所有设计取舍的参照系）

**唯一对标游戏：《逃离鸭科夫》（Escape from Duckov）。**

本项目**不是**《逃离塔科夫》的仿制，两者在玩法和情绪上差异显著。明确这一点是必要的：缺失参照系会导致设计决策不自觉地滑向塔科夫，从而引入与本项目不符的复杂度（本阶段的移动系统设计曾因此出现偏差，详见本文档 7.12 节的记录）。

| 维度 | 《逃离塔科夫》 | **《逃离鸭科夫》（本项目对标）** |
| --- | --- | --- |
| 对抗对象 | PvP 为主，残酷博弈 | **PvE 为主**，玩家对抗 AI 与资源压力 |
| 紧张感来源 | 对枪、穿甲计算、被蹲守 | **贪心与撤离时机**：再搜一个箱子还是现在跑 |
| 死亡代价 | 极高，装备全丢 | 相对宽容，可重复尝试 |
| 射击手感 | 拟真，有大量惩罚项 | **爽快、宽容**，射击本身不是精密博弈 |
| 美术风格 | 写实硬核 | **卡通鸭子**，轻松诙谐 |
| 装备系统 | 拟真的护甲等级与穿透力 | **装备等级驱动成长**，直观可读 |
| 撤离点 | 条件严苛，位置隐蔽 | **相对友好**，无需钥匙 |

**由此推导出的核心设计原则（必须遵守）：**

1. **一切系统服务于"贪婪循环"**，而不是模拟真实。判断一个功能该不该做，标准是"它是否让玩家更纠结于要不要多拿一件东西"。
2. **不引入仅服务于拟真的复杂度。** 拟真项（真实弹道、复杂穿甲公式、呼吸抖动）一律不做，除非它直接强化贪婪循环。
3. **射击体验偏向爽快。** 不设计惩罚玩家枪法的系统。
4. **表现可以轻松诙谐。** 卡通风格不只是美术选择，也允许玩法层面出现夸张与幽默。

### 1.4 定位推导（为什么是这个品类）

- 该品类是**系统驱动**而非美术驱动：招聘方考察的是数据结构、状态管理、UI 交互、AI 逻辑与存档，美术粗糙不构成减分项。
- 复刻对象是**成熟玩法**，无需自行发明玩法创意，全部精力可投入系统实现深度。
- 斜俯视视角在保留 3D 场景、寻路、视线遮挡、弹道判定等硬核系统的前提下，**将角色动画需求压至最低**（仅需朝向旋转 + 简单步进），是"最小美术换取最大系统深度"的最优解。

### 1.5 项目成功的判定标准

项目完成时必须同时满足：

1. **闭环完整**：主菜单 → 配装 → 进入战局 → 搜刮/交火 → 撤离或阵亡 → 结算与仓库更新 → 再接任务 → 再次进入战局，全流程无断点。
2. **系统可信**：物品/背包/弹道/护甲/AI/存档六大系统的行为符合玩家直觉，不出现"看起来像玩具"的破绽。
3. **代码可讲**：任意核心系统都能支撑 5 分钟以上的面试讲解，且能回答"为什么不那样做"。
4. **零环境依赖**：他人克隆仓库后，用指定 Unity 版本打开即可运行，无需任何手动配置或绝对路径调整。

## 3. 工程约束：禁止绝对路径（强制）

这是**红线级约束**。所有源码与配置必须可移植，克隆到任意机器、任意盘符、任意用户目录下都能直接运行。

### 3.1 禁止事项

以下写法在**任何 `.cs`、`.asset`、`.json`、`.md` 文件中都不允许出现**：

```text
❌ D:\SomeProject\Assets\Data\items.json
❌ C:/Users/SomeUser/...
❌ /Users/xxx/...
❌ "D:\\Games\\MyProject\\Builds\\game.exe"
❌ Application.dataPath + "/../../SomeAbsoluteThing"
❌ 在 UnityEvent / Inspector 字段里手填的绝对路径
❌ 在 Process.Start / File.Open 中拼接的绝对路径
```

### 3.2 正确做法对照表

| 场景 | ❌ 错误写法 | ✅ 正确写法 |
| --- | --- | --- |
| 读取工程内资源 | `File.ReadAllText("D:/proj/Assets/Data/x.json")` | `Resources.Load` / `AssetDatabase` / `Addressables` |
| 定位工程根目录 | 写死盘符 | `Application.dataPath`（其父目录即工程根） |
| 读取随包分发的文件 | 写死路径 | `Application.streamingAssetsPath` |
| 读写玩家存档 | `D:/save.json` | `Application.persistentDataPath` + `Path.Combine` |
| 读取配置文件 | `C:/config/balance.json` | `Application.streamingAssetsPath` 下的相对子路径 |
| 拼接路径 | `"D:/proj/" + name` | `Path.Combine(Application.persistentDataPath, name)` |
| 编辑器工具取资源路径 | 手写字符串 | `AssetDatabase.GetAssetPath(Object)` |
| 构建输出 | 写死输出目录 | 命令行参数传入，或 `BuildPipeline` 使用相对路径 |
| 文档中引用文件 | 绝对路径 | 仓库相对路径，如 `Assets/Game/Inventory/` |

### 3.3 分层校验机制（防回归）

仅靠自觉会漏，因此引入三道防线：

1. **EditMode 单元测试** `NoAbsolutePathTests`：扫描 `Assets/` 下所有 `.cs` 源码，用正则匹配 `[A-Za-z]:\\` 与 `[A-Za-z]:/` 形态的盘符路径，命中即测试失败。此测试在 CI 与本地提交前均可运行。
2. **代码评审清单**：每个模块完成时必须对照第 12 章《提交前检查清单》。
3. **CI 校验**（可选，见第 11.3 节）：GitHub Actions 中静态扫描仓库内所有文本文件。

### 3.4 Unity 版本与包的声明方式

- Unity 版本通过 `ProjectSettings/ProjectVersion.txt` 声明，**不在文档与代码中写编辑器安装路径**。
- 第三方包通过 `Packages/manifest.json` 的**包名 + 语义化版本**声明，例如 `com.unity.cinemachine: 3.1.7`，**不写包缓存目录**。
- 任何"需要手动操作编辑器"的步骤，必须改写为脚本或 `Editor` 菜单命令，避免依赖个人环境。

### 4.4 美术方向与素材技术标准（卡通风）

决策 D-16 确定美术风格为**卡通风（Cartoon / Stylized）**。这不只是"选好看"的问题，它直接决定了材质与光照的技术路线，必须在 M7 替换素材前明确。

**风格定位：**

| 维度 | 标准 | 说明 |
| --- | --- | --- |
| 造型 | 低多边形（Low-poly），硬边为主 | 面数低、轮廓清晰，在斜俯视下有良好的可读性 |
| 上色 | 平涂 + 大色块，sRGB 明度高 | 避免写实 PBR 的复杂贴图（法线、粗糙度、金属度） |
| 描边 | 可选，使用 URP Renderer Feature 做背面外扩描边 | 卡通感的关键增益项，但需评估性能 |
| 光照 | 简洁主光 + 环境光，弱化阴影真实度 | 斜俯视下阴影主要用于表现高低差，而非写实 |
| 材质 | **URP Lit 简化配置** 或 **Shader Graph 自定义卡通着色器** | 替换素材时禁止直接使用资源包自带的内置管线材质 |
| 比例 | 角色与道具适当夸张（头身比、道具体积） | 俯视角下小物件需要放大才看得清 |

**素材技术标准（M7 替换时的验收条件）：**

| 项目 | 标准 |
| --- | --- |
| 文件格式 | `.fbx`（优先）或 `.unitypackage` |
| 绑定 | 人形角色需 Humanoid 骨骼（便于复用动画）；静态道具无需绑定 |
| 动画 | 优先选择"动画与模型分离"的资源包，便于交叉复用 |
| 贴图 | 尺寸 ≤ 2K；卡通风格优先使用小尺寸色块贴图或纯色材质 |
| **管线兼容** | **必须是 URP 兼容，或能安全转换**（内置管线材质需转 URP，存在转换失败风险） |
| 授权 | 允许商用与公开演示；有署名义务的必须登记到素材来源清单 |

**必须建立的配套文档：`Docs/Assets/素材候选清单.md`**

该文档由 Codex 调研产出，项目负责人最终挑选。清单中每个来源必须包含：

`名称 / 网址 / 许可证 / 是否需注册登录 / 文件格式 / 内容类别 / 是否卡通风格 / 适用性评分 / 一句话评价`

并额外包含两个专节：

1. **许可有坑清单**：标明不可用于公开作品集的常见来源与具体原因
2. **推荐组合**：若只选 4~6 个来源覆盖全部类别，推荐哪几个及理由

> 素材合规是作品集的红线：求职作品会公开传播，授权不明的素材可能在背景调查或后续使用中造成问题。本项目延续既往项目建立素材来源清单的合规习惯。

## 5. 代码规范

> 基准：Unity 官方 C# 编码风格 + Microsoft .NET 命名约定。所有规则以"新人接手 5 分钟能读懂"为目标。

### 5.1 命名约定

| 元素 | 规范 | 示例 |
| --- | --- | --- |
| 命名空间 | `ProjectName.模块名` | `RaidDemo.Combat` |
| 类 / 结构体 / 枚举 | PascalCase | `InventoryGrid`、`DamageType` |
| 接口 | `I` + PascalCase | `IPathfindingService`、`ISaveSerializer` |
| 方法 | PascalCase，动词开头 | `TryAddItem(...)`、`CalculateDamage(...)` |
| 公开属性 | PascalCase | `public int CurrentAmmo { get; }` |
| **可序列化私有字段** | `m_` + PascalCase | `[SerializeField] private float m_MoveSpeed;` |
| **私有实例字段（非序列化）** | `m_` + PascalCase | `private InventoryGrid m_Grid;` |
| 私有静态字段 | `s_` + PascalCase | `private static EventBus s_Bus;` |
| 常量 | PascalCase | `private const int MaxStackSize = 99;` |
| 局部变量 / 方法参数 | camelCase | `var itemCount = 0;` |
| 事件 | PascalCase（过去式语义更佳） | `public event Action<ItemInstance> ItemAdded;` |
| 异步方法 | `Async` 后缀 | `LoadRaidAsync(...)` |
| 泛型参数 | `T` + 语义 | `TDefinition`、`TState` |
| ScriptableObject 资源类 | `XxxDefinition` | `ItemDefinition`、`AmmoDefinition` |
| 运行时状态类 | `XxxInstance` / `XxxState` | `ItemInstance`、`RaidState` |
| 枚举值 | PascalCase，**显式赋值** | `Patrol = 0, Investigate = 1, Engage = 2` |

**`m_` 前缀的适用边界**：仅用于**字段**（含 `[SerializeField]` 字段）。局部变量、方法参数、属性、常量、枚举值一律不加前缀。C# 属性（Property）用 PascalCase 且无前缀，以符合 .NET 惯例。

### 5.2 代码组织规则

| 规则 | 数值 / 说明 |
| --- | --- |
| 一个文件一个类型 | 主类型与文件名一致；内部辅助类型允许同文件但需 `private` 或 `internal` |
| 单文件行数上限 | **400 行**（超过即拆分，测试文件除外） |
| 单方法行数上限 | **50 行**（超过即提取私有方法） |
| 方法的参数个数 | 建议 ≤ 4；超出时参数封装为 `XxxContext` 结构体或配置对象 |
| 嵌套层级上限 | 4 层（含 `if`/`for` 等）；超出即提前 `return` 或用卫语句（Guard Clause） |
| 魔法数字 | **禁止出现**，一律提取为常量或配置字段 |
| `region` 使用 | 不强制，但不允许嵌套 `region` |
| 字段可见性 | 默认 `private`；需要 Inspector 暴露用 `[SerializeField] private`，而非 `public` 字段 |
| 字符串标识 | 数据用**稳定字符串 ID**（如 `weapon.rifle.ak74`），禁止用枚举序号或数组下标做持久化键 |
| 时间与帧 | 逻辑时间用 `Time.deltaTime`；固定步长逻辑用 `Time.fixedDeltaTime`；禁止在 `Update` 中写死秒数 |
| 随机数 | 统一走 `IRandomProvider` 抽象，便于测试时注入固定种子；禁止直接散落 `UnityEngine.Random` |

### 5.3 注释规范（D-06：丰富详细）

**核心原则：注释解释「为什么」，代码解释「是什么」。** 允许并鼓励较长的说明性注释，但不允许用注释复述代码。

**必须写注释的场景：**

1. **所有 `public` / `protected` 成员**：必须写 XML 文档注释，含 `<summary>`，参数与返回值用 `<param>` / `<returns>`。
2. **非直觉的算法与公式**：如护甲穿透公式、战利品权重抽取，必须写清推导过程与数值来源。
3. **数值常量**：每个可调参数旁注明量纲、合理区间与调参影响。
4. **状态机 / 事件流的时序说明**：描述"谁在什么条件下触发什么"。
5. **绕坑而行的写法**：必须写明"如果不这样写会出什么问题"。
6. **TODO / FIXME**：统一格式 `// TODO(模块名): 待办内容 —— 原因`，便于全局检索。

示例：

```csharp
/// <summary>
/// 视野锥的水平张角（度）。
/// 数值来源：参考同类俯视角射击游戏，60° 在斜俯视下既能形成明确的"被发现"反馈，
/// 又不会让玩家觉得 AI 背后长眼。超过 90° 会显著提高潜行难度，不建议上调。
/// </summary>
[SerializeField, Range(30f, 120f)] private float m_VisionAngle = 60f;
```

**禁止的注释：**

- `// i++`（复述代码）
- 注释掉的死代码（交由 Git 保存历史）
- 与实现不符的过期注释（改代码必须同步改注释，视为同等工作量）

- 低层程序集**禁止**引用高层（例如 `Data` 绝不允许 `using RaidDemo.UI`）。
- UI 不承载业务逻辑：UI 只做"读取状态、发起请求、渲染"，所有规则判定留在对应业务程序集。
- 跨模块通信优先使用 **事件总线** 或 **接口注入**，禁止用静态单例到处 `GetComponent` 横向抓取。

### 5.6 程序集结构与「联机 + 热更新」的兼容要求

第 5.5 节的划分适用于**纯单机**项目。一旦引入 M9（联机）与 M10（热更新），程序集边界还必须满足以下**额外约束**——这些约束必须在 M0 建目录时就预留，否则 M9/M10 将需要大规模重构。

**约束一：业务逻辑与启动层分离。**

代码热更新的前提是"可热更程序集"与"不可热更启动层"严格隔离：

| 层 | 程序集 | 是否可热更 | 内容 |
| --- | --- | --- | --- |
| 启动层 Bootstrap | `RaidDemo.Bootstrap` | **否** | 极薄：AOT 补充元数据加载、热更程序集加载、入口场景。**发布后几乎不再修改** |
| 业务层 HotUpdate | `RaidDemo.*`（Data / Inventory / Combat / AI / Raid / Meta / UI） | **是** | 全部游戏逻辑 |
| 共享层 Shared | `RaidDemo.Shared` | 否 | 客户端与服务端共用的纯数据契约、稳定 ID、与引擎无关的规则函数 |
| 服务端 Server | `RaidDemo.Server.*` | 否（构建期） | 服务端专用逻辑与入口 |

**约束二：共享层不得引用 UnityEngine 运行时类型。**

`RaidDemo.Shared` 被客户端与服务端同时引用；服务端以无头模式运行，不应依赖渲染相关类型。该层只允许包含：

- 纯 C# 数据结构（`readonly struct`、DTO、枚举）
- 稳定字符串 ID 常量
- 与引擎无关的数学与规则计算

> 这是"单一数据来源"原则的延伸：**一份规则代码，两端共用**。若客户端与服务端各写一份伤害计算，必然出现两端数值不一致的经典事故。

**约束三：逻辑层通过接口访问引擎能力。**

业务层若直接调用 `Physics.Raycast`、`NavMesh.SamplePosition` 等静态 API，将无法在服务端复用，也无法单元测试。一律通过接口注入：

| 接口 | 客户端实现 | 服务端实现 | 测试实现 |
| --- | --- | --- | --- |
| `IPathfindingService` | NavMesh 实现 | NavMesh 无头实现 | 网格假实现 |
| `IRaycastService` | `Physics.Raycast` | 服务端物理世界 | 预设结果的假实现 |
| `ITimeService` | `Time.deltaTime` | 服务端固定 Tick | 手动推进的假时钟 |
| `IRandomProvider` | 随机种子 | 服务端权威种子 | 固定种子 |

**约束四：状态变更必须有单一入口。**

这是一切的前提。所有玩家意图（移动、射击、拾取、丢弃）统一表达为**命令对象**（Command），经由统一入口执行：

```text
单机模式：  输入源 → CommandRouter → 本地执行
联机模式：  输入源 → CommandRouter → 网络发送 → 服务端执行 → 状态回传
```

`CommandRouter` 是唯一的执行入口，两种模式共用同一套规则代码。**这条约束在 M1 写移动逻辑时就必须遵守**，它是 M0 阶段最容易被忽略、事后代价最高的设计。

## 6. 架构设计

### 6.1 分层模型

采用**五层架构**，每层职责单一，上层可依赖下层，下层通过事件向上层广播（而非直接调用）。

| 层 | 名称 | 职责 | 禁止事项 |
| --- | --- | --- | --- |
| L5 | Presentation 表现层 | 渲染、动画、音效、VFX、UI 显示 | 禁止包含任何数值计算与业务判定 |
| L4 | Interaction 交互层 | 输入采集、玩家意图解析、交互检测 | 禁止直接改数据，必须走请求 |
| L3 | Simulation 模拟层 | 战斗、AI、战局规则、时间推进 | 禁止直接操作用户界面 |
| L2 | State 状态层 | 背包、装备、仓库、任务、玩家进度 | 禁止依赖场景对象 |
| L1 | Data 数据层 | ScriptableObject 定义、运行时实例、存档 DTO | 禁止持有 Mono 对象引用 |

**依赖规则**：调用只能自上而下；数据变更后用事件自下而上广播。任何"下层直接抓取上层对象"的写法都视为架构破坏。

### 6.2 模块-职责矩阵

| 模块 | 核心类（规划） | 职责摘要 | 对外接口 |
| --- | --- | --- | --- |
| 基础 Kernel | `EventBus`、`ServiceLocator`、`TimerService`、`IRandomProvider`、`ObjectPool<T>` | 提供无业务的地基能力 | 静态入口 + 接口 |
| 数据 Data | `ItemDefinition`、`ItemInstance`、`ItemCatalog`、`LootTable` | 静态定义与运行时状态分离 | 查询接口 |
| 背包 Inventory | `InventoryGrid`、`InventoryContainer`、`EquipmentSlots`、`ItemPlacementService` | 网格占位、堆叠、旋转、冲突检测 | `TryPlace` / `TryMove` / `TryStack` |
| 战斗 Combat | `WeaponController`、`WeaponDefinition`、`AmmoDefinition`、`BallisticsSolver`、`DamageCalculator`、`ArmorPiece`、`Damageable` | 射击、弹道、穿透、伤害与护甲结算 | 请求-结果式 API |
| AI | `AISensor`、`AIBrain`、`IState<T>`、各状态类、`IPathfindingService` 实现 | 感知→决策→行动闭环 | 状态机对外只暴露 `Tick` |
| 战局 Raid | `RaidManager`、`RaidTimer`、`RaidSpawner`、`ExtractionZone`、`RaidResult` | 战局生命周期与胜负判定 | 事件广播 |
| 局外 Meta | `Stash`、`Trader`、`QuestSystem`、`EconomyService`、`SaveService` | 仓库买卖、任务、持久化 | 事件广播 |
| 界面 UI | `InventoryScreen`、`ItemSlotView`、`ItemTooltip`、`HudController`、`ResultScreen` | 展示与交互 | 订阅事件、发送请求 |

### 6.3 数据流示例（一次拾取）

```text
玩家按键 F
   │  L4 交互层：InteractionDetector 检测到附近 LootContainer
   ▼
UI 请求：InventoryScreen 调用 InventoryContainer.TryAdd(item)
   │  L2 状态层：InventoryGrid 做格子冲突检测，成功则写入
   ▼
事件广播：EventBus.Publish(new ItemAddedEvent(item, containerId))
   │
   ├──► L5 表现层：UI 刷新格子、播放拾取音效
   └──► L2 状态层：QuestSystem 检查"上交 X 物品"任务进度
```

**关键点**：拾取成功后**没有任何一处直接调用 UI 或任务系统**，二者都是事件订阅者。新增系统只需订阅事件，无需改动拾取代码 —— 这就是可扩展性的具体体现。

### 6.4 事件总线设计要点

- 事件类型定义为**只读结构体**（`readonly struct`），避免 GC 分配。
- 订阅/退订必须成对，统一在 `OnEnable` / `OnDisable` 中处理，杜绝跨场景悬挂引用导致的内存泄漏。
- 提供**事件调试面板**（编辑器下）：实时显示最近 N 条事件与订阅者数量，便于排查"事件发了但没人响应"。
- 单元测试中提供 `EventBus.Clear()`，保证测试间互不污染。

### 6.5 基础模块（Kernel）接入状态

M0 建立了 6 个基础模块。**它们不一定都被当前代码用到**——有些是为后续里程碑预埋的。

把接入状态明确写出来，是为了避免两种误判：**以为没接入就是没用（于是删掉）**，
或者**以为已接入（于是又重复实现一遍）**。后者真实发生过：M3 首版的弹道绘制
自己另写了一个对象池，而 Kernel 里已经有一个。

| 模块 | 状态 | 接入点 / 未接入的原因 |
| --- | --- | --- |
| `EventBus` | **已接入（核心）** | 十五个文件订阅或发布；移动、背包、战斗三层之间的唯一通道 |
| `ServiceLocator` | **已接入（有限）** | 启动层注册四个服务；`PlayerMotor` 通过 `ServiceLocatorHolder` 取事件总线。其余服务由组合根直接持有，不经定位器 |
| `DeterministicRandom` | **已接入** | 武器散布与 `CombatWorld`；保证同一随机种子下射击结果可复现，这是射击能被自动化测试的前提 |
| `ObjectPool` | **已接入** | 弹道绘制（`TracerRenderer`）。全自动武器每秒打出十发以上，每发新建再销毁会产生明显 GC 压力 |
| `LogService` | **未接入** | 当前没有日志需求。等 M5 战局结算、M9 网络同步时才需要分级日志与上报 |
| `ITimeService`<br>`UnityTimeService`<br>`ManualTimeService` | **未接入（有意）** | 模拟层选择**显式传入 deltaTime**，这是更好的设计：确定性、可在服务端按固定步长重放。为了"用上这个服务"而改回隐式时间源是倒退。它为 M5 的战局计时器预留 |
| `IRandomProvider` | **未接入（有意）** | 当前随机数使用点很少，抽接口没有实际收益。M9 需要客户端与服务端用同一套随机序列时再抽 |

> **判断标准**：一个基础模块该不该接入，看的是"当前有没有真实需求"，
> 不是"既然做了就得用上"。**为将来的里程碑预埋、并如实写明为何现在不接，
> 比硬凑着接上更专业。**

## 7. 核心系统设计

### 7.1 物品系统

**静态定义与运行时状态严格分离**，这是整个项目最重要的数据设计。

| 类型 | 性质 | 内容 | 是否持久化 |
| --- | --- | --- | --- |
| `ItemDefinition`（ScriptableObject） | 静态、只读、共享 | 稳定 ID、显示名、图标、网格尺寸（宽×高）、重量、基础价值、稀有度、分类、堆叠上限、行为定义引用 | 否（随工程提交） |
| `ItemInstance`（普通 C# 类） | 运行时、每份物品独立 | 引用 `ItemDefinition`、当前数量、耐久度、弹药余量、已装配件列表 | 是（写入存档） |

```csharp
/// <summary>
/// 物品静态定义。所有同类物品共享同一份实例，禁止在运行时修改本对象上的任何字段。
/// 若需要"这份物品的当前状态"（剩余耐久、剩余弹药等），一律写入对应的 ItemInstance。
/// </summary>
[CreateAssetMenu(menuName = "RaidDemo/Data/Item Definition")]
public sealed class ItemDefinition : ScriptableObject
{
    // 稳定 ID：形如 "weapon.rifle.ak74"。存档只记录 ID 字符串，
    // 因此重命名显示名、调整图标、改数值都不会破坏旧存档。
    [SerializeField] private string m_Id;

    [SerializeField] private Vector2Int m_GridSize = new Vector2Int(1, 1);
    [SerializeField] private float m_WeightKg = 1f;
    [SerializeField] private int m_BaseValue = 100;
    [SerializeField] private int m_MaxStack = 1;
    [SerializeField] private RarityTier m_Rarity = RarityTier.Common;

    // 行为扩展点：弹匣、医疗包、钥匙等特殊逻辑以独立 SO 实现挂载，
    // 新增物品类型只需新增一个行为 SO，不需要改动 ItemDefinition 或背包代码。
    [SerializeField] private ItemBehavior[] m_Behaviors;
}
```

**扩展性关键：`ItemBehavior` 扩展点。** 弹匣（装填子弹）、医疗包（回血）、钥匙（开门）、任务物品（不可变卖）等特殊规则，各自实现为独立 ScriptableObject 子类，由物品系统在运行时按需派发。新增一类物品**零改动**地接入现有背包与交易系统。

### 7.2 背包系统

采用**网格背包**（塔科夫式格子拼装），而非列表背包。这是搜打撤品类的标志性系统，也是面试讲解的重点。

**必须支持的规则：**

| 规则 | 说明 |
| --- | --- |
| 占用检测 | 物品按 `GridSize` 占用矩形区域，任一格被占用即冲突 |
| 旋转 | 支持 90° 旋转（宽高互换），旋转后重新做占用检测 |
| 堆叠 | 同 ID 且未达 `MaxStack` 时合并；拆分时允许指定数量 |
| 快速移动 | 支持"快速转移"（在背包/装备/容器之间一键搬运） |
| 自动整理 | 按尺寸或分类重新排列，`O(格子数)` 复杂度 |
| 边界与嵌套 | 背包中的背包（容器嵌套）—— 规划为**有限深度**（≤2 层），避免无限递归 |
| 拖拽约束 | 拖拽期间实时预览合法/非法（高亮绿/红） |
| 专用容器 | 容器可限定只接受某一分类的物品。**弹药挂**（一行五格、只收弹药）即由此实现，不需要专属代码 |

**装备栏与随身容器（M2 实现、M3 扩充）：**

| 位置 | 内容 |
| --- | --- |
| 装备槽 | 主武器、副武器、头盔、护甲、背包 |
| 主背包 | 5x5 网格 |
| **弹药挂** | **5x1 网格，只收弹药；换弹只从这里取弹**（见 7.3 节） |

**核心接口（规划）：**

```csharp
/// <summary>
/// 网格容器：以二维格子存储物品，负责占位规则与查询。
/// 本类**不涉及任何 UI**，可在单元测试中脱离场景直接构造和验证。
/// </summary>
public sealed class InventoryGrid
{
    /// <summary>尝试放置物品。失败时返回原因（越界/冲突/堆叠溢出），调用方据此给出 UI 反馈。</summary>
    public PlacementResult TryPlace(ItemInstance item, Vector2Int origin, bool rotated);

    /// <summary>尝试将物品移动到另一容器。这是拖拽与快速转移的共同入口，保证两条路径的规则完全一致。</summary>
    public TransferResult TryTransfer(ItemInstance item, InventoryGrid target, Vector2Int origin, bool rotated);

    /// <summary>查询指定格子上的物品。空格返回 null。</summary>
    public ItemInstance GetAt(Vector2Int cell);
}
```

> 设计要点：拖拽与"快速转移"**必须共用同一套规则代码**，否则极易出现"拖拽被拦、快捷键却塞进去了"的经典 bug。这就是上面 `TryTransfer` 存在的理由。

### 7.3 武器与弹道

俯视角下弹道表现力有限，因此**重点做规则而非视觉模拟**。

> **设计前提（见 1.3 节）**：本项目对标《逃离鸭科夫》，射击体验偏向爽快。
> 因此本系统**不做拟真弹道学**，所有机制都必须满足"玩家一眼能看懂"。

| 机制 | 设计要点 |
| --- | --- |
| 射击模式 | 单发 / 连发 / 全自动，由 `WeaponDefinition` 数据驱动 |
| 弹药 | 按口径分类，弹匣有容量；**换弹只消耗弹药挂中的对应弹药**，背包里的弹药必须先搬进弹药挂 |
| 弹道 | 采用**射线（Hitscan）**，不做下坠与风偏 |
| 后坐力 | 简化为"散布锥随连发扩大"，不模拟真实枪口物理 |
| 命中部位 | **简化处理，见下方说明** |
| 护甲 | **等级减伤模型**：护甲等级决定减伤强度，弹药穿透决定能否抵消该减伤 |
| 穿透 | 弹药穿透力与护甲等级比较，穿透足够则无视该层减伤（公式见下） |
| 射程 | 每种武器各自的射程决定子弹最远能飞多远；弹道**不会**在准星处截止 |
| 枪声 | **开火会产生噪音**，半径等于该武器的射程（手枪 8 米、步枪 12 米）。与命中无关：空枪一样会招人。AI 因此会被引向枪声来源（实现见 `Docs/Modules/04_AI.md` 第 17 节） |
| 切换武器 | 鼠标滚轮 / 数字键 1、2 在主武器与副武器之间切换；弹匣状态按武器分别保留（否则切枪等于免费换弹） |

**命中部位的处理方式（与塔科夫路线的重要区别）：**

塔科夫按头 / 胸 / 四肢精细划分伤害倍率，因为它的射击是精密博弈。
本项目改为**粗粒度两段式**：

| 部位 | 处理 |
| --- | --- |
| 普通命中 | 按基础伤害结算 |
| **暴击命中** | 按命中点与角色中心的高度差判定，触发额外伤害倍率 |

理由：斜俯视下玩家难以精确瞄准部位，精细倍率只会带来"数值不可解释"的困惑；
而粗粒度暴击既保留了"打头更疼"的直觉，又不要求玩家做像素级瞄准。

**护甲减伤公式（草案，数值待 M3 阶段调优）：**

```text
护甲等级护甲值 = 等级 × 10          （0 级 = 无护甲）
有效护甲值     = 护甲值 × (当前耐久 / 最大耐久)
穿透系数       = clamp((弹药穿透力 - 有效护甲值) / 护甲值, 0, 1)     // 无护甲时视为 1

最终伤害 = 基础伤害 × 部位倍率 × (1 - 减伤率 × (1 - 穿透系数))
护甲耐久 -= 基础伤害 × 护甲磨损系数
```

| 护甲等级 | 护甲值 | 减伤率 | 玩家感知 |
| --- | --- | --- | --- |
| 无 | 0 | 0% | 完全不防 |
| 1 级 | 10 | 20% | 轻甲，聊胜于无 |
| 2 级 | 20 | 35% | 常规配置 |
| 3 级 | 30 | 50% | 重甲，明显抗打 |
| 4 级 | 40 | 65% | 顶级装备 |

**这套模型为什么比塔科夫公式更适合本项目：**

1. **数值可读。** 玩家看到"3 级甲 50% 减伤"能立刻理解，而塔科夫那套概率击穿对玩家是黑箱。
2. **护甲会磨损但不会突然失效。** 耐久按比例降低减伤，而不是让护甲"咔嚓一下没了"。
3. **弹药选择有明确意义。** 高穿透弹药打重甲、高伤害弹药打无甲目标，两条路线都成立，且玩家能自己推断出来。

> 所有系数存放在 `AmmoDefinition` 与 `ArmorDefinition` 中，可独立调参而不改代码。

### 7.4 AI 系统

> **设计前提（见 1.3 节）**：本项目对标《逃离鸭科夫》，以 PvE 为主。
> AI 的设计目标是**制造资源压力与交火威胁**，而不是模拟军事级潜行对抗。
> 玩家已确认砍掉蹲下姿态（见 7.13 节），因此感知系统**不承担"潜行博弈"职责**。

**双轴设计：感知 + 决策。** 两者解耦，便于单独测试。

| 组件 | 职责 | 可测试性 |
| --- | --- | --- |
| `AISensor` | 视觉（视野锥 + 射线遮挡判定）、听觉（按移动**速度**给不同半径） | 逻辑集中在纯函数中，EditMode 可测 |
| `AISensesMemory` | 记录"最后已知目标位置"与"记忆衰减时间" | 纯数据结构，易测 |
| `AIPerceptionProfile`（SO） | 视野角度、视距、听觉半径、记忆时长等参数 | 数据驱动，便于调难度 |
| `AIBrain` | 状态机宿主，每帧 `Tick`；状态切换产生日志 | 支持注入固定随机种子 |
| `IState` / `StateMachine<T>` | 通用状态机，状态为普通 C# 类（非 MonoBehaviour） | **可完全脱离场景单元测试** |
| `IPathfindingService` | 寻路抽象，默认实现包装 NavMesh | 测试可注入假实现 |

**听觉的关键调整：按移动速度分档，而不是按姿态分档。**

蹲下姿态已被砍掉，因此噪音来源改为速度：

| 移动状态 | 噪音半径 | 设计意图 |
| --- | --- | --- |
| 静止 | 0 | 完全静默 |
| 步行 | 小 | 安全，但推进慢 |
| **奔跑** | **大** | **这才是本项目噪音系统的核心**：跑得快但把敌人引过来 |
| 负重超载 | 更大 | 贪婪的额外代价（见 7.12 节与 7.13 节） |

> 这条调整让噪音系统从"潜行工具"变成"**贪婪循环的反馈机制**"：
> 玩家越急着带着战利品撤离，就越容易把敌人引过来。这正是本项目需要的张力。

**AI 状态集（规划）：**

```text
Patrol      巡逻：沿路径点移动，低频扫描
   │ 看到目标 ──► Engage
   │ 听到动静 ──► Investigate
   │ 发现可疑目标 ──► Alert
   ▼
Alert       警惕：目标是可疑的（距离偏近但不够确定）——停下、转向、盯着看
   │ 观察满一段时间 ──► Engage
   │ 目标脱离视线 ────► Investigate
   ▼
Investigate 调查：前往声源/最后目击点，搜索四周
   │ 超时未发现 ──► Patrol
   │ 发现目标 ────► Engage
   ▼
Engage      交战：保持距离、射击、寻找掩体
   │ 血量过低 ──► Retreat
   │ 目标丢失 ──► Investigate
   ▼
Retreat     撤退：远离交火、使用治疗物品
   │ 血量恢复 ──► Engage
   ▼
```

> **实现时的修订（2026-09-11）**：上表的"看到目标"在落地时拆成了**两档**——
> 近身（≤6 米）为"必定发现"，中距离（6~9 米、且在视野锥内）为"警惕"，
> 视野锥收窄到 60°、听觉半径下调为步行 4 / 奔跑 10 / 超载 12 米。
> 改动的原因、推导与实测证据见 [`Docs/Modules/04_AI.md`](Modules/04_AI.md) 第 16 节。

> 状态用**普通 C# 类**实现而非 MonoBehaviour，是刻意的：这样 AI 决策逻辑可以在 EditMode 测试中"喂入一串感知输入，断言状态迁移序列"，而无需启动游戏。这是本项目 AI 可验证性的基础。

> **实现落位**：M4 完成后的文件清单、参数表、状态迁移细则与"文档 vs 代码"的差异记录见
> [`Docs/Modules/04_AI.md`](Modules/04_AI.md)。其中一处对本文的修正：`RaidDemo.AI` 不再引用
> `Unity.AI.Navigation`——寻路契约留在 AI 模块，NavMesh 实现放在表现层（与战斗层的 `IHitProbe` 同一做法）。

### 7.5 战局（Raid）流程

```text
主菜单 / 安全屋
      │ 选择装备、接受任务、准备出击
      ▼
加载战局：RaidManager.Initialize()
      ├─ 生成玩家与初始装备
      ├─ RaidSpawner 按配置生成 AI 与战利品容器
      └─ 启动 RaidTimer（倒计时）
      ▼
战局进行中：RaidPhase.Active
      ├─ 搜刮 / 交火 / 撤离点判定
      ├─ 玩家阵亡 ──► RaidPhase.Failed ──► 结算（丢失随身物品）
      ├─ 进入撤离区且满足条件 ──► RaidPhase.Extracting ──► 倒计时结束 ──► 成功
      └─ 时间耗尽 ──► RaidPhase.Failed
      ▼
结算：RaidResult 生成
      ├─ 存活奖励：经验、任务进度、带回的物品
      └─ 阵亡惩罚：丢失带入装备与战利品（保险箱内物品除外）
      ▼
回到安全屋：仓库更新 → 变卖/改装/接任务 → 再次出击
```

**撤离规则（已按对标基线调整）：**

| 规则 | 设计 | 与塔科夫路线的区别 |
| --- | --- | --- |
| 撤离点数量 | 2~3 个 | 相同 |
| **撤离门槛** | **主流撤离点无条件可用**，不要求钥匙或付费 | 塔科夫大量撤离点有严苛条件，本项目不做 |
| 读秒 | 进入撤离区后倒计时 10 秒，离开即中断并重置 | 相同 |
| 附加条件撤离点 | **最多 1 个**作为可选要素（例如需要携带特定物品） | 降级为可选，不作为主要机制 |

> 理由（见 1.3 节）：本项目的紧张感应来自**玩家自己的贪心决策**，
> 而不是来自"找不到撤离点"或"没带对钥匙"这类外部障碍。
> 撤离点应当友好且明确，让玩家能放心地多搜一会儿——然后再为这个决定承担后果。

撤离成功时弹出结算界面，展示：击杀数、搜刮物品清单与总价值、存活时长、
以及**本次出击的收支对比**（带入装备价值 vs 带出价值）——最后这项直接呼应贪婪循环。

**地图主题（已确认：工业区 + 集装箱仓库）：**

选择该主题的四条理由：

1. **空间可读性强**：集装箱与厂房形成天然的高低差与掩体，斜俯视下轮廓清晰，灰盒阶段用方块就能表达。
2. **格子化布局天然适配搜刮玩法**：集装箱彼此独立，可自然划分成"搜刮点"，玩家在箱子间穿插形成节奏。
3. **素材来源最充足**：Kenney 与 Quaternius 均有现成的工业/都市模块包，卡通低多边形风格普遍覆盖这一题材（见 `Docs/Assets/素材候选清单.md`）。
4. **风格统一**：与卡通低多边形美术方向天然契合，金属箱体采用大色块平涂即可出效果，不需要复杂贴图。

灰盒阶段的地图分区规划：

| 区域 | 玩法定位 | 灰盒表达 |
| --- | --- | --- |
| 集装箱堆场 | 主要搜刮区，视野开阔但有大量掩体 | 不同尺寸的箱体阵列 |
| 主厂房 | 室内近战交火，通道狭窄 | 长条形建筑 + 内部隔断 |
| 装卸平台 | 连接区，适合伏击 | 高台 + 坡道 |
| 外围围栏与出口 | 撤离点所在，撤离前的最后风险 | 围栏 + 开阔地带 |
| 地下管廊（可选） | 侧翼绕行路线 | 长通道 + 分支 |

### 7.6 局外系统（Meta）

> **设计前提（见 1.3 节）**：对标《逃离鸭科夫》，本项目的局外成长核心是
> **装备等级与收集**，而不是塔科夫式的拟真经济与保险体系。

| 子系统 | 最小可用范围 |
| --- | --- |
| 仓库 Stash | 比随身背包更大的网格容器，支持筛选、排序、快速变卖 |
| **装备等级系统** | **本项目的核心成长线**：装备分等级（1~4 级），等级越高属性越强；通过搜刮获得或商人购买 |
| **装备部位** | 头盔 / 护甲 / 背包 / 主武器 / 副武器；各部位独立等级与属性 |
| **收集进度** | 记录已获得过的物品种类，提供收集图鉴。收集品本身即目标，强化"再搜一个"的动机 |
| 商人 Trader | 至少 1 名，支持买卖、价格浮动（按稀有度倍数）、库存刷新 |
| 任务 Quest | 至少 2 个任务，目标类型：击杀 N 名敌人 / 上交 N 个指定物品 / 成功撤离 N 次 |
| 经济 | 物品价值 → 变卖收益 → 购买更高等级装备，形成循环 |
| 存档 | 玩家进度、仓库、装备、任务状态、收集进度、设置项 |

**不做的局外内容（Anti-Scope，见第 13 章与 13.1 节）：**

| 不做项 | 理由 |
| --- | --- |
| 保险系统 | 塔科夫式机制，依赖高死亡代价才有意义；本项目死亡代价较轻 |
| 拟真经济（动态供需、跳蚤市场） | 复杂度高且与"轻松搜刮"的基调冲突 |
| 复杂改装树 | 已推迟至 M7 之后（见 13.1 节 P-01） |

### 7.7 存档设计

**原则：显式版本号 + 稳定 ID + 抗篡改崩溃。**

```csharp
/// <summary>
/// 存档根对象。所有需要持久化的数据都必须挂在 SaveData 的子对象上。
/// 版本号用于后续存档迁移：当字段结构变化时，通过版本号判断是否需要转换，
/// 而不是让旧存档直接崩掉——这是"可长期维护"的必要成本。
/// </summary>
[Serializable]
public sealed class SaveData
{
    /// <summary>存档结构版本。任何破坏兼容性的字段改动都必须递增此值，并在迁移逻辑中补齐转换。</summary>
    public int SchemaVersion = CurrentSchemaVersion;

    public StashData Stash;
    public QuestData[] Quests;
    public PlayerProgressData Progress;
}
```

| 关注点 | 方案 |
| --- | --- |
| 序列化方式 | `JsonUtility`（IL2CPP 安全、无反射裁剪风险）；**不使用**依赖反射的第三方 JSON 库 |
| 存储位置 | `Application.persistentDataPath` 下的相对路径（见第 3 章） |
| 抗损坏 | 写入采用"写临时文件 → 校验 → 替换"，避免掉电/强退导致存档损坏 |
| 兼容性 | `SchemaVersion` + 迁移函数；读档失败时回退到上一次备份而非直接崩溃 |
| 可测试性 | 序列化与反序列化逻辑与文件 IO 分离，测试只验证"对象 → JSON → 对象"的一致性 |

### 7.8 UI 设计

| 界面 | 必备功能 |
| --- | --- |
| HUD | 血量、弹药、武器、负重、战局倒计时、准星、受击反馈 |
| 背包/装备界面 | 网格背包、装备槽、容器切换、拖拽/旋转/拆分、物品详情悬浮框、快速转移 |
| 战局内容器界面 | 搜刮容器（含搜索进度条，模拟塔科夫的"逐个翻找"） |
| 结算界面 | 存活状态、击杀数、搜刮物品列表与总价值、任务进度变化 |
| 安全屋界面 | 仓库、商人、任务面板、出击准备 |
| 通用组件 | `ItemSlotView`（可复用格子渲染）、`ItemTooltip`（详情弹窗）、`ModalDialog`（确认框） |

**UI 实现约定：**

- 使用 uGUI + **尽量少用 Layout 组件**（大量物品格子下 Layout 极其耗性能），网格由手写布局计算。
- 物品格子**必须对象池化**回收复用，滚动时不产生 GC 峰值。
- 所有界面走统一的 `UIScreen` 基类，负责显示/隐藏与输入焦点切换（打开背包时冻结射击输入）。
- UI 不直接持有数据对象；通过物品 ID 反查定义，避免 UI 与数据层的生命周期耦合。

### 7.9 服务端 / 客户端与联机架构（M9）

> 状态：**已采纳，排在单机闭环之后实施**。设计约束见第 5.6 节，决策依据见 `Docs/Decisions/ADR-001-服务端权威架构与Netcode选型.md`。

**范围界定（本项目的联机严格限定为）：**

| 项目 | 结论 |
| --- | --- |
| 玩法模式 | **PVE 合作**，2~4 名玩家共同对抗 AI |
| 拓扑 | **专用服务器（Dedicated Server）**，不做 Host-Client 反客为主模式 |
| 传输 | Unity `Netcode for GameObjects` 2.13.2 |
| **不做** | PVP、匹配系统、反作弊、账号体系、跨平台联机、服务器集群 |

**为什么不做 Host-Client？** 主机模式意味着一名玩家的机器同时是权威服务器，该玩家的延迟优势无法消除，且主机退出即全房崩。专用服务器是本项目要展示的正确工程实践——**服务端才是权威**。

**权威模型：**

```text
客户端（预测）                服务端（权威）              其他客户端
   │                             │                          │
   ├─ 采集输入（命令）──────────►│                          │
   ├─ 本地立即预测执行            ├─ 校验输入合法性           │
   │  （不等服务器，保证手感）    ├─ 在固定 Tick 上执行规则     │
   │                             ├─ 更新权威状态             │
   │◄──── 状态快照 / 增量状态 ────┤                          │
   ├─ 与预测结果比对              │                          ├─ 接收状态并插值
   ├─ 偏差超阈值 → 回滚重放        │                          │
   └─ 渲染（视觉插值）            └──────────────────────────┘
```

**状态同步的划分原则（这是网络代码最核心的区分）：**

| 类型 | 机制 | 适用内容 |
| --- | --- | --- |
| **持续状态** | `NetworkVariable`（自动同步，客户端按需插值） | 位置、朝向、血量、弹药数、战局倒计时 |
| **一次性事件** | `ClientRpc` / `ServerRpc` | 开火、命中、拾取、换弹、死亡、撤离成功 |
| **本体权威** | 服务端拥有 `NetworkObject` 所有权 | 玩家角色、AI、可交互物、掉落物 |

**延迟补偿策略（按实施难度递增，逐步做）：**

1. **客户端预测 + 回滚**：仅对玩家自身移动做预测，命中分歧时回滚重放输入队列。
2. **实体插值**：其他玩家与 AI 的位置按时间戳插值，避免抖动。
3. **攻击判定归一**：开火判定**只在服务端执行**，客户端仅播放表现。这是避免"客户端说自己打中了"的唯一可靠做法。

**服务端运行形态：**

- 以 `-batchmode -nographics` 无头模式运行，不加载渲染相关资源。
- 固定 Tick 频率（60 Hz），与第 5.6 节的 `ITimeService` 对接。
- 启动参数通过命令行传入，**不含绝对路径**（见第 3 章）。

**最小网络协议定义（M0 阶段先草案，M9 细化）：**

| 消息 | 方向 | 内容 |
| --- | --- | --- |
| `PlayerInputCommand` | C→S | 输入位、朝向、时间戳、序号 |
| `PlayerStateSnapshot` | S→C | 位置、朝向、血量、武器状态 |
| `FireCommand` / `FireResult` | C→S / S→C | 开火请求 / 命中结算结果 |
| `InventoryCommand` | C→S | 拾取、丢弃、移动、装填 |
| `RaidStateSync` | S→C | 战局阶段、剩余时间、撤离点状态 |

> **面试可讲点**：为什么开火判定不能放在客户端、预测与回滚在什么情况下会出错、如何用序号（sequence number）检测丢包——这些都是网络岗高频题，而这个项目能给出真实实现。

### 7.10 热更新系统（M10）

> 状态：**已采纳**。决策依据见 `Docs/Decisions/ADR-002-采用Addressables实现资源热更新.md` 与 `ADR-003-采用HybridCLR实现代码热更新.md`。

分两层实施，**资源热更是基础，代码热更是进阶**：

| 层 | 技术 | 可更新内容 | 平台限制 |
| --- | --- | --- | --- |
| 资源热更 | Addressables 2.10.3 | 贴图、模型、音频、预制体、**ScriptableObject 数据表** | 全平台 |
| 代码热更 | HybridCLR | 业务逻辑程序集（`RaidDemo.*`） | Windows 无限制；**本项目仅做 Windows 版，因此不受 iOS 审核政策约束** |

**资源热更流程：**

```text
[构建期] 标记 Addressable 分组 → 构建 Bundle → 生成 catalog → 计算哈希
                                  │
                                  ▼
                       发布到静态文件服务（本地 HTTP / GitHub Pages）
                                  │
[运行期] 启动 → 拉取远端 catalog → 与本地版本比对
              ├─ 有差异 → 下载增量 Bundle → 校验哈希 → 写入缓存
              └─ 无差异 → 直接进入
                                  │
                                  ▼
                  Addressables 从缓存加载资源 → 进入游戏
```

**关键设计点：**

- **数据表也走热更**：物品定义、掉落表、数值配置全部是 ScriptableObject 或 JSON，可通过资源热更调整数值，**不用重新发版**。这是本项目热更部分最有实用价值的体现。
- **`ScriptableObject` 的哈希与版本**：catalog 自带内容哈希，不需要自研比对逻辑。
- **断点续传与失败回退**：下载失败必须能用本地已有版本启动，不允许"更新失败导致游戏打不开"。

**代码热更流程（HybridCLR）：**

```text
[构建期] Bootstrap（AOT，不可热更）
              │ 启动时
              ▼
         加载补充元数据（AOT generic metadata）
              │
              ▼
         加载热更程序集（RaidDemo.*.dll）→ 反射调用入口
```

**演示方案**：热更包通过**本地 HTTP 服务器**或 **GitHub Pages / Release 附件**提供。将热更包托管在公开可达位置，可让任何克隆仓库的人**复现完整的热更流程**，这是把"我会热更"变成"你可以验证我会热更"的关键。

**写进 README 的架构说明（体现边界意识）：**

> 本项目仅面向 Windows 平台。代码热更方案（HybridCLR）在 Windows 上无平台限制；若未来移植到 iOS，受 App Store 审核政策限制，代码热更将不可用，届时需退化为仅资源热更 + 业务逻辑随包发布。

### 7.12 核心玩法支柱：贪婪循环

> 本节是**全部玩法系统的设计依据**。任何新功能都应先回答：它如何强化这个循环？
> 若回答不了，就应重新评估是否要做。

**循环的四个环节：**

```text
    ┌─────────────────────────────────────────────────┐
    │                                                 │
    ▼                                                 │
 [ 搜刮 ] 见到物资，判断价值与体积                       │
    │                                                 │
    ▼                                                 │
 [ 贪婪 ] 背包快满了，但那个箱子还没开                    │
    │                                                 │
    ▼                                                 │
 [ 负重 ] 越拿越重，跑得越慢、体力掉得越快、噪音越大        │
    │                                                 │
    ▼                                                 │
 [ 撤离 ] 赌一把再搜一个，还是现在就撤                    │
    │                                                 │
    └────────────► 带出的物资成为下次出击的资本 ──────────┘
```

**支撑该循环的系统映射：**

| 系统 | 如何服务贪婪循环 | 所属阶段 |
| --- | --- | --- |
| 网格背包 | 空间有限，逼迫玩家取舍"带什么" | M2 |
| 物品价值 | 提供取舍的量化依据 | M2 |
| **负重系统** | **把贪心的抽象代价变成可感知的物理代价** | M2 |
| 奔跑与体力 | 负重高时跑不动，撤离变慢 | M1 |
| AI 听觉 | 跑动与超载会引来敌人 | M4 |
| 撤离倒计时 | 制造时间压力，压缩"再搜一个"的空间 | M5 |
| 结算界面 | 用收支对比强化"这次贪对了还是贪错了" | M5 |
| 装备等级 | 带出的物资转化为更强的下次出击能力 | M6 |

**设计检验清单**（新增功能时对照）：

- [ ] 它是否创造了新的取舍，而不只是增加数值？
- [ ] 玩家能否在 3 秒内理解它的作用？
- [ ] 它是否让"要不要多拿一件"这个问题变得更难回答？

### 7.13 移动、体力与负重

> 本节记录移动姿态系统的最终决策。**该决策经历了一次修正**：
> 最初按塔科夫思路设计（保留蹲下、体力影响射击），在明确对标游戏后全部推翻，
> 修正过程记录在本节末尾，作为设计决策的实例。

**最终确定的移动系统：两档速度 + 体力资源。**

| 输入 | 行为 | 说明 |
| --- | --- | --- |
| `WASD` | 步行 | 基础速度，噪音小 |
| `Shift` | **奔跑** | 速度提升，持续消耗体力，噪音大 |
| 鼠标 | 瞄准 | 朝向与移动方向解耦（八向移动 + 独立瞄准） |

**明确砍掉的内容：**

| 内容 | 理由 |
| --- | --- |
| **爬下（Prone）** | 斜俯视下与尸体难以区分；战术价值低于实现成本；跨品类迁移价值低 |
| **蹲下（Crouch）** | 其价值主要来自潜行博弈，而本项目以 PvE 搜刮为核心，缺少该博弈空间 |
| 体力影响射击精度 | 属于塔科夫式惩罚机制，与本项目"射击爽快"的基调冲突 |

**体力系统设计（体力只作用于移动）：**

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| 满体力 | 100 | |
| 奔跑消耗 | 20 / 秒 | 约可持续奔跑 5 秒 |
| 行进速度 | 步行 3.5 / 奔跑 6.5（单位/秒） | 奔跑约为步行的 1.86 倍 |
| 常规恢复延迟 | 停止奔跑 1.5 秒后开始恢复 | 防止"跑一步歇一步"的抖动式操作 |
| 常规恢复速度 | 20 / 秒 | 约 5 秒回满 |
| **力竭恢复延迟** | **3 秒** | **显著长于常规延迟，这是力竭与"喘口气"的本质区别** |
| **力竭解除阈值** | **恢复到 30 才能再次奔跑** | 力竭状态是本系统的核心 |

**力竭机制的完整行为（M1 实现后确定）：**

```text
体力耗尽
   │
   ▼
进入力竭：无法奔跑，只能步行
   │  按住奔跑键也无效——这是刻意的，玩家必须主动停手
   │
   ▼
停手 3 秒（力竭恢复延迟）→ 体力开始以 20/秒 回升
   │
   ▼
体力回到 30（阈值）→ 解除力竭，恢复奔跑能力
   │
   └── 总恢复耗时约 4.5 秒
```

> **实现中发现的两个关键问题（已修正，记录备查）：**
>
> 1. **力竭期间若体力继续按常规延迟恢复，阈值规则会被绕过。** 玩家只要按住奔跑键，
>    体力就会自然涨过阈值并自动解除力竭，使"力竭阈值"形同虚设。因此引入了独立的
>    `ExhaustedRegenDelay`（3 秒），比常规延迟长一倍。
> 2. **若在力竭期间持续按住奔跑键，会出现"刚解除力竭又立刻力竭"的震荡。**
>    这是正确行为而非缺陷——体力一恢复到阈值就被重新抽干。它恰好惩罚了
>    "死按奔跑键不放"的操作，鼓励玩家在力竭时主动停手。

**体力与负重的耦合（M2 接入）：**

体力上限与消耗速率由配置对象提供，**负重通过修改该配置生效**，因此 M1 不需要知道负重系统的存在：

| 负重状态 | 体力上限 | 消耗倍率 | 噪音 |
| --- | --- | --- | --- |
| 轻装 | 100% | 1.0× | 基准 |
| 正常 | 100% | 1.2× | 略增 |
| 超载 | 75% | 1.6× | 显著增加 |

> 这条耦合让"贪心"有了物理后果：**装满战利品时，你既跑不快，也跑不久，还特别吵。**

**设计决策的修正记录（重要）：**

本系统最初按塔科夫路线设计，包含"保留蹲下"与"体力影响射击精度"两项。在项目负责人明确
对标游戏为《逃离鸭科夫》后，这两项被推翻：

| 原设计 | 问题 | 修正 |
| --- | --- | --- |
| 保留蹲下姿态 | 其价值来自塔科夫的潜行博弈，本项目的 PvE 搜刮循环没有该博弈 | 砍掉 |
| 体力影响射击精度 | 塔科夫用体力惩罚跑动中的射击，以服务 PvP 对枪平衡；本项目射击应爽快 | 体力只作用于移动 |
| 噪音按姿态分档 | 姿态被砍掉后该维度消失 | 改为按移动速度分档（见 7.4 节） |

**根因与预防**：该偏差的根因是文档缺少"对标基线"章节，导致设计决策在无参照系时
不自觉地滑向更知名的同类游戏。**现已补充 1.3 节作为强制参照，后续所有设计必须先对照该节。**

### 8.3 质量门禁

每次提交前逐项确认（详见第 12 章清单）：

## 11. 版本控制规范

> 现状：本工程**尚未初始化 Git 仓库**，M0 阶段第一件事就是完成初始化与忽略规则配置。

### 11.1 必须忽略的内容

`.gitignore` 使用 Unity 官方模板，核心忽略项：

```text
[Ll]ibrary/
[Tt]emp/
[Oo]bj/
[Bb]uild/
[Bb]uilds/
[Ll]ogs/
[Uu]ser[Ss]ettings/
*.csproj
*.sln
*.user
*.pidb
*.booproj
*.svd
*.apk
*.aab
*.unitypackage
*.app
```

**原因**：`Library/`、`Temp/` 是本地缓存（本工程该目录已达数百 MB 且含机器相关信息）；`.csproj` / `.sln` 由 Unity 自动生成，其内部含绝对路径，提交后会导致他人克隆即报错 —— 这与第 3 章的红线直接相关。

### 11.2 关于 `com.unity.pipeline` 包的处理

该实验包会在本地开启 HTTP 服务供自动化工具驱动编辑器，属于**开发期工具**：

| 项目 | 处理方式 |
| --- | --- |
| 是否写入 `Packages/manifest.json` | **否**（若已写入需在 M0 阶段移除，改为本地开发时按需安装） |
| 是否提交其生成文件 | **否**（端口文件位于 `Library/` 下，天然被忽略） |
| 是否影响构建产物 | 否 |

这样处理可保证：他人克隆项目后不会意外暴露一个本地 HTTP 端口，同时不影响本地开发效率。

### 11.3 Git 工作流

| 项目 | 规范 |
| --- | --- |
| 分支模型 | `main` 保持可运行；功能开发走 `feature/<模块名>`，完成后合并 |
| 提交信息 | 格式 `<类型>: <简述>`，类型含 `feat` / `fix` / `refactor` / `test` / `docs` / `chore` |
| 提交粒度 | 一次提交只做一件事；**每次提交必须可编译** |
| 大文件 | 若引入二进制美术资源，启用 **Git LFS** 并提交 `.gitattributes` 规则 |
| 行尾符 | `.gitattributes` 中统一 `* text=auto`，Unity 资产强制 `text eol=lf` |
| CI（可选） | GitHub Actions 配置 License 后运行 EditMode 测试 + 绝对路径扫描 |

### 11.4 README 必须包含的内容

README 是招聘方看到的第一份材料，必须包含：

1. 一句话项目简介 + 3~5 张截图或一段 GIF
2. **运行方式**：Unity 版本、克隆后打开步骤（不含任何本地路径）
3. 操作说明表（按键映射）
4. 已实现的系统清单（对应第 7 章）
5. 架构图（复用第 5.5 节的程序集依赖图）
6. 技术亮点 3~5 条，每条配"问题 → 方案 → 效果"
7. 素材来源与许可证清单（继承既往项目的合规习惯）
8. 已知限制（明确写出"未实现联机"等，体现诚实与边界意识）

## 13. 明确不做的事（Anti-Scope）

明确写出"不做什么"是为了防止项目在中期失控。以下内容**在本项目范围内不予实现**，仅在架构上预留扩展点：

| 不做的内容 | 理由 | 预留方式 |
| --- | --- | --- |
| **PVP 对战** | 需要延迟补偿与反作弊的完整方案，不适合个人项目周期 | 联机层已实现服务端权威，PVP 仅是玩法层扩展 |
| 匹配系统 / 账号体系 | 需要后端服务与运营成本 | 联机采用直连或局域网，无账号概念 |
| 反作弊 | 客户端无法自证清白，专业方案超出个人项目范围 | 服务端权威已消除最常见的作弊面 |
| 服务器集群 / 负载均衡 | 单局 2~4 人，单进程专用服务器足够 | 服务器入口已参数化，可水平扩展 |
| iOS / Android / 主机移植 | 项目仅面向 Windows（决策 D-15） | 逻辑层已与平台解耦，若移植则需重做输入与热更策略 |
| 真实弹道物理模拟 | 斜俯视下肉眼无法分辨，性价比极低 | 弹道计算已抽象为 `BallisticsSolver`，可替换实现 |
| 程序化地图生成 | 手搓 1 张地图质量更高且便于设计撤离点 | 生成逻辑与地图数据解耦 |
| 可破坏场景 / 真实物理门 | 做不好反而显廉价 | 交互系统留有 `IInteractable` 扩展点 |
| 大量武器与配件 | 内容量不是考察重点 | 数据驱动，扩充只需新增 SO 资产 |
| 移动端适配 | 项目仅面向 Windows（决策 D-15） | URP 已具备 `Mobile_RPAsset`，未来可切换 |
| **爬下姿态（Prone）** | 斜俯视下与尸体难以区分；战术价值低于实现成本（决策 D-20） | 姿态系统已抽象为枚举，如需可扩展 |
| **蹲下姿态（Crouch）** | 其价值主要来自塔科夫式潜行博弈，本项目 PvE 搜刮循环缺少该空间（决策 D-20） | 同上 |
| **体力影响射击精度** | 塔科夫式惩罚机制，与"射击爽快"的基调冲突（决策 D-21） | 体力数值已通过配置对象暴露，可接入任何消费方 |
| **拟真弹道（下坠、风偏）** | 与卡通 PvE 的基调不符，且斜俯视下无法感知 | 弹道计算已抽象，可替换实现 |
| **塔科夫式穿透概率模型** | 数值对玩家是黑箱，与"一眼看懂"原则冲突（决策 D-22） | 已改为等级减伤模型，见 7.3 节 |
| 完整成就/统计系统 | 超出闭环所需 | 事件总线可无侵入接入 |

| 模式 | 本质 | 适用阶段 | 在本项目中的用法 |
| --- | --- | --- | --- |
| **Default 模式** | 执行：AI 自主判断并直接推进，仅在必要时提问 | 全部实施阶段（M0–M8、M9、M10） | **默认工作模式**，不做额外的交互确认 |
| **Plan 模式** | 规划：只读探索，不修改任何文件，通过选项卡收集决策 | 重大架构开工前 | **M9 联机开工前必须使用一次**：网络同步频率、预测范围、权威边界、协议格式等十余项决策需逐项拍板 |
| **Goal（目标）** | 追踪：为跨多轮的长跑设定明确目标与完成判据 | 开始实施时设定，中途可调整 | 建议在 M0 开工时设定，并在每个里程碑完成时核对进度 |

**关键结论：三种模式不是三选一的关系。**

- Plan 模式管**权限**（能不能改文件），Goal 管**追踪**（做没做完），Default 是**默认执行态**。二者可叠加。
- 推荐流程：**Default 模式推进 + 设定明确目标**；遇到架构分叉（M9 前）临时切 Plan 模式评审一轮，评审完回到 Default 执行。
- **不需要**为了"先规划再执行"而特意进入 Plan 模式——本项目的规划已经通过文档（本文档 + ADR）落地，后续规划以增量形式补写文档即可。
