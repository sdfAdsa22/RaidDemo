# ADR-003：采用 HybridCLR 实现代码热更新

- 状态：已采纳
- 日期：2026-09-10
- 相关代码：`Assets/Game/Bootstrap/`（不可热更）、业务程序集（可热更）、M10 阶段构建流程

## 背景

资源热更（ADR-002）无法更新业务逻辑代码。本项目希望展示**代码热更新**能力——这是国内游戏行业（尤其 Unity 客户端岗位）的常见技术要求。

约束条件：

- Unity 6000.6.0f1
- 发行构建使用 IL2CPP（AOT 编译，不支持运行时动态生成代码）
- 业务逻辑需能独立于启动层更新
- 不得引入显著性能损耗

## 候选方案

| 方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 不做代码热更** | 仅资源热更 | 零风险 | 无法展示该能力；国内多数 Unity 岗位有此要求 |
| **B. ILRuntime** | 纯 C# 实现的解释器 | 不依赖 IL2CPP 支持，跨平台无差别 | 解释执行性能损耗较大；与主工程类型交叉调用需适配器 |
| **C. HybridCLR** | 补充 AOT 元数据 + IL 转换，使热更程序集以接近 AOT 的方式执行 | 性能接近原生 AOT；原生支持跨程序集调用；支持 iOS 外的全平台 | 需修改 IL2CPP 构建产物；构建流程有额外步骤 |
| **D. Lua / xLua 脚本层** | 逻辑写在 Lua 中 | 热更成熟、行业常用 | 需引入第二语言与绑定层；与用 C# 展示工程能力的目标冲突 |

## 决策

选择 **方案 C：HybridCLR**（通过 UPM Git URL 引入 `com.code-philosophy.hybridclr`）。

**平台范围**：代码热更仅适用于 **Android / PC**；iOS 平台仅启用资源热更。

## 理由

1. **性能接近原生 AOT**，不存在 ILRuntime 那种解释执行的持续损耗，对本项目 60 FPS 的性能预算友好。
2. **原生支持主工程与热更程序集之间的双向调用**，不需要编写大量适配器代码——ILRuntime 在这方面的开发成本是持续性的。
3. **国内行业实际使用率最高**，是面试中具备可讨论性的技术名词；而 Lua 方案会引入第二语言，与本项目用 C# 展示工程能力的定位冲突。
4. **与第 5.6 节的程序集划分天然契合**：只要坚持启动层极薄、业务逻辑独立程序集，接入成本主要在构建流程而非代码结构。

## 后果

**正面影响**

- 可在不发版的情况下更新业务逻辑，展示完整的资源加代码双层热更能力。
- 强制了启动层与业务层的严格分离，这是良好的工程实践。

**代价与后续待办**

- **启动层必须保持极薄且稳定**，一旦发布就不再修改；所有游戏逻辑都必须位于可热更程序集。
- 构建流程变复杂：需构建热更程序集 DLL、计算哈希、上传、生成版本清单。
- 构建产物体积与启动时间会有所增加，需在 M10 阶段实测记录。
- **iOS 限制必须写进 README**：App Store 审核政策不允许下载并执行变更应用功能的代码，因此 iOS 构建仅启用资源热更。
- 补充元数据（AOT generic metadata）需要按实际泛型使用情况配置，遗漏会导致运行时异常。

**风险控制**

- 代码热更排在 M10，晚于 M9。若时间不足可只交付资源热更，不影响单机与联机成果。
- M0 阶段就要建立启动层与业务程序集的目录划分，避免后期搬迁。
