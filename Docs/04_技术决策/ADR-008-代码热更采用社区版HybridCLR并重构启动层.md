# ADR-008：代码热更采用社区版 HybridCLR，启动层削薄与"带脚本资产进 Addressables"

- 状态：已采纳
- 日期：2026-09-15
- 相关文件：`Docs/03_模块设计/11_热更新与分发.md` 第 6 章、ADR-002（资源热更）、ADR-003（代码热更）、ADR-004（程序集划分）

## 背景

ADR-003 决定用 HybridCLR 做代码热更，M10 批次 0 按惯例先做兼容性与前提验证
（实际抓取官方文档与仓库数据，不依赖记忆）。验证推翻了两个原本写在计划里的前提：

1. **原计划**：启动层 `RaidDemo.Bootstrap` 继续引用全部业务程序集做组合根，
   靠 HybridCLR 的 **DHE（差分混合执行）** 让 AOT ↔ 热更之间的引用成立。
   **实际**：DHE 是**付费旗舰版**独有功能；社区版官方文档原文写着
   "**请不要在 AOT 程序集中引用热更新程序集，这会导致打包出错**"。
2. **原计划**：热更范围限定在"数据表 + 选定美术"，场景与角色资源留在本体。
   **实际**：挂在资产上的热更脚本要求该资产**必须以 AssetBundle / Addressables 打包**，
   挂在随主包资源上会 `scripting missing`。

同时验证了一个关键的好消息：HybridCLR 对"运行期用 `AddComponent` / `new` 创建的热更类型"
是任何时候都完美支持的；而本项目挂在随包资产上的 MonoBehaviour 只有 **13 个类型**
（涉及 2 张场景 + 15 个角色预制体 + 21 个数据表资产），其余 42 个类型全部是运行期创建。
这决定了搬迁规模是可控的。

另外的两个既有风险点（不影响本决策，但记录在案）：

- HybridCLR 官方版本映射表（`hybridclr_unity/Data~/hybridclr_version.json`）6000 系只有
  `6000` / `6000.3.x` / `6000.5.x` 三档，**没有 6000.6.x**；`il2cpp_plus` 仓库同样只有
  `6000-main` / `6000.3.x-main` / `6000.5.x-main` 分支。官方对此的说明是"会定期合并最新
  il2cpp，尚未合并时多数情况仍能工作；若不行，可先切到最近支持的小版本完成安装再切回"。
  → 批次 5 第一步固定为**可装性探针**。
- 本机 **Windows IL2CPP 模块未安装**（`WindowsStandaloneSupport/Variations` 下只有 mono 变体），
  需要 Unity Hub 补装（下载 270 MB / 安装 1.1 GB）。

## 候选方案

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **A. 启动层削薄 + 带脚本资产进 Addressables**（本决策） | 新建极薄 AOT 加载器 `RaidDemo.Host`；业务程序集整体进热更层；38 个带脚本资产进 Addressables | 唯一能同时保住"IL2CPP + 代码热更"两条价值的方案；搬迁量大头是资产分组与程序集移动，属机械工作，风险可枚举 |
| B. 购买 HybridCLR 旗舰版（DHE） | 用 DHE 支持 AOT ↔ 热更互调 | 付费；作品集项目要求他人可复现，不适合引入商业授权依赖 |
| C. 退回 Mono 后端 + `Assembly.Load` | 不做程序集重构，直接替换 DLL 演示 | 工作量最小，但失去 IL2CPP 场景的说明价值；Windows 发行也该是 IL2CPP |
| D. 只交付资源热更 | 放弃代码热更 | 与 ADR-003 目标不符；仅作为最终降级路径保留（ADR-003 风险条款） |

## 决策

选择 **方案 A**，具体三条：

1. **新建 `RaidDemo.Host`（AOT，极薄）**：只负责解析启动参数、加载热更 DLL、
   反射调用入口、失败兜底界面；发布后不再修改。
2. **业务程序集整体搬迁进热更层**：`RaidDemo.Bootstrap`（含 `SceneBootstrap` /
   `SafeHouseBootstrap` / `RaidFlowController` 等组合根）与 `Kernel.*` / `Shared` / `Data*` /
   `Simulation` / `Input` / `Presentation` / `Inventory` / `Combat` / `AI` / `Raid` / `Meta` /
   `UI` / `Diagnostics` 全部作为热更程序集构建为 DLL；边界严格单向（热更 → AOT 可以，反向禁止）。
3. **带热更脚本的资产进 Addressables**：2 张场景、15 个角色预制体、21 个数据表 `.asset`
   共 38 个资产必须入组（否则 `scripting missing`）；场景加载路径统一改为 Addressables
   （客户端与服务器共用同一加载抽象，服务器从本地 catalog 读取）。

配套纪律：

- 热更程序集要登记进 `HybridCLRSettings.HotUpdateAssemblyDefinitions`；
- **上线后热更程序集名不可更改**（assembly 列表在包内不可变）；
- 批次 5 先跑"可装性探针"（安装 → 生成 → IL2CPP 构建 → 加载 DLL → 补充元数据），
  结论无论成败都写回 `Modules/11_热更新与分发.md` 6.3。

## 理由

1. **社区版限制是硬约束，不是偏好**：AOT 不能引用热更程序集，那么"组合根必须和业务代码一起走热更"
   就是唯一自洽的分层；顺带把 ADR-004 早已写明的"启动层极薄"真正落实。
2. **清点数据支持搬迁可控**：需要特殊处理的只有 13 个类型 / 38 个资产，
   其余热更类型都是运行期创建，HybridCLR 官方明确支持。
3. **与既有架构同向**：项目从 M0 起就按"MonoBehaviour 只做装配、逻辑在纯 C# 层"组织，
   搬迁是"换地方"而不是"改写法"。
4. **连带收益**：地图（场景）与角色资源因此进入热更范围，与"数据表热更"一起构成
   完整的内容运营能力，面试讲解的完整度更高。

## 后果

**正面影响**

- 三层更新的边界完全自洽：AOT 只有加载器与第三方，其余全部可热更；
- 38 个资产的清单是**可枚举、可验证**的（脚本化清点，未来新增脚本会有据可查）；
- `RaidDemo.Host` 极薄带来一个额外好处：本体更新频率极低（只有加载器会进本体）。

**代价与后续待办**

- 批次 4 的 Addressables 分组范围扩大：必须包含场景组与角色组（不是可选项）；
- 场景加载需要统一改造为 Addressables 路径（含 M9 联机进图 / 回安全屋的流程）；
- 启动层搬迁涉及 173 个文件 / 约 3.5 万行代码的目录与 asmdef 调整（机械但量大的工作）；
- 如果探针判定 6000.6 不可用，按降级路径执行（临时 6000.5 安装 → 或 Mono → 或只交付资源热更）。
