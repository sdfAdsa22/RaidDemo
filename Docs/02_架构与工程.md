## 2. 分层模型

采用五层架构，每层职责单一：调用自上而下，数据变更后用事件自下而上广播。

| 层 | 名称 | 职责 | 禁止事项 |
| --- | --- | --- | --- |
| L5 | Presentation 表现层 | 渲染、动画、音效、VFX、UI 显示 | 不做数值计算与业务判定 |
| L4 | Interaction 交互层 | 输入采集、玩家意图解析、交互检测 | 不直接改数据，必须发请求 |
| L3 | Simulation 模拟层 | 战斗、AI、战局规则、时间推进 | 不直接操作用户界面 |
| L2 | State 状态层 | 背包、装备、仓库、任务、玩家进度 | 不依赖场景对象 |
| L1 | Data 数据层 | 定义资产、运行时实例、存档 DTO | 不持有 Mono 对象引用 |

"下层直接抓取上层对象"视为架构破坏。

一次拾取的数据流：

```text
玩家按键 F
   │  L4 交互层检测到附近容器
   ▼
UI/交互请求：InventoryContainer.TryAdd(item)
   │  L2 状态层：网格冲突检测，成功则写入
   ▼
事件广播：ItemAddedEvent
   ├──► L5 表现层：刷新格子、播放音效
   └──► L2 状态层：任务系统推进"上交 X 物品"进度
```

关键点：拾取成功后**没有任何一处直接调用 UI 或任务系统**，二者都是事件订阅者；
新增系统只需订阅事件，无需改动拾取代码。

## 3. 程序集划分

按模块切分程序集，依赖方向单向、低层不反向引用高层——这是可扩展性的核心保障。

```text
                      ┌──────────────┐
                      │  Tests.*     │（测试可引用全部）
                      └──────┬───────┘
   ┌──────────────┬──────────┴─────────┬──────────────┐
   │     UI       │        Raid        │     Meta     │  ← 顶层业务
   └──────┬───────┴──────────┬─────────┴──────┬───────┘
          │        ┌─────────┴─────────┐      │
          │    ┌───▼───┐            ┌──▼───┐  │
          │    │  AI   │            │Combat│  │
          │    └───┬───┘            └──┬───┘  │
          └────────►   Inventory   ◄───────  ─┘
                        │
                     ┌──▼───┐
                     │ Data │
                     └──┬───┘
                     ┌──▼─────┐
                     │ Kernel │  ← 最底层，不依赖任何业务
                     └────────┘
```

| 程序集 | 职责 | 允许依赖 |
| --- | --- | --- |
| `RaidDemo.Kernel.Pure` | 事件总线、服务定位、对象池、确定性随机 | 无 |
| `RaidDemo.Kernel.Unity` | 日志、时间服务 | Kernel.Pure |
| `RaidDemo.Shared` | 客户端 / 服务端共用的契约与纯规则 | Kernel.Pure |
| `RaidDemo.Data` / `Data.Content` | 定义资产与数据目录、物品与掉落规则 | Kernel.*, Shared, Data |
| `RaidDemo.Input` | 输入采集与意图转换 | Kernel.*, Shared, InputSystem |
| `RaidDemo.Inventory` | 网格背包、装备槽、移动规则 | Kernel.*, Shared, Data* |
| `RaidDemo.Combat` | 武器、弹道、伤害、护甲 | Kernel.*, Shared, Data*, Inventory |
| `RaidDemo.AI` | 感知、状态机、寻路契约、战术行为 | Kernel.*, Shared, Data*, Combat |
| `RaidDemo.Raid` | 战局生命周期、计时、撤离、生成 | Kernel.*, Shared, Data*, Inventory, Combat, AI |
| `RaidDemo.Meta` | 仓库、商人、任务、经济结算 | Kernel.*, Shared, Data*, Inventory |
| `RaidDemo.UI` | 界面与 HUD | 以上业务模块 + TextMeshPro |
| `RaidDemo.Bootstrap` | 极薄启动入口（热更边界，不参与热更） | Kernel.*, Shared |

硬性规则：

- 低层程序集禁止引用高层（例如 `Data` 不允许 `using RaidDemo.UI`）；
- UI 不承载业务逻辑，只做"读取状态、发起请求、渲染"；
- 跨模块通信优先事件总线或接口注入，禁止静态单例到处 `GetComponent`。

> 落地时的已知退化：`Kernel.Pure` 与 `Shared` 的 `noEngineReferences` 在当前引擎版本会导致
> 程序集不产出编译产物，"不引用引擎"这条约束改由代码评审与静态检查保证（记录在
> [ADR-004](04_技术决策/ADR-004-程序集划分方案.md)）。

### 3.1 为"联机 + 热更"预留的约束

这四条约束在 M0 建目录时就已预留，避免后来大规模重构：

1. **启动层与业务层分离**：`RaidDemo.Bootstrap` 极薄且不可热更，业务程序集整体处于可热更边界内；
2. **共享层不引用引擎运行时类型**：`Shared` 只允许纯 C# 数据与规则，客户端与服务端共用一份规则代码——
   若两端各写一份伤害计算，必然出现数值不一致；
3. **逻辑通过接口访问引擎能力**：`IPathfindingService`、`IRaycastService`、`ITimeService`、`IRandomProvider`
   在客户端、服务端与测试中各有实现，业务层不直接调用 `Physics.Raycast`、`NavMesh.SamplePosition`；
4. **状态变更单一入口**：所有玩家意图表达为命令对象，经 `CommandRouter` 执行：

```text
单机：输入 → CommandRouter → 本地执行
联机：输入 → CommandRouter → 上行 → 服务端执行 → 状态回传
```

## 4. 关键系统契约

### 4.1 物品与背包

- **定义与实例分离**：`ItemDefinition`（ScriptableObject）是只读资产，`ItemInstance` 持有运行时状态
  （耐久、弹药、堆叠数）；同型号两把枪不共享弹匣——这一条是自查发现共享状态问题后修正的；
- **网格背包**：`InventoryGrid` 负责占位、旋转、堆叠合并 / 拆分、冲突检测与自动整理；
- **稳定字符串 ID**：持久化只认 `weapon.rifle.ak74` 这类稳定 ID，禁止用枚举序号或数组下标做存档键；
- 细节见 [`03_模块设计/02_Inventory.md`](03_模块设计/02_Inventory.md)。

### 4.2 武器与战斗

- 命中判定用射线探针（`IHitProbe`），发射者自身碰撞体被显式忽略——修复"贴脸打到自己"的根因；
- 护甲采用**等级减伤模型**（1~4 级，20%~65%），可读性优先，不做塔科夫式穿透概率；
- 武器射程即枪声半径（手枪 8 米 / 步枪 12 米）：打不中一样会把 AI 引过来，这是"贪婪循环"的压力来源之一；
- 细节见 [`03_模块设计/03_Combat.md`](03_模块设计/03_Combat.md)。

### 4.3 AI

- **感知分档**：6 米内必定发现；6~9 米进入"警惕"（停下、转向、盯住约 3 秒）；听觉按移动档位
  （步行 4 / 奔跑 8 / 超载 12 米）与枪声半径触发调查；
- **状态机为普通 C# 类**：巡逻 / 调查 / 交战 / 撤退等状态不依赖 `MonoBehaviour`，
  可以在 EditMode 中"喂入感知序列、断言状态迁移"——这是 AI 可验证性的基础；
- **寻路契约与实现分离**：`IPathfindingService` 留在 AI 模块，NavMesh 实现在宿主层；
- 细节见 [`03_模块设计/04_AI.md`](03_模块设计/04_AI.md)。

### 4.4 战局

- 生命周期：进入地图 → 生成容器与敌人 → 计时推进 → 撤离成功 / 阵亡 / 超时 → 结算；
- 撤离点判定半径 3.5 米（比角色体积大得多，避免贴边反复进出）；
- 结算数据由服务器或单机规则侧计算：带出价值、击杀数、用时；
- 细节见 [`03_模块设计/05_Raid.md`](03_模块设计/05_Raid.md)。

### 4.5 局外经济与存档

- 仓库跨战局存活；撤离把战利品入库，阵亡、超时或强退则丢光随身物品；
- 商人固定价格（收购价为售价的 75%），五个固定任务串起长线进度；
- 单机存档为带版本号的 JSON；联机存档按账号存在服务器上，与单机互不兼容；
- 细节见 [`03_模块设计/06_Meta.md`](03_模块设计/06_Meta.md)。

### 4.6 联机

- **统一客户端 + 独立专用服务器**：单机模式 = 本机内嵌服务器，联机模式连远端；
  同一份客户端不区分单机 / 联机版本；
- **服务端权威**：位置、战斗、AI、掉落、容器、撤离计时、结算全部由服务器裁定；
  客户端只发送意图并做预测与表现；
- 预测与和解：快照回来后位置误差超容差才回滚重放；
- 断线自愈：服务器重建传输层 + 客户端自动重连；
- 服务端可视化：本机面板窗口 + 云主机 Web 状态页（房间、玩家、日志，写操作需管理口令）；
- 细节见 [`03_模块设计/10_联机.md`](03_模块设计/10_联机.md)。

### 4.7 热更新与分发

- **三层版本**：本体版本（启动器负责）+ 内容版本（Addressables）+ 协议版本（进房握手校验）；
- 更新流程：清单比对 → 增量下载 → 逐文件 SHA-256 校验 → 暂存 → 原子替换 → 失败回滚；
- 更新源支持本机 / 云主机 / 自定义切换，带 Web 面板与逐文件校验接口；
- 细节见 [`03_模块设计/11_热更新与分发.md`](03_模块设计/11_热更新与分发.md)。

## 5. 工程规范

目标：**新人接手 5 分钟能读懂**。核心条目：

| 规则 | 数值 / 说明 |
| --- | --- |
| 单文件行数上限 | 400 行（测试文件豁免），由 EditMode 测试强制 |
| 单方法行数上限 | 50 行（超过即提取私有方法；门禁在计划清单中） |
| 绝对路径 | 源码与配置禁止出现，由 `PathRulesTests` 扫描强制 |
| 魔法数字 | 禁止，一律提取常量或配置并注明量纲与合理区间 |
| 命名 | Unity 官方风格 + .NET 约定；序列化私有字段 `m_` 前缀 |
| 注释 | 公开 API 必须有 XML 注释；注释解释"为什么"，不复述代码 |
| 数据标识 | 持久化只用稳定字符串 ID，禁止枚举序号 |
| 随机数 | 统一走 `IRandomProvider`，保证可注入固定种子 |

提交前检查清单（节选）：无绝对路径、无 `Resources` 滥用、无运行时 `Find`、
公开 API 有注释、新规则有对应测试、无 `Debug.Log` 残留、无编译警告。

## 6. 测试与质量保障

测试目标不是覆盖率数字，而是**把容易算错的规则锁死**：

| 套件 | 类型 | 覆盖 |
| --- | --- | --- |
| 背包 / 掉落 / 伤害 / 状态机 / 经济 / 任务 / 存档 | EditMode | 规则边界、极端数值、往返一致性 |
| 移动仿真 / 战局计时 / 联机协议 / 热更清单 / 版本握手 | EditMode | 纯逻辑与协议函数 |
| AI 交战链路 | PlayMode | 视野触发巡逻转交战等场景集成 |
| 路径规范 | EditMode | 全工程源码不含绝对路径、不超行数上限 |

运行方式：命令行无头触发，**失败即视为该阶段未完成**——每个阶段结束时项目必须处于
"可编译、可运行、测试全绿"状态，不允许"半个功能"的长尾。

性能预算（目标值）：1080p 稳定 60 FPS、战中单帧 GC Alloc ≤ 0.5 KB、Draw Call ≤ 300、
同屏 12 个活跃 AI 不掉帧、背包界面打开 ≤ 50 ms。当前未做系统性的 Profiler 量测（列为已知边界）。

验收证据与实机矩阵见 [`05_测试与验收.md`](05_测试与验收.md)。

## 7. 范围边界

明确写出"不做什么"是为了防止项目中期失控；以下条目在架构上预留扩展点：

| 不做 | 理由 |
| --- | --- |
| PVP、匹配、账号体系、反作弊 | 需要后端与运营成本，超出个人项目周期；服务端权威已消除常见作弊面 |
| 服务器集群 / 负载均衡 | 单局 2~4 人，单进程专用服务器足够 |
| iOS / Android / 主机移植 | 项目仅面向 Windows；逻辑层与平台解耦，移植需重做输入与热更策略 |
| 拟真弹道、塔科夫式穿透概率 | 与"斜俯视 + 爽快射击"基调冲突，玩家无法感知 |
| 程序化地图、可破坏场景 | 1 张手搓地图质量更高，且便于设计撤离点 |
| 蹲下 / 爬下姿态、体力影响射击精度 | 价值来自塔科夫式博弈，与本项目 PvE 搜刮循环不符 |
| 大量武器与配件、成就 / 排行榜 | 内容量不是考察重点，数据驱动可随时扩充 |

主动推迟（设计认可、控制风险）的代表项：

| 推迟项 | 原因 |
| --- | --- |
| 完整武器改装树、多名商人 | 1 把武器 / 1 名商人即可验证链路，扩充即加数据 |
| 保险、钥匙门锁、天气昼夜 | 逻辑分支或美术成本高，1 张地图发挥不出价值 |
| AI 小队协同、AI 避让与编队、AI 掩体寻优 | 单体 AI 已能制造压力；先保证网络层与行为层不同时改动 |
| AI 使用医疗物品、AI 搜刮 | 依赖物品与容器系统，接口已收敛（`AiAgent.Heal` 等） |
| 难度曲线与 AI 数量动态调配 | 需要完整结算数据支撑，参数已数据驱动 |
