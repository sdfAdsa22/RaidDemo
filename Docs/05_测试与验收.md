# 测试与验收

> 本文汇总测试体系、实机验收矩阵与结论。原则：**测试的目标不是覆盖率数字，而是把容易算错的规则锁死；
> 每一轮验收发现的问题都必须修掉并回归，失败即视为该阶段未完成。**

## 1. 测试体系

| 层级 | 手段 | 覆盖内容 |
| --- | --- | --- |
| 规则单元测试 | EditMode（命令行无头运行） | 背包占位、堆叠拆分、掉落权重、伤害与护甲、状态机迁移、经济与任务、存档往返、联机协议、热更清单、版本握手 |
| 场景集成测试 | PlayMode | AI 视野触发交战、背包 UI 拖拽 / 双击 / 整理（用 Input System 测试夹具驱动真实界面） |
| 自动化验收脚本 | 独立 CLI | 启动器 13/13、更新源 17/17、版本握手 6/6、战局超时链路 5/5 |
| 实机验收 | 窗口客户端 + 无头机器人 | 单机 / 本地联机 / 云联机 / 启动器四条链路的全流程走查 |

可验证性的前提在架构里：移动仿真、战局计时、背包规则、AI 状态机都是普通 C# 类，
可以在不启动游戏的情况下断言行为；需要引擎生命周期的部分才放进 PlayMode。

规模随修复轮次增长：1.0.0 验收报告为 **692 项全绿**，1.0.2 轮为 **716 / 716 + PlayMode 8 / 8**，
此后继续增加到 700+ 项量级。

## 2. 实机测试矩阵

| 链路 | 测试范围 | 关键结论 |
| --- | --- | --- |
| 单机 | 主菜单 → 安全屋 → 商人购买 → 整备 → 出口选图 → 战局（搜刮 / 交火）→ 撤离 / 阵亡 / 超时 → 结算回屋 | 三条结局路径全部走通；结算清单与损失口径正确 |

| 云联机 | 云端部署、公网加入、版本握手、4 人完整局、存档保留、覆盖部署 | 公网全流程走通；旧客户端被拒并提示版本 |
| 启动器 / 更新 | 全量下载、增量更新、断点续传、原子替换、回滚、更新源面板、恶劣环境 | 逐文件校验 242 / 0 差异；游戏内热更真实下载并生效 |

## 3. 代表性验收结论

### 3.1 单机（1.0.0 验收轮）

- 主菜单 → 新游戏 → 安全屋 → 商人购买 → 武器入库 → 出击 → 战局：全链路 PASS；
- 撤离读条 10 秒 → 撤离成功结算；阵亡结算与超时结算各跑通，损失清单只列实际损失；
- 暂停菜单（返回主界面 / 返回桌面）与正常退出均验证，`Player.log` 无崩溃。

### 3.2 联机（1.0.0 ~ 1.0.2 验收轮）

- 2 人：进同一房间 → 共享安全屋互相可见 → 房主开图双人同图 → 同步移动 / 开火 / 换弹 PASS；
- 倒地与救援：倒地 60 秒窗口、超时死亡结算、队友扶起（1.0.7 轮端到端复验，恢复量正确）；
- 4 人局（2 实机 + 2 无头）：同房、同图、撤离入库全部通过；
- 服务端存档：账号金币、仓库、任务状态与客户端一致，覆盖部署后旧存档保留；
- 断线自愈：强杀客户端后自动重连回局，进度按账号恢复。

### 3.3 云联机（1.0.1 ~ 1.0.7 验收轮）

- 部署：Linux 专用服务器（含 glibc 兼容层）覆盖部署，状态页显示版本与在线信息；
- 2 人 / 4 人完整局：登录 → 建房 → 共享安全屋 → 进图 → 搜刮 / 交火 → 撤离或超时结算 → 回屋闭环；
- 分发负例：旧版本客户端被握手拒绝并提示双方版本号；
- 游戏内热更：客户端经更新源实际下载内容层并生效（M13-15 闭环）。

### 3.4 启动器与更新源

- 启动器验收脚本 13/13：全量安装、增量更新、断点续传、校验失败回滚、原子替换；
- 更新源面板 17/17：上传 / 发布 / 回滚 / 逐文件校验 / 鉴权；
- 云公网全量下载 157.9 MB / 15.4 秒（M10 验收值），本机与云更新源 `verify` 均 242 文件 / 0 差异；
- 更新源不可用时有明确失败提示（GUI 路径的"失败后旧版本仍可启动"仍挂在未覆盖清单）。

### 3.5 修复轮样例（问题 → 根因 → 回归）

| 问题 | 根因 | 回归方式 |
| --- | --- | --- |
| 联机退出后回不到主菜单（阻断） | 会话 `IsActive` 未排除"已主动断开"终态，重载安全屋时仍走直进分支 | EditMode 用例 + 本地 / 云两轮实机复验 |
| 服务器周期性卡顿 0.6~0.7 秒 | 10 万次 PBKDF2 口令哈希在服务器主线程同步执行 | 拆分后台线程计算 + 日志"口令校验 X ms（后台）"，全日志零卡顿 |
| 撤离读条圈"看着在圈里却不算" | 生成器把判定半径写成 2.0 米（默认 3.5） | 重生成场景 + 实机绕圈复验 |
| 进图瞬间位置回滚 | 两端出生位置在连接接管前不一致 | 共用出生布局预置位置，实机回滚重放 0 次 |
| 容器容量两端不一致 | 容器编号来自不稳定的查找顺序 | 按坐标排序的生成点编号，两端共用；警告归零 |

## 4. 未覆盖与已知边界

| 项 | 状态 |
| --- | --- |
| 100% / 200% DPI 档位回归 | 未覆盖 |
| "更新源不可用后旧版本仍可启动"的 GUI 路径 | CLI 已证，GUI 未取证 |
| 3~4 人交互边界（1.0.7 轮覆盖 2 人） | 部分覆盖：4 人链路在 1.0.2 轮通过，1.0.7 轮以 2 人复验 |
| 门禁负例（队友在战局中时房主禁止开图） | 规则层有测试，真人现场未覆盖 |
| 长时间稳定性（≥2 小时挂机） | 未覆盖 |
| 性能的 Profiler 量化数据 | 未做系统性量测，列为已知技术债 |

## 5. 结论

- 四条链路（单机 / 本地联机 / 云联机 / 启动器）均能跑通完整闭环，且每一轮验收发现的问题都已修复并回归；
- 联机与分发两条最容易出事故的链路，采用"规则层自动化 + 云上实机"双线交叉验证；
- 剩余未覆盖项集中在环境差异（DPI）、GUI 负例路径与长时间稳定性，不影响当前版本作为演示与验收版本使用。
