## P-01：Unity 编辑器卡死，无法编译

### 症状

- `recompile` 命令返回成功，但 `recompile_status` 长期停留在 `triggered`，永不变成 `completed`
- `Library/ScriptAssemblies` 目录下不产出任何 DLL，或目录整体消失
- 新增的程序集（如 `RaidDemo.Kernel.Pure`）始终没有编译产物，引用它的模块报「找不到类型」
- `AssetDatabase.Refresh()`、`RequestScriptCompilation()`、`ImportAsset(ForceUpdate)` 全部无效

### 关键诊断证据

问题表面上像是程序集配置错了，但实际不是。真正的证据来自编辑器内部状态：

```text
EditorUtility.scriptCompilationFailed = True     上一次编译失败，编辑器进入保护状态
EditorApplication.isCompiling          = False    但它并不在编译
Time.frameCount                        = 666      相隔数秒两次读取，帧计数完全不动
```

帧计数停滞是决定性证据：说明编辑器主循环已经不再推进，任何依赖主循环的任务
（资源导入、脚本编译、域重载）都会被无限期挂起。此时从外部发出的一切编译请求都会被丢弃。

另一个辅助证据：进程查询发现有两个 `AssetImportWorker` 进程长期挂起
（命令行含 `-name AssetImportWorker`），它们阻塞了资源导入队列。

### 根本原因

两类原因叠加：

1. 编辑器进入了「上次编译失败」的保护状态。一旦 `scriptCompilationFailed` 被置位且没有新的
   成功编译来清除它，编辑器会停止推进编译相关任务。
2. 资源导入 worker 进程僵死。挂起的 worker 阻塞导入队列，使资产数据库无法重建。

本次的触发链条：修改程序集配置，编译失败，为排查而清理了构建缓存目录，
编辑器在缓存缺失且处于失败保护态的情况下无法自愈，最终卡死。

> 重要认识：在 Unity 编辑器运行期间直接删除 `Library` 下的构建缓存目录是危险操作。
> 增量构建系统依赖这些文件维持状态一致性，删除后编辑器可能无法正确重建。

### 解决方案

唯一有效的做法是完全重启编辑器，并让它从零重建：

1. 关闭全部 Unity 进程（主编辑器加所有 `AssetImportWorker`）
2. 清除 `Library` 目录（可再生缓存，不含任何源码）
3. 删除自动生成的 `.sln` 与 `*.csproj`（由 Unity 自动重新生成）
4. 重新打开工程，等待完整重导入（本工程约需 2 到 5 分钟）
5. 验证：`Library/ScriptAssemblies` 下四个 `RaidDemo.*.dll` 全部产出

### 预防措施

- 不要在编辑器运行时删除 `Library/Bee`、`Library/ScriptAssemblies`。需要强制重编译时，
  优先使用 `CompilationPipeline.RequestScriptCompilation()`；这不够用时再考虑重启。
- 出现编译异常时，先读 `EditorUtility.scriptCompilationFailed` 与 `Time.frameCount`，
  立刻就能区分「编译错误」和「编辑器卡死」这两种完全不同的情况。后者直接重启，不要在配置上反复试。
- 首次导入或重构程序集后出现问题，优先怀疑构建缓存不一致，而不是代码写错。

## P-02：noEngineReferences 导致程序集不产出

### 症状

程序集 `RaidDemo.Kernel.Pure` 被 Unity 正确识别（`CompilationPipeline.GetAssemblies()` 能列出它、
源文件数量正确、`outputPath` 正确、flags 为 `None`），但编译产物在任何位置都不存在：

```text
Library/ScriptAssemblies/RaidDemo.Kernel.Pure.dll        不存在
Library/Bee/artifacts/.../RaidDemo.Kernel.Pure.dll       不存在（连中间产物都没有）
Library/Bee/artifacts/.../RaidDemo.Kernel.Pure.rsp       不存在

对比：同一批次的另外两个程序集都有产物
Library/Bee/artifacts/.../RaidDemo.Shared.rsp            存在
Library/Bee/artifacts/.../RaidDemo.Kernel.Unity.rsp      存在
```

决定性证据来自编译器响应文件：`RaidDemo.Shared.rsp` 与 `RaidDemo.Tests.EditMode.rsp` 中
完全没有对 `Kernel.Pure` 的引用，尽管两个程序的 asmdef 都声明了该依赖。

### 根本原因

asmdef 中的 `noEngineReferences: true` 字段。

该字段的预期语义是「不引用 UnityEngine 程序集」，常用于服务端或工具程序集。
但在本工程的引擎版本（Unity 6000.6.0f1）中，设置该字段会导致该程序集不产出编译产物，
进而使所有引用它的程序集无法解析类型。

该字段的预期用途仍是正确的，只是在本工程的实际环境中不可用。
这属于工具链与文档不一致的情况，不是代码错误。

### 解决方案

将 `Kernel.Pure` 与 `Shared` 的 `noEngineReferences` 改回 `false`。

### 代价（必须如实记录）

「共享层与纯逻辑层不引用引擎」这条约束，从编译器强制退化为代码评审加静态检查保证。
这是功能上的损失：违反约束不会再导致编译失败，只能靠人工与检查发现。

替代方案与后续计划：

| 方案 | 当前结论 |
| --- | --- |
| 保持 `noEngineReferences: false`，靠评审保证 | 当前采用 |
| 增加静态检查测试，扫描这些程序集中的 `using UnityEngine` | 待补（优先级：中） |
| 找到该字段的正确用法后改回编译器强制 | 待验证，若成功应更新 ADR-004 |

详细决策记录见 `Docs/Decisions/ADR-004-程序集划分方案.md`。

## P-03：路径扫描器误报 URL 与漏扫配置文件

### 症状

两个方向的缺陷同时存在。

漏报：路径扫描测试只检查 `.cs` 文件，而工程规范要求源码与配置都不含绝对路径。
`.asset`、`.json`、`.asmdef` 完全没被检查。

误报：扩展扫描范围后，Unity 模板文件中的网址被判定为违规：

```text
Assets/Readme.asset:28     url: https://docs.unity3d.com/Packages/...   误报
Assets/Readme.asset:32     url: https://forum.unity.com/forums/...      误报
```

原因是正则 `[A-Za-z]:[\\/]` 把网址中的 `s:/` 当成了「盘符 s 加斜杠」。

### 根本原因

1. 扫描范围设计不完整：只考虑了源码，忽略了资产与配置文件同样会记录本机路径。
2. 正则缺少边界判断，无法区分「盘符」与「URL 协议前缀」。

### 解决方案

修正正则，增加负向后顾断言：

```regex
(?<![A-Za-z0-9])[A-Za-z]:[\\/]
```

含义：只有当冒号前面不是字母或数字时，才把该位置视为盘符。

- `https://` 中 `s` 前面是 `p`（字母），不匹配
- `D:\SomeProject` 中 `D` 前面是行首或空格，匹配

扩展扫描范围至 `.asmdef`、`.json`、`.asset`。

补充两条互补测试（这是关键，不能只修代码）：

| 测试 | 作用 |
| --- | --- |
| `Verifier_DoesNotFlagUrls` | 防误报：网址协议前缀与工程相对路径不得被判定为违规 |
| `Verifier_FlagsDrivePathEmbeddedInUrl` | 防漏报：`file:///c:/temp` 这类 URL 内嵌盘符仍须报出 |

### 经验总结

一个满屏误报的检查，最终会被人忽略，等同于没有检查。因此修正误报与修正漏报同样重要，
两个方向都必须有测试锁定。

另外，`Verifier_FlagsDrivePathEmbeddedInUrl` 这条用例最初写错了预期。我原本假设
「URL 都不该报」，但 `file:///c:/temp` 里确实含有一个本机盘符路径，报出来才是对的。
是测试纠正了我的错误假设，而不是我去迁就测试。

## P-04：GitHub 推送间歇性失败

### 症状

```text
fatal: unable to access 'https://github.com/...': Failed to connect to github.com:443
fatal: unable to access 'https://github.com/...': schannel: server closed abruptly
fatal: unable to access 'https://github.com/...': Recv failure: Connection was reset
```

三种报错交替出现，且同一台机器上首次推送是成功的，之后才开始失败。

### 关键诊断证据

分端点测试连通性，结果高度不对称：

| 端点 | 443 端口 |
| --- | --- |
| github.com | 有时不可达 |
| api.github.com | 可达 |
| codeload.github.com | 可达 |
| objects.githubusercontent.com | 可达 |

进一步按 IP 测试（用 curl 的 `--resolve` 强制指定节点）：

```text
140.82.113.3     curl=200   可用
140.82.114.3     curl=200   可用
140.82.121.3     curl=200   可用
20.27.177.113    curl=200   可用
20.205.243.166   curl=超时   不可用（系统 DNS 恰好解析到这个节点）
```

### 根本原因

系统 DNS 把 `github.com` 解析到了一个不可达的节点（20.205.243.166），
而同域的其他节点完全正常。同时存在间歇性的 TLS 连接重置，使得问题表现为有时能推有时不能。

`Test-NetConnection github.com -Port 443` 有时返回可达，是因为它每次重新解析 DNS 可能命中不同节点。
这也是一个诊断陷阱：用域名测连通性会得到不稳定的结论，必须按 IP 逐个测。

### 解决方案

临时搭建本地 CONNECT 隧道，把流量定向到已验证可达的节点：

```text
git 客户端 --> 本地隧道（127.0.0.1）--> 指定 GitHub 节点 IP:443
```

推送完成后立即拆除隧道并清除 git 的代理配置。

### 注意事项

- 隧道只是临时绕过手段，不是长期方案。用完必须清理，不要留在工程配置里。
- 会话结束后必须检查 `git config --local --get http.proxy` 应为空。
- 排查时先用 curl 的 `--resolve` 逐个测 IP，确定可用节点后再决定方案，不要盲目重试。
- 若长期存在该问题，应考虑为 Git 配置代理，或使用其他可稳定访问的代码托管镜像。

## P-05：安全软件误报 Unity 官方组件

### 症状

安全软件（火绒）弹出告警：

```text
病毒名称：Trojan/CoinMiner.dm
病毒路径：<工程目录>\Library\PackageCache\.tmp-xxxx\package\RelayApp\~\relay\_linux
操作结果：已处理，删除文件
```

### 关键诊断证据

核实同一组件的 Windows 版本：

```text
文件        C:\Users\<用户>\.unity\relay\relay_win.exe
数字签名     Valid
签名者       Unity Technologies SF
颁发者       DigiCert Trusted G4 Code Signing RSA4096 SHA384 2021 CA1
产品名       Unity AI Assistant Relay
版本         1.3.14
```

签名有效，来源为 Unity 官方。

### 根本原因

误报。启发式查杀基于「常驻进程加持续网络连接加大体积加无信誉记录」的特征做判定，
而 Unity 的 relay 组件正好符合这些特征（它是一个长驻的连接中转服务，且是近期下载的新文件）。

被删除的是 Linux 版本的二进制文件，在 Windows 环境下根本不会被执行，因此不构成实际威胁。

### 解决方案

将工程目录与 Unity 辅助目录加入安全软件的信任区：

| 排除路径 | 理由 |
| --- | --- |
| `<工程目录>/Library` | 可再生的缓存目录，扫描它没有安全收益，只会拖慢导入 |
| `C:\Users\<用户>\.unity` | Unity 辅助组件目录，含已签名的官方二进制 |

### 干扰影响（不只是误报本身）

安全软件的实时扫描会带来两个实际麻烦：

1. 拖慢导入与编译。Unity 需要处理数万个文件，逐个扫描开销显著。
2. 可能中途删除文件导致导入失败。删除 `Library` 时曾出现文件被占用而无法删除的情况
   （报错 `Access to the path 'relay_win.exe' is denied`），说明该进程当时正在运行。
   这类干扰是 P-01 中导入 worker 僵死的可能诱因之一。

结论：即使确认是误报，也应把它当作环境问题处理掉。不只是为了安全，更是为了消除对构建稳定性的干扰。

## P-06：测试断言与实现行为不符

### 症状

```text
EventBusTests.Clear_RemovesEverything
  Clear 应当重置发布计数，保证测试之间隔离。
  Expected: 0
  But was:  1
```

### 根本原因

是测试写错了，不是实现错了。该用例在 `Clear()` 之后调用了一次 `Publish()`，
发布了 1 次事件，因此计数理应为 1。当时写断言时误以为「没有订阅者就不计数」。

### 解决方案

修正断言为 `Assert.AreEqual(1, ...)`，并补上说明：

```csharp
// 发布计数按「调用次数」统计，与是否存在订阅者无关。
// 这个语义是有意的：调试「事件发了但没人响应」时，需要知道事件确实发出去了。
Assert.AreEqual(1, m_Bus.PublishedCount, "Clear 应当重置发布计数：清零后本次发布应计为 1 次。");
```

### 经验总结

- 断言失败不等于实现有 bug。先确认是「期望错了」还是「行为错了」，再动手改代码。
  如果没有想清楚就去改实现，会把正确的实现改成错误的。
- 断言失败信息里写清业务含义，比单纯写「应当为 0」更有价值。
  半年后回看时，不用重新推导一遍。

## P-07：力竭机制被测试暴露出的规则漏洞（M1）

### 症状

玩家移动与体力系统完成后，力竭相关的 3 条用例中先后有 2 条失败：

```text
Exhausted_CannotSprintUntilRecoveredAboveThreshold
  未达到阈值前不应解除力竭。  Expected: True  But was: False

Exhausted_RecoversAndThenSprintsAgain
  恢复到阈值以上后应解除力竭。  Expected: False  But was: True
```

两条失败方向相反，说明不是简单的断言写错。

### 诊断过程与根本原因

**第一轮**，用 `eval_file` 打印模拟器的逐帧状态，得到关键数据：

```text
after exhaustion: stamina=0     exhausted=True
i=240  stamina=10.33  exhausted=True
final  stamina=29.67  exhausted=True      离阈值 30 差 0.33
```

暴露出两个问题：一是测试等待时间卡在临界值上（差异仅 0.33 点，不到一帧的恢复量），
属于测试脆弱；二是恢复延迟的计时起点与阈值规则之间存在漏洞。

**第二轮（真正的设计缺陷）**，用力竭后持续按住奔跑键的场景测试，发现：
体力一旦恢复到阈值就立刻解除力竭，但下一帧因为玩家仍在按住奔跑键，
体力又被立即抽干并重新进入力竭，形成刚解除力竭又立刻力竭的反复震荡。

根因是力竭状态下的恢复延迟与常规恢复延迟相同（1.5 秒），
导致体力在力竭期间恢复得过快，阈值规则形同虚设。

### 解决方案

引入独立的力竭恢复延迟，显著长于常规恢复延迟：

| 参数 | 值 | 作用 |
| --- | --- | --- |
| `StaminaRegenDelay` | 1.5 秒 | 常规情况下的恢复延迟 |
| `ExhaustedRegenDelay` | 3 秒 | 力竭状态下的恢复延迟 |
| `ExhaustedRecoveryThreshold` | 30 | 解除力竭所需的体力 |

并在配置校验中加入约束：`ExhaustedRegenDelay` 不得短于 `StaminaRegenDelay`，
防止后续调参时无意中让力竭失去惩罚意义。

### 关于震荡的结论：这是正确行为，不是缺陷

修正后仍会观察到按住奔跑键不放时反复力竭的现象。经分析确认应当保留：

- 它精确惩罚了死按奔跑键不放这一操作，鼓励玩家在力竭时主动停手
- 若让它在按住时也能恢复，等于允许玩家靠按键糊弄过惩罚期，力竭将失去意义

因此正确的处理是在测试中明确模拟真实玩家行为（力竭后松开奔跑键等待恢复），
并把这一约束写进用例注释，而不是修改实现去迎合测试。

### 经验总结

- 两条方向相反的断言同时失败，通常意味着规则本身有洞。只修其中一条会掩盖问题。
- 临界值测试要留余量。用刚好够的等待时间会因一帧的舍入差异产生偶发失败，
  应按公式计算所需时间并额外留出余量。
- 测试应当模拟真实玩家行为，而不是极限操作。验证力竭能恢复就该松开按键，
  验证力竭跑不动才该按住按键，两者是不同的场景。

| 验证项 | 方法 | 结果 |
| --- | --- | --- |
| 全部程序集可编译 | 触发重编译并检查错误列表 | 0 错误 |
| 程序集划分无循环依赖 | 编译成功即为证明 | 通过 |

## 附录 B：编辑器状态自查命令

排查编辑器问题时，以下内部状态最有用（通过 Unity CLI 的 `eval_file` 执行）：

```csharp
// 1) 是否处于编译失败的保护状态（出现 P-01 时首先看这个）
return UnityEditor.EditorUtility.scriptCompilationFailed;

// 2) 编辑器主循环是否仍在推进（相隔数秒读两次，数字不变即为卡死）
return UnityEngine.Time.frameCount;

// 3) 是否正在编译
return UnityEditor.EditorApplication.isCompiling;

// 4) 列出全部程序集及其源文件数量与引用，用于排查程序集配置问题
foreach (var asm in UnityEditor.Compilation.CompilationPipeline.GetAssemblies()) { }
```

判断顺序建议：先看 `scriptCompilationFailed`，再看 `frameCount` 是否推进。
这两项能立刻把「代码编译错误」与「编辑器卡死」区分开。两者的处理方式完全不同，
混淆会导致在错误方向上浪费大量时间。
