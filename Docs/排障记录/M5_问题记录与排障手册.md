## M5-P-01 子代理任务消息再次未送达

**症状**：新建的三个子代理（战局核心 / 玩家碰撞 / 战利品）返回的答复都是
「我没有收到具体任务，只收到了工作区上下文」，而主代理这边两条投递调用都返回了成功。

**定位**：换成 follow-up 通道重发了一遍完整任务说明，等待 60 秒后三个代理的状态仍然是
「已完成」，它们的最后答复依旧是上一轮的「没收到任务」。

**根因**：与 M4 记录的是同一个问题（见 M4-P-01）：协作通道的任务正文没有送达，
只有环境上下文到达。本次是**复发**，说明它不是偶发抖动。

**做法**：不再等待，主代理自己实现全部三个模块；子代理通道在本阶段只用于
「已经收到过完整说明」的任务。这条也写进了本手册的总览，作为复现率最高的工具问题。

**教训**：协作通道的返回值「成功」只表示消息入队成功，不代表对方读到。
判断依据必须是**对方的回复内容**，而不是调用结果。发现第二次就要果断放弃这条路径，
否则每轮都要白等一分钟。

## M5-P-02 补丁工具在较大的中文补丁里丢行首 `+`

**症状**：写入新文件时，补丁被拒绝，报错形如
`invalid hunk at line 18, '/// 全部交互靠轮询鼠标位置…' is not a valid hunk header`。
被指出的那一行前面**少了行首的 `+`**，而原文里明明是写上的。

**定位**：对比失败与成功的补丁，发现失败的都是「一次写入约 1.5 KB 以上的纯中文内容」，
而拆成几段、每段 1 KB 左右的补丁全部成功。

**根因**：长中文段落在传递过程中被截断，断点处的那一行丢了行首标记，
于是整块补丁的语法就不成立了。

**做法**：把文件写入拆成多次小块补丁：先落地「文件头 + 类声明 + 字段」，
再用 `Update File` 逐段追加方法。中文注释也尽量拆短行。

**教训**：把「一次写一个大文件」换成「多次写小段」不是麻烦，而是把一次失败换成零次失败。
另外，报错信息里指出的行号**就是断点位置**，可以直接按它判断自己撞上了这个坑。

## M5-P-03 玩家移动完全没有世界碰撞

**症状**：地图分区做完之后试走一圈才发现——玩家可以直接穿过集装箱、厂房隔断和围墙。
AI 会被箱子挡住，玩家不会。

**定位**：读 `PlayerMovementSimulator.Step` 的位移那一行：

```csharp
m_State.Position += direction * (speed * deltaTime);
```

它只是纯数学累加，整个模拟层没有任何碰撞查询，也没有任何引擎依赖。

**根因**：这是 M1 留下的缺口。当时地图只有一个空场地，没有障碍物，
「不会碰撞」这件事不会表现出来；等 M5 把掩体真正做进地图，它立刻变成了致命问题——
**掩体对玩家等于不存在**，整个搜打撤的空间玩法都塌了。

**做法**：
1. 在模拟层新增契约 `IMovementCollisionWorld`（不依赖引擎，可在测试里用假实现）；
2. 表现层实现 `PhysicsMovementCollisionService`：胶囊扫掠 + 沿墙滑动 + 排除自身与触发器；
3. 模拟层在位移处调用契约，**碰撞世界为 null 时行为与改动前逐位一致**，保证旧测试不受影响。

**教训**：**掩体是否真的挡人，是地图能不能成立的前提**。做地图之前先确认这件事，
比做完再补要省事得多。另外「逻辑层不认识引擎」这条架构约束本身是对的，
它让这次改动只需要加一个接口，而不必把移动逻辑搬进 MonoBehaviour。

## M5-P-04 导航网格不含高度，平台上的点寻路失败

**症状**：装卸平台上的 AI 巡逻点算不出路径；理论上它应该站在 1.2 米高的台面上。

**定位**：`NavMeshPathfindingService.ToWorld` 把平面点转成世界坐标时 **y 固定写 0**，
而 1.2 米高的台面在导航网格上有独立高度。y 等于 0 的点位于台体内部，
不在任何导航网格面上，`NavMesh.CalculatePath` 直接返回失败。

**根因**：M4 的注释里已经写明「灰盒地图是单层平面，M5 引入高低差之后需要改为按导航网格采样」——
这是一条**当时就预判到、M5 果然触发**的限制。

**做法**：
1. 寻路前对起点与终点各做一次 `NavMesh.SamplePosition`（半径 2.5 米）吸附到网格表面；
2. 表现层的敌人视图同样按导航网格采样脚底高度，否则敌人会一半埋进台面。

**教训**：注释里写下的「已知限制」是有效的——它让这次定位从「猜」变成了「查」。
反过来说，如果当时没写，这次的症状会表现为「AI 在某个区域站着不动」，
排查成本要高得多。

## M5-P-05 撤离读秒走满却什么也没发生

**症状**：自动化验证里把玩家放到撤离点，等 13 秒后战局仍是「进行中」，
`ElapsedSeconds` 正常增长，控制台**没有任何报错**。

**定位**：用反射读出读秒器的内部状态：

```text
pos=-25.00,-25.00 zone=西南角(2) 半径 3.5 米 progress=1.00 alive=True
```

进度已经是 1.00、`HasCompleted` 为真，说明读秒正常完成；
但战局会话仍是 `InProgress`，也就是**完成事件没有被接到「判胜」这一步上**。

**根因**：装配层订阅了击杀事件、战局结束事件与搜刮完成事件，唯独漏了
`ExtractionCompletedEvent → RaidSession.NotifyExtracted()`。逻辑单元测试里这条接线
是测试自己手动接的（所以测试全绿），而真实装配漏了。

**做法**：补上订阅并在 `OnDestroy` 里释放；同时在注释里写明这个症状的隐蔽性。

**教训**：**单元测试全绿不能证明「装好了」。** 事件驱动的系统里，
「事件发了但没人处理」不会有任何报错，唯一可靠的验证方式是把整条链跑一遍
（菜单 → 出击 → 搜刮 → 撤离 → 结算），并在出问题时去读**中间状态**而不是猜。
这次之所以能快速定位，正是因为读到了 `progress=1.00` 这个中间值。

## M5-P-06 阵亡红屏在结算界面不消退

**症状**：阵亡后结算界面整屏被染成红色，标题与按钮都看不清。

**定位**：红屏是 `DamageScreenFlash` 的全屏叠加层，它按 `Time.deltaTime` 衰减；
而结算时装配层把 `Time.timeScale` 设为 0 冻结世界，deltaTime 随之变成 0，
闪烁就永远停在「最红的那一帧」。

**做法**：
1. 衰减改用 `Time.unscaledDeltaTime`，让它在时间冻结后仍能淡出；
2. 结算时显式调用新增的 `ClearImmediate()`，保证进入结算的那一帧就是干净的。

**教训**：任何**与游戏时间无关的界面反馈**（受击闪烁、提示、动画）都应该走 unscaled 时间。
这条规则在平时看不出差别，只在 `timeScale = 0` 的那一刻暴露。

## M5-P-07 单文件行数超限（4 个文件同时超）

**症状**：全量测试里 `PathRulesTests.SourceFiles_DoNotExceedLineLimit` 失败并列出：
`SceneBootstrap.cs` 407 行、`SceneBootstrap.Raid.cs` 467 行、
`GreyboxSceneBuilder.Layout.cs` 481 行、`PlayerInputCollector.cs` 440 行。

**根因**：M5 新增的装配与界面代码都比较大，且习惯性地往「最相关的那个文件」里加。

**做法**：按职责拆 partial：
`SceneBootstrap.PlayerInput.cs`（输入与准星）、`SceneBootstrap.RaidFlow.cs`（战局主循环）、
`GreyboxSceneBuilder.Content.cs`（撤离点与容器）、`PlayerInputCollector.Intents.cs`（意图读取）。

**教训**：这条约束在**写完的当天**就会顶到上限，所以「先写后拆」是行不通的；
每加完一个模块就应看一眼行数。好在测试会拦住它，不会让超长文件混进提交。

## M5-P-08 编辑器失焦导致帧循环停摆（复发）

**症状**：通过 CLI 驱动战局时，倒计时一直停在 480.0 秒不动；
`Time.frameCount` 连续两次读取都是 1。

**根因**：与 M0/M2 记录的一致——编辑器窗口不在前台时 Unity 会停掉帧循环，
`Application.runInBackground` 默认是 false。

**做法**：这一次不再依赖「用 eval 临时改回来」，而是把
`Application.runInBackground = true` 写进 `SceneBootstrap.Initialize`，
从源头消除这个坑（对正式构建也无害：窗口化游戏本来就应该在后台继续跑）。

**教训**：同一个坑出现第三次时，说明之前的「应对」只是绕过。
复发的问题应该在代码里修掉，而不是每次排查一遍。

## M5-P-09 场景生成器的子对象用错坐标参照系

**症状**：撤离点的地面色块、立柱与横梁全部出现在场景原点附近，而不是各自的撤离点位置。

**根因**：`CreateBox` / `CreateDecoration` 都以**世界坐标**摆放对象
（先设 `transform.position` 再 `SetParent(worldPositionStays: true)`），
而撤离点的子对象是按「相对根节点的偏移」传参的。

**做法**：在生成器里统一用 `origin + offset` 的世界坐标计算，并在注释里写明这条约定。

**教训**：生成器的工厂方法存在隐式约定（这里是「参数一律是世界坐标」）时，
约定必须写进方法注释；否则调用方会按直觉传相对坐标，而错误的表现是
「所有同类对象叠在一起」——看起来很离谱，但确实不容易一眼看穿。

## M5-P-10 两个 Canvas 用了相同的 sortingOrder

**症状**：暂时没有症状——是在写战局 HUD 时才发现的潜伏问题：
战局 HUD 与战斗 HUD 都用了 `sortingOrder = 150`。

**根因**：两个界面由不同里程碑创建，各自选了「位于准星 100 与背包 200 之间」的值，
于是撞在一起。相同时的渲染顺序取决于对象创建顺序，而创建顺序会随装配流程变化。

**做法**：战局 HUD 改为 140，并在注释里写清每个层级的用途与取值理由。

**教训**：层级顺序应当**集中约定**（例如在注释里列出 100 准星 / 140 战局 / 150 战斗 /
200 背包 / 300 菜单 / 310 结算 / 400 受击闪烁）。
靠各自「取中间值」迟早会撞车，而撞车的表现是随机出现的遮挡，极难复现。

## M5-P-11 接口刻意不认识行为，取行为只能绕物品目录

**症状**：写医疗品逻辑时，`item.Definition.Behavior` 编译不过：
`'IItemDefinition' does not contain a definition for 'Behavior'`（三处同时报错）。

**定位**：`ItemInstance.Definition` 的类型是 `IItemDefinition` 接口，
而 `Behavior` 只定义在具体类 `ItemDefinition` 上（`RaidDemo.Data` 与 `RaidDemo.Data.Content` 分属两个程序集）。

**根因**：这是**有意为之**的架构约束——`ItemBehavior` 是 Unity 的 ScriptableObject，
把它挂进纯数据接口会让数据层反向依赖内容层，形成循环。
因此接口不认识行为，是正确的设计；报错说明我用错了取法。

**做法**：改为 `m_ItemCatalog.Get(item.Definition.Id).Behavior`——
目录返回的是具体定义，认识行为。三处调用点收敛到一个 `ResolveMedical` 辅助方法里，
并在注释里写明为什么不能从物品实例上直接拿。

**教训**：接口「缺一个成员」时，先分清是**漏了**还是**刻意不给**。
这次如果图省事把 `Behavior` 加进接口，就会用一个循环依赖换掉一次麻烦。
另外，报错点有三处说明**同一件事被重复写了三遍**——把它收敛成一个方法，
下次改规则只需要动一处。

## M5-P-12 装配文件第二次顶破 400 行

**症状**：`PathRulesTests.SourceFiles_DoNotExceedLineLimit` 失败：
`SceneBootstrap.RaidFlow.cs 共 423 行，超过上限 400 行`。

**定位**：这一轮往战局装配文件里加了「物品使用」的五个方法（选药、回血、消耗等）。

**根因**：与 M5-P-07 完全同一个原因——**写完再拆**是行不通的，
因为「拆」这件事总是发生在测试报错之后，那时改动已经落盘。

**做法**：把「存活判定 + 击杀统计」这两个与伤害事件相关的方法挪回
`SceneBootstrap.Raid.cs`，两个文件分别回到 391 与 380 行以内。

**教训**：这条在 M5 内**复发了一次**，说明上次的教训没有变成习惯。
以后每加完一个方法组就先看行数，而不是等测试来提醒——
测试是最后一道防线，不是日常工具。

## M5-P-13 固定产出未排序，大件被静默丢弃

**症状**：测试箱里固定产出四件装备，开箱后**没有背包**，其余三件正常。

**定位**：算一遍装箱。箱子 6×4，按配置顺序放：步枪 3 格 → 背心 2×3 → 头盔 2×2，
这三件把空间切成碎片后，最后 9 格的背包（3×3）找不到连续空位，
`AutoPlace` 返回失败 → **被静默丢弃**（返回值没人看）。

**根因**：这条规则 M2 就吃过一次——当时的注释写着「放置顺序按占地从大到小，
否则小件会先把空间切碎，大件反而一件都放不进去」。但那条规则只体现在
当时那个方法里，加新功能（固定产出）时没有沿用。

**做法**：把排序放进 `LootRoller` 本体，凡是固定产出都按占地从大到小放；
测试箱同时放大到 6×5 留余量。用真实物品目录验证产出为
「小型背包、防弹背心、钢盔、AK-74、30 发 5.45 弹」五件齐全。

**教训**：**已知规则要写进公共路径，而不是留在某个方法的注释里。**
留在注释里的规则，下一次写新代码的人（往往是同一个人的另一天）看不到。
另外「放不下就静默丢弃」这个设计本身也是问题：它把「配置写错了」伪装成「运气不好」，
应当返回被丢弃的清单并打日志。

## M5-P-14 视图被销毁、状态还留着

**症状**：装备或卸下背包导致随身格子变化后，下方搜索容器的格子**消失**，
而且重新搜同一个箱子也不会回来，必须退出背包界面再搜一次。

**定位**：容量变化会整块重建界面。重建销毁了战利品视图，
但 `m_LootContainerId` 仍记着原容器；而 `OpenLootContainer` 有一条优化——
**只在容器 ID 变化时才重建视图**。两条一撞：视图没了、状态说「已经开着」。

**根因**：这是**同类问题的第二次**。上一次是右键菜单：菜单根节点被销毁，
而持有它的字段还指着它（见 M5-P-10 之后的菜单实现）。两次都是
「视图可以被销毁重建，但持有它的字段没有跟着清空」。

**做法**：重建前取出打开的容器 ID 并把状态清零，重建后按原样恢复视图。

**教训**：这类问题应当用一条硬规矩兜住——
**凡是持有视图引用的字段，在视图被销毁的那条路径上必须一起清空**。
两次都靠人记住，说明它需要的是检查而不是纪律（可以在重建路径上断言所有视图字段为空）。

## M5-P-15 装上了但没人读：护甲从未生效、背包容量从未接入

**症状**：两个独立的功能缺失，被负责人在同一次验收里一起报出来——
「护甲、头盔没有防护作用」「背包装备后没有作用」。

**定位**：

| 项 | 数据 | 生效点 |
| --- | --- | --- |
| 头盔 | 物品定义里有 `ArmorStats` | **没有任何代码读取它** |
| 身体护甲 | 同上 | 只在开战那一刻读一次，战局中换装不生效 |
| 背包容量 | 物品定义里有 `ContainerGridSize`（4×4 / 6×6） | 随身网格是固定 5×5 的常量，**从未被接入** |

**根因**：三处都属于同一形状——**数据写了、界面能显示、但「生效」的那一步没接上**。
又因为玩家开局空手，护甲在实战中恒为 `null`，所以连「偶尔生效」的机会都没有。

**做法**：护甲拆成头部/身体两套并在换装时同步；容量改为由背包决定并处理「装不下」的情况。

**教训**：每一个「装上之后应当产生效果」的系统，都要能回答两个问题：
**它改变的是哪个数值？谁在什么时候读它？** 答不上来的，就是还没接完线。
这类问题比崩溃更难发现——它不报错，只是「感觉不对」，
而玩家（甚至开发者）很容易把它归因成「数值没调好」。
