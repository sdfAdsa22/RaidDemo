## T-01 构建期间 Unity 卡在 "Compiling Scripts"（编译进程僵死）

**现象**：出完客户端（`Builds/Update/1.0.2` 已落盘）后立刻发起"构建专用服务器（Windows）"，
Unity 弹出 `Compiling Scripts (busy for 10:37)...`，进度条走满停在
`Compiling C# (RaidDemo.Data)`；点 `Cancel` 后变成 `Cancelling` 也一直不结束。

**判据（怎么确认不是"正常慢"）**：

- Unity 主进程 20 秒只涨 ~1 秒 CPU；`Unity.ILPP.Runner` 的 CPU **完全不涨**；
- `Builds/ServerWindows` 的时间戳停在上一轮构建时间；
- 枚举 Unity 的可见窗口能看到 `Compiling Scripts (busy for …)` 这个模态窗口。

**根因（结论）**：Unity 6.6 的脚本编译阶段偶发僵死，与本次改动的代码无关
（同一份代码在此之前刚编译通过、测试全绿）。

**处置**：结束 Unity 进程（含 `Unity.ILPP.Runner`）后重开工程，重新发起同一个构建即可，
第二次 50 秒就完成。

**下次的省时做法**：构建期间**不要再对同一个编辑器发任何 CLI 命令**
（`eval` / `editor_status` 等）——本次僵死前正好并发发过多条命令。
判断"在忙"用窗口标题 + CPU 采样，而不是继续往编辑器里塞命令。

## T-02 给客户端/服务端传带空格的 `-logFile` 会拆参导致进程秒退

**现象**：用 `Start-Process -ArgumentList '-logFile','D:\unity game\demo\Library\...\a.log'`
起的客户端进程立刻消失，既不联网也不生成日志。

**原因**：`Start-Process -ArgumentList` 是**拼接**成命令行字符串，不做逐参数转义；
路径里的空格把它拆成了两个参数，Unity 的启动参数解析拿到残缺值。

**处置**：两条路任选

1. 参数里自带引号：`-ArgumentList '-logFile','"D:\path with space\a.log"'`；
2. 传**不含空格**的相对路径（服务端/客户端以各自工作目录为基准），
   跑完再把日志复制进证据目录。

**备注**：服务端与客户端的 `-logFile` 都受这条影响；M11 期间用的是相对路径，所以没踩到。

## T-03 含 `Start-Process` 的复合命令会被安全策略拦下

**现象**：把"起进程 + 等待 + 请求状态页"写在一条命令里时，整条命令被拒绝执行
（提示 blocked by policy）；把同样内容拆成"起进程"与"检查"两条命令则正常。

**处置**：起后台进程用**单条最小命令**，后续检查另起一条命令。
这条是执行环境的限制，不影响产品行为，但会浪费排查时间——先记在这里。

## T-04 交付版进图报 `Invalid path in AssetBundleProvider`（资源层没随包走）

**现象**：交付目录里直接双击客户端，进图（或热更后第一次进图）时报
`RemoteProviderException : Invalid path in AssetBundleProvider: '.../StreamingAssets/aa/StandaloneWindows64/<bundle>.bundle'`，
客户端随后不再上行；服务端看到"全员静默"，P-51 看门狗重建传输层，宽限到期后把玩家踢出。

**判据**：报错里的文件**确实存在**于磁盘（本例 3086 字节），说明不是文件丢失，
而是"解析到的位置"和"内容实际所在层"不一致。

**根因**：M10 把客户端产物拆成**本体层**（242 文件）与**资源层**（`content/`，12 文件 / 14.3 MB）。
发到交付目录的客户端只复制了本体层，资源层要由启动器 / 热更从更新源下载到
`persistentDataPath/content/` 再寻址。开发机上因为历史缓存存在，看不出问题；
换台干净机器或换个缓存版本就必现。

**处置**：出包时把资源层一起复制进交付客户端
（`客户端/RaidDemo_Data/StreamingAssets/aa/StandaloneWindows64/`），
`Tools/Release/assemble_delivery.ps1` 已实现；顺手也把"离线可玩"这条设计承诺补回来了。

**排查时踩过的坑**：

- 一开始怀疑路径里的空格（`D:\unity game\...`），把整包复制到 `D:\RaidDemoTest` 复测——
  结果从"报 Invalid path"变成"原生崩溃"，说明空格只是把失败表现改变了，不是根因；
- 判断"是卡住还是慢"要看**客户端日志的最后一行**：日志停在 `加载战局地图` 之后，
  就不要再等服务端看门狗自愈了，直接去客户端目录翻日志最快。

## T-05 启动器装完游戏，第一次进图仍然失败（资源层与本体分开装）

**现象**：用启动器从更新源装好游戏（242 文件 / 158.4 MB）、点「开始游戏」、建房进图——
干净机器上第一次进图失败（客户端日志停在 `加载战局地图`，服务端看到全员静默）。

**根因**：启动器的更新流程只装**本体层**；资源层要游戏首次启动时**自己**从更新源下载，
而"游戏内下载并应用新内容后第一次进图"这条路本身有缺陷（见 T-04 与报告 AR-09）。
开发机上因为有历史缓存，看不出问题。

**处置**：启动器装完本体后，顺带把资源层装进**游戏的内容缓存**
（`%USERPROFILE%\AppData\LocalLow\<公司>\<产品>\content\<内容版本>\` + `state.json`），
游戏启动时就认为"内容已是最新"，直接复用缓存。实现见
`Tools/Launcher/Update/ContentCacheInstaller.cs`；启动器与游戏两侧的目录约定、
状态文件字段名必须逐字一致，改一边就要改另一边。

**验证方式（务必照做）**：先把 `content/` 目录移入回收站模拟全新机器，再走启动器全流程——
不清缓存的话，测到的是"旧缓存恰好可用"，不是修复本身。

## T-06 启动器界面发糊 / 控件错位（高 DPI）

**现象**：在 150% 缩放的显示器上启动器整体发虚、中文边缘糊；拖到别的显示器更明显。

**判据**：窗口的物理尺寸恰好是设计尺寸的 1.5 倍（1000×620 → 1500×930），
而进程内 `GetDpiForWindow` 只报 96——典型的"进程未声明 DPI 感知，由系统做位图拉伸"。

**修法**：`Application.SetHighDpiMode(HighDpiMode.PerMonitorV2)`；
界面按 `DeviceDpi / 96` 显式等比缩放一次（`Scale()` + 显式设置客户区尺寸 + 锁死 Min/Max）；
**字号必须用像素单位**（`GraphicsUnit.Pixel`）——磅值本身会随 DPI 放大，
再叠加一次缩放就等于放大两次，长标签会被顶出面板。

**踩坑记录（都实测过）**：

- `AutoScaleMode.Dpi` + `AutoScaleDimensions` 在本工程这套"全代码摆控件 + 自绘"的结构里
  会把窗口反向缩到 0.67 倍（内容溢出），因此改为自己调 `Scale()`；
- `Control.Scale()` 只缩放子控件、**不改宿主窗口大小**，必须自己再设一次 `ClientSize`；
- 面板的滑入动画若仍按未缩放的设计常量算落点，面板右侧会留在窗口外
  （表现为抽屉最右边的按钮被切掉）——落点要用 `m_Drawer.Width` 这种"当前实际值"。

## T-07 服务端控制台中文乱码

**现象**：Windows 上直接用 cmd 启动 `RaidDemoServer.exe`，中文日志全部显示成 `锛?/鍣?` 之类的乱码。

**根因**：Windows 控制台默认代码页是 936（GBK），而 Unity 播放器按 UTF-8 往 stdout 写字节。

**修法**：服务器模式启动时调用 Win32 `SetConsoleOutputCP(65001)`。
**只设 `Console.OutputEncoding` 在 Unity 播放器里不生效**——日志不是走 .NET 的
标准输出流，而是播放器自己的原生写出口。判断依据很直接：同一台机器上手动执行
`chcp 65001` 再启动，中文立刻正常；而仅靠托管 API 无效。

**顺带**：日志文件一直是 UTF-8、内容正常；乱码只发生在控制台。
一键开服面板（`RaidDemo.ServerHost.exe`）自己按 UTF-8 解码子进程输出，不受影响。
