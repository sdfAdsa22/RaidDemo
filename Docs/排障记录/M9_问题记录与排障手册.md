## M9-P-01：为测试"非法路径"而写下非法路径，被自己的护栏拦下

**现象**：新增的 `ServerLaunchOptionsTests` 里有 6 条用 `[TestCase]` 参数化的用例，全量测试从 451 变 456，
其中 **1 条失败**——失败的是 `PathRulesTests.Assets_DoNotContainAbsolutePaths`，不是我自己写的断言。

**定位过程**：失败信息本身就把证据给全了，直接列出 4 处：

```
Assets\Game\Bootstrap\Session\ServerLaunchOptions.cs:209 盘符绝对路径
    /// Windows 风格的 <c>C:\saves</c> 不会被判定为绝对路径。…
Assets\Game\Tests\EditMode\ServerLaunchOptionsTests.cs:115 盘符绝对路径
    [TestCase("C:/saves")]
Assets\Game\Tests\EditMode\ServerLaunchOptionsTests.cs:117 Unix 绝对路径
    [TestCase("/var/saves")]
```

**根因**：`PathRulesVerifier` 的两条规则扫的是**文件全文**，不区分代码、注释与特性：

- `(?<![A-Za-z0-9])[A-Za-z]:[\\/]` → 匹配任何盘符路径，XML 注释里的示例也算；
- `"[^"\r\n]*/(?:Users|home|var|opt)/` → 匹配字符串字面量里的 Unix 根路径，`[TestCase]` 也算。

所以「为了测试非法输入而写非法输入」这件事，在本工程里本身就是违规的。

**做法**：

1. 测试数据改为**运行时拼接**：`var drivePrefix = "C" + ":";` → `drivePrefix + "/saves"`，
   Unix 那条写成 `"/" + "var/saves"`，任何字面量都不再包含完整路径；
2. 6 条 `[TestCase]` 合成 1 个循环用例（省掉 5 个测试条目，断言消息里带上具体取值）；
3. XML 注释里的示例改写成文字描述（「盘符后紧跟斜杠」），不再写具体路径。

**教训**：写测试之前先看这个工程有哪些**全局护栏**。护栏拦的是"文件里出现了什么"，
而不是"这行代码有没有被执行"——它不理解语境。

## M9-P-02：EditMode 里起不了 NGO 服务器

**现象**：`ServerRuntimeTests`（原计划放 EditMode）里调用 `NetworkManager.StartServer()`，
抛 `System.Exception : There is no NetworkManager assigned to this instance!`

**定位过程**：

1. 先在包里搜报错原文，定位到
   `Library/PackageCache/com.unity.netcode.gameobjects@…/Runtime/Connection/NetworkConnectionManager.cs:412`；
2. 报错来自 `ConnectionManager` 内部的宿主引用为空；
3. 该引用由 `NetworkManager.Awake()` 写入——而 **EditMode 不触发生命周期回调**，
   `AddComponent<NetworkManager>()` 之后立刻 `StartServer()`，`Awake` 从未执行。

**根因**：被测代码没问题，是「依赖 MonoBehaviour 生命周期」这件事在编辑模式下不成立。

**做法**：新建 `Assets/Game/Tests/PlayMode/RaidDemo.Tests.PlayMode.asmdef`（工程里 `Tests/PlayMode/`
一直预留为空），把「起监听 / 关监听 / 重复关闭」三条用例搬过去；
EditMode 只保留纯逻辑的 `ServerAddressReporterTests`。
测试程序集需要显式加 `Unity.Netcode.Runtime` 引用，否则测试文件不会被编译（表现是"过滤器匹配 0 条"）。

**教训**：**EditMode 测纯逻辑，PlayMode 测生命周期**。判定方法很简单——
如果被测代码需要 `Awake` / `Update` / 场景加载，它就不属于 EditMode。

## M9-P-03：`DontDestroyOnLoad` 在编辑模式抛异常

**现象**：搬测试之前先撞上的另一条：
`InvalidOperationException: The following game object is invoking the DontDestroyOnLoad method… cannot be part of an editor script.`

**根因**：`ServerRuntime.Create()` 为了让服务器宿主跨场景存活，无条件调用了 `DontDestroyOnLoad`，
而 EditMode 测试同样会调用它。

**做法**：加 `Application.isPlaying` 判定——跨场景存活只在播放模式下有意义，
编辑模式（测试）创建的对象随测试结束销毁即可。这属于被测代码的真实缺陷，不是测试的锅。

**教训**：运行时为了方便写的 API 调用，一旦有第二类调用者（测试、编辑器工具）就要重新审视前提。

## M9-P-04：Unity CLI 的 PlayMode 运行器不可用

**现象**：`unity command … run_tests --mode PlayMode` 返回
`{"Total":0,"Passed":0,"Failed":0,…}`，同时控制台出现
`KeyNotFoundException: The given key 'services-gateway' was not present in the dictionary.`；
命令结束后编辑器被留在**播放模式**（`editor_status` 显示 `playMode: playing`）。

**排查过的方向**：加 `--filter <Fixture>`（仍然 0 条）、加 `--async_tests true`（仍然 0 条）；
而 `list_tests` 里明明能看到这 3 条用例——说明**测试被发现、但运行器自身失败**。

**做法**：

1. 用 `editor_stop` 把编辑器复位；
2. PlayMode 用例保留在工程里（用户可用 Test Runner 窗口手动跑）；
3. 验收改用**真实产物**：`build --confirm true` 出 Windows 包 → 以 `-server` 启动 → 查 UDP 监听与日志。

**教训**：自动化通道坏了不等于验收要降级——换成"人也能复现的真实路径"验证，
而且这条证据比测试更强（它证明的是能出包、能起监听）。

## M9-P-05：`Start-Process` 把带空格的路径拆成两个参数 → 退出码 127

**现象**：用 `-server -port 7777 -room 验收房间 -batchmode -nographics -logFile <日志路径>` 启动客户端包，
进程**秒退**、退出码 **127**、约定的日志文件根本没生成；而不带任何参数启动同一个包却正常。

**定位过程**：

1. 退出码 127 容易误读成"缺 DLL"，先做**最小对比**：无参数启动 → 正常运行 ✓；只带 `-server` → 正常运行 ✓；
2. 说明包没问题，问题在参数；
3. 回看传参：`-ArgumentList` 数组里的日志路径含空格（工程路径是 `…\unity game\demo\…`），
   PowerShell 拼接数组时**不会自动加引号**，于是 `-logFile D:\unity` 与 `game\demo\…\server.log` 被当成两个参数。

**做法**：显式加引号——`'-logFile', ('"' + $log + '"')`；参数里出现路径就要条件反射地检查引号。

**教训**：遇到"进程秒退且没有任何日志"时，先做**最小可运行组合**再逐步加参数，
比盯着退出码猜原因快得多。

## M9-P-06：缺 Dedicated Server 构建模块

**现象**：点「构建专用服务器（Windows）」后构建失败：
`Error building Player: Dedicated Server support for Win is not installed.`

**定位**：`ProjectSettings` 与 `list_build_targets` 确认当前只装了
`windowsstandalonesupport` 与 `WebGLSupport`；Dedicated Server 在 Unity 6 里是**独立模块**，
与普通 Windows 构建支持分开安装（Linux 侧同理，P6 需要 `StandaloneLinux64`）。

**做法**：

1. P0 的验收不依赖它——用普通客户端包 + `-server` 参数完成「无头启动 + 打印监听地址」验证；
2. 把「补装 Windows / Linux Dedicated Server 模块」记进 `Docs/Modules/10_联机.md` 第 16 节准备清单（P6 前必须完成）。

**教训**：构建目标的支持模块与平台模块不是一回事，规划阶段就要写清楚"谁去装、什么时候装"。

## M9-P-07：构建产物写进了 `Assets/Resources`

**现象**：一次构建之后 `git status` 里出现 `?? Assets/Resources.meta`，
控制台同时有 `[TestRunBuilder] Creating new file 'Assets/Resources/PerformanceTestRunSettings.json'`。

**根因**：测试框架在构建时会往 `Assets/Resources` 写性能采样文件；工程本身不使用该目录
（资源一律放 `Assets/Game/Content`）。

**做法**：删掉该目录（连同 `.meta`），并在 `.gitignore` 里加入这两条路径，
避免以后每次构建都污染工作区。

**教训**：第三方包会往工程里写东西，提交前先看 `git status` 里有没有"不是我改的"。

## M9-P-08：装包之后工程设置的变化不都是噪声

**现象**：装完 NGO 并构建一次后，工作区多出
`Assets/DefaultNetworkPrefabs.asset`，`ProjectSettings` 的 `preloadedAssets` 也从 `[]` 变成了
含 `InputSystem_Actions.inputactions` 的列表。

**定位**：用 `AssetDatabase.GUIDToAssetPath` 反查两个 GUID：

- `Assets/DefaultNetworkPrefabs.asset` —— NGO 建的网络预制体清单（包自身的初始化产物）；
- `InputSystem_Actions.inputactions` —— Input System 包注册到预载列表的输入资产。

两者都不是本机路径噪声（对比 `.mat` 的浮点噪声），而是**包正常工作所需的工程状态**。

**做法**：这两项随提交入库；`.mat` 的浮点噪声仍然按老规矩 `git restore` 还原。

**教训**：提交前对每个"意外变更"问一句"它属于哪一类"——包初始化产物要留，运行期噪声要还原。
判据是**它会不会在别人机器上重新生成**：会重新生成且内容一致的是噪声，不会的是工程状态。

## M9-P-09：客户端连不上服务器——主菜单把时间冻住了

**现象**：1 个专用服务器 + 1 个客户端，服务器日志始终「在线 0 人」；
客户端日志只有「正在连接 127.0.0.1:7777 …」，随后「与服务器断开」。

**定位过程**（关键是先把"谁没做事"分清）：

1. 用客户端内部状态上报把事实钉死：
   `IsClient=True 监听中=True 已连接=False` —— 客户端的传输层确实启动了、端口也绑上了，
   只是握手没完成；
2. 服务器侧确认 UDP 7777 确实被自己的进程持有（`Get-NetUDPEndpoint` 显示的 PID 就是 RaidDemo）；
3. 用 PowerShell 起一个 UDP 监听、让游戏客户端去连它，**收到了 17 个 13 字节的连接请求**
   ——证明客户端的出站完全正常，问题不在安全软件出站，也不在传输层绑定。

**根因**：客户端进入战局场景时流程状态仍是「主菜单」，
而主菜单会把 `Time.timeScale` 置 0。客户端因此既不推进自己的战局逻辑，
**网络栈也拿不到时间推进**——连接请求发出去了，握手却永远走不完。

**做法**：

1. 新增 `RaidFlowController.EnterRaidDirectly()`：只切流程状态、不加载场景、不写存档；
2. 联机客户端在装配时调用它——连上服务器就等于「已经在战局里」，本就该如此。

**教训**：「时间」是联机代码的隐性依赖。任何把 `timeScale` 置 0 的状态
（主菜单、结算、暂停）都会让网络层安静地停摆，而且不会报错。

## M9-P-10：NGO 在打包后的进程里不打日志

**现象**：按 `-logLevel verbose` 启动后，客户端与服务器都**一条 `[Netcode]` 日志都没有**，
只有本项目自己的输出。把 `NetworkManager.LogLevel` 设为 `Developer` 也没有变化。

**判断**：NGO 的日志在非开发版（非 Development Build / 非编辑器）里会被裁掉，
因此"日志里没有报错"不能作为"没问题"的证据——这条与 M9-P-09 是一起的：
正是因为没有任何线索，才需要自己往代码里加状态上报。

**做法**：联机路径加入按 `-autowalk`（验收模式）触发的周期性状态上报，
把 `IsClient / IsListening / IsConnectedClient / LocalClientId / 目标地址` 打到日志里。

**教训**：依赖框架日志前先确认"这份构建里日志还在不在"。
定位联机问题时，自己控制的状态上报比框架日志更可靠。

## M9-P-11：NetworkConfig 不一致——连接请求被服务器静默拒绝

**现象**：客户端 `IsClient=True 监听中=True` 但 `已连接=False`，服务器始终「在线 0 人」。
排除过：端口冲突、场景加载、回环地址、安全软件（用 PowerShell 当接收端实测收到 17 个连接请求）。

**定位过程**（这一步靠的是"换一个能看见日志的构建"）：

1. 打**开发版**构建（`build --options '["Development"]'`）——非开发版会把 NGO 的日志裁掉（M9-P-10）；
2. 服务器日志里立刻出现关键一行：

   ```
   [Netcode] NetworkConfig mismatch. The configuration between the server and client does not match
   Unity.Netcode.ConnectionRequestMessage:Deserialize (…/ConnectionRequestMessage.cs:173)
   [Netcode] [Disconnect Event][Client-1] Client-1 disconnected by server.
   ```

3. 对照两端配置：服务器写了 `TickRate = 60`，客户端用的是 `new NetworkConfig()` 的默认值 30。

**根因**：NGO 在握手时比对双方的 `NetworkConfig`，任何字段不一致就把连接请求判为非法并断开；
它**不会**在客户端给出可读原因（客户端只表现为"连不上"）。

**做法**：新增 `NetworkConfigFactory`，两端共用同一份配置——
`TickRate`、`ConnectionApproval`、`EnableSceneManagement` 只在这里定义；
以后新增配置项也只在这里加，从结构上消除"两端各写一套"的可能。

**教训**：

- 联机框架的"静默拒绝"最贵：现象是"连不上"，原因在服务器侧一行警告里。
  **诊断联机问题的第一件事是确认自己能看到框架日志**——非开发版构建看不到 NGO 日志，
  因此"日志里没报错"不等于没问题；
- 像 `NetworkConfig` 这种"必须两端一致"的东西，不能靠人记得同步，要靠**单一来源**。

## M9-P-12：自己的 Verbose 日志在发行版里被编译器删掉

**现象**：服务器明明在开火（客户端收到了 60 条战斗事件），但服务器日志里
`[服务器] 收到玩家 1 的开火意图`、`[服务器] 玩家 1 开火` 一条都没有。
一度怀疑"输入没上来""服务器没在跑战斗"，白查了两轮。

**根因**：`LogService.Verbose` 上挂着
`[Conditional("UNITY_EDITOR")] [Conditional("DEVELOPMENT_BUILD")]`——
**发行版构建里这些调用会被编译器整个剔除**，连 `IsEnabled` 判断都不会执行。
而 `Info` 级别照常输出，所以症状是"有的日志有、有的日志永远没有"。

**做法**：

1. 联机验收一律用**开发版构建**：`build --confirm true --options '["Development"]'`；
2. 关键链路（"输入有没有上来""开火有没有发生"）除 Verbose 外再留一条 **Info 级**的
   一次性痕迹（例如"已扣下扳机，开始向服务器上报开火意图"）；
3. 这条与 M9-P-10（NGO 日志同样只在开发版可见）是同一条教训的两个化身。

**教训**：**验收用发行版、排障用开发版**这件事要提前分开。
用发行版做诊断时，"日志里没有"只能说明"没人打印"，不能说明"没发生"。

## M9-P-13：服务器的子弹从脚底射出，永远打不到人

**现象**：服务器侧开火正常、弹药正常扣，但所有射击都是 `命中=False`（连地形都没打到）。

**根因**：服务器的"玩家位置"就是移动模拟的水平坐标，我直接拿它当枪口用了，
于是射线从 **y=0（脚底）** 水平射出：目标是站立胶囊（0~1.8 米），
射线要么贴地先撞地形、要么从胶囊下沿擦过去。

**做法**：枪口抬到与客户端一致的 1.05 米
（`ServerRuntime.Combat` 的 `MuzzleHeight`，与 `SceneBootstrap` 取值对齐）。
命中判定必须两端用**同一套空间假设**，否则"客户端看着打中了、服务器说没中"会成为常态。

**教训**：模拟层是二维的（水平面），表现层是三维的。凡是**跨这条边界**的数值
（枪口高度、碰撞体尺寸、单位层）都得显式对齐一次，别指望"差不多"。

## M9-P-14：自动化验收里"开了 60 枪、命中 0 次"

**现象**：修完 P-13 之后仍然打不中。日志显示服务器在开火、弹药在扣，就是没有命中。

**定位**：看两侧客户端的远端位置——玩家 1 已经走到 **(32.1, -1.4)**，
玩家 2 还在 **(3.2, 0.0)** 附近，**相距约 29 米**，而步枪射程只有 12 米。

**根因**：验收辅助（`-autowalk`）让两个客户端各绕各的圈，
它们自然会越走越远——不是代码有问题，是**测试场景根本没让它们对上**。

**做法**：验收模式改为"朝最近的队友走过去并瞄准他"：
命中路径（伤害结算 → 广播 → 客户端扣血）因此才真正被走到。
改完后服务器日志立刻出现 `命中：玩家 2 → 玩家 1，伤害 25.0 …（已阵亡）`。

**教训**：自动化验收要**保证被测路径真的会被走到**。
"跑了 30 秒没报错"与"这条分支执行过"是两件不同的事——
前者只能证明没崩，后者才叫验证。

## M9-P-15：刚 `LoadScene` 完就去找场景里的东西，找不到

**现象**：P2-2 第一步要给服务器烘焙导航网格。日志顺序看起来完全正确——
先"[服务器] 加载地图场景：GreyboxRaid"，紧接着就是
"[服务器] 地图里没有 NavMeshSurface，AI 将退化为直线移动"。
地图文件里明明有这个组件（场景生成器里 `terrain.AddComponent<NavMeshSurface>()`）。

**定位**：把警告文案改成"带上当前活动场景名"，一次就看清了：

```
[服务器] 地图场景「SafeHouse」里没有 NavMeshSurface
```

服务器在 `RuntimeInitializeOnLoadMethod(AfterSceneLoad)` 里调用 `SceneManager.LoadScene`。
那个时刻引擎**仍在处理首个场景**的加载流程，这次场景切换因此被推迟到本帧稍后才生效——
调用是同步的，但"生效"不是。所以紧跟在后面的 `FindAnyObjectByType` 看到的还是安全屋。

**做法**：改成"登记待办 + 每帧检查"，只有当活动场景真的等于目标地图时才烘焙：

```csharp
private void TickNavigation()   // 在 Update 里调用
{
    if (!m_NavigationPending) return;
    if (SceneManager.GetActiveScene().name != m_Options.MapSceneName) return;   // 还没换过去
    m_NavigationPending = false;
    BuildNavigation();
}
```

**教训**：**"调用返回了"不等于"效果生效了"。** 凡是"加载 / 切换 / 初始化"之后立刻要读新状态的地方，
都要先确认新状态真的成立——判断依据要写进日志（这里就是把活动场景名打出来），
否则现象只会是"明明有这个组件却说找不到"。

## M9-P-16：导航网格烘出来了，但每条路径都算不出来

**现象**：服务器日志变成"导航数据已烘焙：三角面顶点 1952 个，耗时 21 ms"，
但紧随其后的三条自检路径**全部失败**（堆场平地 / 装卸平台高差 / 厂房内部）。
网格非空却哪儿也去不了。

**定位**：先怀疑自检点本身写错，于是回看寻路实现，发现它还在用 M5 时期的假设：

```csharp
private static Vector3 ToWorld(Vector2F point) => new Vector3(point.X, 0f, point.Y);   // 旧代码
```

把二维平面点抬到"世界 y=0"再 `SamplePosition(..., 2.5f)`。
而 M7 批次 2 起地图是**下沉盆地**：谷底在 `y = -6`、装卸平台在 `-4.8`、塬面在 `0`
（`ValleyFloorY = -BasinTerrainProfile.RimHeight`）。从 y=0 用 2.5 米半径去够 -6 米的地面，
永远够不着 → 起终点原样落到 `CalculatePath` → 全部失败。

**为什么一直没被发现**：`IPathfindingService` 的契约规定了"寻路失败降级为直线推进"，
而灰盒地图大部分区域是开阔的，AI 走直线看起来只是"有点傻"。
换句话说，**这个降级策略把"寻路全坏"伪装成了"AI 行为不够聪明"**。

**做法**：不再猜高度，改用与敌人视图、AI 地面高度**同一套**分层采样
（`NavMeshGroundSampler.TrySample`：从低到高逐层试，取脚下那层）：

```csharp
private static Vector3 ToWorld(Vector2F point)
{
    return NavMeshGroundSampler.TrySample(point, out var height)
        ? new Vector3(point.X, height, point.Y)
        : new Vector3(point.X, 0f, point.Y);
}
```

改完后三条自检路径立刻全部可用（3 / 2 / 4 个途径点）。

**教训**：

- **"失败→降级"的设计必须配一个定期自检**，否则降级会静默地变成常态；
  服务器启动时用真实路径探三条（平地、高差、门洞）成本极低，收益是"寻路到底通不通"一眼可见；
- 地图改地形（谷底下沉、加平台）时，**所有"地面默认在 0 米"的老假设都要重新过一遍**。
  本项目里这类假设分布在寻路、地面采样、碰撞载体三处，M7 只改了中间一处。

## M9-P-17：服务器的碰撞与子弹整体浮在地面上方 6 米

**现象**：做 P2-2 导航自检时顺手核对实体高度，发现服务器给玩家创建的碰撞载体写的是：

```csharp
instance.transform.position = new Vector3(position.X, 0f, position.Y);   // 旧代码
```

谷底实际在 -6 米，于是服务器的角色胶囊、子弹起点全部悬在谷底上方 6 米。

**为什么严重**：它不会报任何错，只会让"服务器认为的世界"与"客户端看到的世界"错开一层：
子弹从掩体上方飞过、玩家可以"穿过"集装箱（服务器那边那层高度上没有障碍）、
AI（放在真实地面上）与玩家（浮空）互相打不着。
P2-1 验收之所以没暴露，是因为**两名玩家都浮在同一个高度**，互相对射仍然成立。

**做法**：

1. 新增 `Presentation/GroundProbe`：与玩家马达 `PlayerMotor` 用同一套规则
   （同样的遮罩、同样的"朝上才算地面"判据、同样的 0.35 米抬升上限），
   但做成**无状态的一次性采样**——服务器每帧从权威位置重新采样；
2. 玩家载体出生时用导航网格采样定高，之后每帧用 `GroundProbe` 贴地；
3. 每次有玩家加入时打一条 Info 痕迹（`碰撞载体就位：平面 (1.6, 0.0)，地面高度 -5.92 米`），
   让"两端高度是否对齐"在任何构建里都查得到。

**教训**：M9-P-13（枪口高度）是这条的一个特例。**凡是跨越"逻辑平面 ↔ 场景高度"这条边界的数值，
都要显式对齐一次，并且留一条能看见的证据**：枪口高度、胶囊尺寸、单位层、实体所在高度都算。

## M9-P-18：中文 PowerShell 脚本在 PowerShell 5.1 里报语法错误

**现象**：写好的验收脚本（`Library/ServerVerify/*.ps1`，内容含中文注释与中文输出）
用 `powershell -File` 执行时报一串莫名其妙的语法错误，
且报错里显示的中文全是乱码：

```
Write-Host ('鍚姩鍙傛暟锛? + ($serverArgs -join ' '))
Unexpected token ''))
The string is missing the terminator: '.
```

**根因**：Windows PowerShell 5.1 读取 **无 BOM 的 UTF-8** 脚本时按系统 ANSI 代码页解码。
中文变乱码之后，全角标点（`：`）被拆成了会影响解析的字节，于是字符串引号提前"闭合"。
（同一份脚本用 PowerShell 7 执行完全正常，因为 pwsh 默认按 UTF-8 读脚本。）

**做法**：验收脚本一律用 **pwsh（PowerShell 7）**执行：

```powershell
pwsh -NoProfile -File 'Library\ServerVerify\verify_server_navigation.ps1'
```

**教训**：这类"看起来像脚本写错了"的报错，先看**报错文本本身有没有乱码**——
有乱码就说明是编码问题，而不是语法问题，改语法只会越改越乱。
