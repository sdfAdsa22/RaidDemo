## M8-P-01：新建脚本"类型不存在"再次出现——这次定位到 GUID 级缓存

**现象**：批次 1 新增 `CodexMarker.cs` 后，编译稳定报两条
`CS0246: The type or namespace name 'CodexMarker' could not be found`，
并且**只有引用它的两个文件报错**——Meta 程序集自身编译通过，只是 DLL 里没有这个类型。
`recompile`、`AssetDatabase.Refresh(ForceUpdate)`、
`RequestScriptCompilation(CleanBuildCache)` 全套执行都不改变结果；
`Library/ScriptAssemblies/RaidDemo.Meta.dll` 时间戳一直停在几分钟前。

**定位过程**（这次的关键证据是资产导入状态）：

1. 用 `eval` 逐个读取资产类型：
   `AssetDatabase.GetMainAssetTypeAtPath(".../CodexMarker.cs")` 返回 **null**，
   而同目录正常参与编译的 `MetaCodex.cs` 返回 `MonoScript`；
2. 说明问题不在代码，而在**这个文件根本没有作为脚本资产被导入**；
3. 强制 `ImportAsset(ForceUpdate | ForceSynchronousImport)` 后类型变成 `MonoScript`，
   但编译清单仍然不认它——即 Unity 的脚本编译快照按 **GUID** 缓存的旧状态没有失效；
4. 把 `.cs` 与 `.meta` 一起移出工程再移回来（GUID 不变）仍然失败；
   **改写 `.meta` 里的 GUID** 再强制导入后，编译一次性通过。

**根因**：与 M7-P-09 同一个家族——命令行工具链下"把文件写到磁盘"和"让编译管线收录它"是两件事。
本次补充了一条更精确的结论：**卡住的状态是按资产 GUID 记录的**，
因此"删除再原样重建"（GUID 不变）无法自愈，必须换 GUID（或改名换路径）。

**解法（按顺序执行）**：

1. 新建脚本后立刻对该文件执行一次
   `AssetDatabase.ImportAsset(path, ForceUpdate | ForceSynchronousImport)`；
2. 用 `GetMainAssetTypeAtPath` 断言它确实是 `MonoScript` 再触发编译；
3. 若仍然不进编译清单：改 `.meta` 的 GUID（或改名/换目录）后重新导入——
   本次即 `CodexMarker.cs` 换 GUID 后恢复；
4. 触发编译时，首选 `unity command ... recompile`；它报告 `up_to_date` 而结果明显不对时，
   先怀疑编译快照，而不是怀疑代码。

**教训**：新增文件的验收标准不是"文件在磁盘上"，而是
"资产类型是 MonoScript、且 DLL 里能反射到新类型"。两条断言都做，问题会在 30 秒内暴露。

## M8-P-02：`capture_game_view` 的相对路径落在 `Assets/` 下

**现象**：执行
`unity command ... capture_game_view --save_path "Library/M7Preview/codex_ui.png"`
时命令返回成功，但截图出现在 `Assets/Library/M7Preview/codex_ui.png`——
`Assets/` 目录里多出一棵包含 PNG 与 `.meta` 的临时文件树，并被 Unity 当作贴图导入。

**原因**：`capture_game_view` 的 `save_path` 参数以 **authoring root（`Assets/`）** 为基准解析，
不像 `M7PreviewRenderer` 那样以工程根为基准。

**解法**：

- 临时截图不要给相对路径；需要落在 `Assets/` 之外时传**绝对路径**；
- 本项目的既定做法是走 `M7PreviewRenderer`（它自己按工程根写 `Library/M7Preview/`），
  需要命令行截图时才用 `capture_game_view`；
- 已经落进 `Assets/` 的临时文件要连 `.meta` 一起移出，避免被误提交
  （本次移到了 `Library/CodexCaptures/`）。

**教训**：凡是"往磁盘写东西"的命令，先确认**基准目录**是工程根还是 `Assets/`。
两者混用时症状都只是"文件出现在想不到的位置"，不会报错。

## M8-P-03：子代理任务再次空投递

**现象**：批次 1 期间派出的素材调研子代理在开工数十秒后回报
"这一轮你还没提出具体要做的事"，随后列了一串"你想先做哪个"——
与 M4 的 C-01、M5 的 M5-P-01 是同一个症状：**任务消息没有送达子代理**。

**处置**：用 `followup_task` 重新投递同一份任务文本（含完整约束与交付物清单）。

**教训**：本环境下子代理消息投递仍不可靠。派活之后**必须检查第一轮回报是不是在复述任务**；
如果子代理反问"要做什么"，说明内容丢了，重发即可，不要等它自己恢复。
关键路径上的工作不要只押在子代理上。

## M8-P-04：同一个路径，终端与 Unity 进程读出不同文件

**现象**（批次 2 实机验证期间）：同一个存档路径
`C:\Users\DongSu\AppData\LocalLow\RaidDemo\RaidDemo\raid_demo_save.json`，
用 PowerShell 读是 3239 字节（金币 5900 的旧档），用 Unity 进程内的 `File.ReadAllText` 读却是
939 字节（金币 5000 的新档）；两边打印的路径字符串完全一致。

**定位过程**（关键是把"谁写谁读"分开验证）：

1. 让 Unity 写一个探针文件 `codex_probe.txt`：PowerShell **能看到**它；
2. 让 PowerShell 写一个探针 `codex_ps_view.json`：Unity **找不到**它（`Could not find file`）；
3. 让 Unity 把"它看到的存档"复制成 `codex_unity_view.json`：PowerShell 读到的就是 Unity 看到的版本；
4. 结论：**我的命令终端运行在一个文件系统覆盖层里**——
   它的写入不会落到真实磁盘，读取则可能拿到覆盖层里的旧副本；
   而 Unity 进程读写的是真实文件。

**解法 / 规矩**：

- 凡是操作**游戏真实数据目录**（`LocalLow/<公司>/<产品>/`）的文件，
  一律通过 Unity 侧执行（`unity command eval` 里调 `System.IO`），不要用我的 shell；
- 工程目录（`D:\unity game\demo`）内的写入不受影响：
  整个项目就是这么改出来的，Unity 每次都读到了新源码与文档；
  受限的是 `%USERPROFILE%\AppData\LocalLow\` 这类用户数据目录；
- **通用做法**：只要"谁看到的文件不对"成为嫌疑，先做上面三步探针实验，不要猜。

**教训**：跨进程核对文件时，"路径一样"不等于"文件一样"。先写探针、再下结论。

## M8-P-05：改了公司名 / 产品名之后，玩家进度"不见了"

**现象**：批次 2 期间把 `companyName / productName` 从 `DefaultCompany / demo` 改成
`RaidDemo / RaidDemo`（为了让 exe 与窗口标题像个正式作品）。改完之后：

- 安全屋显示金币 5,000（新档数值），仓库空的；
- 而真实磁盘上明明还有一份 5,900 金币、13 件仓库物品的存档。

**原因**：`Application.persistentDataPath` 的路径由 **公司名 + 产品名**拼出，
改名等于换了存档目录：旧进度留在 `LocalLow/DefaultCompany/demo`，
游戏从此只读写 `LocalLow/RaidDemo/RaidDemo`。

**修复**：把旧目录的三份存档（主档、`.bak`、`.hold`）整体复制到新目录，
用 `SaveFileStore.TryLoad` 验证：`ok=True, money=5900, stash=13`；
随后的 Play 冒烟也确认金币 5,900、仓库 13 件、AK-74 在装备槽。

**教训**：

- **改名是"数据迁移事件"而不是纯文案改动**。凡是改 `companyName / productName` 的提交，
  必须同时迁移或明确声明放弃旧存档，并在提交信息里写清楚；
- 迁移要在**真实文件系统**上做（见 M8-P-04，我的 shell 写入可能进不了真实磁盘）。

## M8-P-06：编辑器每次 Play 都复用内存进度，从不读存档

**现象**：多次重新进入 Play 模式，金币始终是 5,000（新档）、测试时临时添加的物品
在**下一次 Play 里还在**；控制台偶尔出现"主存档读取失败"。用反射检查发现
`RaidFlowController` 里的 `MetaProgress` 不是从存档还原出来的那一份。

**原因**：项目开了 `Enter Play Mode Options` 的
**禁用域重载（Disable Domain Reload）+ 禁用场景重载（Disable Scene Reload）**。
两者一起开之后，静态单例（`RaidFlowController.s_Instance`）与它持有的
`MetaProgress` 会跨 Play 会话存活：

- 第一次 Play 读档，之后的每次 Play 都用旧的内存对象——**存档改动不会被重新加载**；
- 测试期间临时塞进背包的物品也不会随 Play 结束消失。

**修复**：把 `EditorSettings.enterPlayModeOptions` 设回 `None`（即重新启用两种重载）。
此后每次 Play 与正式版一样"从存档冷启动"，这一整类"改了存档却看不到效果"的
困惑随之消失。

**教训**：

- 快速迭代选项（禁用重载）的代价是**编辑器行为偏离正式版**；
  对于一个以"存档 + 经济循环"为核心的项目，这个代价不划算；
- 遇到"数据不刷新 / 状态跨会话残留"时，先确认 Play 模式的重载设置，
  再去怀疑业务代码。

## M8-P-07：滚轮"滚了十几圈只动一点点"——输入量纲差 120 倍

**现象**：商人货架接上滚轮滚动后，负责人反馈"滚了十几圈就动一点点"。
代码里写的是"一格 48 像素"，按 Windows 的 `WHEEL_DELTA = 120` 折算系数 0.4，
纸面上完全正确。

**定位**：

1. 读 Input System 包源码：`Mouse.scroll` 是 `DeltaControl`（每帧累计、帧末清零），
   但**数值量纲由平台后端决定**；
2. `InputSystemUIInputModule` 里的换算是
   `scrollDelta / InputSystem.scrollWheelDeltaPerTick`——
   而新版 Input System 在 Windows 上把这个常量接成平台值，
   **一格 = 1.0**（而不是 120）；
3. 于是 `1.0 × 0.4 = 0.4 像素/格`：十几格 = 几像素，症状完全对上。

**解法**：不假设量纲，**先归一成"格数"再换算像素**：

| 原始值绝对值 | 视为 | 归一 |
| --- | --- | --- |
| > 10 | 120 制（老平台 / 部分设备） | `value / 120` |
| ≤ 10 | 已归一（新版 Windows 后端） | `value` |

归一后统一乘"每格像素"（本项目取一行 = 48 像素）；键盘 ↑↓ 也换算成格数
（0.25 格/帧）走同一条通道。

**验证**：反射调用滚动入口，归一制 `-1` 与 120 制 `-120` 都让内容移动 48 像素。

**教训**：

- **"多少输入 = 多少位移"这类换算，第一个要问的是"单位是什么"**，
  而不是先写系数；跨平台输入尤其如此（滚轮、触控板、手柄扳机都有类似的历史包袱）；
- 兼容两种量纲的代价只有三行代码，比"赌一个平台常量"便宜得多；
- 与 M8-P-06 连起来看：这两条都属于"我的假设与运行环境不一致"，
  排查时优先用**实验**（打印真实输入值）而不是推理。

## M8-P-08：给运行中的编辑器登记新层——走编辑器 API，不要改文本

**背景**：M8 基线冻结需要新增 `Units` 层（U-50 修复的基础，见第 12 号文档第二十二节）。

**为什么不能直接改文件**：`ProjectSettings/TagManager.asset` 与场景、预制体一样，
**权威副本在编辑器进程里**，磁盘文件只是它的镜像。在编辑器运行期间做纯文本编辑，
既不确定当前进程是否认，也可能在编辑器下次写回设置时被内存副本覆盖。

**做法**：让编辑器改自己——用 `SerializedObject` 走资产管线，改完立即保存：

```csharp
var assets = AssetDatabase.LoadAllAssetsAtPath("ProjectSettings/TagManager.asset");
var so = new SerializedObject(assets[0]);
var layers = so.FindProperty("layers");
layers.GetArrayElementAtIndex(6).stringValue = "Units";
so.ApplyModifiedProperties();
AssetDatabase.SaveAssets();
```

接入方式：`unity command --project-path <工程> eval --code '<上面的脚本（压成一行）>'`。

**验证**：同一进程内 `LayerMask.NameToLayer("Units")` 立即返回 6；
随后 `git diff` 里能看到编辑器重新序列化的结果——Unity 6 会把 `serializedVersion` 从 2 升到 3，
并把多余的渲染层占位合并成 `m_MigratedRenderPipelines: []`，**这是正常重写，不是损坏**。

**教训**：命令行会话修改任何"编辑器持有"的资产（`ProjectSettings/`、场景、预制体、材质），
一律走编辑器 API；文本编辑只适用于编辑器关闭、或纯随工程走的数据文件（`.json` / `.md` / 代码）。
