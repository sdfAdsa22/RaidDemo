## M10-P-01：外部编辑 `ProjectSettings.asset` 不生效——打出一个"名不符实"的包

**现象**：把 `ProjectSettings.asset` 里的 `bundleVersion` 从 `0.10.0` 改成 `0.10.1`，
执行菜单 ① 构建，产物却仍然落在 `Builds/Client/0.10.0/`，生成的清单也是 `0.10.0`。
再检查磁盘，文件里的值确实已经是 `0.10.1`。

**定位过程**：

1. 读编辑器里的真值：`eval` 执行 `PlayerSettings.bundleVersion` → 返回 `0.10.0`，
   而磁盘文件里是 `0.10.1`——**编辑器内存与磁盘不一致**；
2. 用编辑器 API 写入（`PlayerSettings.bundleVersion = "0.10.1"; AssetDatabase.SaveAssets()`）
   之后，两者才一致；
3. 后续又发现更隐蔽的一层：在"内存 0.10.0 / 磁盘 0.10.1"的窗口期里构建出来的那个包，
   目录名是 `0.10.0`（取内存值），**而包内嵌的版本号是 0.10.1**（玩家构建读磁盘工程设置）。

**根因**：Unity 打开工程后把 `ProjectSettings` 读进内存，之后它会按内存状态重写这些文件；
用外部工具（本工程的补丁工具）直接改磁盘，既不会立刻生效，也可能被覆盖。

**解法**：

1. 改版本号一律走编辑器 API（菜单或 `eval`），不要直接改文本；
2. 构建后**校验产物内嵌版本**：`Builds/Client/<版本>/RaidDemo_Data/globalgamemanagers`
   里应当出现当前版本号字符串——本轮正是靠它发现"名叫 0.10.0 的包其实自称 0.10.1"；
3. 需要一个"真实的旧版本包"做跨版本演练时，先设回旧版本号构建，再设回新版本号重建，
   两次构建之间不要手工改文件。

**教训**：凡是"参数在编辑器内存里、我却在磁盘上改"的设置，都要用一次读回来自证。
版本号尤其危险——它同时决定产物目录名、清单版本和握手判定，三者不一致时排查会绕远路。

## M10-P-02：HTTP 更新源下 catalog 加载失败，内容热更静默退回本体

**现象**：客户端跑着最新的 0.10.1，日志里出现
`[热更] 资源已是最新（0.10.1.c9bdad504）`，紧接着
`[热更] catalog 加载失败，使用本体自带内容`；游戏能进，但内容层的改动（数值表）没生效。
完整异常是：

```
Unable to load ContentCatalogData from location
  <persistentDataPath>/content/0.10.1.c9bdad504/catalog_0.10.1.hash.
Failed to cache catalog to location http://127.0.0.1:8090/content/558132896.bin.
System.IO.IOException: 文件名、目录名或卷标语法不正确。
  : '<安装根>\http:\127.0.0.1:8090\content'
```

**定位过程**：

1. 报错里的路径把 URL 当成了相对路径、拼在进程工作目录后面 → 说明**有人把 URL 交给了
   "按路径写文件"的分支**；
2. 顺着 `Addressables` 的 `ContentCatalogProvider` 找到那句 `Failed to cache catalog to
  location {localCachePath}`：它要写的 `localCachePath` 正是被改写过的那条地址；
3. 回到本工程的寻址重写函数：它只判断"能不能从地址里取出文件名"，于是
   Addressables 自己的 catalog 缓存路径（`com.unity.addressables/<哈希>.bin`）
   也被当成了内容层文件，本地没有就翻译成更新源 URL——**要写进去的目标被换成了下载地址**。

**根因**：寻址重写缺少"这个地址是不是我的内容层"这一层判断。
"能取到文件名"对任何路径都成立，因此那条件等于没条件。

**解法**：重写函数改为三步——① 本地缓存里有同名文件 → 用本地；② 否则只有
`content/` 命名空间（与 Addressables 的 RemoteLoadPath 一致）的地址才翻译成 URL；
③ 其余（本地绝对路径、Addressables 的缓存路径、包内资源）原样返回。
判断抽成 `HotUpdateRuntime.IsContentLayerAddress`，配 2 条 EditMode 测试。

**教训**：凡是"改写别人给的路径"的钩子，都要能回答"这条路径属于哪个命名空间"。
改错的代价是静默降级：功能还在、日志只有一行警告，而验收看的是数值。

## M10-P-03：玩家构建会写 Addressables 产物目录，且不清空

**现象**：按"① → ⑥"（跳过 ⑤ 资源构建）生成清单后，`Builds/Update/0.10.1/manifest.json`
的资源层多出两个文件：`catalog_0.10.0.bin` 与 `catalog_0.10.0.hash`——上一个版本的 catalog。

**定位过程**：

1. 清单是"扫描资源产物目录"生成的，看目录即见两个版本的 catalog 并存；
2. ⑤ 会在构建前清空输出目录，但本轮没有执行 ⑤；
3. 那 0.10.0 的 catalog 是谁写的？——**玩家构建（菜单 ①）**：Addressables 的
   `BuildRemoteCatalog` 会把 catalog 也写到远程构建目录，而玩家构建不清空它。

**根因**：目录清理只挂在 ⑤ 上，而"谁往这个目录写"有两个来源。

**解法**：菜单 ⑥ 在生成清单前清掉"文件名里不带当前版本号"的 catalog（只删构建产物）。
完整顺序保持 ① → ④ → ⑤ → ⑥。

**教训**：产物目录的清理责任不能只挂在一个步骤上。判断"哪些文件属于本次产物"时，
用版本号或哈希这类**自带标识**去判定，比"相信上一步已经清干净"可靠。

## M10-P-04：验收脚本的等待条件太宽，判出一个假失败

**现象**：版本握手验收脚本第一次跑出 `A1 同版本客户端进房成功 —— 30 秒内未见房间建立`，
而服务器日志里明明写着 `房间「默认房间」已创建：房主 2「握手甲」`。

**定位过程**：

1. 脚本等待的日志短语是 `房间「`——它想等"房间建立"；
2. 但服务器**启动日志**里就有一句 `默认房间名「默认房间」`，第一次轮询立刻命中；
3. 于是判据拿到的是一份"房间还没建立"时的快照，随后无论发生什么都不会再刷新。

**根因**：等待条件必须是"只在目标事件里出现的短语"，而 `房间「` 在启动期就出现。

**解法**：改成 `已创建：房主|加入房间（`——这两个短语只可能出现在真正的房间事件里。
同一条脚本里的"被拒者未进入名册"判据也有类似问题：它原本检查"日志里有没有这个名字"，
而拒绝日志本身就带名字，于是永远失败；改为只匹配"房间记录"形态的行。

**教训**：写"轮询日志等事件"时，先问一句"这个短语会不会在别处出现"。
配套的一个技巧：判据失败时把日志原文附在结论后面——本轮正是靠它一眼看出是脚本的问题。

## M10-P-05：为测试"非法路径"而写下绝对路径，被自己的护栏拦下（M9 家族复发）

**现象**：EditMode 全量测试 682 条里挂掉 1 条：
`PathRulesTests.Assets_DoNotContainAbsolutePaths :: 发现 3 处绝对路径`，
三处全部来自新写的测试文件——测试里为了断言"本地绝对路径不该被识别为内容层地址"，
直接写了 `C:/Users/...` 与 `D:\unity game\...` 字面量。

**根因**：与 M9 的同名条目同一个模式——**为了让测试覆盖非法输入，把非法输入写进了源码**。
而本工程的规范是"源码与配置不含任何本机路径"（否则他人克隆后无法直接运行）。

**解法**：路径改为运行时拼出来，测试意图不变：
`Path.Combine(Application.persistentDataPath, "com.unity.addressables", "x.bin")`、
`Path.Combine(Path.GetTempPath(), "RaidDemo", "RaidDemo_Data")`。

**教训**：护栏扫描的是**源码文本**，不区分"这是测试数据"。
凡是"要喂一个绝对路径"的用例，一律用 `Path.Combine` + `Application.*` 现场拼。

## M10-P-06：测试程序集漏引用 `RaidDemo.HotUpdate`

**现象**：新增 `HotUpdateAddressingTests.cs` 后编译报
`CS0234: 命名空间 'HotUpdate' 不存在于 'RaidDemo' 中（是否缺少程序集引用？）`。

**根因**：`RaidDemo.Tests.EditMode.asmdef` 的引用列表里没有 `RaidDemo.HotUpdate`——
工程按模块拆程序集，测试程序集需要显式列出每一个被引用的模块
（M4 的"程序集引用漏配"是同一个家族）。

**解法**：在 asmdef 的 `references` 里补上 `RaidDemo.HotUpdate`。

**教训**：新增测试用到某个模块时，先看 asmdef 的引用列表，而不是先怀疑命名空间写错。

## M10-P-07：静态中文字体资产与新增文案

**现象**：新增的握手提示里有一个字（`致`，来自"不一致"）不在字体图集里，
真机上会显示成空白或方框；另一方面，运行时由玩家输入的昵称
（例如 `跨版本…` 的 `跨`）也可能缺字——字体是**静态**图集，运行时不再扩页。

**定位过程**：

1. 用 `eval` 逐字检查：`font.HasCharacter(c)`，缺哪个字一目了然；
2. 再看字符集收集范围 `UiAssetTool.CollectUiCharacters()`：它只扫描
   `Modules/UI`、`Modules/Meta`、`Modules/Data/Content` 与 `Bootstrap` 顶层，
   而**大厅与服务器侧的失败原因文案在 `Bootstrap/Session/` 下**——
   它们同样会原样显示在界面上，却没有进收集范围，字符齐不齐纯靠巧合。

**解法**：

1. 把 `Assets/Game/Bootstrap/Session/Lobby` 与 `.../Session/Network` 加入扫描目录
   （字符集从 780 → 869，图集仍是 2 页，余量充足）；
2. 重建字体资产：菜单 `RaidDemo/UI/重建中文字体资产`；
3. 用 `font.HasCharacter` 复验新文案零缺字。

**遗留（已知取舍）**：运行时输入的自由文本（昵称、房间名）永远可能缺字。
本工程的取舍是"图集可控优先"，因此这类文本只保证常用字；
真要覆盖任意汉字，需要把字体改回动态模式并承担扩页失败的风险（M7 踩过一次）。

## M10-P-08：子代理任务再次空投递（M4 / M5 / M8 之后的第四次复发）

**现象**：一次只读复核任务里派了 5 个子代理，其中 **3 个**收到的是"只有环境、没有任务正文"的上下文，
于是它们各自回了一句"请告诉我做什么"就结束了——任务清单一条没做，但也**没有报错**。
同一个任务重发给同一个代理，仍然有可能再次空投递（其中一个连续两次收不到）。

**与旧结论的关系**：M8-P-03 记的是"子代理回报没收到任务"，本轮补充了两条更具体的观察：

1. 空投递**不是必现**：同一次派发里，有的代理正常拿到正文并按格式产出 | 有的完全拿不到，
   因此不能"看它起来就算了"；
2. **换代理比重发更有效**：连续两次失败的代理，换一个新代理（新任务名）后一次成功。

**做法（本次实际采用的顺序）**：

1. 派发后**必须先确认对方拿到的正文**——第一次回收时如果答案是"请告诉我做什么"，立刻重发；
2. 重发用 `followup_task`（会触发新回合），不要指望 `send_message`（它不触发回合）；
3. 同一代理连续两次空投递就**换新代理**，不要让同一条线卡在重试上；
4. 关键路径留**兜底**：本轮 72 条里，§三/§六 是主代理自己核的、§四/§五 由代理产出，
   所以即使代理全线失败，结果也只是慢，不会没有；
5. 派发时把"产出格式 + 硬约束（只读、不改文件）"写进正文，这样即使部分代理只完成一半，
   收上来的也是能直接拼进文档的结构化结果。

**教训**：多代理提速的前提是"任务真的送到了"。把"确认送达"当成派发的第一步，
比事后追着问"你为什么不干活"便宜得多。

## 附：本轮用到的复现命令

```bash
# 版本握手：1 服务器 + 2 客户端，6 条判据
pwsh -NoProfile -File Tools/Lobby/verify/p6_version_handshake_check.ps1

# 启动器更新的两段（本机源）
RaidDemo.Launcher.exe --check  --source http://127.0.0.1:8090 --root <安装根>
RaidDemo.Launcher.exe --update --source http://127.0.0.1:8090 --root <安装根>

# 本机更新源（图省事的只读/写两种模式都在这里）
```
