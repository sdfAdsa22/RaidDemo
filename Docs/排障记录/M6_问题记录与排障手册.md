## M6-P-01 自动存档写进交易的中间状态

**症状**：购买流程在设计与代码上都分三步——扣钱、创建物品、放进仓库。
自动存档订阅的是 `MetaProgress.Changed`。最初 `TrySpend()` 在扣钱时立刻广播变化，
于是自动存档有机会在物品入仓之前写盘，出现「金币少了，但仓库里没有枪」的存档。

**定位**：阅读 `BuyItemCommandHandler` 的执行顺序，发现广播点藏在
`MetaProgress.TrySpend()` 内部，而物品放置发生在它之后。

**根因**：把「数据变化」当成了「事务完成」。一次购买其实是一个原子操作，
中途任何一次广播都可能被存档、界面或联机同步当成最终状态。

**做法**：
- `MetaProgress.AddMoney()` / `TrySpend()` 只改数值，不再广播。
- 命令处理器在「金币与物品都提交完成」之后调用一次 `NotifyChanged()`。
- 任务领奖同样遵循「先检查空间 → 发钱 → 放物品 → 统一广播一次」。

**教训**：有自动存档 / 网络同步的系统里，**广播点就是事务提交点**。
所有复合操作都要问一句：广播发生时，另一件状态改完了吗？

## M6-P-02 新游戏没有存档时物品目录没有注入

**症状**：有存档时任务奖励正常，新开局时完成任务却无法解析奖励物品 ID。

**定位**：`RaidFlowController.ApplyPendingSave()` 在 `m_PendingSave == null` 时直接返回，
只有「读到存档并还原」的分支调用了 `Progress.AttachCatalog(catalog)`。

**根因**：局外进度在场景加载前创建，那时还拿不到场景里的物品目录，
因此目录必须延迟注入；但实现时只覆盖了「读档」路径，漏掉了「新游戏」路径。

**做法**：两条路径都在返回前调用 `Progress.AttachCatalog(catalog)`；
读档失败的回退路径也补上同样的调用。

**教训**：延迟注入的依赖，必须**逐个穷举进入业务的路径**：
新游戏、读档成功、读档失败回退。少一条路径，症状就会只在某一种启动方式下出现。

## M6-P-03 仓库标题与仓库总价值重叠

**症状**：商人界面右上角，「仓库总价值 0」与仓库网格标题「仓库（交易来源）」
叠在同一行，文字互相压住。截图验收时才发现。

**定位**：金币在 y=16、仓库总价值在 y=46；仓库网格从 y=56 开始，
但网格自己还会在顶部画 22 像素高的标题，于是标题实际落在 56~78，
与 y=46 的第二行文字距离不足。

**根因**：布局数字按「文字行高」预留，却没有把**子视图自带的标题高度**算进去。
这与 M2-A08 的「布局数字不能写死」是同一类问题的另一种表现。

**做法**：仓库网格起点从 56 下移到 84，为两行常驻信息留出完整空间。

**教训**：凡是「面板 + 自带标题」的复合视图，定位时要把标题高度算进占用。
灰盒阶段最省事的验收方式就是**截图看一眼**，而不是只在脑内推坐标。

## M6-P-04 锁定任务仍显示可点击的蓝色按钮

**症状**：任务页里，「未解锁」和「已完成」的任务右侧仍有一个亮蓝色按钮，
看起来可以点击；点下去才提示「当前不可操作」。

**定位**：任务行的按钮始终存在，只改了文字，没有改可操作性。

**根因**：把「状态文字」与「可执行动作」混在同一个控件上。
玩家看到的蓝色按钮天然意味着「可以按」，而系统却要求他先按一次才知道不能按。

**做法**：`RefreshQuestRows()` 中按状态决定按钮是否激活：
只有 `可接取 / 进行中 / 可领取` 显示按钮，其余状态只显示状态文字。

**教训**：**不可操作必须在视觉上不可操作**，而不是点击后报错。
这条同样适用于库存为空时的出售按钮、余额不足时的购买按钮。

## M6-P-05 存档与任务接线后两个装配文件同时超限

**症状**：`PathRulesTests.SourceFiles_DoNotExceedLineLimit` 报出
`RaidFlowController.cs` 414 行、`SceneBootstrap.Raid.cs` 424 行。

**定位**：两处都是「在原有职责上继续追加方法」导致的增长：
RaidFlowController 追加了整套存档，SceneBootstrap.Raid 追加了任务追踪与受伤标记。

**根因**：功能边界已经发生变化，但文件边界没有同步调整。

**做法**：
- 拆出 `RaidFlowController.Save.cs`（读档 / 自动存档 / 强退惩罚）。
- 拆出 `SceneBootstrap.Raid.Quests.cs`（击杀 / 受伤 / HUD 追踪）。

**教训**：每接入一个**新系统**（存档、任务），就先问「它应该落在哪个 partial」，
而不是先写进最近的文件。行数限制不是形式要求，它是在提示职责已经混在一起。

## M6-P-06 商人交易后常规背包界面可能显示过期仓库

**症状**：在商人界面买完东西后关掉商人、按 `Tab` 打开常规背包，
仓库面板可能看不到刚买的物品；再触发一次背包操作后它才出现。

**定位**：背包界面只在收到 `InventoryChangedEvent` 时重画。商人买卖走的是
`MetaProgress.Changed` 链路，只发布了 `WalletChangedEvent`，没有发布背包变更事件。
而 `OpenContainerView()` 在容器 ID 不变时直接显示旧视图，不做刷新。

**根因**：同一个仓库被两套界面读取，但交易链路只通知了其中一套。
依赖「另一个界面碰巧会发事件」本来就是脆弱的。

**做法**：`OpenContainerView()` 在每次显示前主动调用一次 `RefreshAll()`。
即使某条数据变更路径没有发出背包事件，打开界面时看到的也是当前权威数据。

**教训**：**界面打开时必须从权威数据重画一次**，事件只负责"打开期间的增量刷新"。
这条与 `InventoryGridView` 的只读定位是同一原则的两面。

## M6-P-07 实机验证交易时写进了真实存档

**症状**：用播放模式验证批量出售界面时，先在商人处购买了一件手枪与一个小绷带。
随后发现仓库里有一批预先存在的战利品（AK、钢盔、背心、背包、弹药、绷带），
说明这次验证写入的是玩家真实进度，而不是干净的新档。

**定位**：读取 `Application.persistentDataPath` 下的主档与备份：
主档余额 2,800、绷带 x2；备份余额 3,200、绷带 x1；两次购买正好是 1,800 + 400。
由此反推出购买前的原始状态是余额 5,000、绷带 x1、没有 PM 手枪。

**根因**：`MetaProgress.Changed` 会在每次买卖后自动存档，而播放模式使用的
就是玩家的真实存档目录。测试写操作与正常游玩写操作走的是同一条路径，
备份文件只能防"写坏"，防不了"写对但内容被测试改掉"。

**做法**：从备份反推原始状态，移除测试购买的手枪、把绷带恢复为 1 个、
补回 2,200 金币，然后保存；主档与备份都回到验证前的状态。

**教训**：**涉及经济的实机验证必须先隔离存档**。优先做法是临时把存档目录指到
测试路径，或在验证前复制一份 `raid_demo_save.json`；至少要避免在真实进度上
执行买卖、任务领奖这类会改变资产的操作。界面截图与只读观察不受此限制。

## M6-P-08 水平胶囊扫掠把坡道当成墙

**症状**：玩家沿装卸平台的坡道向上走，在坡道中段停住；移动输入有效，
但没有报错，看起来像被一堵看不见的墙挡住。

**定位**：把移动模拟的状态逐步打印出来，发现水平胶囊扫掠在坡道表面产生了命中。
坡道表面法线与竖直方向夹角约 16 度，本应是可行走面，却被当成障碍参与滑动/阻挡。

**根因**：`CapsuleCast` 只回答"胶囊碰到了什么"，不区分脚下可站立斜面与竖直墙面；
碰撞适配器把两者都当成阻挡。

**做法**：忽略法线与竖直方向夹角 ≤45° 的命中，并在脚底被挡住时把胶囊抬高
0.35 米复测：低台阶与坡道接缝可以通过，1.2 米平台边缘与 2.2 米栅栏仍会被挡住。

**教训**：物理查询给的是几何事实，**"这算不算障碍"是玩法语义**，
必须由适配器翻译；把原始命中直接当规则，坡道、楼梯这类地形就会变成墙。

## M6-P-09 地面探测取最高命中，横向栅栏顶被当成地面

**症状**：玩家走到黑色栅栏或横梁下方时，会被自动抬到其顶面。

**定位**：旧地面探测从角色上方 4 米向下打射线，并取所有命中的最高点。
在播放模式里创建一个位于角色头顶 2.1 米的横向碰撞体，
发布移动事件后角色 y 直接从 0 变成碰撞体顶面高度。

**根因**：查询没有限定"脚下"的垂直范围，头顶/上方物体的顶面也满足"法线朝上"。

**做法**：地面探测只接受当前地面高度 +0.35 米以内的命中；
传送时使用不受限制的采样，避免调试传送被台阶限制挡住。

**教训**：向下射线不等于脚下地面。任何"求地面高度"的实现都必须同时约束
**垂直范围**与**可站立法线**，否则角色会被任何头顶平台吸上去。

## M6-P-10 主菜单与结算被当成战局操作状态，光标每帧被重新锁定

**症状**：主菜单点击一次后鼠标消失；按钮点不中；Esc 直接退出游戏。
结算界面同样可能只能按 Esc、无法点击按钮。

**定位**：安全屋的锁定条件只检查背包、商人、地图是否打开，
没有检查 `RaidFlowController` 的流程状态；主菜单显示时这三个界面都没开，
于是 `SafeHouseBootstrap.Update` 每帧执行 `SetCursorLock(true)`，
把 `ShowMainMenu()` 里的解锁结果覆盖掉。战局场景的结算界面存在同族写法。

**根因**：把“有没有界面打开”当成了“是否需要鼠标”的完整条件。
主菜单与结算不是操作面板，它们是**流程状态**，需要单独判断。

**做法**：
- 抽出 `CursorLockPolicy`：`!uiOpen && !stateNeedsMouse` 才锁定；
- `MainMenu / Result` 状态主动释放光标；
- 主菜单二次确认期间 Esc 先取消确认，隐藏菜单时重置确认状态。

**教训**：输入策略必须同时读取**界面状态**与**流程状态**。
只检查其中一半，症状会表现为“第一次点击正常、之后所有按钮都失灵”，
而逻辑层没有任何报错，极难从业务代码定位。

## 按症状速查

| 症状 | 先查什么 | 大概率原因 |
| --- | --- | --- |
| 存档里出现「钱少了但东西没到」 | 找到广播点，确认它在几步之后 | 广播发生在事务中途（M6-P-01） |
| 新开局某个依赖资产的功能失效，读档却正常 | 看延迟注入是否覆盖了所有启动路径 | 只给读档路径注入了依赖（M6-P-02） |
| 面板文字与子视图标题重叠 | 把子视图标题高度算进布局 | 只按文字行高预留（M6-P-03） |
| 明明不可用的操作仍显示成可点按钮 | 按状态隐藏或置灰控件 | 可操作性与视觉不一致（M6-P-04） |
| 新接入一个系统后突然撞行数上限 | 先按新系统拆 partial，再继续写 | 功能边界变了，文件边界没变（M6-P-05） |
| 商人里买的东西在常规背包里看不到 | 看交易链路有没有发出背包事件；界面打开时是否重画 | 事件缺口 + 打开时不刷新（M6-P-06） |
| 实机测试后发现玩家存档被改 | 检查 `Application.persistentDataPath` 下的主档与 `.bak` | 测试写进了真实存档（M6-P-07） |
| 玩家在坡道中段被无形墙卡住 | 打印胶囊扫掠命中面的法线 | 可行走斜面被当成障碍（M6-P-08） |
| 玩家走到栅栏/横梁下自动升到上方 | 检查向下射线是否取最高命中 | 横向物体顶面被当成地面（M6-P-09） |
| 主菜单点击一次后鼠标消失、按钮点不中 | 看每帧的光标锁定条件有没有读取流程状态 | 主菜单/结算被当成战局操作状态（M6-P-10） |
