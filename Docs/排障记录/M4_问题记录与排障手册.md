## C-01：子代理的任务消息没有送达，代理空转

**症状**

派发子代理后，代理的回报是"我还没有收到指令，消息队列是空的"，
但它在等待期间自行做了一遍只读侦察。同一份任务改用"跟进消息"重发一次，结果相同。

**定位过程**

检查工作区：没有任何属于子代理的改动入库，说明它确实没有开始执行任务。
两次投递（首次派发 + 跟进）都未生效，且代理自身的工具是正常工作的（侦察有输出）。

**根因**

当前环境下的子代理消息投递不可靠。**没有进一步定位到工具侧的具体原因**，
因此记为"已知不可用"，不作为项目的技术结论。

**做法**

改为自己执行原本打算委派的两块工作（NavMesh 实现 + 场景生成器改动、UI 反馈），
并在需要并行时优先选择**互不重叠的文件**。

**教训**

**"已派发"不等于"已在执行"。** 委派之后必须核对产出（工作区是否真的出现改动、
代理是否回报了具体进展），而不是等它自己汇报。发现投递失效后，
不要在同一个通道上反复重试——那只会把时间花在等待上。

## C-02：只给主程序集加了包引用，忘了同目录的 Editor 程序集

**症状**

```text
Assets\Game\Bootstrap\Editor\GreyboxSceneBuilder.cs(125,47): error CS0246:
The type or namespace name 'NavMeshSurface' could not be found
```

**定位过程**

`RaidDemo.Bootstrap.asmdef` 里已经加了 `Unity.AI.Navigation`，编译仍然报错。
报错文件位于 `Bootstrap/Editor/`，而该目录有自己的 asmdef。

**根因**

`RaidDemo.Bootstrap` 与 `RaidDemo.Bootstrap.Editor` 是两个程序集，引用不能继承。

**做法**

给 `RaidDemo.Bootstrap.Editor.asmdef` 也加上 `Unity.AI.Navigation`。

**教训**

加程序集依赖时，把**同一目录树下的所有 asmdef** 当成一个整体检查一遍，
而不是看到主文件能编译就当作完成。

## C-03：包里的组件类与它用到的枚举不在同一个命名空间

**症状**

```text
Assets\Game\Bootstrap\Editor\GreyboxSceneBuilder.cs(127,35): error CS0103:
The name 'NavMeshCollectGeometry' does not exist in the current context
```

`NavMeshSurface` 已经能解析了，但与它配套的枚举解析不了。

**定位过程**

直接在包缓存里读源码（`Library/PackageCache/com.unity.ai.navigation@.../Runtime/NavMeshSurface.cs`）：

```csharp
using UnityEngine.AI;              // ← 枚举来自这里

namespace Unity.AI.Navigation
{
    public class NavMeshSurface : MonoBehaviour
    {
        [SerializeField] NavMeshCollectGeometry m_UseGeometry = NavMeshCollectGeometry.RenderMeshes;
```

**根因**

`CollectObjects` 定义在 `Unity.AI.Navigation`，而 `NavMeshCollectGeometry` 定义在
`UnityEngine.AI`。两个类型在同一个字段上相邻出现，凭直觉会以为来自同一个命名空间。

**做法**

在文件里补 `using UnityEngine.AI;`。

**教训**

**包源码就在 `Library/PackageCache/` 下，报错的类型只要在那里 `Select-String` 一下就能定位。**
这比在搜索引擎里找文档快得多，也不会因为版本差异被误导。

## C-04：单个文件冲到 453 行，触发行数上限

**症状**

```text
PathRulesTests.SourceFiles_DoNotExceedLineLimit 失败：
  Assets\Game\Modules\AI\AiAgent.cs 共 453 行，超过上限 400 行
```

**定位过程**

不需要定位。真正需要判断的是"按什么职责拆"。

**根因**

`AiAgent` 同时承担了两件事：**驱动决策**（位置、朝向、感知快照、状态机）
与**武器结算**（换弹、扳机、射线、伤害、事件）。两者都在 400 行以内时看起来没问题，
边界一旦模糊就会一路加长。

**做法**

拆出 `AiWeaponController`，与玩家侧的 `PlayerWeaponController` 形成对应关系：
Agent 管"走到哪、朝哪看、要不要打"，控制器管"扣扳机之后发生什么"。

**教训**

行数上限的意义不是"必须拆"，而是**在超限之前给出一个信号**：
一个类同时描述两件不相关的事，本身就是需要拆分的证据。
这次拆分还顺带把 C-05 的问题暴露在了一个更小的范围内。

## C-05：换弹永远补不上——完成判定被"重新开始"覆盖

**症状**

AI 打空一个弹匣后再也不开枪，备弹数量始终不变：

```text
换弹应当消耗 AI 自带的备弹。Expected: less than 40  But was: 40
```

**定位过程**

第一步不是去读状态机，而是**把问题范围缩小到武器时序**：
新写一条直接驱动 `AiWeaponController` 的用例（不经状态机、不经感知），
让它按住扳机直到弹匣打空。结果同一条路径在测试里稳定复现，范围随即收敛。

第二步逐帧推演：弹匣归零后的下一帧开始换弹，计时 0.3 秒。
在计时走完的那一帧，代码顺序是先"判断要不要开始换弹"，再"结算已经到点的换弹"。

**根因**

换弹计时走完时 `WeaponRuntime.IsReloadReady` 为 true，但紧接着的
`TryBeginReload` 看到"弹匣是空的、也没在换弹"，于是**又开了一次换弹**，
把 `m_ReloadReady` 覆盖回 false。补弹因此永远不会执行。

整个过程没有任何报错，`IsReloading` 也一直是 true——从外部看，它"正在换弹"。

**做法**

1. 把顺序写死为：**先结算到达的换弹，再判断是否开始新的换弹**。
2. 在"是否开始换弹"的判断里补上 `IsReloadReady` 守卫，让覆盖在结构上不可能发生。
3. 两处都写明原因注释，并补 `EmptyMagazine_Reloads_AndTakesAmmoFromReserve`
   等 5 条直接驱动的用例锁死行为。

**教训**

**共享同一个计时器的两件事，调用顺序本身就是逻辑。**
判断"要不要开始"之前，必须先结算"是不是已经完成"——否则完成状态会被开始动作吃掉。
这类问题的共同特征是**全程无报错、状态看起来正常**，只能靠"账目对不对"的断言抓出来。

## C-06：状态机把初始进入计入迁移次数，测试预期集体偏移

**症状**

```text
Tick_AppliesTransition_AndCallsExitThenEnter  Expected: 1  But was: 2
Tick_IgnoresSelfTransition                     Expected: 0  But was: 1
```

**定位过程**

两条用例的偏差恰好都是 +1，指向"有一次我从没数过的迁移"。
`Start()` 内部调用的是同一个迁移函数，因此初始进入也被计入了。

**根因**

`TransitionCount` 的语义没有被定义清楚：它到底表达"累计进入过多少状态"，
还是"运行期间换了多少次状态"？实现选了前者，测试期望的是后者。

**做法**

`Start()` 结束后把计数与理由清空，并在注释里写明：**这个计数回答的是
"运行期间换了多少次状态"**。

**教训**

**计数器类 API 要先定义"0 是什么状态"，再写实现。** 把"开幕"算进去还是不算进去，
两种都能自圆其说；不清楚定义就会出现"实现与测试各按一种理解写"的偏移。

## C-07：为静止靶子写的位置缓存，在移动单位上失效

**症状**

不报错。风险是：敌人移动之后，视线判定与暴击判定仍以**出生点**为中心。
表现为"AI 看不见跑到掩体后面的敌人""打中了却不算暴击"。

**定位过程**

在设计"玩家与敌人都登记为可受击单位"时回头看 `CombatTargetView`：
M3 的靶子是静止的，因此 `CenterWorldPosition` 在 `Initialize` 里算一次就够了。
M4 的敌人每帧都在移动，同一个写法立刻变成缺陷。

**根因**

代码本身没有错，是**使用前提变了**：M3 的靶子不会动，M4 的单位会动。

**做法**

把 `CenterWorldPosition` 改为每次读取时由碰撞体包围盒计算（顺带缓存碰撞体引用）。
注释写明原因，避免后来者"优化"回缓存版本。

**教训**

**"能用"不等于"对新用法也成立"。** 一个组件从"静态对象"扩展到"动态对象"时，
所有"初始化时算一次"的字段都要重新审视一遍。
这类问题没有报错、只有玄学现象，属于最值得提前拦掉的一类。

## C-08：Transform 驱动的角色 + 物理查询 = 命中停留在出生点

**症状**

同样不报错，但后果严重：AI 的视线射线打在敌人**出生时**的位置上，
玩家的子弹也打不中移动后的敌人。表现为"敌人跑起来之后就打不中了"。

**定位过程**

在设计 AI 的视线判定时意识到：本项目所有角色都由 Transform 直接驱动（没有刚体），
而 Unity 默认 `Physics.autoSyncTransforms = false`——**Transform 的变化不会立刻
同步到物理场景**，物理查询读到的是旧位置。

**根因**

这不是某一处代码的错，而是"用 Transform 驱动角色"这个**整体设计选择的全局副作用**，
只在引入"射线打移动单位"之后才暴露出来。

**做法**

在启动层集中打开 `Physics.autoSyncTransforms = true`，并注明理由与代价：
每次物理查询前多做一次脏检查。本工程每帧的物理查询只有个位数，这点开销
换掉一整类难以复现的命中问题非常划算。

**教训**

**跨系统的设计选择，副作用要在启动层集中处理。** 让每个射线调用点各自
`Physics.SyncTransforms()` 会把同一条规则抄到 N 个地方，漏掉一处就是玄学缺陷。

## C-09：编辑器失焦导致帧循环停摆，运行时验证全读到静止值

**症状**

运行时检查 AI 状态，读到的是：

```text
frame=1  elapsed=0.0  agents=3  #6 Engage pos=(14.000, 4.000)  #7 Patrol  #8 Patrol
```

时间没有推进、敌人还停在出生点。这是 M2 的 A-04 **同一问题的复发**。

**定位过程**

按速查表的第一条，连读两次 `Time.frameCount`：两次都是 1，确认帧循环没有在走。
进一步读 `Application.isFocused` 为 true，但仍需要显式唤醒一次播放循环。

**根因**

编辑器窗口尚未真正获得播放焦点时（例如通过命令行进入播放模式），
播放循环可能停摆；`Time.deltaTime` 虽然有几个毫秒，但帧不再推进。

**做法**

```csharp
Application.runInBackground = true;
UnityEditor.EditorApplication.QueuePlayerLoopUpdate();
```

执行后 `Time.frameCount` 从 1 涨到 2676（约 5 秒），运行时验证随即正常。

**教训**

速查表那一行"运行时不推进 → 先确认帧在走"**再次直接命中**，这是它存在的价值。
本次补充了具体解法（两行代码），写进 M4 的速查条目里，下次不必再摸索。

## C-10：改了场景生成器，仓库里已提交的场景却不会变

**症状**

运行时警告找不到 `NavMeshSurface`，`NavMesh.CalculatePath` 返回 false，
AI 全部退化为直线移动。

**定位过程**

场景生成器已经加上了 `NavMeshSurface`，但仓库里提交的
`Assets/Game/Content/Scenes/GreyboxRaid.unity` 是**上一次生成的产物**。
检查打开的场景：`Ground` 上没有该组件。

**根因**

**改生成器 ≠ 改场景。** 生成器只在执行菜单命令时生效，
而已提交的产物（场景文件）不会自动更新。

**做法**

用 `unity command ... eval` 在打开的场景里就地补组件、显式设置采集方式并保存场景：

```csharp
var surface = ground.GetComponent<NavMeshSurface>() ?? ground.AddComponent<NavMeshSurface>();
surface.collectObjects = CollectObjects.All;
surface.useGeometry = NavMeshCollectGeometry.PhysicsColliders;
EditorSceneManager.MarkSceneDirty(scene);
EditorSceneManager.SaveScene(scene);
```

**教训**

本项目里"由代码生成、又会提交进仓库"的产物有两类：**场景**与**物品资产**。
改动它们的生成器的同时，必须把产物也更新一遍，否则只有"重新生成的人"才会得到新行为
——而下一个克隆仓库的人看到的还是旧场景。

## C-11：截图命令的保存路径必须落在工程内，且会落到 Assets 下

**症状**

```text
Parameter Validation Failed. Path 'C:\Users\...\Temp\m4_view.png' is outside the project root
```

改用相对路径 `Library/m4_view.png` 之后，实际生成的文件是
`Assets/Library/m4_view.png`。

**定位过程**

命令直接返回了落点：`"savedPath":"Assets/Library/m4_view.png"`。

**根因**

工具对路径做了两道限制与转换：**必须在工程根目录内**，且相对路径会被解析到 `Assets/` 下。

**做法**

截图仍放在 `Library/` 下（避开版本控制），但**用完立刻删除**，
并连同自动生成的 `Assets/Library.meta` 一起删掉，避免污染仓库。

**教训**

临时产物用完即删，删除后 `git status` 复核一遍——
"没打算提交的东西"最终被提交，通常就发生在这一步没做的时候。

## C-12：出生点会被敌人秒杀，导致"验证用的场景状态"根本站不住

**症状**

进入播放模式后想验证开发者模式的世界可视化，结果每次读到玩家都是"已阵亡"：

```text
玩家：已阵亡或未登记　噪音：静止　未被发现
```

脚本化奔跑输入也没有生效（角色不动）。

**定位过程**

面板里的状态迁移日志直接给出了答案：

```text
[0.0s] AI#6 Patrol → Engage（巡逻中发现目标）
[0.8s] AI#6 Engage → Patrol（目标丢失且线索中断）
[1.2s] AI#6 Patrol → Engage（巡逻中发现目标）
```

6 号敌人的出生点在玩家出生点的视野范围内，因此进游戏 0.4 秒（反应时间）后就开始射击，
玩家约 2~3 秒阵亡，4 秒后复活又落在同一个位置——**这正是 04_AI.md 13.6 节记录的"复活即阵亡"**。
阵亡期间输入被屏蔽（这是刻意设计），所以脚本化奔跑当然不生效。

**根因**

不是缺陷，而是"玩家出生点位于敌人视野内" + "灰盒复活固定在出生点"两条临时规则叠加的结果。
验证失败的原因是**验证方法**：我默认"进入播放模式后玩家可以自由行动"，而这个默认在当前灰盒布局下不成立。

**做法**

1. 需要"玩家活着且可自由行动"的验证场景时，先把玩家传送到安全位置并回满血
   （`Movement.Reset` + `SetHealth`），或者临时把 `ViewDistanceMeters` 设 0。
2. 需要"看到交战表现"时，接受玩家会被打死，但**在同一个 eval 里读取数据**（见 C-15）。

**教训**

**验证脚本要先确认前提条件，而不是假设它们成立。** 
这与 M3 的"先确认帧在走"是同一类问题：环境不会按你的假设运行，
先把前提读出来（存活、位置、帧号），再谈结论。

## C-13：调试图形第一版几乎看不见

**症状**

三档听觉参考圈画出来了，但截图里几乎找不到——灰色地面上一条 0.18 透明度的细线。

**根因**

按"装饰"的思路选了低不透明度，而调试图形的唯一职责是**被看见**。

**做法**

参考圈不透明度从 `0.18` 提到 `0.32`，当前档位的高亮圈保持更高对比度。

**教训**

调试可视化的审美标准与游戏美术相反：**宁可丑，也要一眼看到**。
判断标准是"能不能在 1080p 截图里被认出来"，而不是"是否融入了场景"。

## C-14：标签写成"弹匣 27/90"会被读成容量

**症状**

AI 头顶标签显示 `弹匣 27/90`。27 是弹匣余量，90 是备弹总数——
但斜杠的写法在别处（HUD）表示"当前 / 容量"，因此第一眼会被读成"27 发 / 容量 90"。

**做法**

改成 `弹匣 27 · 备弹 90`，用文字而不是斜杠区分两个不同的量。

**教训**

调试信息宁可多两个字，也不要让人会错意。
**同一个符号在同一个项目里只能有一种含义**——HUD 已经把斜杠定义为"当前 / 容量"。

## C-15：读到的运行时数据早于自己的假设

**症状**

把玩家传送到集装箱后方，然后验证"被掩体挡住"这一条。结果读到的是"可见"，
而且距离与两秒前完全不同：

```text
玩家位置=(8.000, 9.000)      ← 传送成功
... 两秒后 ...
玩家物体位置=(0.00, 0.00, 0.00)   ← 已经死过一次并复活回出生点
```

**定位过程**

用物理射线独立复核，发现射线确实被 `Container_01` 截断——判定逻辑没问题，
是**我读到的世界已经不是我要验证的那个世界**：玩家在传送过去的 2 秒内被两个 AI 打死并复活，
位置回到了出生点。

**根因**

"构造场景"与"读取结果"被分开成两次命令，中间隔了几秒。AI 在实时运行，
这段时间足够让战场发生彻底变化。

**做法**

把**构造与读取放进同一次 eval**，或者先冻结战场（把 AI 生命设为 0 / 视距设为 0），
再读取结论。

**教训**

**在实时运行的场景里做验证，"读取"必须与"构造"紧挨着发生。**
否则你验证的是另一个时刻的世界，而失败信息会把你引向错误的代码位置——
本例中我一度以为是视线判定漏了遮挡。
