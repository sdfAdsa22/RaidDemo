## M7-P-01：嵌套预制体的缩放与位移在保存新预制体时被回退

**现象**：用 `PrefabUtility.InstantiatePrefab(fbx)` 得到模型实例，设置 `localScale` 与 `localPosition` 后
`SaveAsPrefabAsset`；构建过程打印的缩放是 2.562，但重新加载预制体量到的身高仍是原始的 0.671 米。

**原因**：FBX 模型是**嵌套预制体实例**，直接改它的 Transform 属于"实例覆盖"，
保存为新预制体时不保证被固化。

**解法**：先 `PrefabUtility.UnpackPrefabInstance(..., PrefabUnpackMode.Completely, ...)` 解包成普通节点，
再设置缩放与位移。解包后网格与材质仍按 GUID 引用原 FBX，不影响后续替换模型。

## M7-P-02：重建预制体时删除再创建会换 GUID，场景引用断裂

**现象**：构建脚本里用 `AssetDatabase.DeleteAsset(path)` + 重新保存来"重建"预制体；
重新生成场景后，场景里原来的角色引用变成 Missing。

**原因**：删除资产会同时删除 `.meta`，重建时生成新的 GUID，而场景保存的是旧 GUID。

**解法**：**覆盖保存**（直接 `PrefabUtility.SaveAsPrefabAsset` 到同一路径）可保留 GUID 与 `.meta`。
只有确实需要换引用时才删除重建；动画控制器这类"被预制体重新赋值的依赖"可以删重建。

## M7-P-03：eval 中创建附加场景被未保存场景挡住

**现象**：在 eval 里调用 `EditorSceneManager.NewScene(..., NewSceneMode.Additive)` 报
`Cannot create a new scene additively with an untitled scene unsaved.`

**原因**：编辑器当前场景是未保存的 Untitled 场景，Unity 不允许在其上叠加新场景。

**解法**：渲染预览时不要新建场景，直接在**当前场景**创建临时对象、渲染完立刻销毁；
再用专用 Layer + 相机 `cullingMask` 控制只拍到预览对象（见 M7-P-04）。

## M7-P-04：预览渲染把编辑器当前打开的场景一起拍进去

**现象**：渲染角色预览图时，画面里出现安全屋的墙、地面等无关物体。

**原因**：相机渲染的是**所有已加载场景**，不只是它所在的那一个。

**解法**：给预览对象统一设置专用 Layer（用户层 30），相机 `cullingMask = 1 << 30`；
灯光不受影响仍然照常照明。渲染结束销毁临时对象。

## M7-P-05：导入的动画剪辑默认不循环，角色出现"滑步"

**现象**：角色开始移动时播放一次动作，之后姿势冻结但位置继续移动。

**原因**：FBX 导入的剪辑默认 `loopTime = false`，播完停在最后一帧。

**解法**：在构建脚本里通过 `ModelImporter.clipAnimations` 给循环类剪辑打开 `loopTime`
（`idle` / `walk` / `sprint` / `holding-right`），射击与倒地保持单次；设置后 `SaveAndReimport()`。
注意：若 `clipAnimations` 为空数组，要先取 `defaultClipAnimations` 再赋值回去。

## M7-P-06：给"世界坐标"再补一次高度，等于重复抬高

**现象**：修完"平台上的敌人打不到人"之后，敌人反而**永远停在警惕、不进入战斗**；
只有走到平台下方才恢复正常。

**原因**：`CombatWorld` 里的 `CenterWorld` 是**带世界高度的中心点**（站在 1.25 米平台上就是 2.10 米），
不是逻辑平面坐标。当时按"眼睛和目标两端都要补高度"的思路又给目标补了一次平台高度，
瞄准点于是高出目标 1.25 米，射线从目标头顶飞过、什么也打不到 → 视线恒为 false。
平地上补的是 0，所以问题只在有高差时暴露。

**解法**：先分清每个坐标是"逻辑平面坐标"还是"世界坐标"——
**只有逻辑平面坐标需要补场景高度**（本项目的 AI 自身位置、枪口均属此类），
战斗层给出的 `CenterWorld` 属于世界坐标，原样使用。

## M7-P-07：调试图形的高度不要用"从天而降的物理射线"

**现象**：F1 的视角锥画在单位头顶，看起来像感知范围算错了。

**原因**：为取地面高度从 y=50 向下打物理射线，而单位自身就有碰撞胶囊（子弹命中判定需要），
射线第一个命中的是它自己的胶囊顶。

**解法**：调试层与 AI 判定**共用同一套高度采样**（本项目的 `NavMeshGroundHeightProvider`）；
若必须用物理射线，需要过滤掉单位自身的碰撞体。另外图形渲染器要尊重传入点的 Y，
不能把 Y 强制成常量（否则上层无论怎么传都会画在地面）。

## M7-P-08：播放模式下用 CLI + 反射读取运行时私有状态

**场景**：平台敌人的高差问题反复修不好，纯靠读代码猜了两轮。

**做法**：让负责人在 Unity 里复现并**保持播放模式不动**，然后用 CLI 的 `eval` 读取真实数据：

- `FindObjectsByType<EnemyAgentView>()` 拿到所有敌人
- 反射取私有字段 `m_Agent` → `m_Director`，再取 `Probe` / `Profile` / `GroundHeight`
- 打印：逻辑位置、站立高度、两种高度采样结果、眼位、目标中心、视线判定结果
- 遍历场景里的 `LineRenderer`，直接读出弹道线两个端点的世界坐标

**价值**：一次读取就定位了两个反复猜错的问题（目标中心被重复补高、弹道线被压到 y=0.05）。
**教训：涉及高差、坐标换算的问题，不要在纸面上推断，直接用运行时数据说话。**

**注意**：读取时编辑器必须处于播放模式；若负责人已退出播放，拿到的是空结果。

## M7-P-09：新建脚本"类型不存在"，刷新与请求编译都不生效

**现象**（批次 2 开工时）：新增了若干 `.cs` 文件，编译报 `CS0103: The name 'M7MaterialUtility' does not exist`。
用 `eval` 检查类型时确认：同一批里有的脚本（`BasinTerrainProfile`、`M7SceneAssetResolver`）已经在程序集里，
唯独 `M7MaterialUtility.cs` 不在。`AssetDatabase.Refresh(ForceUpdate)`、`ImportAsset(ForceSynchronousImport)`、
`CompilationPipeline.RequestScriptCompilation()` 全都执行成功，但 DLL 的时间戳一直停在几分钟前没变。

**定位过程**：
1. `AssetDatabase.LoadAssetAtPath<MonoScript>(path)` 一开始返回 null → 说明资产数据库都没收录这个文件；
   强制 `ImportAsset` 后能拿到 MonoScript，但 `GetClass()` 仍为空（没参与编译）。
2. 检查编译输入清单 `Library/Bee/artifacts/<hash>.dag/RaidDemo.Bootstrap.Editor.rsp`：
   同一目录下其余脚本都在，**只有这一个文件不在**；清单文件的时间戳也不再更新。
3. 结论：Unity 的**脚本编译输入快照**卡在了旧状态，之后每次"重编译"都拿旧清单去编，于是稳定复现同一个错误。

**解法**：
1. **换资产路径**——把该文件改名（类名一并改），新路径会产生新的资产记录，快照随之重建。本次即
   `M7MaterialUtility.cs` → `M7MaterialLibrary.cs`，改名后一次性编译通过。
2. 触发重编译最可靠的方式不是 `RequestScriptCompilation`，而是**修改一个已在编译清单里的文件**
   （哪怕只是加一行注释），随后照常执行 `unity command ... recompile`。

**教训**：命令行工具链下"新建文件"与"让编辑器看见新文件"是两件事。
遇到"只有某个新文件里的类型找不到"时，先去看编译清单里有没有它，而不是怀疑代码写错。

## M7-P-10：FBX 的"文件缩放"被覆盖，模型放大 3.7 倍

**现象**：Kenney 集装箱在场景里像一栋楼：渲染包围盒 10.27 × 9.59 × 22.67 米，
对应的 `BoxCollider` 也是这个尺寸，把整片堆场堵死；AI 的导航网格里那一带全是障碍。

**原因**：Kenney 的 FBX 在模型空间里只有 0.35 个单位高，导入器把「文件单位换算」写成**模型根节点的缩放**。
加工脚本里写的是 `instance.transform.localScale = Vector3.one * (目标高 / 当前高)`，
**直接覆盖**就把这份换算丢掉了，于是模型变成期望尺寸的 `1 / 0.27 ≈ 3.7` 倍。

**解法**：改成**乘算**：`localScale = localScale * scale`。导入器给的换算与我们自己的尺寸校正同时成立。
（同类加工逻辑还包括角色构建器：Quaternius 的模型没有这层换算，所以那边一直没暴露问题。）

**自检手段**：预制体生成后打印一次渲染包围盒；尺寸与设计值偏差超过 10% 立刻报警，
不要等到场景里"看起来不对劲"才发现。

## M7-P-11：只替换 `sharedMaterial`，第二块子网格保留旧材质

**现象**：远景山石换成一个灰色材质后，石头上仍带一片青色面。

**原因**：Kenney 的山石网格有**两个材质槽**（岩石 + 草），`renderer.sharedMaterial = m` 只改第一个槽位；
第二个槽位继续用资源包自带的材质（在这个包里正好是青色），于是同一块石头上出现两种颜色。

**解法**：整份替换 `renderer.sharedMaterials`，把每一个槽位都指向同一个项目材质：

```csharp
var slots = renderer.sharedMaterials.Length;
var materials = new Material[slots];
for (var i = 0; i < slots; i++) { materials[i] = target; }
renderer.sharedMaterials = materials;
```

## M7-P-12：贴图优先写成硬规则，纯色素材全变惨白

**现象**：Toon Shooter 的木箱、纸箱、仓库在场景里全是白色，而同一套素材在预览图里是棕/灰/绿的。

**原因**：加工脚本只从源材质里取 `mainTexture`，颜色一律写成 `Color.white`。
但 Quaternius 的环境道具是**纯色材质**（材质名 Wood / Cardboard / Grey，没有贴图），
真正的颜色在材质的 `_BaseColor` 里——只搬贴图等于把所有颜色丢掉。

**解法**：材质策略按素材形态分两支：

1. **贴图型**（Kenney 工业套件，整包共用一张色板贴图）→ 整包共用一个项目材质，减少材质数量；
2. **纯色型**（Quaternius 环境道具，逐模型不同颜色）→ 按模型分别建材质，基础色取自源材质的 `_BaseColor`。

**教训**：资源包之间"颜色存在哪"并不统一。写通用的材质加工时，贴图与基础色都要读，
并且要能分别回退，不能假设其中一种一定存在。

## M7-P-13：撤离点画得没错，但玩家与 AI 都走不到

**现象**：南侧谷口撤离点做好后，`NavMesh.CalculatePath` 从谷底到该点返回 `PathPartial`，
路径停在装卸平台南缘——第四个撤离点实际上是一座孤岛。

**原因**：谷口原本开在 x 等于 0，而正南方的装卸平台是 22×9 米的实体台体（x 从 -9 到 13，z 从 -28 到 -19），
**正好堵住谷口**。地形上谷口与谷底看起来是连着的，但可行走面被台体切断。

**解法**：把谷口中心移到平台东侧（`SouthCanyonCenterX = 17`），谷口直接连通谷底主空间；
四个撤离点重测全部 `PathComplete`。

**教训**：地形与建筑都是"看起来连着"就够了吗？不够。**改动地形或大件布局后必须跑一次连通性检查**：
用 `NavMeshSurface.BuildNavMesh()` 烘一遍，再对"出生点 → 每个撤离点"逐个 `CalculatePath`，
确认状态是 `PathComplete`。这类问题在俯视截图里完全看不出来。

**补充（2026-09-12，负责人验收发现"东/西撤离点被堵住过不去"）**：
`CalculatePath` 全绿并不等于玩家走得过去。当时的实际情况是：

- 东侧坡道走廊（宽 6 米）正压着一个集装箱；
- 西侧坡道走廊整条穿过厂房西墙，外加一台设备；
- 北侧坡道中线上停着一个战利品木箱。

导航会**绕开**障碍继续找路（所以 `CalculatePath` 是 `PathComplete`），
但坡道本身只有 6 米宽，实物占掉一半之后玩家的胶囊扫掠就挤不过去了——
导航查询算的是"平面上通不通"，而玩家移动靠的是"胶囊扫掠 + 地面吸附"，两者不是一回事。

**这次的修法**：把三条坡道的横向中心挪到空地上（北 x=0、东 z=25.5、西 z=-20），
并把让位的集装箱/木箱/围栏/掩体各挪开一处；走廊的悬崖装饰缺口也跟着坡道中心走，
否则瓦片会整排堵在新入口上。

**新增的常驻检查工具**：`RaidDemo → M7 → 校验四个撤离点可达性`
（`M7ExtractionAccessVerifier`）。它对每个撤离点做两件事：

1. 算一次 `NavMesh.CalculatePath`，查规划上通不通；
2. 让一个"虚拟玩家"沿路径拐点一步步走——每一步都用与 `PlayerMotor` 相同的
   胶囊扫掠（`PhysicsMovementCollisionService`）与向下射线落地，连续 24 步几乎走不动就判定卡住。

顺带还抽检三处地面采样（谷底 / 平台顶 / 坡道中段），防止"落地采样选错层"的问题复发。
**今后只要动了地形、坡道、大件摆放，跑一次这个菜单即可。**

## M7-P-15：AI 走到掩体旁瞬移到上面、或直接穿墙

**现象**（负责人验收反馈）：小兵靠近箱子时会突然出现在箱子/平台上方；有时又会直接穿过墙体与集装箱。

**原因一：落地采样半径给大了，选错了"层"。**
批次 2 把 `EnemyAgentView` 的采样半径从 4 米放大到 12 米（为了覆盖 6 米下沉），
而 `NavMesh.SamplePosition` 返回的是**离采样点最近**的导航面，不是"脚下那一层"。
装卸平台顶面（-4.8）与谷底（-6）只差 1.2 米，敌人在平台 12 米范围内任意位置，
平台顶面都离采样点更近——于是被摆到平台上。坡道下半段同理。

**修法**：新增 `NavMeshGroundSampler`，改成**从下往上一层层试**：
在固定的层高表（-6 → +6，间隔 1.5 米）上各做一次半径 1 米的搜索，先命中的那层就是脚下这层。
同一垂线上不会有"上层悬在下层正上方"的结构，因此"最低命中"等价于"脚下"。
`EnemyAgentView` 与 AI 逻辑用的 `NavMeshGroundHeightProvider` 共用它，避免两处规则不一致。
采样失败时保留上一次高度（而不是回退到 0——回退到 0 等于把单位瞬移到塬面高度）。

**原因二：AI 没有移动碰撞。**
`AiMovement.Step` 在"没有路径"时会直接朝目标直线走（寻路失败、路径走完、目标很近这三种情况都会），
而直线推进不做任何障碍判断——这就是穿墙。

**修法**：`AiMovement` 增加可选的 `IMovementCollisionWorld`（与玩家移动用的是同一条接口，
实现是表现层的 PhysX 胶囊扫掠），由启动层在创建敌人宿主对象后注入；
不注入时行为与之前完全一致，无头服务端与既有单元测试不受影响。

**顺带修的观感问题**：敌人模型含持枪手臂实测宽约 1.3 米，而碰撞胶囊直径只有 0.8 米，
贴着墙走时手臂会插进墙里。注入碰撞时把半径取 0.55（大于胶囊的 0.4），
让身体与墙面留出约 0.15 米余量。

**验收方式**：进入战局后读取每个敌人的落地高度，必须等于其所在层的导航面高度
（谷底 -5.92 / 平台 -4.75），且没有任何敌人的身体中心落在障碍碰撞体内部。

## M7-P-16：没被遮挡的墙也透明了——透视孔的判定过宽

**现象**（负责人验收反馈）：角色明明露在墙上方，墙上却被抠出一个圆洞，看起来像"没遮挡也透明"。

**原因**是着色器里的判定条件只有两条：

1. 像素落在以角色屏幕位置为中心的圆内；
2. 该像素比角色胸口**更靠近相机**。

第二条只比较"离相机的远近"，不判断"这条视线是否真的打在角色身上"。
于是墙顶边缘、平台顶面、矮墙这类**只是擦过视线**的面，只要屏幕位置落在圆内就会被抠掉；
再加上孔是固定半径，"只被挡住一点点"也会显示成"整面墙透明"。

**修法**：保留圆孔外观，但在写半径之前加一道 CPU 闸门——
从相机朝角色**头 / 胸 / 膝三点**各打一条射线，**至少两点被挡**才认为角色真的被遮挡、才开孔。
同时排除角色自身的碰撞体（否则永远判定为被挡）与其它单位（否则玩家能拿敌人当掩体看穿）。

**验收结果**（实机读取 `IsOccluded` 与孔半径）：

| 情况 | 判定 | 孔半径 |
| --- | --- | --- |
| 站在空地上（无遮挡） | false | 0 |
| 完全躲在集装箱后 | true | 135 px（正常开孔） |
| 只被一个矮箱擦到脚下 | false | 0（不再出现莫名其妙的洞） |

**代价**：每帧 3 次短射线（复用命中缓冲，零分配），全部在表现层，不动渲染管线。

**复盘**：屏幕空间的"透明"效果必须由"世界空间的可见性判定"来开关。
只靠深度比较（"比目标近"）等价于"这条线路上有东西"，而不是"目标被挡住了"——
这两件事在斜俯视相机下差别特别大，因为大量面是斜着擦过视线的。

## M7-P-17：循环名单漏了"兜底剪辑"，士兵走一小段后保持姿势滑行（M7-P-05 复发）

**现象**（负责人实机反馈 + 截图）：敌人的移动动画**前一段正常**，走出一段距离后
保持一个固定姿势继续平移。三个敌人变体里只有士兵（绿头盔）这样，玩家侧正常。

**定位过程**：

1. 先问"是不是所有敌人都这样"——黄防化服与红头盔正常。三者共用同一套构建流程与控制器结构，
   因此可以排除 Animator 组件、`cullingMode`、`applyRootMotion` 这类全局因素，
   方向收敛到"某个状态绑的剪辑不一样"。
2. 直接在编辑器里把三个控制器的每个状态打印出来（状态 → 绑定的剪辑 → `loopTime` → 剪辑长度）：
   **士兵的 Walk 状态绑的是 `CharacterArmature|Run_Gun`，`loopTime = false`，长度 0.73 秒**；
   另外两个的 Walk 绑的是 `CharacterArmature|Walk`，`loopTime = true`。
3. 0.73 秒正好解释"走一小段就定格"：AI 巡逻速度 2 米/秒，走约 1.5 米正好是这段剪辑播完的长度。

**根因**：士兵模型**没有 Walk 剪辑**，M7 批次 1 的兜底链（`Walk → Walk_Shoot → Run_Gun → Run`）
在它身上选中了 `Run_Gun`；而 M7-P-05 留下的循环名单只写了
`Idle / Walk / Run / Duck`——**名单是按"动作名字"维护的，兜底链是按"有没有这个动作"选的**，
两者一旦对不上，被兜底选中的剪辑就落在名单外，播完定格在最后一帧。
位置仍被 AI 逻辑推着走，于是看起来就是"保持姿势滑行"。

**修法**：

1. 循环名单补上会被当作走路/跑步播放的 `Walk_Shoot / Run_Gun / Run_Shoot`（治标）。
2. 更关键的是把规则从"名字表"搬到**使用点**：新增 `CharacterAnimationLoopTool`，
   构建器在把剪辑绑到 Idle / Walk / Run 这类"会长期停留"的状态上时再确认一次是否循环，
   没开就地打开、重新导入并把状态指向新对象（重新导入会让旧剪辑对象失效，必须换引用）。
   玩家构建器走同一套工具，避免两边规则各写一份（治本）。
3. 加资产测试 `CharacterAnimationLoopTests`：扫描角色目录下所有动画控制器，
   **循环状态必须绑循环剪辑，一次性状态不得循环**——这类缺陷不报错、不崩溃，
   只有进游戏用眼睛看才发现，因此必须有一条可执行的检查钉住它。
4. 三个敌人模型的导入设置已就地校准（`.fbx.meta`），并复查了三个预制体上的
   Animator 引用没有因为重新导入而断裂。

**证据（修复前后对照）**：

| 控制器 | 状态 | 修复前 | 修复后 |
| --- | --- | --- | --- |
| Character_Soldier | Walk | `Run_Gun`，loop=false，0.73 秒 | `Run_Gun`，loop=**true** |
| Character_Hazmat | Walk | `Walk`，loop=true | 不变 |
| Character_Enemy | Walk | `Walk`，loop=true | 不变 |
| 三者 | Idle_Shoot / Death / HitReact | loop=false（正确） | 不变 |

**验证**：364 项 EditMode 测试全绿（新增 2 条）；三个预制体的 `runtimeAnimatorController` 非空；
玩家控制器四个循环状态的剪辑均保持 loop=true。

**顺带修掉的相邻缺陷（同一段代码，同一类"位置差分"误解）**：敌人宿主对象是在原点建好、
再被搬到 AI 逻辑位置上的，而 `EnemyAgentView` 的位置差分把这次"装配位移"当成移动，
算出每秒几百米的速度——刚出生时动画状态机会切进走路/跑步，要十几帧才衰减回来，
表现为"敌人一出生就原地跑一段"。修法是给差分加一个"第一次采样只对齐基准"的闸门。

**复盘**：这是 M7-P-05 的**复发形式**。第一次的教训是"名单里漏了剪辑"，
第二次暴露的是**名单这个机制本身不可靠**：凡是"按名字维护的清单"，迟早会和
"按条件选择的兜底逻辑"漂移，因为后者只看"有没有"，不看"叫什么"。
可靠的写法是把规则放在**使用点**（绑定时检查用途），清单退化成批量初始化的便利手段。
更一般地说：**靠肉眼才能发现的缺陷，都值得在构建期加一道可执行检查。**

## M7-P-18：两张预览图一模一样——后创建的对象没被刷到预览层

**现象**：`M7CombatAssetPreviewRenderer` 渲染"角色手持步枪"与"角色手持手枪"两张图，
输出文件大小完全一致，MD5 也一致——说明两张图是同一张。

**定位**：把两张图并排看，角色都在，但**手里没有任何武器**；
再用 eval 实例化一次 `PlayerWeaponView` 并统计它下面的 Renderer，得到 `usesReal=True`、
枪口坐标正确、却一个 Renderer 都没有。真正的原因是统计写错了对象（模型挂在角色节点下，不挂在视图组件节点下），
但这个错误恰好指向了真相：**预览相机只渲染第 30 层，而武器模型是后创建的，没被设到该层。**

**根因**：预览工具在创建角色时调了一次"整棵子树设为预览层"，
之后才 `view.Build(...)` 创建武器模型；新对象继承的是默认层（0），
于是相机（`cullingMask = 1 << 30`）把它整组剔除了。角色是从预制体实例化的、早就刷过层，所以只有枪不见了。

**做法**：把"刷层"这一步挪到**所有对象创建完之后**（`Build` 之后再刷一次整棵子树）。

**教训**：`cullingMask` 这类"白名单"机制对**创建顺序**敏感。凡是"先设层、后建对象"的写法都会漏，
正确顺序永远是"先把对象建完，再统一刷层"；反过来写，漏掉的对象不会报错，只是安静地不显示。

## M7-P-19：粒子系统挂在子节点，对象池在根节点上取不到

**现象**：特效预制体全部生成成功，但资产测试报
`Vfx_MuzzleFlash 根节点上没有粒子系统`。

**原因**：构建器先建了一个空的容器 GameObject，再把粒子系统作为一个**子节点**加进去。
编辑器里看预制体是正常的（Hierarchy 里展开就能看到粒子），
但运行时的对象池按"根节点上的 `ParticleSystem`"取组件，于是取到 null。

**做法**：容器本身直接 `AddComponent<ParticleSystem>()`，子特效（枪口烟）才另建子节点；
测试断言"根节点必须有粒子系统"，把这条约定钉死。

**教训**：预制体的**根节点**是一个约定位置——对象池、实例化、批处理都按它取组件。
层级上"看起来一样"的两种搭法，在按类型取组件时完全不同。

## M7-P-20：销毁渲染纹理时报 "Releasing render texture that is set as Camera.targetTexture!"

**现象**：每次离屏渲染都在控制台留下 5~6 条红色报错，功能本身正常。

**原因**：`DestroyImmediate(renderTexture)` 时，相机仍然把它当作 `targetTexture`。
Unity 允许销毁，但会报错提示这个引用关系没有解除。

**做法**：销毁前先 `camera.targetTexture = null`（或恢复成原来的目标）。

**教训**：离屏渲染的收尾顺序是"解除引用 → 释放资源 → 销毁相机"。
报错不影响画面，但**控制台里的红字会掩盖真正的问题**——排查时第一条要问的就是"这些红字是不是本来就有的"。

## M7-P-21：`unity command menu` 报"找不到菜单"，但菜单确实存在

**现象**：`unity command ... menu --path 'RaidDemo/M7/重建表现层资产（音效 / 武器 / 特效）'`
返回 `MenuItem ... was not found`；而列出全部菜单项时，
同一个菜单显示为 `RaidDemo/M7/重建表现层资产（音效/武器/特效）`——**斜杠两侧没有空格**。

**原因**：Unity 在注册 `[MenuItem]` 时会按 `/` 拆分路径并**去掉每一段的首尾空格**，
因此 C# 源码里写的 `（音效 / 武器 / 特效）` 与运行时的菜单名 `（音效/武器/特效）` 不是同一个字符串。

**做法**：用 CLI 执行菜单前，先 `unity command --project-path <项目> menu` 列出真实菜单名，
或干脆在菜单路径里不写空格。

**教训**：**属性里的字符串不一定是最终生效的字符串**。凡是"注册名"与"使用名"分离的地方
（菜单、动画参数、着色器属性、输入动作），都以运行时枚举出来的名字为准。

## M7-P-22：新增序列化字段把主文件顶过 400 行

**现象**：给 `SafeHouseBootstrap` 加一个 `[SerializeField] private PresentationCatalog ...` 之后，
`SourceFiles_DoNotExceedLineLimit` 报 `SafeHouseBootstrap.cs 共 401 行，超过上限 400 行`。

**原因**：主文件本来就贴着上限（397 行），新增的字段与它的注释合计 4 行。

**做法**：把这个字段挪到**用到它的那个 partial 分册**（`SafeHouseBootstrap.Combat.cs`），
并在注释里写明"定义放在使用点旁边，主文件已接近上限"。

**教训**：行数上限不是形式主义，它逼着人做正确的切分——**字段应该和它的使用点待在一起**。
用一个文件装下"整个类的所有字段"在 partial 架构里本来就不必要。

## M7-P-23：布尔表达式里 `&&` 与 `||` 的优先级写反，某个分支永远不生效

**现象**：玩家阵亡后，倒地动画会被自己的枪声打断，看起来像"尸体站起来开枪"。

**定位**：视图里那一行是
`if (m_Animator == null || m_IsDead && !IsLocalPlayer(evt.ShooterId))`。
C# 的 `&&` 优先级高于 `||`，实际等价于
`hasAnimator == false || (isDead && !isLocalPlayer)`——
**本地玩家已阵亡时**（`isDead = true, isLocalPlayer = true`）整体为假，
于是不会提前返回，接着执行 `SetTrigger(Shoot)`，把倒地动画打断。

**做法**：

1. 把判断抽成静态方法 `PlayerCharacterView.ShouldPlayShootAnimation(hasAnimator, isDead, isLocalPlayer)`，
   写成三个明确条件相与；
2. 加断言测试，覆盖"本地玩家阵亡后不再触发开火动画"这一条。

**教训**：**混合 `&&` 与 `||` 的条件，一律加括号或拆成命名变量。**
这一行的逻辑读起来是通的——因为读的人会自动按自己的意图断句，
编译器却严格按优先级执行。更要紧的是：这类缺陷不报错、不崩溃、不影响任何数值，
只有盯着画面看才会发现，因此**必须把"该不该做某件事"从 MonoBehaviour 里抽出来变成可断言的表达式**。

## M7-P-24：构建器里的常量与另一处的数值漂移，导致某段动画永远不播

**现象**：三个敌人的"跑"动作一次都没有出现过，即使它们正在全力撤退。

**定位**：动画控制器里"走路 → 跑步"的条件是 `Speed > 4.5`；
而 AI 的速度档位是巡逻 2、警戒 2.5、调查 3、交战 3.2、撤退 4.2——
**没有任何一个状态能达到 4.5**，`Run` 状态是死代码。

**做法**：阈值改为 3.6（交战仍走路、撤退才跑），并新增资产测试：

```text
断言：RunSpeedThreshold > EngageSpeed 且 <= RetreatSpeed
```

这样将来调 AI 速度档位时，测试会立刻失败，而不是等验收时才被问"敌人怎么从来不跑"。

**教训**：这是 M7-P-17 同一个家族的第三种形态——**规则写在了使用点之外的地方**。
第一次是"循环名单漏了兜底剪辑"，第二次是"名单机制本身不可靠"，
这一次是"表现层的常量跟着玩法数值一起漂移"。
共性结论是：**凡是"两处数值必须保持某种关系"的地方，都值得写一条断言把它钉住**；
如果写不出断言，说明这个关系本身没被想清楚。

## M7-P-25：Windows 下"测试文件豁免行数上限"静默失效

**现象**：给测试文件 `CombatCommandTests.cs` 加了三个用例后，行数变成 413，
`SourceFiles_DoNotExceedLineLimit` 报它超限——但工程规范里写明**测试代码豁免行数上限**
（`PathRulesVerifier.IsTestFile` 专门为此存在）。

**定位**：判断依据是"相对路径里包含 `/Tests/`"，而 `ToRelativePath` 返回的是**平台原生分隔符**。
在 Windows 上路径是 `Assets\Game\Tests\...`，**永远匹配不到 `/Tests/`**——
这条豁免从写下那天起就没生效过，只是因为此前没有任何测试文件超过 400 行，一直没暴露。

**做法**：`IsTestFile` 先统一分隔符再匹配，并加用例同时断言
"反斜杠路径算测试文件""斜杠路径算测试文件""生产代码不算测试文件"。

**教训**：**路径比较一律先归一化分隔符。** 这类缺陷的共同特征是"平时完全看不出来"：
它不影响任何正常路径的行为，只在边界情况（恰好超限、恰好跨平台）暴露。
换句话说，一条"从来没有触发过的规则"和"没有这条规则"在可观测层面是等价的——
所以每条豁免规则本身也值得一条测试。

## M7-P-26：九宫格贴图只画出左下角一块，面板缺了大半

**现象**：新的界面主题层上线后，主菜单的奶油面板只显示了左下角一小块，
标题条、按钮也各自缺了一半；而同一次布局读出来的矩形尺寸完全正确
（面板就是 900×660、按钮就是 420×88），文字位置也分毫不差。

**定位**：先怀疑九宫格边界（`border`）与 `pixelsPerUnit`，于是把运行时的
`Image.sprite`、`type`、`rect` 全部打印出来——**全部正确**。
既然布局与切片配置都对，问题只能在贴图本身的像素上。

回头看生成贴图的距离场代码：

```csharp
var point = new Vector2(x + 0.5f, y + 0.5f);   // 左下角为原点
var distance = RoundedBox(point, half, radius); // 内部用 |x|、|y| 判断对称
```

圆角矩形的距离场假设坐标**以中心为原点**（它靠 `Mathf.Abs` 得到对称性）。
传进去的却是以左下角为原点的纹理坐标，于是画出来的只是一个贴着左下角的四分之一形状；
九宫格再把它拉伸，就变成"面板只剩左下角"。

**修法**：减去贴图中心坐标，把点平移到中心为原点：

```csharp
var point = new Vector2(x + 0.5f, y + 0.5f) - center;
```

**教训**：**距离场、噪声、对称图形这类算法都有自己的坐标约定，传参前必须先对齐。**
这类错误不会抛异常，只会画错东西；而"布局数据全对、画面却不对"正是它的典型指纹——
遇到这个组合，第一件事就是把怀疑对象从布局转向**被绘制的像素**。

## M7-P-27：TMP 基础资源缺失导致文字不显示，且导入过程会卡住 CLI

**现象**：界面改用 TextMeshPro 之后，文字区域一片空白；
控制台报 `TextMesh Pro Essential Resources are missing`。

**定位与处置**：

1. TMP 的基础资源（着色器、默认字体、设置资产）**不在包内自动生效**，
   必须从 `com.unity.ugui` 包的 `Package Resources/TMP Essential Resources.unitypackage` 导入一次。
2. 走官方菜单 `Window > TextMeshPro > Import TMP Essential Resources` 时，Unity 会弹两次需要人工确认的东西：
   先是"签名不在可信来源"的确认框（包内附带 unitypackage 的正常提示），
   再是导入进度。**在弹出的模态框被点掉之前，编辑器主线程被占住，所有 CLI 命令都会排队超时**
   ——从外部看就像"Unity 卡死了"，但进程 CPU 几乎为 0、消息循环仍然响应。
   这正是"模态框阻塞"与"真的死锁"的区分方法。
3. 导入完成后，用工程内菜单 `RaidDemo/UI/重建中文字体资产` 生成中文字体资产即可。

**教训**：

- **需要人工确认的编辑器操作不要放在无人值守的流程里**。先确认它会不会弹窗，
  会弹窗的就明确交给负责人点一次，并把这一步写进文档（本文档与《08_UI主题与界面规范》都记了）。
- 排查"Unity 无响应"时，**先量 CPU 再下结论**：CPU 接近 0 说明它在等人，不是算不过来。

## M7-P-28：批次 4 新增中文文案缺字/乱码，旧文案正常

**现象**：批次 4 加上结算、暂停、安全屋、物品图标与角色选择之后，
主菜单里“选择角色”只剩“选”字，角色卡片只显示 A/B/C，说明牌与商人里也出现缺字。
旧文案里的汉字仍然正常，因此看起来像“某个字体的字被删了”，而不是整体字体失效。

**定位**：

1. 默认字体引用没有问题——`TMP Settings` 的 GUID 指向 `NotoSansSC SDF.asset`；
2. 源字体也没有问题——`NotoSansSC-Regular.otf` 是完整文件，FreeType 能加载，
   `GetGlyphIndex('选')` 返回有效 glyph；
3. 真正的问题是字体资产在运行时处于**断裂状态**：
   `characterLookupTable['角'].glyphIndex = 24004`，但 `glyphLookupTable` 里没有 24004。
   也就是“字符表有记录、字形表没有 glyph”，TMP 只能画空白或缺失字形。
4. 这份动态字体资产原本只预烘焙了 253 个旧文案字形，使用 3 张 1024×1024 图集；
   序列化数据里第 4 张图集是 `fileID: 0`。批次 4 新增的界面文案超过容量后，
   TMP 尝试扩图集页失败，留下了上面那种半写入状态。
5. 之前实机截图正常，是因为 Play 模式已经把新字形写进了本地工作区；
   提交前按旧约定 `git restore` 回仓库版本后，缺失状态才在下一台/下一次会话暴露。

**修复**：

1. `UiAssetTool.AtlasSize` 从 1024 提到 **2048**，采样从 90 降到 **64**
   （界面最大字号 46，64pt SDF 足够清晰，同时能多容纳英文与汉字），padding 取 **6**；
2. 新增 `UiAssetTool.CollectUiCharacters()`：
   - 扫描 `Modules/UI`、`Modules/Meta`、`Modules/Data/Content` 与两个内容构建器的 C# 字符串字面量；
   - 跳过注释、测试代码与编辑器报错文案，避免图集为不显示的文字膨胀；
   - 额外扫描物品/表现层资产与两个场景 YAML，并解析其中的 `\uXXXX` 中文转义；
   - 最后补齐 ASCII、中文标点与 `✓ × ÷ ±` 等界面符号。
3. 重建流程改为：先 `TryAddCharacters(收集到的全部字符)`，再挂图集/材质子资源，
   最后把 `atlasPopulationMode` 设为 **Static**。运行时不再写图集，也就不会再出现扩页失败；
4. 新增 EditMode 测试 `中文字体资产覆盖全部界面文案`：
   用同一套扫描逻辑检查字体资产是否包含所有界面字符，缺字时直接列出缺字；
5. 重建字体后重新执行 `RaidDemo/生成安全屋场景`，让墙上说明牌写入新的字体材质 fileID。

**结果**：当前字体资产为静态子集，607 个字符 / 607 个字形 / 1 张 2048×2048 图集，
覆盖率测试通过；398 项 EditMode 测试全绿。

**教训**：

- **“动态字体资产”不等于“永远不会缺字”**。图集有容量上限，多图集扩页失败时不会崩溃，
  只会留下“字符有记录、glyph 不存在”的半写入状态；这类问题必须在资产层做覆盖率测试。
- 对界面文案已经稳定的 Demo，**静态子集比运行时动态扩页更稳**：
  改文案时重建一次，测试兜底；不要把“字体资产是否完整”留给运行时碰运气。
- **Unity 的 YAML 会把中文写成 `\uXXXX` 转义**。扫描 `.unity` / `.asset` 时不能只按字面取字符，
  否则“衣柜”这类只存在于场景序列化数据里的文案会被漏掉；字面扫描 + 转义解析必须同时做。
