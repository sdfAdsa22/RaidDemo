## 一、协作工具

### A-01：子代理任务下发失败，且可能未经授权改文件

**症状**

本阶段任务量较大（30 多个文件），我按"数据层 / 背包核心 / 命令与界面"兵分三路，
给每个子代理发了约 3000 字的任务书（含完整冻结接口清单）。结果：

- 三个子代理**全部回复"只收到环境信息，没有任务正文"**，一个文件也没动；
- 更早的一次调研任务中，子代理自己又派生了两个子代理，其中一个在**未经授权**的情况下
  写出了 `Docs/Modules/02_Inventory.md`。

**定位过程**

对比成功与失败的派发：成功的那次任务书约 600 字，失败的三次都在 3000 字以上，
且包含大量代码块。据此判断是**长任务书在下发链路上被截断或丢弃**，
而不是子代理"看不懂任务"。收窄范围重发的两次里，一次成功、一次仍失败，说明并不可靠。

**根因**

1. 长任务书的下发不可靠；
2. 子代理对仓库有**写权限**，授权边界不明确时可能产生计划外的改动。

**做法**

放弃分工，M2 的全部代码由我自己写。已经产生的那份设计文档没有直接丢弃，
而是**逐节复核后收编**——它方向正确，我在此基础上改成了负责人拍板的版本
（三段式负重、稀有度五档、内联状态的取舍说明）。

**教训**

- 派发子代理时，任务书应控制在几百字内，把详细契约留在**文件里**让它自己去读，
  而不是全部塞进消息；
- 涉及仓库的派发必须写明"只读"或"只允许改这几个文件"，事后用 `git status` 核对；
- **发现计划外改动时，先查清它是谁写的、内容对不对，再决定收编还是回退**——
  直接删除会把可能有价值的内容一起丢掉。

### A-02：补丁工具处理中文长文本时会丢行首标记

**症状**

写代码与文档时，补丁反复被拒绝，报错形如：

```text
invalid hunk at line 53, '/// 那部分代码没有任何玩法价值，却会成为最容易出错的地方。</para>'
is not a valid hunk header.
```

报错指向的那一行，正是我写的注释内容——**它的行首标记 `+` 凭空消失了**。

**定位过程**

统计了几次失败：出错行几乎都出现在**中文多行注释的第三行**，且前后文含全角标点。
同一段文字重新组织后再提交，往往就通过了；把连续三行的 `<para>` 压成一行后不再复现。

**根因**

工具在处理这类文本时会把某一行误判成补丁指令行。这是工具侧的问题，不是内容写错了。

**做法**

- 中文长注释**拆成短段**，XML 文档里的 `<para>` 尽量一行写完；
- 补丁失败时**不要反复原样重试**，改写那几行往往比调试更省时间；
- 大文件改动改用"删除后重建"，而不是带大段上下文的定点替换。

**教训**

这不是能"修好"的问题，只能规避。它拖慢的是**写注释与写文档**的速度，
而这两件事在本项目里占比很高（注释要求丰富详细），所以规避手段值得固定下来。

### A-03：后台辅助进程的启动命令被策略拦截

**症状**

推送 GitHub 失败后，我写了一个临时 CONNECT 隧道脚本，用
`Start-Process node ... -WindowStyle Hidden` 启动、`finally` 里 `Kill` 收尾。
整条命令被策略拒绝：`rejected: blocked by policy`。

**做法**

改用工具自身的**长驻会话**机制：

1. 用会话形式直接运行 `node 隧道脚本`，拿到会话标识；
2. 在另一个命令里执行 `git push`（走本地隧道代理）；
3. 用 `Stop-Process` 结束隧道进程，确认端口不再监听，再删除临时脚本。

**教训**

需要后台辅助进程时，优先用会话机制而不是 `Start-Process`；
收尾动作（结束进程、删除临时文件、清理代理配置）要和启动动作一样明确，
**不要留下任何持久配置**。本次收尾后确认过端口已关闭、脚本已删除、git 配置未改动。

## 二、Unity 编辑器行为

### A-04：编辑器失焦时帧循环停摆，让"实现没生效"

**症状**

进入播放模式后，我通过命令把物品搬进背包，负重从 0 涨到 14.7 千克，
按规则应当进入"重装"并禁用奔跑。反复检查实现都没问题，但每帧执行的负重修正
**始终没有生效**——配置里的可奔跑标志一直是 `True`。

**定位过程**

这条如果只盯着实现看，会一直找不到问题。真正的证据来自帧计数：

```text
第一次读取：frame=22  time=0.4  paused=False
两秒后再读：frame=22  time=0.4  paused=False
```

**帧计数完全不动 = 主循环根本没有推进**，所以依赖每帧执行的逻辑当然不会生效。
问题不在实现，在于我当时是在一个失焦的编辑器里做验证。

**根因**

Unity 编辑器在窗口失焦、被遮挡或最小化时会停止推进主循环。

**做法**

- 需要验证"每帧执行"的逻辑时，改用**反射直接调用那个方法**，不依赖帧推进；
- 或者先读两次帧计数确认它确实在走，再开始验证。

**教训**

**"看起来功能没生效"时，先排除"它根本没跑"，再怀疑实现。**
这条与 M0 的编辑器卡死是同一个诊断手段——**帧计数是 Unity 里最有力的
"它到底有没有在动"的证据**，值得作为默认的第一步。

值得一提的是：在这个假象上我多花了一轮排查，最后是帧计数一句话定案。

### A-05：截图拍不到 Screen Space Overlay 界面

**症状**

背包界面在运行时是存在且正确的（结构、层级、坐标都查过），
但 `capture_game_view --source screen` 连续三次都拍不到界面。

**一次误判**：第一次截图里左下角有一大块黑色矩形，我一度以为那是"面板渲染出来了
但子元素没画出来"。对比第二次截图（黑块消失了）之后才确认，
那其实是**场景里的灰盒箱子**，与界面无关。差一点就去排查一个不存在的问题。

**根因**

该截图路径不包含 Screen Space Overlay 画布。这是工具能力的边界，不是项目的问题。

**做法**

改为**数值验证**，逐项确认能确认的部分：

| 验证项 | 结果 |
| --- | --- |
| 画布尺寸与缩放 | 1920×1080，缩放系数 1.33 |
| 面板位置 | 世界四角 (680,307)~(1880,1133)，在屏幕中心 |
| 格子坐标 | 落在屏幕范围内 |
| 文本 | 17 个文本对象，字体有效 |
| 网格视图 | 2 个，格子数 25 与 20，物品视图数与数据一致 |
| 数据绑定 | 派发移动命令后，两个网格视图的数量同步变化 |

**教训**

- 拿不到视觉证据时，把"能验证的"验证到位，并把"没能验证的"**明确告诉负责人**，
  不要用"应该没问题"含糊过去；
- **不要把截图里的每个异常形状都当成自己代码的产物**。先确认它属于界面还是场景，
  再决定要不要排查；否则容易在幻觉问题上浪费时间。

### A-06：场景里的序列化值覆盖代码里的新默认值

**症状**

战利品箱的容量改为 6×5 后，运行时却只装进去 3 件物品，与 30 格的容量完全不符。

**定位过程**

先查生成逻辑：过滤规则、排序、放置循环都逐行确认过，没有问题。
最后回头去看**场景文件里实际存的值**：

```text
修改前 size=(4, 3)  cap=30
```

也就是说，我在代码里把默认值从 `(4,3)` 改成 `(5,4)`、再改成 `(6,5)`，
**全都没有生效**——因为场景里的 `SceneBootstrap` 组件在第一次序列化时
就已经把 `(4,3)` 存了下来，之后代码里的字段初始值不再参与。

**根因**

MonoBehaviour 的字段默认值只在对象**首次创建**时生效；一旦序列化进场景或 prefab，
运行时读的是存下来的值。

**做法**

用 `SerializedObject` 直接修改场景里组件的字段值，再保存场景：

```text
修改前 size=(4, 3) cap=30 → 已保存 GreyboxRaid
```

**教训**

凡是"改了配置但运行时不生效"的现象，**第一步就去场景 / prefab 里看字段实际存的值**。
代码里的默认值只是"新建对象时用什么"，不是"运行时一定是什么"。

这条已经写进文件夹索引的速查表。

### A-07：改组件代码后必须完全重进播放模式

**症状**

改了组件代码后进入播放模式，跑的是修改前的版本。

**说明**：这条在 M1 阶段已经踩过一次，M2 又验证了一遍——
**它不是可选的谨慎操作，而是必须遵守的流程**。本阶段我修完准星层级、
拖拽逻辑与分类规则之后，都需要提醒负责人"完全退出再重进播放模式"。

**做法**

固定流程：改组件 → `editor_stop` → `recompile` → 等 `recompile_status` 返回
`completed` 且 `failed=false` → 再 `editor_play`。

**教训**

把"需要重进播放模式"写进交付说明。负责人看到修复没生效时，
第一反应会是"你改错了"，而不是"我该重启一下"。

## 三、工程约束与架构

### A-08：单文件 400 行上限连续触发两次

**症状**

`PathRulesTests.SourceFiles_DoNotExceedLineLimit` 一次报出两个文件超限：

```text
Assets\Game\Bootstrap\SceneBootstrap.cs 共 494 行，超过上限 400 行
Assets\Game\Modules\UI\Inventory\InventoryScreenController.cs 共 647 行
```

**做法**

用 `partial` 按**职责**拆（不是按行数机械对半砍）：

| 原文件 | 拆成 |
| --- | --- |
| `SceneBootstrap` | 主文件（装配与主循环） + `SceneBootstrap.Inventory.cs`（背包装配） |
| `InventoryScreenController` | 主文件（状态与主循环） + `.Layout.cs`（布局与刷新） + `.Drag.cs`（拖拽与点击） |

**拆完又踩了两个坑**：

1. 主文件忘了加 `partial` 关键字 → `CS0260: Missing partial modifier`；
2. 拆出的新文件缺 `using` 指令 → `CS0246: 找不到类型`。

**教训**

- `partial` 是**成对**出现的，拆一个类必须同步改主文件；
- 拆出的文件要带上它自己需要的 `using`，不要指望从原文件"继承"；
- **机械拆分之后必须立刻重编译**，否则这两个错误会一直留到下一个流程节点才暴露；
- 行数上限这条约束本身是有价值的：它逼着我在 647 行时就意识到
  "布局和拖拽是两件事"，而不是继续往里堆。

### A-09：命令契约引用了业务层的枚举

**症状**

写装备命令时发现 `EquipmentSlot` 定义在 `RaidDemo.Inventory`，
而命令契约在 `RaidDemo.Shared`——按 ADR-004 的依赖方向，
共享层不能引用业务层，编译不过。

**根因**

写枚举时按"它描述的是背包里的槽位"归类，放进了背包层；
但命令契约需要携带它，于是依赖方向被打破。

**做法**

把 `EquipmentSlot` 移到 `RaidDemo.Shared`，并在类型注释里写明**为什么它属于共享层**
（命令要携带它），避免下次有人又把它搬回背包层。

**教训**

**凡是命令要携带的类型，必须放在共享层。**写一条新命令之前，
先把"它要携带哪些类型"列出来，逐个确认数据层归属——
这类错误编译期就能发现，但发现得越晚，改动面越大。

### A-10：修改枚举成员导致已序列化资产整体错位

**症状**

把 `ItemCategory.Armor` 拆成 `Helmet` 与 `BodyArmor` 之后，
运行时的物品分类全乱了：防弹背心变成了头盔、背包变成了 `BodyArmor`。

**定位过程**

钢盔的枚举值原本是 3，拆出来的 `Helmet` 恰好也是 3，看起来是对的；
但防弹背心的 3 现在指向 `Helmet`，背包的 4 指向 `BodyArmor`——
**`Armor` 之后的所有成员整数值都位移了 1**，而资产文件里存的是整数。

**根因**

枚举以整数形式序列化进 `.asset`。在中间插入或拆分成员，
会让其后所有成员的数值整体位移，而已有的资产不会自动跟着改。

**做法**

重新生成全部物品资产。抽查确认：钢盔=3、背心=4、背包=5、金表=6、弹药=1、武器=0，全部正确。

**教训**

- 修改枚举成员（插入、删除、拆分、调序）之前，**先确认它有没有被序列化**；
- **数据资产用代码生成器产出，而不是手工在 Inspector 里填**——
  这次整体位移只花了一次重新生成，如果当初是手工填的 13 个资产，就得逐个打开改分类；
- 这次改动同时暴露了"枚举顺序即存档格式"这件事，值得作为长期约束：
  **发布过的枚举只能追加，不能插入。**

## 四、测试自身

### A-11：测试失败时先怀疑了实现，其实是期望写错

**症状**

两个测试失败，第一反应都是"实现有问题"。

**案例一：排序测试**

断言"整理后左上角是那堆 60 发弹药"，实际拿到的是步枪。
期望值是按我以为的布局写的，而规则定义的布局是**按占地降序**——
3×1 的步枪面积更大，本来就该排在左上角。

**根因**：断言写成了"我以为的布局"，而不是"规则定义的布局"。

**案例二：体力恢复测试**

期望体力恢复到 20，实际是 10，差了一倍。
原因是我漏算了一个细节：**恢复计时器的初值是 −1**，
所以真正开始恢复的时刻比 `StaminaRegenDelay` 晚 1 秒，我的期望值多算了一秒。

**做法**

- 排序测试改为断言"占格最大的物品在左上角"，直接对应规则，而不是硬编码某个坐标；
- 恢复测试改为**先推进到确认已开始恢复、记录起点，再推进固定步数**，
  期望值由"倍率 × 每秒恢复量 × 实际推进时间"精确推出，不再依赖对延迟的估算。

**教训**

**测试失败时，先判断是实现的错还是期望的错。**
这两次如果图省事直接去改实现，就会把一个正确的实现改坏——
而且改完测试还会变绿，问题被永久掩盖。

一个可操作的判据：**期望值里如果出现了"手算的中间量"（比如延迟多少秒、第几格），
就先怀疑期望**；好的断言应当直接由规则推导，而不是复述一遍计算过程。

### A-12：GitHub 推送失败：DNS 解析到不可达节点

**症状**

推送在阶段内**间歇性失败**，报错固定为：

```text
fatal: unable to access 'https://github.com/...': Failed to connect to github.com:443
after 21080 ms: Could not connect to server
```

同一天里有时成功、有时失败（M0 阶段的 P-04 已经记过这条，本阶段补充具体的诊断与处置手段）。

**定位过程**

先解析域名，再逐个测试节点连通性（TCP 443）：

```text
DNS 解析结果            20.205.243.166             连接失败
备选 140.82.113.3      连接成功
备选 140.82.114.3      连接成功
备选 140.82.121.3      连接成功
备选 20.27.177.113     连接成功
```

**根因**：DNS 把域名解析到了一个不可达的节点，而本机无法指定用哪个节点。

**做法**（按代价从低到高，依次尝试）

1. **直接重试**。DNS 每次解析结果可能不同，重试有时就通了——成本最低，先试它；
2. **走本机代理**。负责人开着代理软件时，用一次性参数而不是写入配置：

```text
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push origin main
```

   用 `-c` 传参的好处是**不留任何持久配置**，命令结束即失效；
3. **临时隧道**。代理没开时，写一个几十行的本地 CONNECT 代理，
   把 `github.com:443` 转发到上面测通的节点，推送期间运行、推完立即关闭并删除脚本。

**教训**

- 这条不值得为它改全局配置。**宁可每次多敲一个参数，也不要在仓库或全局留下代理设置**——
  否则换网络环境时会变成一个很难想到的故障源；
- 处置动作的**收尾要和启动一样明确**：关闭进程、确认端口不再监听、删除临时脚本、
  确认 git 配置未被改动。这四条本次都逐一核对过；
- 注意 A-03：启动后台辅助进程不能靠 `Start-Process`（会被策略拦截），要用会话机制。
