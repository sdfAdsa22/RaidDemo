# M10 复现与演示指南（更新与分发）

> 面向"别人克隆仓库后如何复现"与"面试时如何演示"两条用途。
> 协议与批次细节见 [`Modules/11_热更新与分发.md`](Modules/11_热更新与分发.md)；
> 启动器与更新源的用法见 [`Tools/Launcher/README.md`](../Tools/Launcher/README.md)、
> [`Tools/UpdateSource/README.md`](../Tools/UpdateSource/README.md)。

## 1. 五分钟跑通本地更新源

```bash
# 1) 构建工具（自包含单文件，目标机器无需 .NET 运行时）
dotnet publish Tools/UpdateSource/RaidDemo.UpdateSource.csproj -c Release -r win-x64 \
    --self-contained true -p:PublishSingleFile=true -o Builds/Tools/UpdateSource-win

# 2) 起本地更新源（只读模式即可分发；写操作需要口令）
Builds/Tools/UpdateSource-win/RaidDemo.UpdateSource --root "<更新源目录>" --port 8090 --token <口令>

# 3) 浏览器打开面板
#    http://127.0.0.1:8090/
```

`<更新源目录>` 的布局（发布时由面板维护）：

```text
<更新源目录>/
├─ manifest.json                 ← 当前发布清单（"发布"= 用某个版本的清单覆盖它）
└─ versions/<版本>/
   ├─ manifest.json
   └─ body/ · content/ · code/   ← 三层文件
```

## 2. 发布一个新版本的完整流程（Unity 侧）

| 步骤 | 菜单 | 产物 |
| --- | --- | --- |
| ① | `RaidDemo/M10/① 构建客户端（Windows）并生成更新清单` | `Builds/Client/<版本>/` + `Builds/Update/<版本>/`（本体层） |
| ④ | `RaidDemo/M10/④ 配置 Addressables 分组（幂等）` | 分组与资产入组（数据表 / 场景 / 角色 / 音效） |
| ⑤ | `RaidDemo/M10/⑤ 构建资源（Addressables）` | `Builds/Addressables/<平台>/`（catalog + bundle，构建前会清空旧产物） |
| ⑥ | `RaidDemo/M10/⑥ 生成更新清单（本体 + 资源）` | `Builds/Update/<版本>/`（含 `content/` 与资源版本号） |

然后把 `Builds/Update/<版本>/` 整目录上传到更新源的 `versions/<版本>/`，
在面板上点**发布**（或先点**校验**确认哈希一致）。

## 3. 客户端如何更新

```bash
# 图形界面（玩家）
RaidDemo.Launcher.exe            # 选更新源 → 检查更新 → 更新并启动

# 命令行（脚本 / CI）
RaidDemo.Launcher.exe --check  --source <更新源> --root <安装根>
RaidDemo.Launcher.exe --update --source <更新源> --root <安装根> [--launch]
```

启动器把更新源与默认服务器地址通过 `-updatesource` / `-serverhost` 传给游戏
（`-serverhost` 只预填联机界面的地址，不自动连接——游戏仍然先进主菜单；隐藏源会额外带 `-hideserver`，
地址在界面上显示为"已隐藏"、连接时仍用真实值。自动化/无头验收继续用 `-connect` 直接联机）；
**资源层由游戏内热更流程下载**（先比对 `content.version`，只下变化的文件，逐文件校验 SHA-256）。

## 4. 演示脚本（7 条，均可复现）

| # | 演示 | 操作 | 期望 |
| --- | --- | --- | --- |
| 1 | 全新安装 | 清空安装根，仅留启动器 → 选更新源 → 更新并启动 | 全量下载（本体约 159 MB）→ 校验通过 → 游戏启动 |
| 2 | 增量更新 | 改一处代码或资源后重新发布 → 再检查更新 | 只下载变化文件，体积明显小于全量 |
| 3 | 源切换 | 面板停掉云源，改用本机目录源 | 同一套流程成功，版本信息刷新 |
| 4 | 失败回退 | 更新中途断网 / 指向不可达的源 | 旧版本仍可启动；日志给出失败原因（游戏内日志为 `更新源不可用，使用本地内容`） |
| 5 | 资源热更 | 改一个数值（如 AK 伤害）→ ⑤ 重建 → ⑥ 生成清单 → 发布 → 重启游戏 | **不重装本体**，数值变化；日志出现 `资源已生效（<新内容版本>）` |
| 6 | 代码更新 | 改一段业务逻辑 → ① 重建客户端 → 发布 → 启动器更新 | 由启动器完成（Mono 下业务逻辑在 `RaidDemo_Data/Managed/*.dll`，属本体层）。2026-09-15 实测：本轮代码改动=版本握手，重建 `0.10.1` → 发布 → 启动器更新，安装根清单变为 `0.10.1 / 247 文件` |
| 7 | 版本一致 | 客户端与服务器版本不一致时 | 进房被拒并提示两个版本号。2026-09-15 实测：服务器 `0.10.0` + 客户端 `0.10.1` → `客户端 0.10.1 与服务器 0.10.0 不一致，请更新客户端。`；反向（新服务器 + 无该字段的老客户端）按"未知版本"放行 |

## 4.1 版本握手的自动化验收

```bash
# 前置：菜单 RaidDemo/M10/① 构建客户端（Windows）并生成更新清单
pwsh -NoProfile -File Tools/Lobby/verify/p6_version_handshake_check.ps1
```

它拉起"1 服务器 + 2 客户端"的真实进程，输出 6 条判据（服务器就绪 / 同版本进房 /
旧版本被拒 / 提示含两个版本号 / 服务器记录拒绝原因 / 被拒者不进入名册），日志落在
`Builds/HandshakeCheck/`。脚本用 `-buildid` 启动参数伪造旧版本号——
它走的判定路径与真实旧版本完全一致，但不需要为每次回归重打一个旧包。

## 5. 边界：为什么"代码热更"走的是启动器而不是进程内

M10 原计划用 HybridCLR 做**进程内**代码热更。批次 5 做了完整探针，结论是当前不可用：

```text
Unity.AI.Navigation.cpp: error C2065: "Object_tC12DECB..._StaticInit": 未声明的标识符
Generics__150.cpp:        error C3861: "il2cpp_codegen_method_rgctx": 找不到标识符
```

27 处同类型错误，全部是"6000.6 的代码生成器产出、patched il2cpp 运行时里不存在的符号"——
即官方尚未把 **Unity 6000.6** 的 il2cpp 合并进 `il2cpp_plus`（其分支只到 6000.5.x）。

因此本项目采取的做法是：

1. 资源热更（Addressables）**照常交付**，已在真实客户端验证；
2. 代码更新由**启动器的本体更新**承担——Mono 后端下业务逻辑位于 `RaidDemo_Data/Managed/RaidDemo.*.dll`，
   天然属于本体层，启动器的清单比对与替换完整覆盖；
3. 探针步骤与失败特征已留档（`Modules/11_热更新与分发.md` 第 12 节），
   待官方合并 6000.6 的 il2cpp 后，按那四步重跑即可启用进程内代码热更。

> 面试里这条边界本身就是可讲的工程判断：**用什么版本、受什么约束、验证到什么程度、如何降级**，
> 以及"降级后功能是否仍然完整"——比"用了 HybridCLR"这句话有信息量得多。
