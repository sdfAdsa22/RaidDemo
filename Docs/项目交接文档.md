## 1. 项目概述

### 1.1 一句话定位

**RaidDemo** 是一款用 **Unity 6** 制作的、**Windows 平台**的 **3D 斜俯视（约 45°）PVE 搜打撤（Extraction Shooter）Demo**：
携带装备进入地图 → 搜刮物资 → 与 AI 交火 → 在限时内抵达撤离点 → 把战利品带回仓库，
用于变卖、升级装备与接取任务。支持 **2~4 人联机合作**，并通过**自研启动器**完成分发与增量更新。

- **对标基线**：《逃离鸭科夫》。博弈点不是塔科夫式的穿甲对枪，而是**贪心与撤离时机的抉择**——
  多搜一个箱子，就多一分被听见、被打死、装备全丢的风险（见 `00` 文档 7.12 节）。
- **目标用途**：面向 Unity 客户端开发岗位的作品集项目；评价重心是**系统完整性与工程质量**，不是美术表现。

### 1.2 核心循环

```text
安全屋整备（买卖 / 任务 / 试枪 / 选图）
   → 出击进图（8 分钟一局）
   → 搜刮（站定 2 秒开箱，移动打断）
   → 贪婪（背包快满了，但那个箱子还没开）
   → 负重（越拿越重 → 跑得慢、体力掉得快、噪音大）
   → 撤离或阵亡（撤离成功全部入库；阵亡随身全丢）
   → 回到安全屋，循环重新开始
```

### 1.3 三种交付形态

| 形态 | 组成 | 场景 |
| --- | --- | --- |
| **单机** | 一个客户端即可完整游玩 | 主菜单 → 继续 / 新游戏 |
| **本地 / 云联机** | **同一个客户端** + 独立专用服务器进程；2~4 人 | 主菜单 → 联机 → 建房 / 进房 |
| **启动器分发** | 启动器（下载 / 增量更新 / 启动）+ 更新源（本机 / 云） | 玩家安装与热更新入口 |

> 关键事实：**单机与联机不是两个客户端**。同一个可执行文件，启动参数决定身份；
> 单机模式下游戏内部起一个本机服务器，走的是同一套服务端权威逻辑。

| PowerShell 7（`pwsh`） | 验收脚本用 | Windows PowerShell 5 可能不够 |
| （可选）自定义 `unity` CLI | 作者机器上在 `C:\Users\DongSu\AppData\Local\Unity\bin\unity.exe` | 用于"重编译 / 跑测试 / 执行菜单"的无头操作；没有就用编辑器界面或 `-batchmode` 等价命令 |

### 2.2 打开工程、跑单机

1. `git clone`（先装 Git LFS）——仓库根目录就是 Unity 工程根目录；
2. Unity Hub → 添加 → 用 Unity 6000.6.0f1 打开（首次会自动还原包）；
3. 打开场景 **`Assets/Game/Content/Scenes/SafeHouse.unity`** → Play；
4. 进游戏先看到主菜单：点「开始 / 继续」进安全屋；商人（北墙）按 `E` 买卖与接任务，
   仓库按 `E` 整备，东侧出口按 `E` 选图，按 `1` 进工业区。

单机存档位置：`Application.persistentDataPath` 下的 `raid_demo_save.json`；
主菜单「新游戏」会清空仓库、金币与任务并重置为 5,000 金币。

> 从 `GreyboxRaid.unity` 直接 Play 也能进主菜单（点继续会自动加载 SafeHouse），
> 但推荐从 `SafeHouse.unity` 启动。

### 2.3 跑测试（改代码的底线动作）

- **编辑器内**：`Window → General → Test Runner → EditMode → Run All`（当前 762 项）。
- **CLI（作者环境装了自定义 CLI 时）**：

```powershell
unity command --project-path 'D:\unity game\demo' --no-banner --non-interactive recompile
unity command --project-path 'D:\unity game\demo' --no-banner --non-interactive run_tests --mode EditMode
```

> 工程有三条硬规则由测试强制：**单文件 ≤ 400 行、单方法 ≤ 50 行、禁止绝对路径**（`PathRulesTests`）。
> 每次提交前至少要：编译 0 错误 + EditMode 全绿。

### 2.4 本地联机（1 服务器 + 2 客户端）

```powershell
# 服务器（普通客户端构建 + -server；也可用「Windows 一键开服」面板）
RaidDemo.exe -server -port 7777 -room 测试房间 -batchmode -nographics -logFile server.log

# 客户端（同机多开时昵称必须不同）
RaidDemo.exe -connect 127.0.0.1:7777 -nickname 甲 -passphrase 246810 -autoroom
RaidDemo.exe -connect 127.0.0.1:7777 -nickname 乙 -passphrase 246810 -autoroom
```

**常用服务器参数**（完整说明见 `Assets/Game/Bootstrap/Session/LaunchOptions.cs` 注释）：

| 参数 | 用途 |
| --- | --- |
| `-port` / `-room` | 监听端口（默认 7777）与默认房间名 |
| `-autostart <秒>` | 房间成立后自动开局（验收 / 录像用） |
| `-raidDuration <秒>` | 战局总时长上限（默认 480；0 = 不判超时） |
| `-dashboardPort` / `-discoveryPort` | 状态页（默认 8080）与局域网发现（默认 47777）；0 = 关闭 |
| `-saveDir <相对路径>` | 服务端存档目录（**只接受相对路径**，绝对路径会导致配置解析失败） |
| `-grace <秒>` / `-watchdog <秒>` | 掉线宽限（默认 60）与断线自愈看门狗（默认 2.5，0 = 关） |
| `-downtest` / `-spawnzone` | 验收辅助：把玩家 1 打到 0 血 / 指定出生区 |

**客户端参数**：`-connect <ip>` `-port` `-nickname` `-passphrase` `-autoroom`
（验收还有 `-autowalk` 无头自动走、`-autotrade` 自动买卖接任务）。

**Windows 一键开服面板**：`RaidDemo.ServerHost.exe`（服务器包内）——端口、房间名、存档目录在
`server.config.json` 里配置；面板能看在线人数、当前世界与实时日志，并可复制连接信息给队友。
详见 `Tools/ServerHost/README.md` 与 `Docs/Modules/10_联机.md` 第 34 节。

`server.config.json` 字段（示例为交付版默认值）：

```json
{
  "port": 7777, "room": "默认房间", "saveDir": "server_saves",
  "logLevel": "info", "map": "GreyboxRaid", "raidDuration": 480,
  "autoStart": 0, "dashboardPort": 8080, "discoveryPort": 47777,
  "grace": 60, "watchdog": 2.5, "adminToken": ""
}
```

```powershell

# 启动器：图形界面双击即可；命令行等价：
RaidDemo.Launcher.exe --check  --source http://127.0.0.1:8090 --root <安装根>
RaidDemo.Launcher.exe --update --source http://127.0.0.1:8090 --root <安装根> --launch
```

**发布一个新版本的完整流程**（细节见 [`M10_复现与演示指南.md`](M10_复现与演示指南.md)）：

1. Unity 菜单 `RaidDemo/M10/① 构建客户端（Windows）并生成更新清单`；
2. `④ 配置 Addressables 分组（幂等）` → `⑤ 构建资源（Addressables）` → `⑥ 生成更新清单（本体 + 资源）`；
3. 把 `Builds/Update/<版本>/` 上传到更新源的 `versions/<版本>/`，在 Web 面板点**校验 → 发布**；
4. 启动器检查更新 → 增量下载 → 启动；资源层由游戏内热更流程按内容版本比对后下载。

> 注意：启动器与游戏两侧对"内容缓存目录 / `state.json` 字段"的约定必须逐字一致
> （`Tools/Launcher/Update/ContentCacheInstaller.cs` ↔ 游戏侧热更运行时），改一边要改另一边。

## 3. 架构设计

### 3.1 分层模型（五层）

| 层 | 名称 | 职责 | 禁止 |
| --- | --- | --- | --- |
| L5 | Presentation | 渲染、动画、音效、VFX、UI 显示 | 数值计算与业务判定 |
| L4 | Interaction | 输入采集、意图解析、交互检测 | 直接改数据（必须走请求） |
| L3 | Simulation | 战斗、AI、战局规则、时间推进 | 直接操作用户界面 |
| L2 | State | 背包、装备、仓库、任务、进度 | 依赖场景对象 |
| L1 | Data | ScriptableObject 定义、运行时实例、存档 DTO | 持有 Mono 对象引用 |

调用自上而下；数据变更用**事件总线**自下而上广播。

### 3.2 程序集划分（asmdef 强隔离）

当前工程有 20 个 asmdef（含测试与编辑器程序集）。核心依赖方向：

```text
                    Tests.*（可引用全部）
        ┌───────────────┼────────────────┐
        │               │                │
      UI            Raid             Meta          ← 顶层业务
        │               │                │
        │      ┌────────┴────────┐       │
        │      │                 │       │
        │     AI             Combat       │
        │      │                 │       │
        └──► Inventory ◄─────────┘       │
                │  ▲                     │
              Data │                     │
                │  └─────────────────────┘
        Kernel.Pure / Kernel.Unity（最底层）
        Bootstrap（极薄启动入口，不可热更）
        Shared（两端共用契约，不依赖 UnityEngine 运行时类型）
```

| 程序集 | 职责 |
| --- | --- |
| `RaidDemo.Kernel.Pure` / `.Unity` | 事件总线、服务定位、对象池、日志 / 时间服务；无业务 |
| `RaidDemo.Shared` | 客户端 / 服务端共用：命令契约、稳定 ID、纯规则函数 |
| `RaidDemo.Data` / `Data.Content` | 物品 / 武器 / 掉落数据定义与 ScriptableObject 资产目录 |
| `RaidDemo.Input` | Input System 采集 → 玩家意图 |
| `RaidDemo.Inventory` | 网格背包、装备槽、移动 / 堆叠 / 旋转规则 |
| `RaidDemo.Combat` | 武器、弹道、伤害、护甲、命中判定 |
| `RaidDemo.AI` | 感知、状态机、寻路契约、战术行为 |
| `RaidDemo.Raid` | 战局生命周期、计时、撤离、生成 |
| `RaidDemo.Meta` | 仓库、商人、任务、经济、存档 |
| `RaidDemo.UI` | 全部界面与 HUD（只读状态 + 发请求） |
| `RaidDemo.Bootstrap` | 启动入口（含 Editor 工具与全部菜单） |
| `RaidDemo.HotUpdate` | 资源热更运行时（清单比对 / 下载 / 应用） |
| `Tests.EditMode` / `Tests.PlayMode` | 单元测试与少量集成测试 |

> 有一条已记录的退化：`Kernel.Pure` 与 `Shared` 原计划用 `noEngineReferences: true`，
> 但当前引擎版本下该设置会导致编译产物缺失，现改由**代码评审与测试**保证"不引用引擎"这一约束（ADR-004）。

### 3.4 四条贯穿全项目的机制

1. **命令模式（单机 / 联机共用一套逻辑）**
   界面不直接改数据，一律发"意图"（Command）→ 由 `CommandRouter` 执行。
   单机在同一进程执行；联机把同一意图上行给服务器，服务器执行后广播结果。
   → 这是"同一个客户端既能单机又能联机"的地基。
2. **事件总线**
   数据变更加只读结构体事件，UI / 任务 / 音效各自订阅；新增系统不改拾取代码。
3. **共享层单一数据来源**
   伤害、背包、结算等规则写在 `Shared`/`Data` 的纯 C# 类里，客户端与服务器**引用同一份代码**；
   引擎能力（射线、寻路、时间、随机）通过接口注入（`IRaycastService` / `IPathfindingService` / `ITimeService` / `IRandomProvider`），
   所以规则可以脱离场景做 EditMode 单测，也能在无头服务器上跑。
4. **数据驱动**
   物品 / 武器 / 掉落 / 地图数值都是 ScriptableObject 或 JSON 配置，扩充内容不改逻辑代码。

### 3.5 联机架构要点

- **服务端权威**：移动、射击、搜刮、装备、商店、任务、结算全部由服务器裁定；
  客户端只上报输入并做本地预测，收到快照后和解，**误差超容差才回滚重放**。
- **状态同步（非帧同步）**：合作 PVE 更看重掉线恢复与输入合法性；服务器校验全部上行输入，非法值丢弃。
- **共享安全屋**：联机第一站是同一间安全屋；仓库按房间共享；**全员回屋后房主才能从出口选图**（服务器判定）。
- **倒地与救援**：倒地可被队友扶起（M13 已在本地双端 E2E 验证）。
- **断线自愈（P-51）**：服务器看门狗发现全员静默 → 重建传输层；客户端自动重连接管会话。
- **服务端存档**：按账号存金币 / 仓库 / 装备 / 任务（`-saveDir/profiles.json`），与单机存档**完全隔离**。
- **可视化**：只读状态页（8080）+ 管理操作（踢人 / 解散房间，需 `adminToken`）。
- **云部署**：Linux 专用服务器 + `deploy/` 脚本；低版本 glibc 用 Ubuntu rootfs chroot 兼容层。

### 3.6 分发与热更架构

- **三层版本**：本体版本 / 资源版本 / 代码版本 → 对外汇总成一个构建标识 `buildId`。
- **更新清单**：逐文件 SHA-256 + 分层（body / content / code）；启动器按清单做
  增量下载、断点续传、原子替换、失败回滚；更新源有本机与云两份，一键切换。
- **资源热更**：Addressables；改数值 → 重建资源 → 发布 → 客户端只下变化的文件（真机验证过）。
- **代码热更**：按 ADR-008 **降级**——社区版 HybridCLR 与 Unity 6000.6 的 il2cpp 不兼容（探针 27 处编译错误），
  代码更新由**启动器替换本体**承担；代价是必须重启进程。官方合并后可按探针四步重启该能力。
- **版本握手**：进房前比对两端本体版本，不一致直接拒绝并提示更新；无版本字段的老客户端按"未知"放行。

### 6.4 高风险坑位（新开发者最容易踩）

1. **chroot 的 bind mount**：云上更新服务端时，直接 `mv` 替换 `/root/raid-demo` 会让 chroot 继续挂旧 inode
   （状态页显示旧版本）——要"覆盖复制"或先 `umount` 再替换（详见 `deploy/README.md`）。
2. **`-saveDir` 只接受相对路径**：绝对路径会让配置解析失败、服务器退化。
3. **`-logFile` 等启动参数带空格会被拆参**（M12 排障 T-xx）；另注意后台进程策略可能拦截启动方式。
4. **Unity CLI 的 `menu` 30 秒超时 ≠ 失败**：构建类菜单要查 `Logs/Editor.log` 的成功标记
   （如 `[服务器构建] 成功`），不要重复发第二条命令（同一编辑器不要并行发指令）。
5. **大截图会把工具请求撑爆（413）**：读图前先缩到 ≤800px 的 JPEG（作者本机工具 `Library/TestRuns/tools/Shot.ps1`）。
6. **推送需要网络代理**：`git push` 前确认代理已开；推送与发布前先跑第 2.3 / 2.7 节的两套验证。
7. **公开仓库脱敏**：公网 IP、SSH、口令只能放 `Docs/Local/`（该目录被 `.gitignore` 忽略）。
8. **编辑器产物**：`Library/`、`Temp/`、根目录 `.csproj`/`.sln` 都是本地产物，
   不要提交（`Tools/**/*.csproj` 是手写工具工程，必须入库——`.gitignore` 已做白名单）。
9. **更新源的发布批号必须等于清单里的本体版本号**：下载路径按
   `versions/<清单.body.version>/` 解析；用别的目录名发布会出现"磁盘文件是新的、
   `/api/verify` 也通过，但 `/body/...` 仍取旧文件"的假象（U-104 实际踩到，
   启动器下载后哈希校验失败）。
