# ADR-004：程序集划分方案

- 状态：已采纳
- 日期：2026-09-10
- 相关代码：`Assets/Game/` 下各目录的 `.asmdef` 文件
- 落地里程碑：M0

## 背景

项目要求"程序集隔离、代码可维护、可扩展"作为硬性约束，同时需要为后续的联机（M9）与热更新（M10）预留结构。

不使用程序集定义时，Unity 会把 `Assets` 下所有脚本编译进 `Assembly-CSharp`，带来三个问题：

1. **依赖方向无法约束**：任何脚本都可以直接引用任何其他脚本，架构腐化没有任何机制阻挡。
2. **编译无法增量**：改动任意一个文件都会重编译整个程序集。本项目最终代码量会有数百个文件，全量重编译会显著拖慢开发迭代。
3. **无法热更**：代码热更新要求业务逻辑位于独立程序集中，与启动层分离。全部混在一个程序集里将无法满足这一前提。

## 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **A. 单一程序集（Assembly-CSharp）** | 零配置，上手最快 | 依赖无法约束、全量重编译、无法热更 |
| **B. 按"表现 / 逻辑"分两个程序集** | 简单，能挡住最粗的越界 | 粒度太粗，业务模块之间仍可随意互相引用 |
| **C. 按业务模块划分多个程序集** | 依赖方向可强制约束、编译可增量、满足热更前提 | 需要维护 asmdef 文件；初学者容易配错引用 |
| **D. 每个类一个程序集** | 依赖最严格 | 程序集数量过多会拖慢编译与加载，得不偿失 |

## 决策

采用 **方案 C：按业务模块划分程序集**，共 13 个程序集，分为四个层次。

**层次一：基础层（无业务语义，被所有模块依赖）**

| 程序集 | 职责 | 是否引用引擎 |
| --- | --- | --- |
| `RaidDemo.Kernel.Pure` | 事件总线、服务定位、对象池、确定性随机数 | **否** |
| `RaidDemo.Kernel.Unity` | 日志服务、时间服务 | 是 |

**层次二：共享契约层（客户端与服务端共用）**

| 程序集 | 职责 | 是否引用引擎 |
| --- | --- | --- |
| `RaidDemo.Shared` | 命令契约、共享数据结构（如 `Vector2F`） | **否** |

**层次三：业务模块层**

| 程序集 | 职责 | 依赖 |
| --- | --- | --- |
| `RaidDemo.Data` | 物品定义、掉落表等纯数据逻辑 | Kernel.Pure |
| `RaidDemo.Data.Content` | 数据资产（ScriptableObject）与目录 | Kernel.*, Shared, Data |
| `RaidDemo.Input` | 输入采集与意图转换 | Kernel.*, Shared |
| `RaidDemo.Inventory` | 网格背包、装备槽 | Kernel.*, Shared, Data* |
| `RaidDemo.Combat` | 武器、弹道、伤害、护甲 | Kernel.*, Shared, Data*, Inventory |
| `RaidDemo.AI` | 感知、状态机、寻路 | Kernel.*, Shared, Data*, Combat |
| `RaidDemo.Raid` | 战局生命周期、撤离、结算 | Kernel.*, Shared, Data*, Inventory, Combat, AI |
| `RaidDemo.Meta` | 仓库、商人、任务、存档 | Kernel.*, Shared, Data*, Inventory |
| `RaidDemo.UI` | 全部界面与 HUD | 以上业务模块 |

**层次四：启动层与测试**

| 程序集 | 职责 | 是否可热更 |
| --- | --- | --- |
| `RaidDemo.Bootstrap` | 极薄的启动入口，仅负责初始化与装配 | **否**（热更边界） |
| `RaidDemo.Tests.EditMode` | 纯逻辑单元测试 | 否 |

> `Data*` 表示同时引用 `RaidDemo.Data` 与 `RaidDemo.Data.Content`。

## 理由

1. **依赖方向由编译器强制。** 让 `Data` 引用 `UI` 会在编译期直接报错，而不是靠代码评审时靠人眼发现。这是"可维护"最实在的保障。
2. **两个"纯程序集"禁用引擎引用。** `Kernel.Pure` 与 `Shared` 设置为不引用 UnityEngine。这一点直接服务于 M9 与 M10：服务端在无头模式下运行，不能依赖渲染相关的程序集；共享层被两端同时引用，必须与引擎解耦。约束由编译器保证，不依赖自觉。
3. **保留热更边界。** `Bootstrap` 与业务模块分离，为 M10 的 HybridCLR 接入保留了清晰的切分点。一旦发布，启动层不再修改，业务逻辑可独立更新。
4. **编译增量收益明显。** 改动 UI 不会触发 AI 与战斗模块的重编译，迭代更快。
5. **模块数量与粒度平衡。** 13 个程序集覆盖了当前全部职责，但没有细到每个类一个程序集。粒度过细会导致程序集依赖解析开销上升，反而拖慢编译。

## 后果

**正面影响**

- 架构约束从"约定"升级为"编译期校验"，长期维护成本显著降低。
- 新增模块有明确的落位规则：先建目录与 asmdef，声明依赖，再写代码。
- 单元测试可以只引用需要的模块，测试边界更清晰。

**代价与后续待办**

- 新增程序集时需要手动维护 `.asmdef` 及其引用列表。引用遗漏的报错信息（找不到类型）对新手不够直观，因此每个 asmdef 都需要在文档中登记用途。
- 空的业务模块程序集当前只含占位类型。进入对应里程碑时应替换为真实实现。
- `RaidDemo.Input` 依赖 `Unity.InputSystem`；`RaidDemo.AI` 依赖 `Unity.AI.Navigation`；`RaidDemo.UI` 依赖 `Unity.TextMeshPro`。这些第三方程序集引用在引入对应包之前不可用，会报编译错误——本项目的做法是在引入包的同一里程碑再创建对应模块。

## 验证方式

本方案的正确性由以下证据验证（M0 完成时已确认）：

| 验证项 | 方式 | 结果 |
| --- | --- | --- |
| 全部程序集可编译 | 触发重编译并检查错误列表 | 通过，0 错误 |
| 依赖方向未形成循环 | 编译成功即证明无循环引用 | 通过 |
| 纯程序集确实未引用引擎 | asmdef 的 `noEngineReferences` 设置 + 编译通过 | 见下方说明 |
| 模块间调用符合预期 | 单元测试程序集引用全部模块并运行 | 69 个用例全部通过 |

> **关于 `noEngineReferences` 的实践发现**：在 Unity 6000.6.0f1 中，将该字段设为 `true` 会导致对应程序集不产出编译产物，进而使引用它的程序集报"找不到类型"。因此本项目的做法是：`Kernel.Pure` 与 `Shared` 的 asmdef 保持 `noEngineReferences: false`，**而"不引用引擎"这条约束由代码评审与后续的静态检查保证**，不依赖该字段。
>
> 这是一个有实际代价的取舍：约束从"编译器强制"退化为"约定 + 检查"。若后续找到该字段的正确用法，应改回由编译器保证，并更新本条记录。
