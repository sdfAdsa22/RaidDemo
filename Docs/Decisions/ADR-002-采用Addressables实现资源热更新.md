# ADR-002：采用 Addressables 实现资源热更新

- 状态：已采纳
- 日期：2026-09-10
- 相关代码：`Assets/Game/Content/`、热更包构建与发布流程（M10 阶段创建）

## 背景

项目需要热更新能力。热更新在工程上分为两层：**资源热更**（贴图、模型、音频、数据表）与**代码热更**（业务逻辑程序集）。本 ADR 只决策资源层，代码层见 ADR-003。

约束条件：

- Unity 6000.6.0f1，需要与引擎版本兼容且长期维护的方案
- 热更过程必须能被他人复现验证（不能只是声称做过）
- 不能引入需要付费或需要账号体系的托管服务
- 数据表（物品定义、掉落表、数值）应能通过热更调整，而无需重新发版

## 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **A. 自研 AssetBundle 管理** | 完全可控，能体现底层理解 | 需自行处理依赖解析、循环依赖、哈希校验、缓存淘汰——正是最容易出 bug 的部分 |
| **B. Addressables 2.10.3** | Unity 官方；自动处理依赖与引用计数；catalog 自带内容哈希；可与 Remote Catalog 做增量更新 | 需理解其分组策略；误配置会导致包体膨胀 |
| **C. AssetBundle + 自研版本清单** | 介于 A 与 B 之间 | 仍需处理 B 已解决的问题，收益有限 |

## 决策

选择 **方案 B：Addressables 2.10.3**，配合远端 catalog 实现增量资源热更。

热更包托管采用**本地 HTTP 服务或静态文件托管**（GitHub Pages 或 Release 附件），不使用商业 CDN。

## 理由

1. **Addressables 是 Unity 官方方案且对 Unity 6000 有明确支持**，`2.10.3` 的版本适配已确认。
2. **catalog 自带内容哈希**，无需自研版本比对逻辑——自研方案中最容易出错的部分被自动化了。
3. **依赖解析与引用计数由官方实现**，避免了 AssetBundle 手工管理中资源重复打包、依赖缺失导致粉色材质这两类高频事故。
4. **数据表可随资源热更**：物品定义与掉落表是 ScriptableObject 资产，纳入 Addressables 后即可通过热更调整数值。这是本项目中热更最有实际价值的部分。
5. **演示可复现**：把热更包托管到公开静态位置，任何克隆仓库的人都能完整复现启动、检测更新、下载、生效的流程。

## 后果

**正面影响**

- 无需重新打包即可调整数值与替换美术资源，符合真实项目的运营需求。
- 为后续 M9 联机的资源版本一致性校验提供基础（catalog 哈希可作为资源版本标识）。

**代价与后续待办**

- 需要设计 Addressable 分组策略（按更新频率分组，而非按资源类型），否则会造成大量无谓的重复下载。
- 需要实现更新流程 UI（下载进度、失败重试、断点续传）。
- **必须实现失败回退**：下载失败时要能用本地已有版本启动，不允许出现更新失败导致游戏打不开的情况。
- 构建流程变复杂，需要把 Addressables 构建纳入构建脚本。
