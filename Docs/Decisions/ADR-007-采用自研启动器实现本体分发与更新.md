# ADR-007：采用自研启动器实现游戏本体分发与更新

- 状态：已采纳
- 日期：2026-09-13
- 相关文件：`Tools/Launcher/`（待创建）、`Docs/00_项目工程规范与系统设计.md` 第 7.10 节、M10 构建与发布流程

## 背景

M10 原有的两层热更（ADR-002 资源、ADR-003 代码）只能更新**游戏内的内容**。
而 IL2CPP 发行构建里，exe、`UnityPlayer.dll`、AOT 程序集与启动层是编译死的：
它们没有任何"自己替换自己"的通道。

2026-09-13，项目负责人提出目标：**客户端可以从服务器下载游戏、更新游戏**——
即同时覆盖"新玩家安装"与"老玩家升到新版本"两条路径。经确认，
它指的是**下载器 / 启动器形态**（装一个启动器，由它拉取并维护游戏本体），
而不是 Steam 式的多游戏平台。

约束条件：

- 仅 Windows 平台（决策 D-15），无 iOS 审核问题；
- 不引入付费服务、账号体系与商业 CDN，更新源必须可被他人复现（沿用 ADR-002 的托管原则）；
- 作品集定位（D-03）：要能讲清"为什么这样做"，拒绝黑盒；
- 与 M9 联机、M10 游戏内热更共存：三层更新必须有统一的版本标识，供联机握手校验。

## 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **A. 不做本体更新**（玩家手动重装） | 零成本 | exe 一变就得重发压缩包；"从服务器下载游戏"的目标无法演示 |
| **B. 自研启动器**（清单 + 哈希 + 下载 + 暂存替换） | 完全可控，细节可讲；与热更共用一套清单基础设施 | 需自写下载、校验、替换与失败恢复；杀软可能误报 |
| **C. 现成更新框架**（Squirrel / NetSparkle / Velopack 等） | 省事、开箱即用 | 黑盒，面试讲不了细节；与"展示工程能力"的定位相悖 |
| **D. Steam / 平台分发** | 真实运营方案 | 需要账号与上架流程，对作品集不适用 |

## 决策

选择 **方案 B：自研启动器**。

形态：`Tools/Launcher` 下的**独立 C# 程序**（控制台或 WinForms，不依赖 Unity 运行时、不进游戏程序集），
与游戏共用一份**更新清单**（`manifest.json`）：版本号 + 逐文件路径、大小、SHA-256 与下载地址。

更新源沿用 ADR-002 的托管策略：**本地 HTTP 服务或 GitHub Release 附件**，不使用商业 CDN。

```text
[构建期] 出包 → 逐文件计算 SHA-256 → 生成 manifest.json → 上传更新源
                                  │
[启动器] 启动 → 拉取远端 manifest → 与本地清单比对（新增 / 变更 / 删除）
              ├─ 有差异 → 断点续传下载到 staging/ → 逐个校验哈希 → 全部通过后原子替换
              │             （任一步失败：放弃本次更新，保留旧版本可启动）
              └─ 无差异 → 直接启动游戏
                                  │
                                  ▼
                      启动 RaidDemo.exe（游戏内再做资源 / 代码热更）
```

首次安装 = "本地清单为空"的特例，同一套逻辑天然覆盖"从服务器下载整个游戏"。
**不做二进制差分**（bsdiff 之类）：Unity 产物按文件哈希比对已能拿到足够增量，
引入差分工具的收益与复杂度不成正比。

配套策略：

1. **更新动作必须发生在游戏进程之外**——Windows 上运行中的 exe / dll 会被占用，覆盖必然失败；
2. **三层更新共用一份版本标识**：联机握手时客户端上报"本体版本 + catalog 哈希 + 热更程序集版本"，
   与服务器不一致就提示更新（M9 对接）；
3. **保持朴素**：明文 HTTP + SHA-256 校验，不混淆、不加壳——这是规避杀软误报最直接的写法，
   并在 README 说明更新源如何本地启动。

## 理由

1. **架构限制决定了必须有进程外的更新入口**：IL2CPP 的 AOT 部分不能自更新，
   启动器是唯一合理的位置；把这条边界写清楚本身就是有价值的工程判断。
2. **与 ADR-002 / ADR-003 天然共用基础设施**：三者都是"版本清单 + 下载 + 校验 + 失败回退"，
   M10 一次做出三层（本体 / 资源 / 代码）的统一版本体系，演示与讲解都更完整。
3. **自研才有可讲的内容**：断点续传、哈希校验、原子替换、失败恢复、版本握手——
   这些正是更新环节最容易出错、也最值得在面试里展开的部分。
4. **成本可控**：demo 级启动器约数百行 C#，更新源用静态文件即可；
   风险与后续待办都在可预期范围内（见下）。

## 后果

**正面影响**

- 完整覆盖"新玩家下载安装 → 本体增量更新 → 游戏内资源 / 代码热更 → 联机版本握手"全链路；
- 更新清单成为三层更新的统一入口，M9 联机的版本一致性校验可直接复用；
- README 可演示一条命令启动本地更新源，他人克隆仓库即可复现。

**代价与后续待办**

- 构建流水线变复杂：出包后需要生成清单并上传（与 ADR-002 / ADR-003 的构建期步骤合并成一条脚本）；
- 需要处理 Windows 文件占用、更新中断、杀软误报等边界，README 需写明演示步骤；
- 启动器放在 `Tools/Launcher`，**不纳入 Unity 游戏工程**，避免污染游戏程序集与构建产物；
- **优先级约定**：若时间不足，游戏内热更（ADR-002 / ADR-003）优先于启动器；
  启动器可退化为"全量下载 + 校验 + 启动"的最小演示，不影响 M10 主体交付。
