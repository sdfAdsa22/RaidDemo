# ADR-006：采用 Git LFS 管理大型美术与音频资源

- 状态：已采纳
- 日期：2026-09-12
- 相关文件：`.gitattributes`、`Docs/Assets/M7_素材选型与技术标准.md`

## 背景

M7 阶段开始把灰盒替换为卡通 Low-poly 资源，工程将第一次引入大量第三方二进制文件：FBX 模型、PNG 贴图、WAV/OGG 音频。
这些文件体积远超源代码，而 Git 对二进制文件无法做增量存储——每次修改都会保存一份完整快照，且历史无法回收。

约束条件：

- 仓库要作为**公开作品集**发布在 GitHub，克隆速度与体积是面试官的第一印象。
- M8 的完成判据是"他人克隆后按 README 可一键运行"，素材不能放在仓库之外。
- 免费方案优先；GitHub LFS 免费额度有限（存储与月流量各 1 GB）。
- **不重写已有历史**：M0~M6 已经推送的提交必须保持原样。

## 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **A. 二进制直接提交** | 零配置，克隆即用 | 仓库单向膨胀且不可回收；美术迭代几次后克隆会变得非常慢 |
| **B. Git LFS** | GitHub 原生支持；仓库只存指针；克隆按需拉取；配额对低多边形资源足够 | 协作者需安装 `git-lfs`；超出免费额度需付费 |
| **C. 素材移出仓库**（网盘 / Release 附件） | 仓库最小 | 违背 M8"克隆即运行"判据；演示前还要额外下载步骤 |
| **D. 自建 LFS / Unity Accelerate** | 完全可控 | 需要服务器与账号体系，对单人作品集过重 |

## 决策

选择 **方案 B：Git LFS**，在 `.gitattributes` 中按扩展名过滤，覆盖模型、贴图、音视频与 `unitypackage` 四类。

配套策略：

1. 只提交**最终采用**的素材，候选与试装资源不入库。
2. 第三方原始资源集中在 `Assets/Game/Content/External/`，项目层预制体再引用。
3. **不追溯迁移**历史中已有的二进制文件，避免重写已推送历史；此后新增或修改的才走 LFS。

## 理由

1. **克隆体验直接决定作品集的第一印象**：源码仓库保持在几 MB 量级，克隆只需数秒。
2. **素材可随仓库完整还原**，满足 M8 的"一键运行"判据，也便于面试现场演示。
3. **免费额度够用**：本轮候选素材以低多边形为主，主要资源包合计不足 100 MB，远低于 1 GB 额度。
4. **与后续里程碑兼容**：M10 的 Addressables 热更资源同样是大二进制文件，走 LFS 可保持一致的工作流。
5. **不重写历史是低成本选择**：已有 PNG 等文件保持原状，新资源走 LFS，避免 `filter-branch` 带来的协作风险。

## 后果

**正面影响**

- 仓库体积与克隆时间可控，素材来源与授权随仓库一起保存。
- 新增二进制资源无需手动 `git lfs track`，`.gitattributes` 已覆盖常用扩展名。

**代价与后续待办**

- README 的克隆说明必须写明"需安装 Git LFS"，否则协作者只会拿到指针文件（M7 批次 0 已记录，M8 再复查一遍）。
- 需要关注 LFS 配额；若后续引入高模或大体积音频，先评估再入库。
- Unity `.meta` 文件、材质、场景仍是文本，保持普通 Git 管理，便于 diff 与代码评审。
