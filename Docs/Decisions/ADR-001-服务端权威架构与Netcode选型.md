# ADR-001：采用服务端权威架构与 Netcode for GameObjects

- 状态：已采纳
- 日期：2026-09-10
- 相关代码：`Assets/Game/Raid/`、`Assets/Game/Shared/`、服务端工程（M9 阶段创建）

## 背景

项目原定为**单机搜打撤 Demo**。在准备阶段，项目负责人提出加入服务端、客户端与多人联机。

本项目为求职作品集，联机能力能显著提升简历稀缺度（多数应届作品为单机），但必须满足以下约束：

- 单人开发者 + AI 辅助实现，无专职后端
- 演示环境无公网固定 IP、无服务器运维预算
- 单机版本必须仍是保底可交付的成果
- 不得因联机需求破坏既有的模块化与可测试性设计

## 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **A. 不做联机** | 零风险，单机系统深度已足够支撑秋招 | 错失稀缺度；无法展示网络编程能力 |
| **B. Host-Client（房主即服务器）** | 实现最简单，无需独立服务器部署 | 房主有延迟优势；房主退出即全房崩；不是正确的工程实践 |
| **C. 专用服务器 + Netcode for GameObjects** | 服务端权威、架构正统、Unity 官方维护、与 URP 生态兼容 | 需要单独构建服务端；同步逻辑调试成本高 |
| **D. 专用服务器 + Mirror** | 社区成熟、文档多、上手快 | 非官方方案；长期维护风险由社区承担 |
| **E. Photon 等第三方托管服务** | 免运维、自带房间匹配 | 引入外部依赖与账号体系，脱离可离线复现的项目目标 |

## 决策

选择 **方案 C：专用服务器（Dedicated Server）+ Unity Netcode for GameObjects 2.13.2**。

联机范围严格限定为 **2~4 人 PVE 合作**，不做 PVP、匹配、账号与反作弊。

## 理由

1. **服务端权威是唯一正确的做法。** 主机模式让一名玩家的机器同时充当权威服务器，该玩家的延迟优势无法消除，且主机退出导致整局失败。用专用服务器可以从根本上消除这类问题。
2. **Netcode for GameObjects 是 Unity 官方方案**，`2.13.2` 明确支持 Unity 6000，长期维护有保障；其 `NetworkVariable`（持续状态）与 `Rpc`（一次性事件）的划分恰好对应本项目的同步语义。
3. **PVE 而非 PVP** 是关键的范围收缩。PVP 才真正需要严格的延迟补偿与反作弊，而 PVE 合作对同步精度的容忍度高得多，工作量差异巨大。
4. **不引入第三方托管服务**，因为项目要求他人克隆后即可复现，依赖外部账号体系会破坏这一目标。

## 后果

**正面影响**

- 项目从单机系统 Demo 升级为可展示网络编程能力的作品，可覆盖网络/服务端方向的岗位。
- 服务端权威架构让开火判定只在服务端执行成为自然选择，从架构上消除最常见的作弊面。
- 强迫逻辑层与表现层彻底分离，反向提升了单机代码的可测试性。

**代价与后续待办**

- 所有状态变更必须走单一入口（`CommandRouter`），这项约束**必须在 M0/M1 阶段就遵守**，事后补做的代价是重写绝大部分输入与逻辑代码。
- 必须实现客户端预测与回滚，才能保证射击手感；这是 M9 中技术难度最高的部分。
- 需要额外的服务端构建流程（`-batchmode -nographics`）。
- 调试复杂度显著上升，需要网络日志与状态可视化工具。

**风险控制**

- 联机实施**排在 M8 之后**。若 M8 时进度不及预期，应果断停止在单机版本，保证保底交付物成立。
