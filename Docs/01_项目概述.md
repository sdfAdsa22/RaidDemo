# RaidDemo — 项目概述

> 一款卡通风格的 **3D 斜俯视（45°）搜打撤（Extraction Shooter）** 游戏 Demo：
> 携带装备进入地图，搜刮物资、与 AI 交火，在限时内抵达撤离点，把战利品带回仓库，
> 用于变卖、升级装备与接取任务。支持 2~4 人 PVE 合作（专用服务器）与完整的启动器分发链路。

**对标游戏**：《逃离鸭科夫》（Escape from Duckov）。本项目不是《逃离塔科夫》的仿制——紧张感不来自对枪与穿甲博弈，而来自**贪心与撤离时机的抉择**。

## 1. 项目定位

| 项 | 说明 |
| --- | --- |
| 类型 | 3D 斜俯视搜打撤（PvE） |
| 平台 | Windows（PC） |
| 形态 | 单机 + 本地 / 云联机（2~4 人合作）+ 启动器分发 |
| 用途 | Unity 客户端开发岗位求职作品集 |
| 评价重心 | 系统完整性、代码质量、工程规范、可扩展性 |
| 非评价重心 | 美术表现、内容体量、玩法创新度 |

项目成功的判定标准（开工时定下，未变过）：

1. **闭环完整**：主菜单 → 配装 → 进入战局 → 搜刮/交火 → 撤离或阵亡 → 结算与仓库更新 → 再接任务 → 再次进入战局，全流程无断点；
2. **系统可信**：物品、背包、弹道、护甲、AI、存档六大系统的行为符合玩家直觉；
3. **代码可讲**：任意核心系统都能支撑 5 分钟以上的面试讲解，并能回答"为什么不那样做"；
4. **零环境依赖**：他人克隆仓库后，用指定 Unity 版本打开即可运行，无需手动配置。

## 2. 核心玩法：贪婪循环

全部系统服务于同一个循环：

```text
搜刮  →  贪婪（背包快满了，但那个箱子还没开）
      →  负重（越拿越重，跑得越慢、体力掉得越快、噪音越大）
      →  撤离（赌一把再搜一个，还是现在就撤）
      →  带出的物资成为下次出击的资本  →  回到搜刮
```

判断一个功能该不该做的标准：**它是否让"要不要多拿一件"这个问题变得更难回答。**

主要玩法特征：

- **网格背包**：物品按格子占用空间，支持旋转、堆叠、拆分与嵌套容器；负重影响移速、体力消耗与噪音半径；
- **两档移动与体力**：步行 / 奔跑；体力归零进入力竭，无法奔跑。体力只作用于移动，不影响射击精度；
- **会听也会看的 AI**：近身（6 米内）必定发现；中距离（6~9 米）转为警惕——停下、转向、盯住 3 秒才动手；噪音按移动档位分档（步行 4 / 奔跑 8 / 超载 12 米）；
- **开枪有代价**：枪声半径等于武器射程（手枪 8 米 / 步枪 12 米），打不中一样会把敌人引过来；
- **等级化护甲**：1~4 级护甲提供 20%~65% 减伤，可读性优先，不做塔科夫式穿透概率；
- **搜刮风险**：容器需要搜索时间，战斗收益与撤离时限形成风险决策；
- **局外成长**：仓库、固定价格商人（买价 / 75% 收购价）、五个固定任务与本地存档构成循环。

## 4. 三种运行形态

### 4.1 单机（编辑器 / 独立客户端）

1. 克隆仓库（仓库根目录即 Unity 工程根目录）；
2. 用 Unity Hub 以 **6000.6.0f1** 打开，首次打开自动还原依赖包；
3. 打开启动场景 `Assets/Game/Content/Scenes/SafeHouse.unity`，点击运行。

进游戏后：主菜单 →「开始 / 继续」→ 安全屋（商人处按 `E` 买卖与接任务，仓库前按 `E` 整备）→ 东侧出口按 `E` 选择地图 → 战局 → 撤离或阵亡 → 结算回屋。存档写入 `Application.persistentDataPath`。

### 4.2 联机（专用服务器）

单机模式 = 本机内嵌服务器；联机模式 = 独立专用服务器，客户端不区分单机 / 联机版本。

```powershell
# 服务器（Windows 双击 RaidDemo.ServerHost.exe 更简单；这是手工联调写法）
RaidDemo.exe -server -port 7777 -room 测试房间 -batchmode -nographics

# 客户端（同机多开需改 -nickname）
RaidDemo.exe -connect 127.0.0.1:7777 -nickname 甲 -autoroom
```

服务器带可视化：本机 / 局域网版是原生面板窗口（在线人数、房间、日志），云主机版是无头进程 + Web 状态页（`http://<服务器IP>:8080/`，写操作需管理口令）。Linux 部署（含 glibc 兼容层）见 [`../deploy/README.md`](../deploy/README.md)。

### 4.3 启动器分发

正式分发形态是**启动器 + 更新源**：玩家在启动器里选择更新源（本机 / 云主机 / 自定义），完成下载、校验、安装与启动；更新走增量文件清单与逐文件 SHA-256 校验，支持断点续传、原子替换与回滚。资源层由游戏内 Addressables 热更流程负责。日常操作以 `Tools/Launcher/README.md` 与 `Tools/UpdateSource/README.md` 为准。

## 5. 开发方式与协作模型

本项目采用 **AI 辅助开发**：选题、范围界定、系统与架构取舍、玩法数值与手感调校、美术方向、验收测试与最终决策均由作者负责；AI 编码助手（Codex）承担实现与测试代码的编写、文档草稿与素材调研。

为保证质量，工程建立了 700+ 项自动化测试与规范门禁（例如"单文件不超过 400 行"由测试用例强制），AI 的产出必须通过测试与实机验收才能进入版本。全部提交记录与最终验收由作者完成。

这套协作方式对项目的实际影响：

- **能快**：实现与测试代码的编写速度显著提升，使"单机 → 联机 → 热更"的完整路线在数周内跑通；
- **有护栏**：自动化测试、行数上限、路径规范与逐批次验收清单把 AI 的产出约束在可维护范围内；
- **要我判断**：所有架构决策（对标基线、服务端权威、分发形态等）经过我的取舍与记录，走不通的方案（如进程内代码热更）以探针证据否决，见 [`04_技术决策/`](04_技术决策/)。
