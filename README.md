# RaidDemo — 3D 斜俯视搜打撤射击游戏

> 一款卡通风格的 3D 斜俯视（45°）搜打撤（Extraction Shooter）游戏：携带装备进入地图，搜刮物资、与 AI 交火，在限时内抵达撤离点，将战利品带回仓库用于变卖、升级装备与接取任务。
>
> 联机支持 2~4 人 PVE 合作（专用服务器）。

**对标游戏**：[《逃离鸭科夫》](https://store.steampowered.com/app/3105440/)（Escape from Duckov）。
本项目不是塔科夫的仿制——两者的紧张感来源完全不同：塔科夫来自对枪与穿甲博弈，
本项目来自**贪心与撤离时机的抉择**。

## 项目简介

**核心循环**：进入地图 → 搜刮物资 → 与 AI 交火 → 抵达撤离点 → 回收战利品 → 变卖/升级装备/接任务 → 再次出击。

### 核心玩法支柱：贪婪循环

本项目的全部系统都服务于一个循环：

```text
搜刮  →  贪婪（背包快满了，但那个箱子还没开）
      →  负重（越拿越重，跑得越慢、体力掉得越快、噪音越大）
      →  撤离（赌一把再搜一个，还是现在就撤）
      →  带出的物资成为下次出击的资本  →  回到搜刮
```

判断一个功能该不该做的标准是：**它是否让"要不要多拿一件"这个问题变得更难回答。**
完整说明见技术基准文档 7.12 节。

**玩法特征**

- **网格背包**：物品按格子占用空间，支持旋转、堆叠、拆分与嵌套容器
- **负重压力**：携带重量影响移动速度、体力消耗与噪音半径——这是贪心的物理代价
- **奔跑与体力**：两档移动速度（步行/奔跑）；体力归零后进入力竭状态，无法奔跑
- **搜刮风险**：容器需要搜索时间，战斗收益与撤离时限形成风险决策
- **会听也会看的 AI**：近身（6 米内）必定发现，中距离（6~9 米）只会让它**警惕**——停下、转向、盯着你看 3 秒才动手；噪音按移动档位分档（步行 4 / 奔跑 8 / 超载 12 米），**跑动与超重会把敌人引过来**；AI 会巡逻、调查动静、保持距离交火，并在重伤时撤退
- **开枪是有代价的**：射程即枪声半径（手枪 8 米 / 步枪 12 米），**打不中的枪声一样会把敌人引过来**——武器射程压到近战范围，正面交火很难不被其他人听见
- **等级化护甲**：护甲按 1~4 级提供 20%~65% 减伤，可读性优先（不做塔科夫式的穿透概率）
- **友好撤离**：多个撤离点，主流撤离点无条件可用，让玩家能放心多搜一会儿
- **局外成长**：装备等级提升、仓库、商人交易、任务系统与收集图鉴构成循环

**目标定位**：本项目是面向 **Unity 客户端开发岗位**的作品集项目，评价重心为**系统完整性与代码质量**，而非美术表现。

## 运行方式

### 环境要求

| 项目 | 要求 |
| --- | --- |
| Unity 版本 | **6000.6.0f1**（Unity 6） |
| 平台 | Windows 10 / 11（本项目仅面向 Windows） |
| 图形 API | DirectX 11 / 12 |

### 启动步骤

1. 克隆仓库（仓库根目录即 Unity 工程根目录）
2. 用 **Unity Hub** 添加该目录，使用 Unity `6000.6.0f1` 打开
3. 首次打开时 Unity 会自动还原 `Packages/manifest.json` 中声明的依赖包
4. 打开启动场景 `Assets/Game/Content/Scenes/GreyboxRaid.unity`，点运行

> **进游戏后**：先看到主菜单，点「出击」或按 `Enter` 开始一局；战局结束后可用
> `Enter` 再来一局、`Esc` 回主菜单。整条流程不需要重启编辑器。

> 灰盒场景由菜单 **`RaidDemo → 生成灰盒测试场景`** 生成；物品资产由菜单
> **`RaidDemo → 生成初始物品资产`** 生成。两者都是可重复执行的，场景与资产均已提交，
> 正常克隆后直接运行即可，不需要先执行菜单命令。

> 工程使用 Unity 的 **Force Text** 序列化与 **Visible Meta Files**，`.meta` 文件已一并提交，无需任何手动配置。

## 架构设计

采用**分层 + 程序集隔离**的架构，依赖方向单向，低层不反向引用高层。

```text
                      ┌──────────────┐
                      │  Tests.*     │
                      └──────┬───────┘
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
   ┌────▼────┐         ┌─────▼─────┐        ┌─────▼────┐
   │  UI     │         │   Raid    │        │   Meta   │
   └────┬────┘         └─────┬─────┘        └─────┬────┘
        │                    │                    │
        │        ┌───────────┴───────────┐        │
        │   ┌────▼─────┐            ┌────▼────┐   │
        │   │    AI    │            │ Combat  │   │
        │   └────┬─────┘            └────┬────┘   │
        │        │      ┌───────────────┘        │
        │   ┌────▼──────▼────┐                   │
        └───►   Inventory     ◄──────────────────┘
                 └─────┬─────┘
                  ┌────▼────┐
                  │  Data   │
                  └────┬────┘
                  ┌────▼────┐
                  │ Kernel  │
                  └─────────┘
```

**关键设计**：

- **逻辑与表现分离**：业务逻辑不依赖 `MonoBehaviour` 与场景，可在 EditMode 测试中直接验证
- **单一数据来源**：客户端与服务端共用同一套规则代码（`Shared` 层不引用 `UnityEngine` 运行时类型）
- **状态变更单一入口**：所有玩家意图经 `CommandRouter` 执行，使单机与联机共用同一套逻辑
- **数据驱动**：物品、掉落、数值均由 ScriptableObject / JSON 配置，扩充内容无需改动代码

完整说明见 [`Docs/00_项目工程规范与系统设计.md`](Docs/00_项目工程规范与系统设计.md) 第 5、6、7 章。

## 工程规范

本项目遵循一套明确的工程约束，核心几条：

| 约束 | 说明 |
| --- | --- |
| **禁止绝对路径** | 源码与配置中不允许出现任何本机路径，保证克隆即可运行；并有单元测试自动扫描拦截 |
| **程序集隔离** | 各模块独立 asmdef，依赖方向单向，防止架构腐化 |
| **注释解释为什么** | 公开 API 必须有 XML 文档注释；数值参数注明量纲与调参影响 |
| **测试锁定规则** | 背包占位、伤害公式、状态机迁移等易错逻辑均有 EditMode 单元测试 |
| **数据与代码分离** | 新增物品/武器只需新增数据资产，不需要改动逻辑代码 |

## 技术亮点

> 本节将在对应里程碑完成后补充具体实现说明与量化数据（问题 → 方案 → 效果）。

| 亮点 | 说明 | 状态 |
| --- | --- | --- |
| 可单测的 AI 状态机 | 状态以普通 C# 类实现而非 `MonoBehaviour`，可脱离场景断言状态迁移序列；54 项 AI 用例覆盖感知、记忆、寻路与迁移 | **已完成（M4）** |
| 噪音即贪婪的代价 | 听觉半径按移动档位分档（静止 0 / 步行 4 / 奔跑 8 / 超载 12 米），把"跑得快"与"引来敌人"绑成同一件事 | **已完成（M4）** |
| 有中间态的感知 | 视觉分"必定发现 / 警惕 / 看不见"三档，警惕档会让 AI 停下来盯着你看 3 秒——玩家能从颜色读出自己的处境 | **已完成（M4）** |
| 枪声也是噪音 | 开火产生与射程等长的噪音（手枪 8 / 步枪 12 米），与命中无关；AI 与玩家共用同一条噪音链路，因此 AI 交火也会把同伴引过来 | **已完成（M4）** |
| AI 与玩家共用战斗链路 | AI 复用同一套 `WeaponRuntime`、射线契约与伤害结算，不存在"AI 专用简化规则" | **已完成（M4）** |
| 可解释的 AI 调试工具 | 独立 `Diagnostics` 程序集：视野锥 / 听觉圈 / 视线 / 路径可视化 + 数据面板 + 状态迁移日志，还会直接写出"为什么看不见"；关闭时零开销 | **已完成（M4）** |
| 拖拽与快速转移共用规则 | 两条操作路径经过同一套验证逻辑，避免"拖拽被拦、快捷键却塞进去了"的经典 bug | **已完成（M2）** |
| 网格背包的原子性保证 | 任何失败操作都保证状态与操作前完全一致，物品数量与总重量守恒有断言兜底 | **已完成（M2）** |
| 护甲等级减伤模型 | 护甲按 1~4 级提供 20%~65% 减伤，可读性优先，数值外置可调 | **已完成（M3）** |
| 反馈信号优先 | 枪声、弹道、弹药数量、体力弧在灰盒阶段就必须做——去掉它们，玩家无法判断操作是否生效 | **已完成（M3）** |
| 引擎能力单点收敛 | 射线检测收敛到 `IHitProbe` 一个接口，战斗规则因此完全脱离场景可测 | **已完成（M3）** |
| 整局重载代替原地复位 | 每局重新加载场景：容器、掉落、AI、事件订阅全部回到初始值，从根上消灭"第二局和第一局不一样"这类问题 | **已完成（M5）** |
| 搜刮读条作为贪婪的成本 | 开箱必须站定 2 秒，移动即打断且进度清零——「要不要再多搜一个」这个问题才有代价 | **已完成（M5）** |
| 结算回答"贪对还是贪错" | 带入价值与带出 / 损失价值并列显示，物品逐项列出；阵亡不真正扣物（M6 才接仓库）也如实写明 | **已完成（M5）** |
| 有掩体的地图 | 玩家与 AI 都被集装箱、隔断与高台挡住；装卸平台还引入了高低差与坡道 | **已完成（M5）** |
| 物品行为扩展点落地 | 医疗品用 `ItemBehavior` 子资产描述「回多少血、读条多久」；加一种止痛药只需建一个资产，不碰逻辑代码 | **已完成（M5.5）** |
| 医疗品真正能用 | `H` 键读条使用，**优先用刚好补满缺口的最小那件**；允许边走边包扎，唯一打断条件是受伤且不消耗物品 | **已完成（M5.5）** |
| 右键上下文菜单 | 右键列选项而不是直接执行动作，战利品箱里的「使用」灰显；`Shift+右键` 保留一键拆分这条高频路径 | **已完成（M5.5）** |
| 分部位护甲 | 命中上部位由**头盔**挡、其余由**防弹背心**挡，磨损各记各的；换装立即生效，左下角实时显示两边等级与耐久 | **已完成（M5.6）** |
| 背包决定随身容量 | 没装备背包 = 5×5 口袋，小包 6×6，突击包 7×7；换包时先搬物品，放不下就放弃调整而不是让东西消失 | **已完成（M5.6）** |
| 资源 + 代码双层热更 | Addressables 更新资源与数据表，HybridCLR 更新业务逻辑 | 待 M10 |
| 服务端权威网络架构 | 射击判定只在服务端执行，客户端仅做预测与表现 | 待 M9 |

## 已知限制

本项目为个人作品集 Demo，存在以下明确的范围限定：

| 限制 | 说明 |
| --- | --- |
| **仅 Windows 平台** | 不做主机 / iOS / Android 适配 |
| **联机规模有限** | 支持 2~4 人 PVE 合作；不包含 PVP、匹配系统、账号体系与反作弊 |
| **地图数量** | 1 张地图（工业区 + 集装箱仓库），优先保证系统完整度 |
| **AI 的灰盒边界** | AI 之间不做避让、不做掩体寻优，交战时会走到期望距离但不主动找掩体；撤退仍用匀速恢复代替医疗物品 |
| **代码热更的平台边界** | HybridCLR 在 Windows 上无限制；若未来移植 iOS，受 App Store 政策约束将不可用 |
| **美术为卡通风低多边形** | 美术表现非本项目重点，资源在 M7 阶段统一替换 |
| **交付前必须清掉开发期测试箱** | `crate.debug`「测试箱」（品红色，出生点旁，固定产出武器/护甲/头盔/背包）只用于验证装备链路。M8 之前要删掉容器定义、场景标记，并把 `LootTableTests` 的容器数量断言从 6 改回 5。全局搜索 `crate.debug` 即可找全 |
| **换包时不会丢东西，但可能暂时不缩容** | 背包塞满时卸下它，容量会保持到腾出空间为止（自愈）。正式版应改为「拒绝卸下并提示」 |

主动推迟的功能清单见 [`Docs/00_项目工程规范与系统设计.md`](Docs/00_项目工程规范与系统设计.md) 第 13.1 节。
